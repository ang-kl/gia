## Decisions (new this entry)

| # | Decision | Rationale |
| :--- | :--- | :--- |
| D-106 | **When a second caller needs an existing mechanism in a different shape, extract the core and make the original a wrapper — never hand-roll a parallel copy.** The bot handlers couldn't use Express middleware, but a second Redis counter would have drifted from the first the moment either was touched. The proof the extraction was safe is that the 12 pre-existing middleware tests pass with **zero** edits — a refactor that requires rewriting the incumbent's tests to stay green has, by definition, changed its behaviour. | v0.62.716 |
| D-107 | **Rate-limit AFTER the processing-lock check but BEFORE acquiring the lock.** In `runFlow`, checking after `setProcessing` would leave a rate-limited user holding a lock with no work running to release it — they'd get "you've hit the limit", then "still working on your last request" until the lock expired. The ordering is load-bearing, not incidental. | v0.62.716 |
| D-108 | **Share a rate-limit counter between paths that cost the same and are freely interchangeable; separate it otherwise.** `/s` and free-text search both run Places + Gemini and a user can alternate between them at will, so one shared `bot-search` budget is the honest accounting. `/eat` gets its own `bot-flow` counter so an `/eat` spree doesn't silently consume the search budget, and `/hidden` gets a much tighter cap (8 vs 40) matching its much higher per-call cost. | v0.62.716 |

## Note — the cost-audit plan, closed

All four phases are now built and sitting on PR #1705 (v0.62.713–716), from an operator concern that
began: *"serious concern over the use of tokens… And firing model, per user and if there are leaks."*
Mapped against that sentence:

- *"how many request… per user"* → **Phase A** made ~35 previously-invisible Gemini + Maps call sites
  report into `/cost`, and **Phase D** now bounds what one user can trigger.
- *"firing model"* → **Phase A**'s `recordGeminiUsage` captures the actual model name at each call site,
  so `/cost`'s `byModel` breakdown answers this directly.
- *"if there are leaks"* → **Phase B** removed the one confirmed leak (sanctuary re-fetching reviews it
  already had). The other candidate from the same audit — the disabled search cache — was investigated
  and **correctly excluded**: it's a deliberate, documented v0.60.11 operator decision, not a bug.
- *"serious concern"* as an ongoing state → **Phase C** turns the now-trustworthy number into an
  automatic daily brake with an owner alert, so the concern doesn't depend on someone remembering to
  run `/cost`.

What remains is honest and worth stating plainly: **none of it has been observed against production.**
O-175/176/179/182 all say the same thing from four angles — this work is code-complete and
test-complete, not field-verified. The first deploy is where the real numbers arrive, and O-180's cap
tuning should wait for them rather than guess twice.
