## Decisions (new this entry)

| # | Decision | Rationale |
| :--- | :--- | :--- |
| D-98 | **Thread an optional `redis = null` parameter rather than reach for a global/singleton client.** Every instrumented function outside `index.js` gained (or reused an already-existing) `redis` param, defaulting to `null` — `recordGeminiUsage`/`recordMapsCall` already no-op safely on a missing client (confirmed in `api-cost.js`'s own `_connect()` guard), so a caller that can't reach redis degrades to "untracked" rather than throwing. Keeps every touched module's dependency graph explicit instead of introducing implicit global state. | v0.62.713 |
| D-99 | **Wrap an injected function reference at the call site rather than change the library file.** `cuisine-special-mode-widen.js` and `cuisine-nearby-refetch.js` both take `discoverFn` as an injected dependency and neither needed to know redis exists — `index.js` wraps `pipeline.discover` as `(opts) => pipeline.discover({ ...opts, redis })` at the two injection points instead of adding a redis param to either widen/refetch helper. | v0.62.713 |
| D-100 | **Check for live callers before threading redis through a legacy code path.** `pipeline.js`'s v0.26.0 `runPipeline()` (Reason-Fetch-Refine) has zero callers anywhere in the codebase, confirmed by grep — its `fetchClusterContext → nearestMrtStations` chain was left untouched rather than spending effort threading redis through dead code. `transport.js`'s `nearestMrtStations` still gained the redis param, because its OTHER caller (`index.js:5912`) is live. | v0.62.713 |

## Note

This is Phase A of 4 in the operator-approved cost-audit remediation plan — pure instrumentation, zero
behaviour change to any user-facing response. The plan's own framing (per the earlier audit) treats
Phase A as the natural first PR precisely because it's the lowest-risk: every new line is a fire-and-
forget Redis write immediately after a call that already existed and already fired in production, guarded
by a tracker that was already designed (in `api-cost.js`'s own v0.61.307 header) to swallow every error
rather than ever risk the underlying call. The two upstream bugs found IN the tracker itself while wiring
it up (no Routes price entry; Routes billed-per-element silently truncated to "1 call") are a reminder
that "instrument it" is not always as mechanical as it sounds — the tracker's own correctness needed
verification, not just its coverage.
