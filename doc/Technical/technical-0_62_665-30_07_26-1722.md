## T-65.1 — Two independent Michelin data systems, unified only at the render layer

The repo has always had two separate Michelin schemas: `SG-michelin.js` (flat, one row per award, Singapore
only) and `michelin-data.js` + 11 per-country files (venue-centric, `awards:[{year,category}]` per venue,
already supporting real multi-year history). Rather than merge them — which the operator's spec explicitly
forbids ("do not create a new... unified... structure") — this entry adds a NEW shared derivation, not a new
data model: `retainedAwardYears(venue)` in `michelin-data.js` produces the exact same compact
`["'26","'25"]`-style output that SG's own `awardYears` field stores directly. Both systems now feed one
render contract (`michelinAwardYears` on the venue object reaching the TMA) without becoming one system.

## T-65.2 — The compact-year derivation is a single rule: walk newest-to-oldest, stop at the first category change

```js
function retainedAwardYears(venue) {
  const sorted = [...venue.awards].sort((a, b) => b.year - a.year);
  const latestCategory = sorted[0].category;
  const years = [];
  for (const a of sorted) {
    if (a.category !== latestCategory) break;
    years.push(`'${String(a.year).slice(-2)}`);
  }
  return years;
}
```
This one rule correctly produces every case the operator's spec walks through by example: pure retention
(both years, same category → both kept), promotion (2025 one-star → 2026 two-star → only `'26`, since the
loop hits the category change on its very first backward step), demotion (three-star→two-star, same shape),
and a pure debut (single award → single year). No special-casing per scenario was needed — the "only show
years matching the CURRENT category" rule, applied mechanically, already produces the "no promotion/downgrade
wording, just the honest years" behaviour the spec asks for as a UI constraint.

## T-65.3 — A single ambient "year" parameter can't survive a field that holds more than one year

`formatMichelinLine(entry, year = 2025)` and `ResultCard.jsx`'s `michelinAnnotation(category, year)` both
took a bare year as their second argument, defaulting to a hardcoded "2025" — a leftover from when SG had
exactly one edition ever curated. Once a venue can retain its category across MULTIPLE editions, there is no
longer a single "the year" to default to; the function must read the array off the entry/venue itself. Both
were changed from `(x, year)` to `(x, awardYears)`, with a `["'25"]` fallback ONLY for the case of a bare
`{ category }` object with no awardYears at all (kept so minimal test fixtures and any not-yet-updated caller
don't render a dangling `" · "` with nothing after it) — not as an ambient "current year" default any more.

## T-65.4 — A field whose SHAPE becomes wrong is a case for renaming, not just adding

`venue.michelinYear` (singular) was retired as a setter (not just left to rot) once it became structurally
incapable of representing the truth: a venue retaining an award across two editions cannot be described by
one number without lying about at least one of the years. This is the "required to fix an existing defect"
carve-out in the operator's own "don't rename/remove fields" instruction — but the fix respects that OLD data
(already-saved Clipboard clips) was never wrong for what it was AT THE TIME (a single year, because only one
edition existed when it was saved), so the old field stays as a read fallback rather than being deleted
outright. The distinction: stop WRITING a field that can no longer tell the truth; don't stop READING one that
told the truth when it was written.
