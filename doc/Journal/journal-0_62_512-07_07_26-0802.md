# Journal — soleat v0.62.512 (Oversight TMA safe-area bottom padding)

> Follow-up from the 7-TMA responsive render audit: the one real (if low-priority)
> flag was that the Oversight dashboard had no `env(safe-area-inset-bottom)` padding,
> so on a notched phone its last row / close button could tuck under the home
> indicator. Closed with the same inline-style idiom the other TMAs already use.

## New

### [HDR] #868 | 08:02 SGT 07-07-26 | v0.62.512 — Oversight safe-area bottom padding | 1 file | PR #(pending) |

- **[INTENT].** Operator ran the render audit (all 7 TMAs × device widths, mocked SDK),
  which surfaced 3 non-blocking flags; operator: *"1"* = fix flag #1 (Oversight had no
  bottom safe-area inset). This was the only flag with a concrete UX failure mode.

- **[ROOT CAUSE].** `web/oversight/src/App.jsx` renders the whole page as one scrolling
  `<div className="… py-3 …">` (and an auth-error variant with `py-6`), ending in a full-width
  `🔚 close` button. `py-3`/`py-6` give a fixed 0.75rem/1.5rem bottom pad — no
  `env(safe-area-inset-bottom)`. `index.html` already sets `viewport-fit=cover`, so the app
  paints into the home-indicator region; without the inset the final row sat under it on
  notched phones. Every other TMA (transport/hawker/menu/cuisine/clipboard) already applies
  the inset — Oversight was the lone gap.

- **[DELTA].**
  - `web/oversight/src/App.jsx` — added `style={{ paddingBottom: 'calc(0.75rem + env(safe-area-inset-bottom, 0px))' }}`
    to the main scroll container, and `'calc(1.5rem + env(safe-area-inset-bottom, 0px))'` to the
    401/403 auth-error container. Inline `paddingBottom` overrides only the *bottom* of the
    existing `py-*` class (top padding untouched); the `, 0px)` fallback degrades to the plain
    base padding on browsers with no notch API (desktop/tablet). Matches the verbatim idiom at
    `web/transport/src/App.jsx:140`, `web/hawker/src/App.jsx:176`, `web/menu/src/App.jsx:677`.
