### [HDR] #372 | 17:00 SGT 27-05-27 | v0.61.171 — Chat free-text seen-set + 🔍 for more button + recycle | 6 files | 1 PR | 1 build |

- **[INTENT]** Bring the cuisine TMA's per-(chatId, criteria) dedup
  behaviour to the **chat free-text search** path (the bot's plain
  text replies). Goal: when a user types "italian food" then asks
  for "more", the next batch surfaces fresh venues rather than
  repeating the same 8. Mirror the TMA's recycle button so the same
  criteria can be re-rotated through.

- **[DELTA]**
  - **`chat-freetext-seen.js`** (NEW, ~60 lines): Redis-backed seen-set
    + query-text storage keyed by a SHA-256(chatId, normalised text)
    prefix.
    - `TTL_S = 1800` (30 min) — matches the typical chat-attention
      window and prunes stale state cheaply.
    - `SEEN_CAP = 80` — ~10 batches of 8 venues; aligns with the
      cuisine TMA's 100-cap (chat-side 80 reflects the typical
      smaller free-text pool: a "schnitzel" search rarely yields
      80+ verified SG venues, so 80 is comfortably above the
      practical ceiling).
    - **`hashCriteria(chatId, text)`** — `sha256(chatId|normText).slice(0,10)`.
      Lowercased + whitespace-collapsed for stability across
      keystroke variance ("ITALIAN food" === "italian  food").
    - **`getSeenSet(redis, chatId, hash)`** — returns a `Set` of
      placeIds. Defensive: returns empty set when redis is null /
      closed / errors.
    - **`addSeen(redis, chatId, hash, placeIds)`** — `SADD` +
      `EXPIRE` to refresh the TTL. No-ops when redis is null or
      placeIds is empty.
    - **`clearSeen(redis, chatId, hash)`** — `DEL`. Used by the
      ↺ recycle path.
    - **`setQuery / getQuery`** — stores the raw query text by
      hash so the callback can re-run runFreeTextSearch without
      needing the text in callback_data (Telegram's 64-byte limit
      forbids embedding the query directly for longer dish names).
    - **`pickUnseen(redis, chatId, hash, venues, take=8)`** —
      orchestrator: filters venues by seen-set, slices to `take`,
      computes `exhausted` (`true` when the cumulative seen-set
      hits SEEN_CAP OR fewer unseen venues than `take` were
      available). Returns `{topUnseen, exhausted, seenSizeAfter}`.
  - **`__tests__/chat-freetext-seen.test.js`** (NEW, 21 tests):
    constants shape, hashCriteria (determinism + case/whitespace
    insensitivity + chatId/text variance), getSeenSet+addSeen
    round-trip, TTL setting (`EXPIRE` called with TTL_S), clearSeen,
    setQuery+getQuery round-trip, pickUnseen (skips seen, exhausted
    detection at SEEN_CAP, exhausted detection on shortfall).
    All 21 pass in 13 ms.
  - **`index.js`** (2 wiring edits):
    1. **`runFreeTextSearch`** (line ~8732):
       - **Pre-filter** before the disambig/dessert/plain slice
         paths: read seen-set; drop venues whose placeId is
         already in the set.
       - **Post-deliverPicks** (line ~8876): call `setQuery` to
         store the query text, `addSeen` to record the shown
         placeIds, then send a follow-up inline-keyboard message.
         When unseen results may remain (`shownIds.length === 8`
         AND `seenSizeAfter < SEEN_CAP`): two-button keyboard
         ([🔍 Search for more] [↺ Start over]) with a "💡 Want
         different picks for the same search?" hint above. When
         exhausted: one-button keyboard ([↺ Start over]) with
         "🔚 No more matching results · Change criteria or tap ↺
         to start over." caption.
    2. **`bot.on('callback_query')`** dispatcher (line ~2493):
       new `ft:` branch handling `ft:more:<hash>` and
       `ft:recycle:<hash>`. Both retrieve the stored query text;
       `ft:recycle` additionally `clearSeen`s before re-running.
       Graceful "⌛ That search has expired. Please re-type your
       query." reply if the 30-min TTL has elapsed.
  - **`i18n.js`** (5 new keys, EN + FR):

  - Type `italian food` in chat — receive 8 venues + a follow-up
    message with "💡 Want different picks for the same search?" +
    two buttons.
  - Tap **🔍 Search for more** — receive 8 *different* venues
    (no overlap with the first 8) + the same follow-up keyboard.
  - Repeat. After ~10 taps OR when the candidate pool runs dry:
    receive the "🔚 No more matching results" message with only

    of Redis).

- **[KNOWN GAPS]**
  - **No analytics on tap-through.** The /api/cuisine/search path
    logs D790 + diagnostic context; the chat free-text path
    doesn't log seen-set state. Would be a 5-min follow-up to
    surface "seen=12/80, exhausted=false" in the existing
    `[free-text]` console.log line.
  - **Query text storage TTL = 30 min.** A user who opens the
    chat tomorrow and taps yesterday's "🔍 for more" button gets
    the "expired" message. Could lengthen to 24 h at minimal
    Redis cost if operator wants longer button shelf-life — but
    30 min matches typical chat-session duration.
  - **No "seen-set carry-over" between sessions.** Each new
    typed query starts fresh (criteria hash includes the text,
    so the seen-set is per-query, not per-chat-history). This is
    correct UX — typing the same query verbatim a week later
    SHOULD start fresh — but worth noting that the cap of 80
    venues per (chatId, query) is per-query, not per-chat.
  - **No corresponding feature on the /search alias.** `/search`
    + `/s` route through a different code path (the
    "search-method picker"); seen-set there would mean a deeper
    refactor. Filed.
