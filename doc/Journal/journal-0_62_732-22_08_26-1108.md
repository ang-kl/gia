- **[2 — SLOT-PADDING ARTEFACTS: 377 lines repaired mechanically]** The slot-substitution
  translator wrapped every protected run in spaces and never took them back out:
  `* {n} *` (Telegram renders literal asterisks, not bold), `<i> {street} </i>`,
  `/buddy block<chat_id> ` (the delimiter moved off the command onto the far side of the
  argument), `{i} . {name}`, and 44 keys that lost a **leading space** they needed because
  they are fragments concatenated onto a preceding run.

  Every repair is derived from the English source for the same key — nothing is invented.
  The rule is **context-gated in both directions**: a space is collapsed only when the
  target's neighbouring non-space character is the one the source has flush against the
  token, and restored only when the character now touching the token is the one on the far
  side of the source's space. Ungated, the first draft turned a correct Indonesian
  `{target} diblokir` into `{target}diblokir` (English word order is `Blocked {target}.`)
  and a correct `<b>{n} tempat` into `<b> {n} tempat`. Both were caught by reading the
  dry-run diff, which is the only reason this entry can say the rule is gated.

  Chinese and Japanese additionally never set a space either side of full-width
  punctuation. Carrying the English spacing across gave `状态： {status}` in 72 places.

  The cause is exact. Three of the five Mini Apps do not keep every language inline in the


  1. **A command at the end of a string was not counted.** `cmd-spacing` read the following
     character and short-circuited on `undefined`, so French *"Copier la commande /cuisine"*

     there is.

     `Dim/fériés` and Spanish `Dom/feriados` — for English `Sun/PH` — both matched `/f` and

     word character; that is the actual entity rule.

     anchor consuming the preceding character, `.match()` returned the whole match, so
     `，/forgetme` compared against English `/forgetme`. Comparing the **capture** rather than
     the match fixed it. Full-width punctuation opens a command exactly like a space.

  the cases each check exists for — `/l<place>` and `/cuisineで` — still fail, asserted by
  name alongside the correct forms that must now pass.

### [AMD-8] The zh/ja typed examples — and running the classifier instead of guessing at it

*(22-08 '26 15:32 SGT — anchor computed in python3 as the D-203 max over the live NEA reading

  and `「ラーメンを探して」`. Whether that is a defect depends on one fact: can the free-text path
  resolve a CJK query? Rather than reason about it, the classifier was **run**:

  ```
  'find me ramen'   → ['find','me','ramen']
  '找拉面'           → 1 token
  'ラーメンを探して'  → 1 token
  ```

  `freetext-classify.js`'s `tokenize()` splits on non-letter/number, and CJK is written without
  spaces, so **an entire Chinese or Japanese query collapses into a single token**. Every list it
  is then checked against — `CUISINE_UMBRELLA_WORDS`, `FOOD_SPECIFIC_NOUNS` — is English. No CJK
  query can reach the cuisine-browse path at all. Query-side dish aliases (`dish-aliases.js`)
  contain exactly one entry, a Cantonese nickname; they are not general CJK support.

  So the string was advertising an input the code in front of it cannot classify.

- **[WHAT WAS DELIBERATELY NOT CLAIMED]** Whether **Google Places** would still return ramen shops
  for `拉面` in Singapore is **Not Verifiable here** — it needs a live API call, and the operator's
  key was for one task. The fix therefore pins the example to the form that demonstrably works
  rather than asserting the other one fails.

- **[WHAT CHANGED]** Two strings. The surrounding sentence stays in the target language; only the
  quoted example returns to Latin:
