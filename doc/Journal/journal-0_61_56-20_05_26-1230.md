## New

### [HDR] #260 | 12:30:00 SGT 20-05-26 | v0.61.56 — CR6 Phase 2a bus services per exit | ~7 kb | 5 files | 1 PR | 1 build |

- **[INTENT]** Fetch services-per-stop from LTA DataMall, and join the nearest stop
  (with services) to each station exit so the CR6 info card can render the bus list
  per exit.

- **[DELTA]**
  - **`scripts/fetch-bus-services-by-stop.js`** (new, ~90 lines) — uses LTA DataMall
    `/BusStops` + `/BusRoutes` (paginated `$skip=500`). De-dupes services per stop
    across directions, natural-sorts service numbers (`5 < 10 < 13 < 100 < NR1`),
    writes `data/bus-services-by-stop.json`. Requires the operator's
    `LTA_ACCOUNT_KEY` (same env var the live transit feeds already use). Volume:
    ~5,500 stops + ~26,000 route records → ~63 API calls in ~30–60 s.
  - **`scripts/build-station-info.js`** — now optionally loads the bus-services
    file (graceful fallback when missing, so the build is still runnable in
    sandbox CI without the LTA key). For each exit:
    - box-filter bus stops within `BUS_NEAR_M = 80 m` of the exit;
    - haversine-sort the survivors;
    - take the **nearest stop that has ≥ 1 service** (fall back to the next-nearest
      within the cap only if the closest has zero services — per the operator
      decision).
    - Result emitted as `exits[].nearest_bus_stop = { code, lat, lng, services }`,
      or `null` if no stop within the cap.
    - `_meta` carries `busServicesJoined: <bool>` and an explicit "run the fetcher
      to populate" `schemaNotes` line when the file is absent.
  - **`package.json`** — `0.61.55` → `0.61.56` (PATCH).

  > Not committed in this PR: `data/bus-services-by-stop.json` and the
  > regenerated `data/stations.json` with `nearest_bus_stop` populated. The
  > sandbox has no `LTA_ACCOUNT_KEY`; the operator runs the fetcher locally and
  > commits both files in a tiny follow-up (or the same merge if they want).
