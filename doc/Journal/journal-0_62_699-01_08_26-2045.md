## New

### [HDR] v0.62.699 — the expanded Cuisine map hid the card strip and the footer

- **[INTENT]** Operator: *"when I tap … ⇲ to expand the map in Cuisine TMA, why the footer is gone and
  the card, only when i tap ⇱ again, both will appear. the card and footer are important despite the
  google map being expand"*. Then: *"make sure the drawer works even when map is expanded"*.

- **[MY BUG, FROM TWO VERSIONS AGO]** v0.62.691 gave Cuisine's ⇲ a real action by porting Hawker's
  v0.62.627 overlay. I copied the value **and its justification**:

  > *"z-[35] … clears the carousel while staying under the footer dock (z-40), so the footer and its
  > Map toggle stay reachable."*

  That sentence is true in Hawker and **false in Cuisine**. The two apps do not share a stack:

  | | Hawker | Cuisine |
  |---|---|---|
  | result carousel | `z-30` | `z-30` |
  | **footer dock** | **`z-40`** | **`z-30`** (`App.jsx:5582`) |

  At `z-[35]` the overlay cleared the carousel *and* the footer, so both vanished behind the expanded
  map — exactly as reported. The number was ported without re-checking the stack it was being ported
  into, and the comment I wrote asserted a fact about Cuisine that I had only verified about Hawker.

- **[DELTA]** Cuisine's expanded overlay `z-[35]` → **`z-20`**. The map still grows to the full
  viewport, but paints **below** the carousel, the footer and the sticky header (all `z-30`), so the
  operator's *"the card and footer are important despite the google map being expand"* holds.
  **Hawker is deliberately untouched** — its `z-[35]` is correct for its own stack, and re-checking
  that was the first thing done rather than assumed a second time.

- **[THE DRAWER STILL WORKS — and the hit-test is the proof]** "Works when expanded" is decided by
  which element wins `elementFromPoint`, so that is what was measured, using the compiled Cuisine
  stylesheet and the exact class strings from source:

  | tap target | with `z-20` | with the shipped `z-[35]` |
  |---|---|---|
  | a carousel card | **card** ✅ | overlay ❌ |
  | the footer | **footer** ✅ | overlay ❌ |
  | above the drawer | **map** (still pannable) ✅ | overlay |

  The drawer's wrapper is `pointer-events-none` with the inner scroll track `pointer-events-auto`, so
  cards receive taps and the map receives everything outside the strip.

- **[ONE HONEST FOOTNOTE ON THAT TABLE]** A fourth probe — tapping the drawer's band at x=380, past the
  last card — returns the **track**, not the map. The scroll track is `pointer-events-auto` across its
  full width, which it must be to capture horizontal swipes. So the carousel owns its whole band, not
  just the card rectangles. That is pre-existing and correct, and it is recorded here because the
  probe's first reading looked like a miss and is not one.

- **[VERIFICATION (sandbox)]** Stacking measured against the **compiled** bundle (both `.z-20` and
  `.z-30` confirmed emitted), not inferred from the class list. Cuisine build green; full
  `npm test -- --run` **156 files / 3901 tests** green.

- **[STATUS]** DRAFT — branch `claude/handover-july-11-49uzvf`.

- **[KNOWN GAPS]**
  - The probe reconstructs the stack from real classes and real CSS, but it is **not the live app** —
    Cuisine's drawer needs a completed search to render, which this sandbox cannot perform. If some
    other element sits between z-20 and z-30 in the real tree, this would not have caught it.
  - The expanded map now sits **below the sticky header** as well. That is a consequence of choosing a
    z beneath the whole z-30 tier rather than a decision made on its own merits; the operator asked
    only about the card and the footer. If the header should be covered while those two stay, the
    header needs its own z, which is a larger change to the stack.
