# Journal — v0.62.700 (the Michelin edition ticks stop being a constant)

_(№ 1,039 — 02-08 '26 15:00 SGT)_

## New

### [HDR] v0.62.700 — O-124 closed: the year ticks are data-driven

- **[INTENT]** Operator: *"O-124 - yes, make it data-driven"*.

- **[WHAT O-124 ACTUALLY WAS]** Not a defect — a **latent** one. v0.62.676 shipped the Michelin
  edition filter as a hardcoded 2026/2025 pair, which is correct for today's data and silently wrong
  the day a `'27` edition lands: a venue awarded only in `'27` would match neither arm and vanish
  from results, with a green suite, a normal-looking UI and nothing in the logs. The ticks would
  still toggle; they would simply be filtering against a year universe that no longer described the
  data.

- **[SIX SITES, NOT ONE]** The pair was written out by hand in more places than the Register knew:

  | # | Site | What it hardcoded |
  |---|---|---|
  | 1 | `index.js` (search handler) | `years.includes("'26") \|\| years.includes("'25")` |
  | 2 | `index.js` (walk hash) | a fixed 3-bit string `"110"` — cannot describe a third edition |
  | 3 | `MichelinFilterDrawer.jsx` | `KEYS = [2026, 2025, bib]` |
  | 4 | `state.js` (default) | `{ year2026: true, year2025: true, bib: true }` |
  | 5 | `state.js` (hash) | one param per year — `michY26` / `michY25` |
  | 6 | **`michelin-sort.js`** | `YEAR_RANK = { "'26": 2, "'25": 1 }` |

  **Site 6 was found during the work, not before it.** It is the worst of the six: a `'27` entry
  would score 0 there and sort **below** `'25`, i.e. newest-last — an ordering error with no visible
  cause. O-124 named "the ticks"; the sort was carrying the same constant one file away.

- **[THE RULE THAT REPLACES THEM]** One convention, both halves: **only OFF is ever transmitted**.
  A year nobody has mentioned is ON. That inversion is what makes it data-driven — "everything not
  switched off" already contains editions that do not exist yet, so a new one needs no new key, no
  server change and no client deploy to filter correctly.

- **[DELTA]**
  - **`michelin-year-filter.js`** (NEW, root, CJS) — `yearsOffFromFilter()` (`year<YYYY>: false` →
    `'YY` token), `yearUniverse()`, `makeMichelinYearMatcher()`. Extracted out of the search handler
    so the rule is testable; it was previously inline in a ~400-line route and could only be checked
    by reading it.
  - **`web/cuisine/src/v2/lib/michelin-years.js`** (NEW) — the client half: `yearOfToken`,
    `buildMichelinKeys`, `tickTokens`, `unionYears`. Same reason — the repo has no React render
    harness (O-93), so logic held inside a component is verified by eye.
  - **`index.js`** — handler uses the matcher; `michSelectedYears` is now *this country's editions
    minus what the client switched off*; the walk hash becomes `'26,'25|1` instead of `110`.
  - **`michelin-sort.js`** — `yearRank(token)` returns **the year itself**. Newest-first is a
    property of the number, not of a lookup table. `YEAR_RANK` stays exported, now computed.
  - **`MichelinFilterDrawer.jsx`** — tick list built from data. Takes a new `allYears` (union across
    countries) **separate from** `availableYears` (live in this country).
  - **`state.js`** — default `michelinFilter` is `{}`; hash years travel as one `michYoff=2026,2025`
    list. Links shared while v0.62.676–699 were live are still **read** (`michY26`/`michY25`), so an
    old link keeps meaning what it meant.
  - **`App.jsx` / `CuisineDrawer.jsx`** — thread `michelinAllYears` through.

- **[WHY TWO YEAR LISTS AND NOT ONE]** The obvious build — drive the ticks from the country's own
  editions — would have **deleted a feature**. Singapore's 2026 star list is unannounced, so its
  per-country list is `["'25"]` only; a list built from that alone would make the 2026 tick silently
  disappear. v0.62.696 (D-65) deliberately *shows* it, greyed, with a reason. So **which ticks
  exist** comes from the union across all countries and **which are live** from the per-country
  list. Two questions, two inputs.

- **[VERIFICATION (sandbox)]**
  - **Old vs new over the real datasets.** The pre-v0.62.700 predicate was transcribed verbatim from
    `index.js@c982ba6` and run beside the new matcher across **12 countries / 2,114 venues × all 8
    tick combinations = 96 comparisons**. **94 identical.** The two differences are analysed below —
    they are not incidental.
  - **45 new tests** across three new files: `michelin-year-filter.test.js` (17),
    `cuisine-michelin-hash.test.js` (13, incl. legacy-link reads), `cuisine-michelin-years.test.js`
    (15). **+5** appended to `michelin-sort.test.js` for the `'27` ordering.
  - Full `npm test`-equivalent (`npx vitest run`): **159 files / 3,951 tests** green (was 156/3,901).
  - Cuisine build green; the tick classes re-checked as **emitted** in the compiled stylesheet
    (`.bg-tg-accent`, `.text-[11px]`, `.line-through`, `.rounded-full`, `.gia-hit`) — the D-22…D-28
    Tailwind-silent-drop check, run because the class list's *shape* changed even though no class
    string did.

- **[THE TWO DIFFERENCES — a live zero-results path, found by the comparison]** Both are the same
  shape, and both are in the only two **single-edition** countries:

  | | star editions | reachable state | on main today | with this change |
  |---|---|---|---|---|
  | **SG** | `'25` only | untick 2025 + Bib (2026 is greyed) | **0 results** | 140 (fail-open) |
  | **PH** | `'26` only | untick 2026 + Bib | **0 results** | 34 (fail-open) |

  The fail-open guard's own comment says it exists so a tick combination *"fails OPEN rather than
  silently returning zero"*. The hardcoded version measured "all ticks off" against the **literal
  pair**, so with 2026 nominally ON — even though it can match nothing in SG — it judged "not all
  off" and returned nothing. The new version measures against **the editions this country actually
  has**, so the guard fires and the user sees results.

  **This is a behaviour change, in Singapore, reachable by tapping two ticks.** It is shipped because
  it is what the guard was written to do — but it is not unambiguous, and it is filed as **O-131**
  rather than declared correct: fail-open makes the last untick *appear to do nothing*, which is
  exactly the complaint D-69 was written about. The alternative (return empty, say "no results for
  this filter") is defensible and is the operator's call.
