## New

### [HDR] #378 | 23:00 SGT 27-05-27 | v0.61.177 — Cuisine-venue-counts chat trigger + Redis persistence | 4 files | 1 PR | 1 build |

- **[INTENT]** Close the v0.61.173 known gap: the JSON output file
  lives on Railway's ephemeral container filesystem, so the count
  data is wiped on every redeploy. Move storage to Redis (single
  blob, 60-day TTL) and surface a chat-side owner button so the
  operator never needs to drop to a terminal to refresh the data.

- **[DELTA]**
  - **`cuisine-venue-counts.js`** (additions):
    - `REDIS_KEY = 'cuisine-venue-counts:latest'`
    - `REDIS_TTL_S = 60 * 24 * 60 * 60` (60 days — well past any
      reasonable manual-recount cadence).
    - `persistToRedis(redis, result)` — JSON.stringify + SET with
      EX TTL, returns boolean. Defensive: returns false on closed
      redis or non-object result.
    - `loadFromRedis(redis)` — GET + JSON.parse with try/catch.
      Returns null on missing / corrupt JSON / closed redis.
  - **`__tests__/cuisine-venue-counts.test.js`** (+10 tests):
    REDIS_KEY/TTL shape + sane range; round-trip persist → load;
    EX TTL passed correctly; defensive null/closed/missing/
    corrupt-JSON paths. Total 18 → **28 tests, all passing**.
  - **`index.js`** (3 wiring edits):
    - **`/v` + `/ver` admin keyboards** gain a new row:
      `[🍽 Cuisine venues (48)]` → callback_data `cv:menu`.
      Lives in both menus since the operator may enter either way.
    - **`callback_query`** dispatcher: new `cv:` branch (mirrors
      `per:` branch). Three actions:
      - `cv:menu` → `ownerCuisineVenueMenu(chatId, messageId)`
      - `cv:run` → `ownerCuisineVenueRecount(chatId)`
      - `cv:close` → `bot.deleteMessage`
      Owner-gated via `isOwnerChat`.
    - **NEW `ownerCuisineVenueMenu(chatId, messageId)`**:
      ```
      🍽 Cuisine Venue Counts (48 cuisines)  ·  v0.61.177

      Total: 612 venues  ·  Last run: 2026-05-27 15:00 UTC
      Capped at 60+: 5  ·  Errors: 0
      Capped: italian, japanese, korean, american, thai

      [🔄 Recount now (~$3.45)]
      [✕ Close]
      ```
      "No data yet" placeholder + "Run now" CTA when Redis is
      empty (first-time setup). Uses `editMessageText` when
      messageId set so the panel updates in-place.
    - **NEW `ownerCuisineVenueRecount(chatId)`**:
      1. Validates `GOOGLE_MAPS_API_KEY` is set; bails with a
         clear message if not.
      2. Sends "⏳ Running Places sweep across 48 cuisines…
         (~15 s)" acknowledgement.
      3. Calls `cvc.countAll()` — parallel sweep, paginated
         per-cuisine. Defensive try/catch.
      4. Persists result via `cvc.persistToRedis(redis, result)`.
      5. Sends a summary message (total / capped / errors / pages
         / elapsed seconds / Redis store status).
      6. Re-opens the menu via `ownerCuisineVenueMenu(chatId,
         null)` so the operator sees the refreshed view.

- **[KNOWN GAPS]**
  - **No idle-timeout / debounce on the Recount button.**
    Operator could tap "Recount now" twice in quick succession
    and spend $7 instead of $3.45. A 60-s debounce key in Redis
    would catch this — filed as a 5-line follow-up.
  - **No per-slug detail view from the chat menu.** The bot only
    shows total + capped + errors summary. Per-slug breakdown is
    in the Redis blob; would need a "📋 Details" button to dump
    it as a code block (could exceed Telegram's 4096-char limit
    if all 48 slugs are non-zero, so might need chunking).
  - **`data/cuisine-venue-counts.json` is now redundant** for
    production but kept for local-dev convenience (the CLI runner
    still writes it). v0.61.178 will read FROM Redis for marketing
    copy, not the JSON. We could delete the placeholder JSON in
    a future cleanup PR but it's small + harmless.
  - **No history.** Each sweep overwrites Redis with the new
    result. By design — operator's "manual-only" call. If history
    becomes useful, the count-history ZSET schema from v0.61.166
    is reusable (would need a separate Redis key namespace).
