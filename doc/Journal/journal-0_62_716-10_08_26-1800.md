# Journal — v0.62.716 (Cost-audit Phase D: per-user caps reach the bot commands — plan complete)

_(№ 1,055 — 10-08 '26 18:00 SGT)_

## New

### [HDR] v0.62.716 — extend the rate limiter from 12 HTTP endpoints to the Telegram bot commands

- **[INTENT]** Fourth and final phase of the operator-approved cost-audit plan. The original audit found
  that `rate-limit.js`'s per-chatId limiter (v0.60.173 / DF-54) covered **only** the 12 HTTP
  `/api/cuisine/*` endpoints — every Telegram bot command (`/s`, free-text search, `/eat`, `/drink`,
  `/hidden`) was **completely uncapped per user**. Phase C caps what the *system* spends in a day; this
  phase caps what any *one user* can trigger. Neither substitutes for the other: without D, a single
  user can exhaust the daily budget under C and degrade the product for everyone else. That gap is
  precisely what this closes.

- **[THE EXTRACTION — SHARE THE MECHANISM, DON'T COPY IT]** The bot handlers have no `req`/`res`/`next`,
  so the Express middleware couldn't be reused as-is. Rather than hand-roll a second Redis counter (which
  would drift from the original the first time either side was touched), the counter core was extracted
  **verbatim** out of `makeRateLimiter`'s body into a bare `checkRateLimit(redis, { endpoint, key, cap,
  windowSec, now })`, and `makeRateLimiter` became a thin wrapper that delegates to it. Same
  `gia:rl:<endpoint>:<key>:<bucket>` key shape, same fixed-window semantics, same 429 body.
  **The strongest evidence the extraction was behaviour-preserving: all 12 pre-existing middleware tests
  — written against the pre-extraction implementation — pass completely unchanged.** No test was edited
  to accommodate the refactor.

- **[THE CAPS, AND WHY EACH NUMBER]** All on a 15-minute fixed window, matching the HTTP limiter's
  existing default:
  | endpoint | cap | reasoning |
  |---|---|---|
  | `bot-search` | 40 | Shared by `/s` turns AND free-text search — they cost the same (Places + Gemini) and a user can freely alternate, so a shared budget is the honest accounting. 40/15min is far above any real conversational pace. |
  | `bot-flow` | 40 | `/eat` + `/drink`. Its own counter so an `/eat` spree doesn't consume `/s`'s budget. |
  | `bot-hidden` | 8 | The priciest single command by a wide margin (grounded Gemini + up to 5 Places verifier lookups, uncached, with a retry ladder). Deliberately much tighter. |

- **[ONE ORDERING DETAIL THAT MATTERS]** In `runFlow` the rate-limit check is placed **after** the
  `isProcessing` lock check but **before** `setProcessing`. Putting it after `setProcessing` would leave
  a rate-limited user holding the processing lock with no work running to release it — they'd be told to
  wait, then told "still working on your last request" until the lock expired. Cheap to get wrong,
  annoying to debug from a user report.

- **[FAIL-OPEN THROUGHOUT]** `checkRateLimit` returns `{ limited: false }` on every abnormal path — dev
  bypass, missing key, Redis down, Redis error — with a `reason` field distinguishing "allowed because
  under cap" from "allowed because the check couldn't run". `botRateLimited` (the index.js helper that
  sends the refusal) wraps the whole thing in its own try/catch too. A broken limiter must never block a
  real user; that's the same posture as the pre-existing middleware and as Phase C's `readSpend`.

- **[DELTA]** (3 files)
  1. `rate-limit.js` — `checkRateLimit()` extracted from `makeRateLimiter`'s body; `makeRateLimiter`
     rewritten as a wrapper over it; both exported.
  2. `index.js` — `botRateLimited(chatId, endpoint, cap, lang)` helper (bilingual EN/FR refusal naming
     the cap and the minutes remaining, fail-open on any error), applied at 4 call sites:
     `handleSearchTurn` (`/s`), `runFreeTextSearch`, `runFlow` (`/eat` + `/drink`), and both `/hidden`
     entry points.
  3. `__tests__/rate-limit.test.js` — 10 new tests for the bare `checkRateLimit` (cap boundary, key
     shape, per-endpoint/per-key isolation, window rollover, all four fail-open paths, arg validation),
     appended below the 12 untouched middleware tests.

- **[KNOWN GAPS]**
  - **The caps are per-chatId, not per-account or per-IP.** Consistent with the existing HTTP limiter,
    but it means the bound is on a Telegram chat, not a person.
  - **Cap values are reasoned, not measured.** 40/40/8 come from an argument about relative cost and
    plausible human pace, not from real usage percentiles — `/ftlog` and the Oversight usage log now have
    the data to tune them, which hasn't been done.
  - **Fixed window, not sliding** (inherited): a user can spend the full cap at the end of one window and
    again at the start of the next, briefly doubling the nominal rate. Same trade-off the HTTP limiter
    already accepted.
  - **Not exercised against a live bot** — no Telegram runtime in this sandbox; every path here is
    unit-tested against fake Redis, not observed end-to-end.
  - **Other bot commands remain uncapped** — `/carpark`, `/weather`, `/transport` and friends. Deliberate:
    they hit free government APIs (LTA / data.gov.sg), so they carry no per-call spend and were out of
    this plan's cost-driven scope.
