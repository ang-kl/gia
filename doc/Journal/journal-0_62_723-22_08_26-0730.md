### [AMD-1] The S-2 finding was wrong, and the reply serials were the wrong counter

*(journal № 1,064 - 22-08 '26 07:30 SGT)*

- **[AMENDS]** the `[OBSERVED STATE]` bullet of `[HDR]` above, which read verbatim:

  > - **S-2** — `.serial-state.yml` was missing two required keys outright:
  >   `last_anchor_iso8601` and `last_anchor_utc`. The file has been edited **six times**
  >   this session — every edit passed over the absence without noticing it.

  **That is false.** Both keys were present, nine and three times respectively, further
  down a 5,923-line file. The claim was made from reading the first eighteen lines and
  concluding from their absence *there* that they were absent *everywhere* — a file this
  long was assessed by its head. Recorded as **X-10**.

  Worse, it was written into a Journal, a Register-adjacent record, a commit message and a
  merged PR body as a measured finding, in the same entry that criticises asserting without
  measuring. The correction is the fourth of that family this session (X-7, X-8, X-9).

- **[WHAT WAS ACTUALLY WRONG — and it is a real defect, just not that one]** A prior Codex
  review on PR #1438 had already found the genuine hazard and left the fix in the file:

  > `last_anchor_iso8601` below is duplicated many times over past sessions (append-only
  > history, never pruned) -- a last-key-wins YAML reader would pick up a stale June value
  > instead of the current anchor. […] `last_anchor_iso8601_current` is the single
  > authoritative field […] The plain `last_anchor_iso8601:` lines below this point are
  > historical log only, not current.

  Two things follow. **(1)** `last_anchor_iso8601_current` — the field that convention
  declares authoritative — read `2026-07-17T09:36:00+08:00`: **stale by more than a month**,
  while `last_anchor_time` two lines above it was re-anchored repeatedly all session. The
  authoritative field was the one nobody was updating. **(2)** The "missing key" I added at
  line 17 was a *tenth* plain `last_anchor_iso8601`, which does not help a last-key-wins
  reader at all — it still resolves to a July value further down — and reintroduces
  precisely the ambiguity the convention exists to prevent. The remedy made the defect
  marginally worse while reporting it as fixed.

- **[SECOND CORRECTION — the reply serials used the wrong counter]** §3.2 is explicit:

  | Context | Reset trigger |
  |---|---|
  | Chat session log (`doc/Chat/`) | counter starts at 1 on first message of each new chat session; resets per session |
  | Commit messages | counter is the cumulative commit number; never resets |

  The four replies made immediately after the violation was surfaced carried
  **№ 1,236 / 1,237 / 1,238 / 1,239** — the *commit* counter. Their `[§X.Y]` tags, which
  correctly used the session response numbers 1–4, therefore disagreed with their own
  headers. Having just been corrected for not numbering replies at all, the numbering was
  then done with the wrong counter for four consecutive replies. Recorded as **X-11**.

- **[DELTA]**
  - `doc/.serial-state.yml` — the two plain duplicates removed from the head;
    `last_anchor_iso8601_current` updated to the live anchor and its superseded value
    preserved in the historical log rather than overwritten (AU-1);
    `last_anchor_utc_current` added on the same terms, since `last_anchor_utc` carries the
    same hazard and had no `_current` variant; `current_chat_counter` corrected to 5 with
    the mis-numbering recorded inline.
  - `doc/Chat/chat-0_62_723-22_08_26-0730.md` — turns appended, not edited (AU-4).

- **[VERIFICATION (sandbox)]** Counts are measured: `grep -c '^last_anchor_iso8601:'` → 9
  before the edit, `'^last_anchor_utc:'` → 3, file length 5,923 lines. The convention block
  is quoted from the file at lines 176–182, not paraphrased.

- **[STATUS]** DRAFT. No code changed; no test run implicated.
