- **[DELTA]**
  - **`loc-drift-log.js`** (new) — `logLocDrift(event, fields)`: ONE compact single-line JSON record
    per event. `ENABLED = process.env.LOC_DRIFT_LOG !== '0'` (default ON; set `LOC_DRIFT_LOG=0` to
    silence). `r5()` rounds coords to 5 dp (~1 m).
  - **`index.js` `/api/cuisine/set-location`** — `[LocDrift] set-location {chat,dev,from,to,moved_m,
    label,region,country,cap_m,ambient,kept}` per write (reuses the `prevLoc` already read for the
    area-change notify; `moved_m` via `location-mode.haversineMeters`).
  - **`index.js` `/api/cuisine/search`** — `[LocDrift] search-anchor {chat,center,region,radius_m,
    cap_m,cap_src}`. New `capSource` tracks the cap origin: `explicit` (persisted radiusCapM) /
    `city-default` (nearest-city radiusM) / `other-default` (40 km OTHER ceiling) / `none`.
    `cap_src='city-default'` on an OTHER free-text pick is the fingerprint of the 12-06 "Putrajaya pick,
    durian results spilled to KL" (45 km nearest-city default from a ~12 km city).
  - **`__tests__/loc-drift-log.test.js`** (new, 5).

- **[per-ChatID answer]** Location is stored **per-user**: `loc:${hashChatId(chatId)}` (+ a per-device
  `:dev:<id>` sub-key) in Redis (`location-cache.js`), written only after `verifyInitData(initData,
  TELEGRAM_BOT_TOKEN)` resolves the CALLER's own Telegram `userId` (`index.js` set-location). No
  module-level/global location variable exists in `index.js`. ⇒ one ChatID **cannot** leak into
  another; the last 2 days' changes (plate-clear = UI; autocomplete `radiusM` = soft bias) never touch
  the set-location write path or its keying. The log the operator linked
  (`log/logs.1781301427251.json`) is the **Next.js `gia-web`** landing service (`gia-web@0.1.160`,
  service `b3c56e8d`), NOT the Cuisine/Express service (`f9a39516`/`678921e6`); it only carries
  "Failed to find Server Action … older or newer deployment" (Next.js bundle version-skew, unrelated to
  cuisine location). Diagnosing another ChatID's failure needs the Express/cuisine service log.
