### [HDR] #465 | 18:00 SGT 29-05-29 | v0.61.264 — Gemini-verify pipeline | 3 files | 1 PR | 1 build |

- **[INTENT]** Build an independent classifier that labels each `kept[]` venue from a `durian-variance-runner` report as `specialist` / `occasional` / `unrelated`. This converts the 18 % keep-rate finding into a real precision number — and gives us a path to the operator's 95 % target via post-filter.

- **[DELTA]**

  **1. `durian-gemini-verifier.js`** (new, ~245 lines)

  Pure module — no I/O, no env reads at top level — exporting `verifyKeptVenues({ report, mode, apiKey, ... })`. It:

  - Flattens `report.regions[*].queries[*].kept[]` into a sequential id-keyed list, attaching the top 3 review snippets per venue (capped at 240 chars each so 10-venue batches stay well under Gemini's input budget).
  - Builds a mode-specific prompt (durian fruit vs. durian pastry — the contract sentence differs explicitly). Output format: strict JSON array, one object per venue, with `label` / `confidence` / `reason`.
  - Calls `gemini-2.5-flash-lite` with `responseMimeType: 'application/json'` and `temperature: 0.1`. SDK call wrapped in a 30-second timeout. The user-facing `@google/generative-ai` SDK is already in deps thanks to `gemini-client.js` (v0.58.28+).
  - Batches venues (default 10/batch) and runs `concurrency=5` workers from a shared cursor — so 1,668 venues → 167 batches → ~34 wall-clock seconds at p99-Flash latency (one worker firing every ~1s). Failures in one batch don't take down others; failed venues default to `unrelated` / `low` so the totals math still adds up, and the per-batch error is surfaced in `result.errors[]`.
  - Roll-ups: strict precision (`specialist / venues`), lenient precision (`(specialist + occasional) / venues`), per-region breakdown, plus the raw labelled venue list for the document attachment.
  - Same `_genAIFactory` test seam pattern as `gemini-client.js` — tests pass a mock factory and never touch the network.

  **2. `__tests__/durian-gemini-verifier.test.js`** (new, 14 tests)

  - `_flattenKeptVenues` — sequential ids, region attribution, snippet cap.
  - `_safeParseJson` — handles raw JSON, code-fenced JSON, leading-prose JSON, and garbage.
  - `_buildPrompt` — fruit vs. pastry prompts say different things.
  - `verifyKeptVenues` end-to-end — full label roundtrip via mock factory.
  - Mode validation rejects unknown modes.
  - apiKey requirement (when no test seam).
  - Batch failure recovery — one batch throws, the rest succeed, totals still add up.
  - Per-region roll-up math (50 % + 100 % example).
  - Progress callback fires per batch.
  - Strict vs lenient precision arithmetic.

  All 14 pass in 14 ms.

  **3. `index.js`** — wired `/ver → 🥥 Durian variance → 🤖 Gemini verify (post-run)` button + `dvg:` callback family

  - Reads the most-recent variance report from Redis (`dv:latest:<mode>`), runs the verifier, posts the strict/lenient precision summary to chat, and attaches the labelled JSON as a Telegram document.
  - Persists the labelled result to Redis at `dvg:latest:<mode>` (60-day TTL) for future replays.
  - Owner-gated by `isOwnerChat(chatId)` exactly like `dv:`.
  - Surfaces friendly errors when GEMINI_API_KEY is unset, Redis is offline, or no prior `dv:latest:<mode>` exists.

- **[KNOWN GAPS]**
  - The verifier classifies based on what Places returned to us (name + primaryType + review snippets). If Places' review snippet doesn't mention durian items but the menu does, Gemini will likely under-label. For 95 % precision we may still need to round-trip through the venue's actual Google Maps page (per-venue Place Details lookup with editorial summary + full review pull), but that's an order of magnitude more API spend (~$0.10 per venue). Pure-text-classification is the cheap first pass.
  - Concurrency = 5 is conservative. Gemini Flash Lite RPM is generous; we could push to 10-15 if the operator wants faster runs. Held back here because per-key quota varies by Cloud project tier.
  - If a batch fails for a transient reason (rate limit, network hiccup), the venues in that batch are silently demoted to `unrelated` / `low`. This is the conservative choice — they show up in `result.errors[]` and the operator can re-run the verifier to clean them up. An auto-retry was considered and skipped to keep this PR small.
