## New

### [HDR] v0.62.660 — friction scales by device class; the landscape-iPhone list question is a recommendation, not a build

- **[INTENT]** Operator: *"Are you able to adjust the friction setting for the drawer handle on the iPhone,
  reducing it by 20% on iPads and tablets, and further decreasing it on desktop devices? Additionally, in
  iPhone landscape mode, when using the list feature, it may be advisable to revert to the previous version of
  the list below, which allows scrolling both up and down... What are your thoughts on this adjustment,
  specifically for iPhone in landscape mode when using the list feature?"*

- **[READING "FRICTION"]** The shared `BottomSheet.jsx` (used by all three map TMAs' list-mode drawer) tracks
  the finger 1:1 while dragging WITHIN its snap range — there was no friction concept there, and none should
  be added, since a laggy in-bounds drag would feel broken on a touchscreen. The only resistance the drawer
  handle has ever had is the OVER-drag past its two ends: a flat `0.06 × viewport-height` allowance on the
  collapsed side, and a hard wall (no give at all) on the expanded side. That flat allowance is the one
  "friction" concept this component actually has, and it is the one the request maps onto. It also already had
  a name and a value in the sibling vanilla `bottom-sheet.js` component — `rubberBandFactor: 0.35`, "resistance
  applied to over-drag" — never wired into the React version's drag loop at all.

- **[THE FIX]** Both ends of the drag now use a real rubber-band curve (diminishing returns, capped at 48 px —
  `rubberBand()`, imported from the vanilla component rather than re-implemented) instead of the old flat
  allowance / hard wall. The resistance FACTOR is scaled by device class (`classifyViewport()`, the same
  classifier the responsive grid columns already use — no new breakpoints invented):
  - **Phone: 0.35** — the vanilla component's existing default, unchanged.
  - **Tablet: 0.28** (0.35 × 0.8) — 20% less resistance, per the operator's number.
  - **Desktop: 0.21** (0.35 × 0.6) — 40% less than phone; "further decreasing" beyond tablet's cut wasn't given
    a number, so this reads it as roughly doubling tablet's 20% reduction. A mouse-driven overdrag is a
    deliberate, precise gesture in a way a thumb-flick on glass isn't — less resistance rewards that precision
    rather than fighting it.
  - Device class is read once per drag, at `onDown` — not recalculated mid-gesture — so an orientation change
    mid-drag can't retune the feel of a drag already in flight.

- **[THE LANDSCAPE-IPHONE QUESTION — ANSWERED, NOT BUILT]** The operator explicitly asked "what are your
  thoughts," which this entry treats as an exploratory question, not a build instruction — recommendation
  given in-chat, no code changed for it this entry. The recommendation: yes, this is a sound, narrow carve-out
  specifically for iPhone landscape's list mode. Landscape phone viewport height (~375–430 px) is unusually
  short, so even the drawer's tightest peek snap (1/4, per v0.62.659) covers a larger fraction of an already
  small vertical budget than the same snap does in portrait — which is exactly "the drawer overlay obstructing
  the map" the operator describes. The trade going back to a below-the-map, always-visible scrolling list
  (the pre-v0.62.606 stacked model) is losing the "the map stays visible under a peeking drawer" affordance
  FOR THIS ONE CASE — reasonable, since the drawer already can't deliver that affordance well at this
  viewport height. The cost is a third render branch (portrait-phone overlay / landscape-phone split-panel /
  tablet-desktop unchanged) rather than one shared drawer path for all of phone. Recommendation stands;
  awaiting operator confirmation before implementing.
