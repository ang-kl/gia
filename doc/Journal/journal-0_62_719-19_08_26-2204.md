### [HDR] v0.62.719 — an unpriced Gemini model no longer costs out at exactly zero

- **[INTENT]** Not requested. It came out of the operator finally running `/cost`
  against the deployed build — the action logged as O-175 since v0.62.716 and
  pushed at them repeatedly this session. Their output:

  ```
  Gemini — 1 calls · ~$0.0000
    in: 2,519 tok · out: 172 tok
    • gemini-3.1-flash-lite — 1 · 2,519 in · 172 out · ~$0.0000
  Maps — 30 req · ~$0.3120
    • routes — 24 · ~$0.1200
    • searchText — 6 · ~$0.1920
  ```

  The Maps arithmetic is exact — 24 × $0.005 + 6 × $0.032 = $0.3120 — which is
  precisely what makes the Gemini line legible as a defect rather than a
  plausibly small number. 2,519 input tokens are not free.

- **[DELTA]**
  - **`api-cost.js` — `_geminiUsd` no longer returns 0 for an unpriced model.**
    It was `if (!rate) return 0`. Now an unknown model is costed at the most
    expensive known flash tier and returned as `{ usd, estimated: true }`.
    Same treatment for `_mapsUsd` and unknown Maps endpoints.
  - **`getCostSummary`** threads `estimated` through to `gemini.byModel[m]`,
    `maps.byEndpoint[e]`, and two new collections `gemini.unpricedModels` /
    `maps.unpricedEndpoints` (converted from `Set` to array before return — a
    `Set` does not survive `JSON.stringify`, and this object is passed as data).
  - **`formatCostSummary`** renders `⚠️ est.` on each affected row plus a
    *"Not in the rate card"* block naming the offenders.
  - **`index.js` — `?batch` now defaults to `all`**, merging every batch of a
    language into one 265-item file. See the separate rationale below.
  - **`__tests__/api-cost.test.js`** — 6 regression tests, one of which replays
    the operator's reading verbatim.

- **[WHY THIS MATTERED MORE THAN THE DOLLARS]** `spend-guard.js:93` computes
  `gemini.totalUsd + maps.totalUsd`. With Gemini silently zero, the Phase C
  circuit breaker was blind to the priciest provider in the system. Phase A
  existed specifically to make this number trustworthy. Setting `GEMINI_MODEL` to
  a name the table has not heard of is a normal operational act — the operator
  did it today — and it silently disabled half the brake.

- **[CORRECTION MADE MID-CHANGE]** This session first wrote, as fact, *"your
  deployed model is gemini-3.1-flash-lite"*. The operator replied that they had
  deployed `gemini-2.5-flash-lite`. They were right to push back: the Redis key
  is a receipt for one call at one moment, and `recordGeminiUsage` stamps
  whatever `GEMINI_MODEL` resolved to *then*. A present-tense claim was built
  from a historical record — the third instance of that exact error in one
  session (see X-3, X-4). `grep` confirms `gemini-3.1-flash-lite` appears in no
  production code, including both fallback chains, so it can only have come from
  the env var at call time. Both facts hold: that call ran under 3.1, and the var
  now reads 2.5-flash-lite. The comment in `api-cost.js` was rewritten to say so.

- **[NO INVENTED PRICE]** A `gemini-3.x` rate was deliberately *not* added to
  `PRICES`. This sandbox cannot verify Google's current pricing, and a confident
  wrong number in a spend tracker is worse than a labelled estimate. The fallback
  over-estimates on purpose: under-counting is the dangerous direction for a
  brake.

- **[DELTA — `batch=all`, prompted by an operator observation]** The operator
  noted: *"Gemini have no write/edit access to github within Gemini chat
  session."* Correct, and it was never required — but it makes the **return path**
  explicit, which the v0.62.718 design had not accounted for. Gemini emits audited
  JSON into a chat window; nothing carries it back. Not Gemini, and not the route
  either, which writes to an ephemeral Railway disk nobody can read afterwards.
  The loop is route → browser → operator uploads to the Claude session → applied
  to `i18n.js` → pushed. At one 50-item batch per request that was 36 downloads
  **and** 36 re-uploads. `?batch` now defaults to `all`: six round trips instead
  of thirty-six. Single batches stay addressable because the Gemini step still
  wants ~50 items at a time — it is the transport that benefits from merging, not
  the audit. The merged `summary` is re-derived from the merged item list rather
  than summed from the per-batch summaries, so a computed total cannot drift from
  what is actually in the file.
