A food concierge for Singapore and Johor Bahru — sourced from Google, curated for humans.

Soleat is a Telegram-native picker that takes the venue list straight from Google Places and re-shapes it around how people actually decide where to eat — by region, by cuisine specialism, by walking time, by what they last picked, by what they have not seen yet.

Two search surfaces

The 🔍 in the Cuisine app, and /cuisine in chat. Different UI, same Google-only sourcing.

Both routes call Google Places searchText directly. Neither asks an LLM to “suggest restaurants by name” — that path was retired so hallucinated venues can never reach you.

1

Cuisine Mini App — the 🔍 button

Map-first, criteria-rich. You set anchor, cuisines, radius, mode, and a few quality filters — the app runs one Places query, post-filters in memory, and renders pins on a styled vector map.

  1. Pick anchor — current GPS, a recent location, or a typed Place.
  2. Pick cuisines from the chip grid (48 slugs incl. parent expansion like Chinese → Cantonese / Teochew / Sichuan…).
  3. Tune radius, transport mode, recency, queue tolerance.
  4. Tap 🔍 — same pool surfaces for repeat taps; “next 12” pages through the same criteria.
2

Chat — /cuisine or free text

Conversational. Type the command (or just describe what you want) and Soleat returns a short ranked card-stack in the chat — no app to open. Same Places-first source as the 🔍 path; the wrapper is the only thing that differs.

  1. Send /cuisine for a quick pick, or free-text like “halal lunch near Bedok”.
  2. Soleat shares the anchor with the rest of the bot — /eat, /weather, /transport all see the same location.
  3. Cards include walking minutes (Google Routes), open-now, rating, and a one-tap “save to map”.
  4. Tap again for a different slice (the no-cuisine browse rotates iconic-dish seeds).

vs Google Maps

Same data, fundamentally different shape.

Google Maps is a database with a search box. Soleat is a decision aid built on top of that database, tuned for one specific decision: where should I eat right now?

Google Maps Database in a search box

  • Distance-sorted or popularity-sorted. Tap “restaurants near me” and you get a fixed list — taps two and three return the same one.
  • Global chains rank on the same surface as a 12-seat hawker stall. McDonald’s and Burger King take half the screen.
  • “Chinese restaurant” collapses Cantonese, Teochew, Sichuan, Hakka, Shanghainese into one slug.
  • Searching “durian” returns any café with a durian dessert on the menu — not durian shops specifically.
  • No memory of where you were last week, or where you searched from yesterday.
  • Crossing the SG ↔ JB causeway means a manual map pan. The query keeps biasing toward where you opened the app.
  • Standalone app; no link to weather, transport, or the rest of your decision.

Soleat Decision aid on top of the same Places data

  • Variant-pool architecture — repeat taps walk through the same criteria’s next 12 venues. The no-cuisine browse rotates 7 seed phrases so “tap again for variety” actually delivers it.
  • Hard-coded global-chain exclusion list — McDonald’s, KFC, Burger King, Starbucks etc. never reach your results.
  • Parent-cuisine expansion — “Chinese” fans out to 14 regional slugs; “Indian” fans out to 9; “European” to 14. Picking a parent gets you the children, picking a child gets you only that child.
  • Specialist filter for 31 cuisines / modes (durian, fruits, japanese, korean, italian, sichuan…) — Gemini classifies each venue as specialist, occasional, or unrelated; only specialists surface. Verdicts cache for 30 days so the second search is free.
  • Per-chat 20-entry recent-locations LRU, surfaced as an in-app drawer (📍 → 🧭) and as a chat list (/lr). Country flags, dedup by coordinate.
  • Region pill flips synchronously when the anchor crosses SG / JB / OTHER borders. JB queries route through regionCode: 'MY' with an addressComponent guard, not a SG-biased lat/lng radius.
  • One anchor, one bot — /eat, /weather, /transport, /carpark all read the same location SSOT (24 h freshness gate).

What this is addressing

The friction of small daily food decisions, in two countries that touch.

🔁

Decision fatigue, not search fatigue

The problem is rarely can I find a list of restaurants — it’s I have looked at five lists and they all show the same fifteen places. Soleat’s variant pool is the antidote.

🇸🇬↔🇲🇾

The causeway is a country border

SG and JB are 1 km apart. Maps treats them as one nearby area; food culture treats them as two countries. Soleat’s region model (SG / JB / OTHER pill, plus a coords-based country detector) keeps them coherent.

🍜

“Cuisine” is a fuzzy word

People say “Chinese” but mean “Sichuan tonight”. They say “Indian” but mean “proper south Indian thali”. The parent-cuisine expansion + Gemini specialist filter resolve fuzzy intent without asking 20 questions.

📍

One anchor, many decisions

You should not have to set your location three times in one lunch. Soleat keeps a single per-chat anchor (24 h fresh) that every command — food, weather, transit, parking — reads from.

🍱

Solo-friendly by default

Most “best restaurants” lists optimise for groups. Soleat surfaces venues that work for a single diner — counter seats, hawker stalls, casual cafés — without requiring you to filter manually.

🗂

Memory you do not have to manage

Your last 20 anchors are remembered per chat. Tap the 🧭 drawer in the Cuisine app or send /lr in chat — re-anchor in one tap, flagged by country.

Under the hood

Boring tech doing serious work.

No magic. Plain Express + Redis + Telegram WebApp. The interesting bit is how the pieces are arranged.

Source: 100% Google Places

Every venue comes from places.googleapis.com/v1/places:searchText. There is no LLM in the venue-selection loop. Soleat may use Gemini to classify a Place (e.g. “is this a durian specialist or a café that happens to serve durian?”) but it never invents a venue.

Variant pools, not pagination

Search results live in cuisine:pool:<chat>:<criteria>:v<n> for 20 minutes. Repeat 🔍 taps walk through the same criteria’s pool with a 12-h seen-set, so you never see the same venue twice within a session.

Walking time, not crow flies

Distances on cards come from Google Routes Matrix — the actual walking duration via the real path. Two venues 600 m apart can rank very differently if one is across a river.

One anchor SSOT

Per-user location lives in a single Redis hash loc:<chatId> with a 24-h freshness gate. Every TMA and every chat command reads from the same key. Set it once.

JB hybrid filter

Searching from a JB anchor routes through regionCode: 'MY' with an addressComponent guard — venues returned must actually be in Johor Bahru, not “somewhere within 30 km of the JB centroid” (which would include SG’s north shore).

Specialist verdict cache

Per-(mode, placeId) Gemini verdicts live in dgv:labels:<mode> for 30 days. First query for a cuisine warms the cache; subsequent queries are free and instant. Currently covers 31 cuisines.
