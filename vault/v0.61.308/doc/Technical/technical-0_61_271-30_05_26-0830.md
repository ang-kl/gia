## 1. Positioning — one brain, three faces

The search pipeline, fuzzy matchers, Gemini, the curated Vault, and the cuisine/geo taxonomy stay in the existing backend and are **never re-implemented** in the web repo. Telegram and Web are both thin clients of the same `/api` brain.

- **Keep Telegram in its sandbox.** Telegram retains its native superpowers — chat conversation, deep links, buddy-match, location-share, "copy to chat". Web does **not** replicate chat; it gets web-native equivalents (accounts, shareable URLs, saved lists, big map, SEO surfaces).
- **Reframe from parity to public product (UX review).** The web app is *"a public, anonymous-first, indexable, two-pane discovery product that happens to share a brain with the bot,"* not a port of the TMA. This is a positioning + sequencing stance, not a re-architecture.

```
   Telegram ──webhook──▶┐
   TMAs (initData) ─────▶│  EXISTING BACKEND (Railway, index.js Express)
                         │  principalResolver → req.principal { storageKey, canSendToChat }
   soleat-web ──────────▶│   • tg:<chatId>        (Telegram)
     • JWT (account)     │   • web:<uuid>         (web account)
     • cookie (anon) ───▶│   • web:anon:<uuid>    (cold visitor)   ◀── NEW kind
                         │  pipeline / gemini / Vault / Redis
                         │  Postgres ── identity tables only       ◀── NEW
                         └──────────────────────────────────────────
   soleat-web (Vercel · Next.js App Router · Tailwind · shadcn) — NEW REPO, calls /api/v1/* over HTTPS
```

## 3. The integration seam — dual/tri-auth **principal resolver** (keystone change)

Today `/api/cuisine/*` is gated by one chokepoint — `app.use('/api/cuisine', requireInitDataFromBodyOrHeader)` (`index.js:11414`) — **and** ~25 inline `verifyInitData(...)` re-derivations inside handlers (e.g. search `index.js:13361-13362` `csChatId`; nl-query `15063-15067`). Even `/api/cuisine/catalogue` (`:11416`) and `/api/reverse-geocode` (`:16000`) require valid Telegram initData today.

**Change:** introduce a `principalResolver` middleware that accepts any of three credentials and resolves a uniform `req.principal`:

| Credential | `principal.kind` | `storageKey` | `canSendToChat` |
|---|---|---|---|
| `X-Telegram-Init-Data` (existing) | `telegram` | `tg:<chatId>` | `true` |
| `Authorization: Bearer <web JWT>` | `web` | `web:<uuid>` | only if `linkedTelegramId` **and** user opted in |
| signed device cookie (cold visitor) | `web-anon` | `web:anon:<uuid>` | `false` |

Every downstream handler that reads `chatId` reads `principal.storageKey` instead. The `web-anon` kind (UX review's #1 move) is a one-line extension that makes **search + save work with zero login** — without it, web is *worse* than Telegram's pre-authenticated one-tap.

### 3.1 Side-effect firewall (red-team finding)
The resolver must carry `canSendToChat`. The hyphenated `/api/cuisine-search` (`index.js:16305`) calls `safeSend(tgUserId,'🌿 Sensing the vibe…')` (`:16313`) + chat-locks (`:16311-12`) + `setUserLocation` (`:16329`). With a `linkedTelegramId`, a web search could emit **ghost Telegram messages**. Mitigation: assert `principal.canSendToChat` before any `safeSend`/`setProcessing`/copy-to-chat; web/anon principals are hard-blocked. An explicit inventory of chat-side-effecting endpoints is a P0 deliverable.

## 4. Data model

### 4.1 Postgres (identity tables only — refined post-review)
- `users(id uuid pk, email, email_verified, created_at, lang, display_name)`
- `oauth_identities(user_id, provider, provider_sub, unique(provider,provider_sub))`
- `sessions(id, user_id, refresh_token_hash, expires_at, user_agent, revoked_at)`
- `telegram_links(web_user_id, telegram_user_id unique, linked_at, status)` — the explicit, reversible bridge

> **Why identity-only (red-team middle path):** search+transport otherwise need only recent-locations, saved-venues, prefs, seen-sets — small KV/list structures namespaced Redis already models, and the principal refactor is required regardless. Postgres is reserved for what is genuinely relational (accounts/OAuth/sessions/links). The original draft's 8-table model over-built ~4 non-load-bearing tables; migrate them to Postgres later if query needs grow.

### 4.2 Redis (unchanged role + new namespace)
- Source of truth for Vault (`gia:vault`, `gia:place:*`), taxonomy caches, response cache, transport/LTA cache, **and Telegram user data** (untouched).
- **New:** `web:<uuid>:*` / `web:anon:<uuid>:*` for web recent-locations, saved-venues, seen-sets, prefs.
- Web reads Vault/taxonomy **through the API**, never directly.

### 4.3 Linking consistency (red-team R-4)
recent-locations is an LRU that keeps mutating Redis-side (`recent-locations.js`, key `recent-locations:<chatId>`). A one-shot import on link leaves a stale-data path for a user who keeps using *both* faces. Decision required: post-link, treat the web account as authoritative for web reads; the import is one-time + user-initiated + reversible (unlink must **not** delete Telegram-side data).

## 6. The `chatId`-coupling blast radius (red-team R-1 — reframed)

The coupling is **fail-silent, not fail-loud**: per-user Redis helpers no-op on a null `chatId` (`appendSeenSet` guards `if(!chatId)` at `index.js:8616`; `pickSingaporeanDishesForChat` at `pipeline.js:512`) instead of throwing. A half-finished principal refactor therefore **passes CI and ships a web app where "load more" returns the same 12 venues forever**, recent-locations never persist, sg-dish memory is stateless, analytics under-count.

Affected subsystems threaded through `principal.storageKey` (≥8): seen-set, `cuisineSession` clipboard, page-history, recent-locations LRU, user-location anchor/radius-cap, sg-dish memory, usage-log, **rate-limit**. The `/api/cuisine/search` handler alone (~`13317`→`15048`, ~1.7k lines) reads `csChatId` at ≥7 sites (`13371`,`13414`,`13439-57`,`13505`,`14886`,`14909`,`14918-30`).

> **P0 deliverable:** an exact file:line audit of every `chatId` read in the search+transport paths **plus a web-principal persistence test matrix** (null / `web:<uuid>` / linked-telegram) proving seen-set + recent-locations actually write under `web:<uuid>`. This is the first task, and it is the residual ~1-5% the plan cannot close without touching code.

Public read-only routes (`catalogue`, public venue/cuisine data) must be **split out** from under the `/api/cuisine` initData chokepoint into e.g. `/api/v1/public/*` — today they are Telegram-gated, contradicting the SSR/SEO surface in §9 P4.

## 7. Budgets & cost controls

| Resource | Limit / control | Change vs. today |
|---|---|---|
| Places billable per search | ~1 searchText + ~5 Place Details + 1 Routes-Matrix per call (`index.js:13319-24`); cap=500/hr/key | **public origin widens exposure** — was tuned for trusted Telegram users |
| Gemini `/nl-query` | 60/hr/user (`index.js:15077`) | a web account is cheap to mint → 1 account = full budget |
| **Rate limiter** | **REWRITE required** | `rate-limit.js` does `const chatId=req.tg?.user?.id; if(!chatId) return next();` → **fails OPEN for every web/anon principal**. Must re-key on `principal.storageKey` **+ mandatory per-IP fallback** |
| **Per-principal cost budget** | NEW | count-windows are insufficient; add a per-account *cost* budget + a **global daily kill-switch** for Places/Gemini, per-environment (the `cloud-console daily quota` backstop must be explicit) |
| Turnstile / WAF | NEW | must gate **search itself**, not just auth — a logged-in scraper drains Places |
| Dev bypasses | HARDEN | `SKIP_INIT_DATA_AUTH` (`twa-auth.js:72`) + rate-limit env bypass become catastrophic on a public origin; remove/guard per-env |

> **Gated milestone:** "public origin live" must require the rate-limit rewrite + per-IP fallback + cost budget + kill-switch **before** enablement — not a P3/P4 polish item. G4 (paid-API) discipline applies to any new Places/Gemini path.

## 8. Build constraints

- **Separate repo `soleat-web`** (D-3). Backend changes land in *this* repo and are **additive**: `/api/v1/*` aliases over existing handlers + the resolver; TMAs keep `/api/cuisine/*` for back-compat. Aliasing a route does **not** alias its inline `verifyInitData` — each handler in scope must be refactored.
- **CI contract tests** against the OpenAPI spec guard cross-repo drift (R-4).
- **`gia-preflight` is mandatory** for every touched backend file (this refactor hits `index.js`, the search flow, and venue rendering — exactly its trigger set): `node --check`, Vitest green (per-file under O-21), version bump, web build if `web/` changes. Add a **web-principal test matrix** to the preflight scope (§6).
- The iCloud-Drive plumbing-commit pattern + pack-corruption recovery (O-22, see `technical-0_61_147`) still apply to backend commits made from this working tree.

## 9. Phased delivery

- **P0 — Backend foundations (this repo; highest risk).** Principal resolver (3 kinds) + `canSendToChat` firewall; **rate-limit rewrite + per-IP + cost budget + kill-switch** (gated before any public origin); thread `storageKey` through the ≥8 helpers + persistence tests; split public read-only routes out of the chokepoint; Railway Postgres + identity tables + auth endpoints (email magic-link, OAuth, link-telegram, refresh/logout); harden dev bypasses; gia-preflight.
- **P1 — Web skeleton (new repo).** Next.js + Tailwind + shadcn on Vercel; **anonymous principal from first paint**; auth UI *deferred* (not in the header on first run).
- **P2 — Search (anonymous-first).** Geolocation-optional results in <3 s; fused quick-pick + free-text command bar; **two-pane list↔map with synced focus + shareable URL state**; results held in client state (drop the 80-cap seen-set paging scaffolding); cards with **hero photos**, Save→Lists, share-link, compare; auth nudge only at a continuity moment.
- **P3 — Transport.** Interactive map **default** (invert the phone-era PNG-first compromise, `transport/src/App.jsx:36-41`); deep-linkable station URLs; **"what's near this station" food×transport fusion** (one canvas the two separate TMAs cannot offer).
- **P4 — Linking, SEO, continuity.** SSR cuisine/area/venue/station pages (the reach engine — promoted toward first-class); "Connect Telegram" import; anon→account claim migration; "send to phone"; PWA.

## 11. UX directives (review — "decisively better than Telegram")

Top moves, ranked, folded into the phases above:
1. **Anonymous-first, zero-friction first search** (`web-anon` principal; auth deferred to a continuity moment; migrate anon→account on signup).
2. **Indexable public surfaces (SSR)** — cuisine/area/venue/station pages; the only thing that delivers *reach*, which Telegram structurally cannot.
3. **Two-pane list↔map workspace** with synced focus + shareable URL state (fixes Telegram's worst flaw: results scroll away, no map-alongside-list).
4. **Delete the Telegram scaffolding** — copy-to-chat, SG/JB/OTHER region pills, IATA/Gemini auto-detect, 80-cap paging/seen-set machine, drift prompts, diagnostics easter-eggs, anthropomorphic loading copy. Map center = single location source of truth. ~40% of TMA complexity evaporates.
5. **Venue cards with photos + Save/share-link/compare** (decisions chat cannot support; add the missing hero image).
6. **Transport: interactive map default + station deep-links + food×station fusion.**
7. **Cross-device continuity** — portable URLs for everyone; "send to phone" + synced lists for the logged-in.

Accessibility quick wins flagged: the TMA cards nest `<button>` inside `<button>` (`ResultCard.jsx:177`) — invalid + a keyboard/SR hazard; web card = `<article>` with discrete focusable actions; own the palette → WCAG AA from day one.
