## 0. What this project is

**Soleat** (package name `soleat`; product name *Gia4lunch* / "Gia") is a production Telegram bot + five Telegram Mini Apps (TMAs) + an Express server that helps a solo diner in Singapore decide where to eat — and get there. It spans F&B discovery (cuisine picker, hawker centres, Michelin / Bib Gourmand, hidden gems), free-text and cooking-method search, live transport and traffic, an interactive Google-Maps overlay system, carpark availability, weather, and a bilingual (EN/FR) interface. It is a single-operator project built with AI-assisted development, deployed on Railway, and has reached **v0.61.76** across ~287 numbered commits and ~574 pull requests.

The Builder doc records *how* the project is built — the operating lens, the conceptual framework, and the recurring patterns — distinct from *what* it does (Feature), *what it runs on* (Technical), and *who builds it* (Persona).

The v0.61.29 → v0.61.76 arc covered by this master is, almost in its entirety, a **map-and-transport refinement campaign**: a 7-phase map-controls redesign, a multi-Change-Request (CR1–CR10) operator backlog delivered in phased PR stacks, a 6-phase (CR6 Phase 1 → Phase 3) station-info data-and-card build, a chain of POI overlay layers (Clinics / Police / Hospitals / Bus Stops), and a steady run of /transport chat-reply layout reworks. The work is overwhelmingly PATCH-grade — small, reversible, operator-screenshot-driven.

## 5. How this project is built — the working cadence (v0.61.29 → v0.61.76 observed)

> New in Builder #3 — a narrative of the observed build cadence across the arc this master covers. Append-only; future masters extend it.

- **PATCH-iteration rhythm.** The arc is ~48 versions of almost-entirely PATCH bumps. A typical PR touches a handful of files (often just `index.js` + `i18n.js`, or the three map modules), ships one focused change, and merges within a tight open → CI → merge → sync loop (PP-13). MINOR-grade rewrites do not appear in this arc.
- **The CR backlog.** Mid-arc the operator handed over a numbered change-request set (CR1–CR10) for the in-map controls. It was delivered as a phased campaign (FW-12, BL-16): v0.61.51 shipped CR1/2/3/7/8/9 and deferred CR4/5/6; CR4 and CR5 landed across v0.61.52–.58; CR6 — the largest — was sub-phased into a data layer (Phase 1, v0.61.55), enrichment passes (Phase 2a v0.61.56, Phase 2b v0.61.67), and a UI card (Phase 3, v0.61.57), with CR10 (a pin-colour lift) folded in along the way. Every deferral was logged and re-picked-up — no CR was silently dropped.
- **Offline-fetch scaffolds for paid/keyed data.** Where a feature needed a billed Places call or a keyed LTA/OneMap feed, the arc's pattern (FW-14, PP-16) was to commit a `scripts/fetch-*.js` / `enrich-*.js` scaffold — with filtering, coverage and error reports, and a README — and leave the actual data run to the operator with their own API key. This keeps the G4 paid-API gate satisfied (the sandbox never bills) and the build reproducible. Five such scaffolds shipped in the arc.
- **Doc-system catch-up cadence.** Journal entries are per-PR (the standing rule); Feature / Technical / Register batch per arc milestone (`doc/CLAUDE-FULL.md` §17.3). The arc shows the Journal kept current PR-by-PR while the cross-cutting doc-types were carried as "still due" in `[KNOWN GAPS]` until a catch-up pass — and this Builder #3 master, with the `vault/v0.61.76/` snapshot, is one such pass.
- **Vault-snapshot cadence.** A frozen `vault/<version>/` mirror is taken at the close of a coherent arc; this master ships alongside `vault/v0.61.76/`, following the v0.61.28 precedent (journal #231 / decision D-1028). The most recent vault is the named rollback target for any risky change (`doc/CLAUDE-FULL.md` §17.7).
- **Preflight discipline.** Every code-touching PR in the arc ran the `gia-preflight` checklist — `node --check` on each changed `.js`, `npm test` 100 % green, a `web/` build when a TMA changed, a `package.json` version bump. Verification is recorded in each Journal `[VERIFICATION (sandbox)]` block, CI-run-numbered.
- **Agent-assisted doc regeneration.** The documentation set itself is regenerated with agent assistance under operator instruction — fresh non-incremental masters on a vault pass, the `doc/VibeCodingRecord/` ledger appended and re-run, the Journal kept per-PR. The operator directs; the agent executes and the trace stays auditable (BL-6, BL-10).
- **Operator standing rules.** Two standing rules bind the arc: *"Update the Journal every time a new PR is created and done"* (G3, `journal-0_60_144`) and the documentation protocol in `doc/CLAUDE.md`. New rules require operator approval and a verbatim quote (`doc/CLAUDE-FULL.md` §17.6, Rule SR-1).
