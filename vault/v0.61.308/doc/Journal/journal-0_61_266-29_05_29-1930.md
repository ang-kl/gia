## New

### [HDR] #467 | 19:30 SGT 29-05-29 | v0.61.266 — Cuisine TMA honors Menu-set label | 3 files | 1 PR | 1 build |

- **[INTENT]** Patch the cuisine TMA's `fetchUserLocation` consumers so the `label` field written by `/api/menu/set-location` is actually installed as the cuisine `locationAnchor` — not silently discarded in favour of a reverse-geocoded neighbourhood.

- **[DELTA]**

  **Root cause** (audit reported in this morning's task):

  The two TMAs already share Redis (`loc:${hashChatId(chatId)}`) via the `setUserLocation` / `getUserLocation` helpers in `location-cache.js`. The menu TMA's `/api/menu/set-location` route at `index.js:12805–12842` correctly writes the typed/picked anchor's label via `setUserLocation`'s `label` opt (location-cache.js:28). The `/api/cuisine/user-location` route at `index.js:13028–13094` correctly surfaces that label in the response payload (line 13079).

  **The leak was on the cuisine read side** at `web/cuisine/src/v2/App.jsx:448–482` (`tryServerCache`) and the parallel `refetchAndFlip` on the visibility-restore path at lines 624–642. Both functions consumed `r.lat` / `r.lng` / `r.region` / `r.precinctId` from the response but **discarded `r.label`** entirely. Without the label being installed as `locationAnchor`, the cuisine TMA's banner / pill reverse-geocoded the coords back to a generic neighbourhood ("Tanjong Pagar", "Telok Blangah"), overriding the user's pick from the Menu TMA.

  **Fix** (3 + 3 lines at each call site):

  ```jsx
  if (r.label && typeof r.label === 'string' && r.label.trim()) {
    setLocationAnchor({ lat: r.lat, lng: r.lng, name: r.label.trim() });
  }
  ```

  Applied in `web/cuisine/src/v2/App.jsx`:

  - **Line ~450 (`tryServerCache`)** — runs on initial mount. Catches the cold-launch case (open Cuisine TMA after setting location in Menu TMA earlier).
  - **Line ~630 (`refetchAndFlip`)** — runs on `visibilitychange` + Telegram `viewportChanged`. Catches the warm-switch case (open Menu TMA, set location, switch to Cuisine TMA which was already open in the background).

  The third `fetchUserLocation` call at line 587 (inside the deep-link / GPS auto-detect post-init effect) intentionally reads ONLY `r.region` + `r.precinctId` — it doesn't touch `userLoc` or `locationAnchor`, so it stays unchanged.

  **No server-side changes.** The route already returns the right shape; only the client was leaking.

  **2. `package.json`** — `0.61.265 → 0.61.266`.

  **3. `doc/.serial-state.yml`** — commit 478→479, build 268→269, journal 466→467; re-anchored 29-05 '26 19:30 SGT.

It does NOT also `saveUserLocation` back (which would write to `/api/cuisine/set-location`) — that's intentional because the menu TMA already wrote to the shared Redis cache, and re-writing on read would be a redundant round-trip. If a future PR needs to *modify* the anchor on cuisine open, it should call `setLocationAnchor` AND `saveUserLocation` to keep the cache in sync.
