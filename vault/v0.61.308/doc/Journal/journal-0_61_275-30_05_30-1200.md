## New

### [HDR] #476 | 12:00 SGT 30-05-30 | v0.61.275 — Plan B cached Gemini labels | 12 files | 1 PR | 1 build |

- **[INTENT]** Persist the Gemini cross-check verdicts (run on demand via `/ver → 🤖 Gemini verify`) as a Redis hash keyed by `placeId`, then have the cuisine-search route drop any venue Gemini classified as `unrelated`. Unlabelled venues pass through (trust the v0.61.262 heuristic). Per-search Gemini cost: $0. Per-search latency hit: ~1 ms (single Redis `HGETALL`). Refresh cadence: operator-driven, same `/ver` panel.

- **[DELTA]**

  **1. `durian-gemini-verifier.js`** — surface `placeId` through the flatten + labelled output

  Pre-v0.61.275, the verifier emitted `{ id, region, name, primaryType, label, confidence, reason }` per venue — no placeId. That meant downstream consumers couldn't join the labels back to a Places result at search time. Three edits:
  - `_flattenKeptVenues` row now includes `placeId: String(v?.placeId || '')`.
  - `_processBatch`'s `labelled` row now includes `placeId: v.placeId || ''`.
  - The failed-batch default fill (when a Gemini batch throws) now also includes `placeId` so the totals add up.

  **2. `index.js` — `ownerDurianGeminiRun`**: write per-placeId labels to Redis hash

  After the existing `dvg:latest:<mode>` full-result persist, a new block iterates `result.venues[]` and writes each `(placeId, { label, confidence, reason, verifiedAt })` to a Redis hash `dgv:labels:<mode>` (via `redis.hSet(key, entries)` where entries is `{ placeId: stringifiedJson, ... }`). TTL is set to 30 days via `redis.expire`. Console log line: `[Cuisine-TMA] dgv:labels:<mode> populated N placeId → label entries (30d TTL)`.

  **3. `index.js` — `/api/cuisine/search` route**: cached-Gemini-label post-filter (D703e)

  Right after the existing `specialMode` heuristic filter (`D779 specialMode=… post-filter`), a new block activates ONLY when `specialMode === 'durian'` or `'durian-pastry'`:

  - `redis.hGetAll('dgv:labels:' + specialMode)` reads the entire labels hash for this mode.
  - If empty / missing → no-op (the operator hasn't run Gemini verify yet, or labels expired).
  - Otherwise, every kept venue is looked up by `v.placeId`:
    - Unlabelled venue → kept (trust v0.61.262 heuristic; the unlabelled venue may be brand-new since the last verify run).
    - Labelled `unrelated` → dropped.
    - Labelled `specialist` or `occasional` → kept.
  - Log: `[Cuisine-Search] D703e Gemini-label post-filter (durian-pastry): 16 → 12  (dropped=4 unrelated, unlabeled=0 passed through)`.

  The filter is bypassed gracefully on any Redis error (try/catch with `console.warn`) — never blocks the search.

  **4. `__tests__/durian-gemini-verifier.test.js`** — +4 tests for the placeId flow

  - `_flattenKeptVenues` emits placeId from source.
  - `_flattenKeptVenues` defaults placeId to `''` when source omits it.
  - `verifyKeptVenues` end-to-end: labelled venues carry placeId through to output (specialist + unrelated cases).
  - Failed-batch defaults also include placeId so the hash-write doesn't skip them.
