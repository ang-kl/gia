- **[INTENT]** DF-80 carried from v0.60.185 — operator reported "Michelin listing cannot refresh next 12 again". v0.60.185 shipped diagnostic logging while awaiting Railway evidence. On a closer code-review of `handleMichelinSearch` (index.js:6007–6776), the bug surface was visible without needing the reproduction:

  ```js
  // index.js:6271 (truthy placesData — HAPPY path, the vast majority of venues)
  const venue = placesData ? {
    placeId: ...,
    name: ...,
    /* … 40+ fields …  but NO michelinDedupKey here … */
    michelinHalal: entry.halal === true
  } : {
    // index.js:6311 (fallback — Places lookup failed, rare)
    placeId: '',
    name: entry.name,
    /* … fewer fields … */
    michelinHalal: entry.halal === true,
    michelinDedupKey: `${entry.name}|${entry.address || ''}`.toLowerCase()   // ← only HERE
  };
  ```

  Downstream at line 6502 the handler appends keys to the seen-set:

  ```js
  const postFilterDedupKeys = filteredVenues
    .map((v) => v.michelinDedupKey)
    .filter(Boolean);                              // ← drops every undefined
  await appendSeenSet(csChatId, criteriaHash, postFilterDedupKeys);
  ```

  Because virtually every Michelin entry resolved successfully via Places, `michelinDedupKey` was `undefined` on each happy-path venue → `filter(Boolean)` dropped them all → `postFilterDedupKeys` was empty → `appendSeenSet` was a no-op → **the seen-set never grew** → every subsequent 🔍 tap re-filtered the SAME `allEntries` against the SAME empty seen → returned the SAME first 12.

  The v0.60.162 commit comment ("attach the dedup key to the venue object itself so the seen-set append at the bottom of the handler can derive keys from `filteredVenues` (post cuisine/veg/halal/price filtering) instead of the pre-filter slice") makes clear the intent was to attach the key on BOTH branches. The author edited the fallback object first and missed the happy-path object — exactly the failure mode noted in DF-77's heuristic "regression after a refactor / merge".
