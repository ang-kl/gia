# Soleat Web — Migration / Standalone Web App Plan (v0.9 draft for review)

## 0. Operator decisions (fixed constraints)
1. **Identity:** Separate web accounts (email magic-link + Google/Apple OAuth), with *optional* "Connect Telegram" linking to import history.
2. **Scope at launch:** Core **search** (cuisine + free-text + location + venue cards) **+ transport** (MRT map, status, station context). Defer: hawker, buddy-match, /hidden, surprise, oversight.
3. **Repo:** **Separate repo** (`soleat-web`) for the frontend, calling the **existing Railway backend over HTTP** (shared API).
4. **Database:** **Add Postgres** for web users/accounts/history; keep Redis for cache/Vault/transient; share the curated Vault + taxonomy.

## 1. Guiding principles
- **One brain, two faces.** The search pipeline, fuzzy matchers, Gemini, Vault, and taxonomy stay in the existing backend and are *never* re-implemented in the web repo. Telegram and Web are both thin clients of the same `/api` brain.
- **Keep Telegram in its sandbox.** Telegram keeps its native superpowers (chat conversation, deep links, buddy-match, location-share drift handling, "copy to chat"). Web does NOT try to replicate chat; it gets web-native equivalents (accounts, shareable URLs, saved lists, richer map, SEO landing pages).
- **The API is the contract.** The integration seam is a versioned, documented `/api/v1/*` surface with a **dual-auth** principal model. Web never reaches into Redis or the pipeline internals directly.
- **No silent data coupling.** Web user data lives in Postgres keyed by `web_user_id`. Telegram data stays Redis-keyed by `chat_id`. Linking is an explicit, reversible bridge — never an implicit merge.

## 2. Target architecture

```
                         ┌─────────────────────────────────────┐
                         │   EXISTING BACKEND (Railway)         │
   Telegram  ──webhook──▶│   index.js Express + bot handlers    │
                         │   pipeline / gemini / fuzzy / Vault  │
   TMAs (initData) ─────▶│   Redis (cache, Vault, TG user data) │
                         │                                      │
   soleat-web (JWT) ────▶│   /api/v1/* (dual-auth principal)    │
                         │        │                             │
                         │        └──▶ Postgres (web users) ◀───┼── NEW
                         └─────────────────────────────────────┘
                                    ▲
                                    │ HTTPS JSON
                         ┌──────────┴───────────┐
                         │  soleat-web (Vercel) │  NEW REPO
                         │  Next.js + Tailwind  │
                         │  email/OAuth auth    │
                         └──────────────────────┘
```

### 2.1 The dual-auth principal (the central integration piece)
Today: `/api/cuisine/*` is gated by `requireInitDataFromBodyOrHeader` (Telegram initData HMAC → `chatId`).
Change: introduce a **principal resolver** middleware on the backend that accepts EITHER:
- `X-Telegram-Init-Data` (existing) → `{ kind:'telegram', id: chatId }`
- `Authorization: Bearer <web JWT>` (new) → `{ kind:'web', id: webUserId, linkedTelegramId? }`

It resolves to a uniform `req.principal`. Every downstream handler that currently reads `chatId` reads `principal.storageKey` instead, where `storageKey` = `tg:<chatId>` or `web:<uuid>`. This is the single most important refactor: it lets the same pipeline serve both faces without duplicating logic, and keeps the two data namespaces cleanly separated.

### 2.2 Data model (Postgres, new)
- `users(id uuid pk, email, email_verified, created_at, lang, display_name)`
- `oauth_identities(user_id, provider, provider_sub, unique(provider,provider_sub))`
- `sessions(id, user_id, refresh_token_hash, expires_at, user_agent, revoked_at)` (or use a session lib; see §6)
- `telegram_links(web_user_id, telegram_user_id unique, linked_at, status)` — the explicit bridge
- `recent_locations(user_id, lat, lng, label, country, region, set_at)` — web equivalent of the Redis LRU
- `saved_venues(user_id, place_id, payload jsonb, saved_at)` — web-native replacement for "copy to chat"
- `search_history(user_id, query jsonb, created_at)` — optional, for "recent searches"
- `prefs(user_id, key, value)` — language, country, units
Redis stays the source of truth for: Vault (`gia:vault`, `gia:place:*`), taxonomy caches, response cache, transport/LTA cache, and *Telegram* user data. Web reads Vault/taxonomy through the API, never directly.

### 2.3 What the web frontend reuses vs. rebuilds
| Concern | Reuse (call API) | Rebuild (web-native) |
|---|---|---|
| Cuisine/free-text search | ✅ `/api/v1/cuisine/search`, `/nl-query`, `/catalogue` | — |
| Venue data/enrichment | ✅ same JSON the TMAs already get | Render as web cards (not TG-HTML) |
| Location picker + autocomplete | ✅ `/place-autocomplete`, `/place-resolve`, `/set-location` | Browser geolocation + map UI |
| Transport (MRT/status/context) | ✅ `/api/v1/transport/*`, `/geo/*` | Full-screen interactive map |
| i18n strings | ✅ port `i18n.js` table (pure data) | Client i18n (already mirrored in TMA) |
| "Copy to chat" | ❌ Telegram-only | Save / share-link / add-to-list |
| Conversation/drift prompts | ❌ Telegram artifact | Stateful UI; geolocation = no drift guessing |

## 3. Delivery phases

### Phase 0 — Foundations (backend, in existing repo)
- Add `pg` + a migration tool (node-pg-migrate or Prisma). Provision Railway Postgres.
- Implement `principalResolver` middleware; refactor `chatId` reads behind `principal.storageKey` for the **search + transport** routes only (scope-bounded).
- Stand up `/api/v1/*` as aliases over the existing handlers (versioned, CORS for the web origin, rate-limited per principal). Keep `/api/cuisine/*` working for TMAs (back-compat).
- Add web-auth endpoints: `/api/v1/auth/email/start`, `/auth/email/verify`, `/auth/oauth/:provider/callback`, `/auth/refresh`, `/auth/logout`, `/auth/link-telegram` (Telegram Login Widget verification).
- **Tests + gia-preflight** for every touched backend file (node --check, vitest green, version bump).

### Phase 1 — Web skeleton (new repo `soleat-web`)
- Next.js (App Router) + Tailwind + shadcn/ui (matches TMA stack; SSR for SEO landing pages — the whole point is reach beyond Telegram).
- Deploy to Vercel with preview URLs. Env: `NEXT_PUBLIC_API_BASE`, OAuth secrets, JWT secret.
- Auth flows wired to backend; session in httpOnly cookie + refresh.
- App shell: header, language toggle, location chip, responsive layout (mobile-first; this replaces a phone-only TMA).

### Phase 2 — Search (the core)
- Location: browser geolocation → reverse-geocode via API; manual picker with autocomplete; recent-locations from Postgres.
- Cuisine quick-pick + free-text box → `/api/v1/cuisine/search` / `nl-query`.
- Results: web venue cards (rating, hours, price, crowd, Michelin, maps link, photos), map view, "save" + "share link" actions.
- Saved venues page; recent searches.

### Phase 3 — Transport
- Full interactive MRT/LRT map (line-paths GeoJSON), live status, station context, bus arrivals. This is *better* on web than in a cramped TMA (bigger canvas, deep-linkable stations).

### Phase 4 — Linking + polish
- "Connect Telegram" via Login Widget → writes `telegram_links` → one-time import of recent-locations/prefs/clips from Redis into Postgres (explicit, user-initiated, reversible).
- SEO landing pages per cuisine/area (SSR) — discovery channel that Telegram can't offer.
- PWA (installable, offline shell), share-target.
- Analytics parity (identity-free hashes, same as Telegram side).

## 4. Cross-cutting concerns
- **Auth security:** JWT short-lived + refresh rotation; OAuth state/PKCE; magic-link single-use tokens; rate-limit auth endpoints; constant-time compares (reuse twa-auth patterns).
- **CORS:** lock `/api/v1/*` to the web origin(s) + TMA origin; preflight cache.
- **Rate limiting & cost:** Google Places + Gemini cost real money. Per-principal quotas; reuse `rate-limit.js`; cache aggressively (response-cache already exists).
- **Privacy/GDPR:** web `/forgetme` equivalent = `DELETE ... WHERE user_id`; privacy policy page; cookie consent; data-export. Unlinking Telegram must not delete Telegram-side data.
- **Abuse:** web is public (no Telegram gate) → bot/scraper risk on the search API. Need WAF/Turnstile on auth + search, per-IP throttle.
- **Observability:** Sentry (already present) extended to web; structured logs per principal.
- **Versioning/back-compat:** `/api/v1` is additive; TMAs keep using `/api/cuisine/*` until migrated.

## 5. Risks & mitigations
- **R1 — Pipeline coupling to chatId is deeper than the search routes.** Mitigation: scope the principal refactor strictly to search+transport handlers; audit each `chatId` read in those paths; leave bot handlers untouched.
- **R2 — venue-templates.js emits Telegram-HTML, not web JSON.** Mitigation: web uses the *structured* venue objects the search endpoint already returns (TMAs prove this works); templates stay Telegram-only.
- **R3 — Public API cost/abuse explosion.** Mitigation: auth-gate expensive endpoints, Turnstile, per-principal + per-IP quotas, cache.
- **R4 — Two codebases drift.** Mitigation: shared API is the only contract; publish an OpenAPI spec + typed client; contract tests in CI.
- **R5 — Identity/link edge cases (same person, two accounts).** Mitigation: link is 1:1, reversible, explicit; conflicts surface to user, never auto-merge.
- **R6 — search-conversation/location-drift assume Telegram chat semantics.** Mitigation: web keeps conversation state client-side/Postgres keyed by web_user_id; drift detection is dropped on web (geolocation is explicit) — a UX win.
- **R7 — SEO/SSR vs. an API that expects auth.** Mitigation: public landing pages use a read-only, cacheable, unauthenticated subset (catalogue, public venue pages); personalized actions require login.

## 6. Open technical choices (reviewer: challenge these)
- Next.js vs. Vite SPA (chosen Next.js for SEO/SSR — is that worth the complexity given core is an authed app?).
- Auth: roll-your-own JWT vs. Auth.js (NextAuth) vs. Clerk/Supabase Auth. (Lean Auth.js for OAuth+email, custom for Telegram-link.)
- Prisma vs. node-pg-migrate + raw SQL.
- Where web session JWT is verified — at Vercel edge vs. the Railway backend (backend, to keep one trust boundary).
- Do we need websockets (live transport)? Probably SSE/poll is enough at launch.

## 7. Rough sequencing/effort (relative)
P0 backend foundations (largest risk) → P1 skeleton+auth → P2 search → P3 transport → P4 linking+SEO+PWA. P0 and P2 are the load-bearing phases.
