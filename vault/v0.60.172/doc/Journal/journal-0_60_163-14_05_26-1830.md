- **[DELTA]**

  **`index.js` `/api/cuisine/copy-all` (~line 7969-7988)** — Issue 1 root cause: Telegram caps single messages at 4096 chars. The v0.59.29 cap of 12 venues was sized for the pre-Michelin-enrichment era; the v0.60.147 + v0.60.153 enrichment added `dishes` (3 lines) + `recentReview` blockquote per Michelin venue, pushing each block to ~300-400 chars. 12 × 350 + header ≈ 4250 chars → breaches the 4096 limit on Bib Gourmand-heavy combos. The v0.60.145 plain-text retry strips HTML tags but doesn't shorten the body (HTML overhead is < 5% of total length), so the retry also hits the same ceiling. Operator log line proves it:

  ```
  [Cuisine] copy-all sendMessage failed (HTML mode): Bad Request: message is too long
  [Cuisine] copy-all sendMessage retry failed (plain): Bad Request: message is too long
  [VLOG-CLIENT 100000001] {"kind":"fetch","method":"POST","url":"/api/cuisine/copy-all","ms":1039,"ok":false,"error":"HTTP 500"}
  ```

  Fix: when `body.length > MAX_CHARS` (3800 — 4096 with safety margin for Telegram entity overhead), pack the venue blocks into N chunks via a greedy bin-packing algorithm (`packBlocksIntoChunks` — local helper). Each chunk gets a header `Picks (i/N)` so the user sees pagination. Inline keyboard (the map button) rides on the LAST chunk so it visually lands at the bottom of the message stack (after the user has scrolled past all venues). Plain-text retry path uses the same chunking helper so the fallback also splits correctly.

  **`web/cuisine/src/v2/components/ResultCard.jsx` (~line 153-185)** — Issue 2 root cause: the v0.60.159 dedup filter at line 165 was `venue.dishes.filter((d) => norm(d) && norm(d) !== norm(primaryDish))` — exact-match equality only. Substring-related dishes ("wanton mee" ⊂ "char siew wanton mee") read as duplicates to the user but pass the filter. v0.60.159 caught the operator's prior screenshot (Cheok Kee + Hong Kong Yummy Soup, where signature dish exactly equalled `dishes[0]`); the new screenshot's variant case ("wanton mee" is a substring of `dishes[0]`) slipped through.

  Fix: tighten the predicate to drop any rest entry where (a) it equals primary (existing exact check, retained), OR (b) `n.includes(primaryNorm)` (the dish name is a more specific version, e.g. "Char siew wanton mee" contains "Wanton mee"), OR (c) `primaryNorm.includes(n)` (the dish name is a less specific umbrella, e.g. primary "Hainanese chicken rice" includes rest entry "chicken rice"). Plus dedup WITHIN the rest list (a `Set` of normalised entries) so two LLM-narrated names that normalise the same don't both render.

  Risk audit: the substring check could over-filter in edge cases like primary "Sashimi" + rest "Salmon sashimi" (legitimately distinct preparations). Operator preference per the screenshot is clearly "no apparent duplicates", so the slightly aggressive filter is the right trade-off — better to under-show than to read as a typo. If a future screenshot shows under-filtering on a legitimately-distinct pair, add a min-word-count guard (only substring-match when primary is ≥ 2 words).
