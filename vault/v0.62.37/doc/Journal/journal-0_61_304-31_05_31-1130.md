# Journal — soleat v0.61.304 (Menu TMA visibility-rehydrate + tile hash-preserve)

> Operator (31-05 '26, post-investigation): *"The menu TMA doesn't link to the cuisine TMA, train TMA, hawker TMA"* + *"It goes back to the telegram chat to click open. Also the location cache in the location field in a menu TMA is not tightly cobbled"* + *"Investigate first, don't change"*. After the investigation report identified two root causes, operator directive: *"PR bundling"* — ship both fixes in one PR.
>
> v0.61.304 bundles the two minimal-surface fixes for the Menu TMA both touching `web/menu/src/App.jsx`:
>
> 1. **Visibility-rehydrate of the location anchor.** Menu read `/api/cuisine/user-location` once on mount and never again; meanwhile Cuisine TMA's v0.61.186 listener re-pulls on `document.visibilitychange` + `Telegram.WebApp.viewportChanged`. Operator's "not tightly cobbled" symptom: open Menu, switch to Cuisine, change anchor (e.g. flip country), return to Menu → Menu still shows stale anchor. The SSOT (Redis `loc:<chatId>`, written via `/api/cuisine/user-location` since v0.61.270) was correct — Menu just wasn't reading it again.
>
> 2. **Tile-navigate hash-preserve.** Menu's `handle(tile)` for `kind: 'navigate'` (Cuisine + Hawker tiles) did `window.location.href = tile.path + window.location.search`. The URL **hash** (`#tgWebAppData=…`) was dropped; `telegram-web-app.js` reads initData from that hash on script load; the new page loaded with empty initData; gated API calls 401-ed; Telegram's WebApp container responded by returning the user to chat on some clients. The original v0.60.55 intent ("in-webview, no chat round-trip") was correct — the implementation just lost the hash.
>
> Commit 518 / journal 505 / build 307, on branch
> `claude/v0.61.304-menu-rehydrate-hashfix` off `main` at v0.61.303.

## New

### [HDR] #505 | 11:30 SGT 31-05-31 | v0.61.304 — Menu TMA visibility-rehydrate + tile hash-preserve | 3 files | 1 PR | 1 build |

- **[INTENT]** Eliminate two operator-reported pain points in the Menu TMA:
  - Anchor changes made in other TMAs don't propagate back when Menu becomes visible again.
  - Tapping a navigate tile (Cuisine / Hawker) ends with the user back in chat rather than landing in the target TMA.

  Both fixes are surgical and isolated to `web/menu/src/App.jsx`. No bot-side changes; no new endpoints.

- **[DELTA]**

  **1. `web/menu/src/App.jsx`** — two additions:

  - **Visibility-rehydrate useEffect** (inserted after the existing mount-time anchor fetch at line ~170). Adds `document.visibilitychange` + `Telegram.WebApp.onEvent('viewportChanged')` listeners that re-fetch `/api/cuisine/user-location` and `setAnchor({...})` with the same parse shape the mount-time effect uses. Cleanup removes both listeners. Mirrors the Cuisine TMA's v0.61.186 block at `web/cuisine/src/v2/App.jsx:790–849`, adapted to Menu's `anchor` state object (label / lat / lng / region / radiusCapM / street / building / postal / country).
  - **`handle(tile)` for `kind: 'navigate'`**: append `(window.location.hash || '')` to the constructed URL so the Telegram `#tgWebAppData=…` fragment survives the same-origin nav. One-line change with a 5-line inline comment.

  **2. `package.json`** — `0.61.303 → 0.61.304`.

  **3. `doc/.serial-state.yml`** — commit 517→518, build 306→307, journal 504→505; re-anchored 31-05 '26 11:30 SGT.
