- **[BUG 1 — criteria chip showed "Durian" not "Durian Fruits"]** `ActiveFilters.jsx` rendered the **raw
  slug** (`slug.replace(/-/g,' ')` → "Durian"), ignoring the catalogue display-name override
  (`cuisines-vault.js` `DISPLAY_NAME_BY_SLUG = { 'durian': 'Durian Fruits' }`, v0.61.255) that the
  drawer **and** the result-header `comboLine` already use. Fix: App.jsx passes a `nameForCuisine(slug)`
  resolver (catalogue flatten → `m.name`) into `ActiveFilters`; the criteria chip now reads
  **"Durian Fruits"** (and any future renamed slug stays consistent across drawer / header / chip).

- **[BUG 2 — KL durian returned restaurants & cafes]** `ACCEPT_PRIMARY_TYPES_DURIAN` **deliberately**
  accepts `restaurant / asian_restaurant / chinese_restaurant / diner` (+ `cafe`, `bakery`) because
  Google **mis-types many real durian stalls** as those (e.g. "皇后镇榴莲档 Durian Stall" →
  `chinese_restaurant`) — gated by "durian" in the name. So it's not a filter bug. Per the operator's
  intent ("Durian Fruits" = the **fruit** seller), added **`special-mode.durianTypeTier`** (a RANKING
  tier, NOT a filter): **0** = fruit seller (`fruit_and_vegetable_store` / `fruit_parlor` /
  `fresh_fruit_store` / `produce_market` / `market` / `greengrocer` / `farm` / `wholesaler`), **2** =
  durian-themed eatery (`restaurant` / `cafe` / `bakery` / `diner` / `chinese_restaurant` / …), **1** =
  neutral (`food_store` / `store` / `meal_takeaway` / unknown). In the cuisine-search durian sort it is
  now the **PRIMARY key (above the v0.62.14 soft-rating order)** for **DURIAN mode only** (NOT
  durian-pastry — its intent IS the cafe/bakery): fruit sellers page first, eateries last. Mis-typed
  real stalls are **kept, just demoted** — recall (incl. the v0.62.14 KL work) is preserved.
