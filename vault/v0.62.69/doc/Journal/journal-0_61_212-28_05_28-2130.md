- **[DELTA]**

  **`scripts/place-search-variance/venues.json`** — 340 curated
  landmarks per the operator's breakdown:

  | Country | Cities | Venues |
  |---|---|---|
  | MY | KL, Putrajaya, Penang, Melaka, Johor Bahru | 100 (5 × 20) |
  | JP | Tokyo, Osaka | 60 (2 × 30) |
  | KR | Seoul, Busan | 60 (2 × 30) |
  | ID | Jakarta, Bali | 60 (2 × 30) |
  | TH | Bangkok, Phuket, Chiang Mai | 60 (BKK 20 + HKT 20 + CNX 20) |

  Each row: `{ id, country, city, name, type [, nativeName] }`.
  Native script provided for JP/KR/TH; MY/ID Latin-script only.

  **`scripts/place-search-variance/typing-variants.js`** (~90 lines):

  `generateVariants(venue) → [{ variant, query }, …]` produces 5
  per venue:
  1. **`full`** — canonical name verbatim
  2. **`shortened`** — `shortenName()` strips qualifier tokens
     (city / country / "mall" / "centre" / etc.) so e.g. "Berjaya
     Times Square" → "Times Square"; "IOI City Mall Putrajaya"
     → "IOI City"; "Pavilion Kuala Lumpur" → "Pavilion".
  3. **`native`** — `venue.nativeName` (JP/KR/TH); falls back to
     **`name+country`** form for MY/ID (`"Pavilion Kuala Lumpur Malaysia"`).
  4. **`typo`** — deterministic single-edit: drop a mid-word
     vowel, swap two adjacent consonants, or double a consonant.
     Same input → same typo every run.
  5. **`descriptive`** — vague / language-mixed / "near" form
     keyed off `venue.type` (`mall` → `"shopping mall <city>"`;
     `station` → `"train station <city>"`; `beach` → `"beach
     near <city>"`; etc.).

  **`scripts/place-search-variance/run.mjs`** (~250 lines, ESM):

  One-shot runner. For each test row:
  1. `POST places.googleapis.com/v1/places:searchText` with
     `textQuery + includedRegionCodes:[cc] + pageSize:6`. Mirrors
     v0.61.201's endpoint shape (no `regionCode`, just
     `includedRegionCodes`; minimal field mask + rating +
     userRatingCount + types).
  2. `GET maps.googleapis.com/maps/api/geocode/json` with
     `address=<query>&components=country:<cc>`.
  3. Both in parallel via `Promise.all`. Merge + dedup by
     placeId + rounded coord (same logic as the endpoint).
  4. Score top-1 / top-6 hit via fuzzy name-token overlap:
     tokenize `expectedName` (length ≥ 3 word tokens, drop
     stopwords), then require ≥ 50% of expected tokens present
     in candidate's `displayName + formattedAddress` (case-
     insensitive substring). Permissive — "Times Square" matches
     "Berjaya Times Square".
  5. Write a row to results array.

  Concurrency: 6 in-flight, 200 ms pause between batches.
  Total run: ~10 min wall clock for 1700 rows.

  Output: `scripts/place-search-variance/results-<isostamp>.json`
  with `{ _meta, summary, results }`. Summary breaks down hit
  rate by **variant**, **country**, **city**. Console prints a
  formatted table at the end.

  CLI flags:
  - `--limit N` — smoke-test the first N rows (~$0.05/N)
  - `--country CC` — single-country deep dive

- **[KNOWN GAPS]**
  - The "intended landmark" check uses ≥ 50% token overlap. This
    is permissive but can over-match on common words. Manual
    review of low-hit rows recommended.
  - Some venues' "shortened" form may equal "full" (e.g. "Siam
    Paragon" — no stopword tokens). The test still runs all 5
    variants distinct; the typo + descriptive forms ensure non-
    trivial coverage even when shortened collapses.
  - The runner shares the prod GCP API key. Don't run alongside
    heavy prod soleat traffic.
  - Currency: this rig measures top-1 hit RATE today. Tuning the
    endpoint to improve the rate is the follow-up PR's job.
