### [HDR] #110 | 11:00:00 SGT 13-05-26 | v0.60.145 | n/a kb | 1 PR

- **[INTENT]** Operator: *"In Cuisine TMA the copy all button in /cuisine still shows occasionally same error. Check past PR and compare with current source code, first. Plan well."* — diagnosis (via the Phase 1 Explore agent): the `/api/cuisine/copy-all` handler builds an HTML body and calls `bot.sendMessage(..., { parse_mode: 'HTML' })` **without a try/catch**. Telegram rejects the body when a venue name contains a stray `&` or `<`/`>` that doesn't pass through `escapeHtml` (or when the rare path `buildMapHashUrl` returns `null` because every slim venue lacked lat/lng) — the outer catch then 500s and the TMA shows the `err.copyFailed` alert ("Couldn't send to chat — try again"). Past PRs #231 / v0.59.26 (trim-loop), #234 / v0.59.29 (16 → 12 cap), #200 / v0.58.53 (enrichment fields), #202 / v0.58.55 (FR i18n) fixed the body **size** but never wrapped the send itself; the failure mode is therefore state-dependent and recurring.

- **[DELTA]**

  **`index.js` `/api/cuisine/copy-all` (lines ~7383–7475) — wrap the sends + drop-the-button null-safety**
  - Both `bot.sendMessage(...)` calls are now inside `try { … } catch { … }`. On a Telegram parse-mode rejection (or any other rejection): log the Telegram-supplied `err.response.body.description`, then **retry once in plain text** — the body is stripped of `<b>`/`</b>` tags and HTML entities (`&amp;` → `&`, `&lt;` → `<`, `&gt;` → `>`) are unescaped. The reply_markup (when present) is carried into the retry. If the plain-text retry also fails, the handler 500s with `{ error: 'send_failed' }` and a structured `[Cuisine] copy-all sendMessage retry failed` Railway log line — same visible surface to the TMA, but actionable.
  - `buildMapHashUrl(slim, …)` returning `null` (every slim venue lacked lat/lng so `buildSlim` returned `[]`) no longer 500s the whole copy. The handler now drops the inline-keyboard map button, appends a one-line `📍 Map unavailable for this set.` (EN) / `📍 Carte indisponible pour cette sélection.` (FR) footer via `trn('pick.mapUnavailable', reqLang)`, and sends the message anyway. 12 valid venues with one bad-lat outlier shouldn't take the whole copy down.

  **`i18n.js`**
  - New key `pick.mapUnavailable` (EN + FR). Renders only when the multi-pin path can't build a map button — single-venue copies are unaffected.

  **`__tests__/copy-all-html.test.js` (new, 5 tests)**

  - The plain-text retry's inverse (`<b>` stripped, entities unescaped) recovers the human-readable name.
  - Clean venue names round-trip through both paths.
  - `escapeHtml` smoke (null/undefined/0 handling) — guards against `escapeHtmlForTelegram` regressing into the silent-render class that PR #369 / v0.60.133 fixed.

## Amendments

### `index.js` `/api/cuisine/copy-all` — bot.sendMessage error handling

> Prior (≤ v0.60.144): `await bot.sendMessage(chatId, body, { parse_mode: 'HTML', … })` ran unguarded at two call sites (slim.length === 1 and the multi-pin branch). A Telegram parse-mode rejection propagated to the outer catch → `res.status(500)` → the TMA showed `err.copyFailed` ("Couldn't send to chat — try again"). The recurring class of failure described by the operator.
>
> Change (v0.60.145, this PR): both call sites are now inside `try { … } catch { … }`. On rejection, the handler retries once with a plain-text body (`<b>/</b>` stripped, `&amp; &lt; &gt;` unescaped); the `reply_markup` survives the retry. A second failure 500s — structured log `[Cuisine] copy-all sendMessage retry failed (plain): <description>`. Rationale: the past PRs fixed the body **size** (#234 16→12; #231 map-URL trim-loop) but the underlying class — Telegram refusing the HTML — has no size signature. A plain-text retry covers every parse-mode failure mode with one branch and zero new state.

### `index.js` `/api/cuisine/copy-all` — buildMapHashUrl null return

> Prior (≤ v0.60.144): `const mapUrl = buildMapHashUrl(slim, { webhookDomain }); if (!mapUrl) return res.status(500).json({ error: 'could not build map URL' });`. When every slim venue lacked lat/lng (rare but observed), `buildSlim` returned `[]` and `buildMapHashUrl` returned `null` → the whole copy 500'd → the user saw `err.copyFailed`.
>
> Change (v0.60.145): null `mapUrl` now drops the inline-keyboard map buttons (it's the multi-pin path's optional decoration, not the picks themselves) and the handler appends a one-line `📍 Map unavailable for this set.` (EN) / `📍 Carte indisponible pour cette sélection.` (FR) to the body before sending. The user still gets the 12 picks. Rationale: one bad-lat venue shouldn't take the whole copy down.
