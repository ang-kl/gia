## New

### [HDR] #74 | 22:30:00 SGT 01-05-26 | v0.34.1 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead "The UI is awful for this buddy on, is there indicator somewhere in the chat the buddy is on or off". Buddy state was invisible after the initial `/buddy on` confirmation — users had to remember they enabled it or run `/buddy status` to check. This patch ships an ambient indicator on every pick result so the user always knows whether `👥 Connect` buttons can appear, and how many connections they have left in the daily cap.

- **[DESIGN]**
  1. **Footer line on every pick result** — appended after the staleness reminder in `deliverPicks` and after the single-card markup in `deliverSurprise`. Fire-and-forget; never blocks delivery.
  2. **Three states surfaced**:
     - `👥 Buddy: OFF — /buddy on to enable live solo-dining match.` (most common; opt-in is off-by-default)
     - `👥 Buddy: ON · 3/5 connections used today (2 left).`
     - `👥 Buddy: ON · daily cap reached (5/5). Resets in 24 h.` (when remaining=0, signal explicit cap-hit)
  3. **`/ver` adds a Buddy row** below the deploy timestamp: `Buddy: ON · 3/5 connections used today` or `Buddy: OFF (use /buddy on to enable)`. Implementation lives in `runVerCommand` (not `ver.js`), since per-chat state requires `chatId` that the generic health-check doesn't carry.
  4. **`formatBuddyFooter(chatId)` helper** — renders the single-line state string. Used by both `deliverPicks` and `deliverSurprise`. Reads `buddy.isOptedIn` + `buddy.dailyCount` + `buddy.DAILY_CAP` (all existing exports, no schema change).

- **[DELTA]**
  - **`index.js`**:
    - NEW `formatBuddyFooter(chatId)` async helper.
    - `deliverPicks` — appended `await safeSend(chatId, await formatBuddyFooter(chatId))` after the staleness-reminder block.
    - `deliverSurprise` — same footer appended after the markup-rendered card.
    - `runVerCommand` — appends a `Buddy:` line below the `Deployed:` line in the `/ver` HTML report.
  - **`package.json` + `web/cuisine/package.json` + `web/menu/package.json`** — version 0.33.0 → 0.34.1. (Note: this skips v0.34.0 in this branch; v0.34.0 lives on PR #81 unmerged at branch-cut time. Whichever PR merges last sets the final main-branch version.)

- **[POST-DEPLOY VERIFICATION]**
  1. `/cuisine` → tap Search → after the picks render, the LAST line of the bot's reply chain should read `👥 Buddy: OFF — /buddy on to enable…` (assuming buddy is off).
  2. `/buddy on` → re-run `/cuisine` → footer now reads `👥 Buddy: ON · 0/5 connections used today (5 left).`
  3. Trigger one mutual-confirm match → footer next time shows `1/5`.
  4. `/surprise` → same footer appears below the surprise card.

  6. `/buddy off` → next `/cuisine` reverts the footer to OFF.

- **[KNOWN GAPS]**
  - **Footer adds one extra message per pick session** — small chat-history bloat. Acceptable: it's a single line, and the alternative (status invisible) was the actual UX problem.
  - **No expiry-date display** — buddy opt-in TTL is 30 days but the footer doesn't show the expiry yet. Future patch could add `expires in N days` when remaining is high; left out here to keep the footer one line.
  - **NL search path** (typing free-text instead of `/cuisine`) routes through `deliverPicks` indirectly via `runNLFlow` → so the footer fires there too. ✓
  - **Vault picks path + Hidden Sanctuary fallback** also funnel through `deliverPicks`. ✓
  - **`/share` recent-picks** doesn't go through `deliverPicks` (it sends per-pick share-link buttons directly). The footer doesn't fire on `/share`; share is a copy-link operation, not a fresh pick set, so this is fine.
  - **`/buddy` sub-menu refactor** (Train-style 4-button menu) deferred to v0.34.2 if A+C isn't enough discoverability. Plan-mode option B from the prior turn.
