## New

### [HDR] #368 | 13:00 SGT 27-05-27 | v0.61.167 — autoResetOnLowCount: never on firstBatch | 4 files | 1 PR | 1 build |

- **[INTENT]** Fix a v0.60.188 / v0.61.163 interaction bug. The
  client-side `autoResetOnLowCount` gate (v0.60.188) compared the
  result count against the server's intended slice size. v0.60.191
  added a `firstBatch ? 6 : 12` ternary to avoid looping the
  planned 6-venue first batch. v0.61.163 unified the server slice
  to 19 on EVERY tap → but the client still used `firstBatch ? 6
  : 12`, which means a real area with only 8 matching venues
  returns 8 on the first tap (firstBatch=true) → arms resetSeen →
  next tap wipes seen → server returns the same 8 again → loop.

  v0.61.167's fix: **never auto-reset on a firstBatch response**.
  firstBatch=true means the seen-set was empty server-side;
  whatever came back IS the natural pool. Only follow-up taps
  (firstBatch=false, user has been clicking through) can
  legitimately indicate burnthrough that warrants reset.

- **v0.60.191 `lowCountThreshold = firstBatch ? 6 : 12`** — the
  ternary served the 6-venue first batch's loop-prevention. With
  v0.61.163's unified 19-cap, the firstBatch distinction no

  collapse to "never on firstBatch, else < 19".

  now only on `!firstBatch` so it doesn't mislead users in
