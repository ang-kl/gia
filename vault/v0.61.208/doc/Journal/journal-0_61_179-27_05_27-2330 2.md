# Journal — soleat v0.61.179 (60-second debounce on chat-side Cuisine Venues Recount)

> Closes v0.61.177's known gap: accidental double-tap on the chat
> "🔄 Recount now (~$3.45)" button would fire TWO Places sweeps
> (~$7 instead of ~$3.45). 60-second Redis-backed debounce so the
> second tap within a minute gets a friendly "wait N seconds"
> reply instead.
>
> Commit 392 / journal 380 / build 182, on branch
> `claude/v0.61.179-recount-debounce` off `main` at v0.61.178
> (PR #680).

## New

### [HDR] #380 | 23:30 SGT 27-05-27 | v0.61.179 — 60-second debounce on Recount button | 4 files | 1 PR | 1 build |

- **[INTENT]** Defensive guard rail so a slip of the finger on the
  /v owner menu doesn't cost double. The debounce is a safety hint,
  not a security gate — it FAILS OPEN on Redis errors (better to
  allow the sweep than to silently block a legitimate run).

- **[DELTA]**
  - **`cuisine-venue-counts.js`** (additions):
    - `DEBOUNCE_KEY = 'cuisine-venue-counts:debounce'`
    - `DEBOUNCE_TTL_S = 60`
    - **NEW `claimDebounceSlot(redis)`** — uses Redis `SET NX EX`
      semantics to atomically claim the debounce slot. Returns
      `{ won: bool, remainingSec }`. When the slot is held by a
      recent caller, returns `{won: false, remainingSec: <TTL>}`
      so the UI can show "wait N seconds". On null / closed
      Redis or any SET error, returns `{won: true}` (FAIL OPEN —
      debounce is a hint, not a hard lock).
  - **`__tests__/cuisine-venue-counts.test.js`** (+6 tests):
    constants exported; first caller wins; second concurrent
    loses + reports remainingSec; null-redis / closed-redis /
    SET-throws all fail-open. Total 28 → **34 tests, all passing**.
  - **`index.js`** (`ownerCuisineVenueRecount`):
    - Before `await cvc.countAll()`, call
      `cvc.claimDebounceSlot(redis)`.
    - If `won === false`, send
      `"⏱ Another sweep just ran — wait {remainingSec} s before
      re-running (debounce prevents accidental double-charge)."`
      and return without firing the sweep.
    - Otherwise proceed as before.

- **[KNOWN GAPS]**
  - **60-second window is hardcoded.** If the operator wants a
    longer cool-down (say 10 minutes to prevent oversprend),
    bump `DEBOUNCE_TTL_S` — trivial edit. Could be operator-
    configurable via a `/ver` setting, but probably overkill.
  - **No "force run" override.** If the operator genuinely
    needs to re-run within 60 s (debug a failed sweep), they'd
    have to wait. The fail-open behaviour on Redis errors gives
    a manual override path (kill Redis briefly = bypass). But a
    proper `cv:run-force` callback would be cleaner. Filed.
  - **Doesn't debounce concurrent owner sessions.** Two owners
    on the same chat ID can still race (one wins SET NX, the
    other gets blocked). Since there's only one owner per
    `TELEGRAM_OWNER_CHAT_ID`, this isn't a practical concern.
