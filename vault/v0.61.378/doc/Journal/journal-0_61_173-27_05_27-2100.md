- **[DELTA]**
  - **`cuisine-venue-counts.js`** (NEW, ~135 lines):
    - `SCOPE_SLUGS` — frozen array of 48 slugs. The 19 dropped
      slugs (singaporean / south-indian / malaysian / indonesian /
      chinese / sichuan / cantonese / hunan / hokkien / teochew /

      cuisines-vault drift can't silently re-include them.
    - `PLACES_SEARCH_TEXT_URL` — Places API New `/v1/places:searchText`.
    - `FIELD_MASK_COUNT` — `places.id` + `nextPageToken` only. Keeps
      us on the cheapest Places SKU (~$0.032 per Text Search "ID
      Only" call as of 2026-Q2 pricing).
    - `PAGE_SIZE = 20`, `MAX_PAGES = 3` — Places enforces a 60-result
      ceiling via 3 paginated pages. Beyond that the API drops
      `nextPageToken`.
    - `buildTextQuery(vault, slug)` — prefers `vault.searchQuery`
      (the same query string the chat free-text + TMA search use,
      so the count matches what a user would see). Falls back to
      `"<name> restaurant Singapore"` then bare slug.
    - `countOne(slug, opts)` — paginates up to MAX_PAGES,
      accumulates `placeId`s in a `Set` (Places sometimes returns
      overlapping IDs between pages 1 and 2 — Set dedups). Returns
      `{ slug, n, capped, pages, error }` with `n=null` on missing
      API key or transport error. `opts.fetchFn` injection lets
      tests run without a real Places call.
    - `countAll(opts)` — parallel sweep across all 48 slugs.
      Returns `{ ts, total, perSlug: {slug: n}, capped: [slug, ...],
      errors: {slug: msg}, pages, elapsedMs }`. Per-cuisine failures
      isolated; one slug erroring out leaves the rest intact.
    - `_defaultFetch` — axios-based, `regionCode: 'SG'`, 8 s timeout.
  - **`scripts/recount-cuisine-venues.js`** (NEW, ~55 lines):
    Manual CLI runner. Loads `.env`, validates
    `GOOGLE_MAPS_API_KEY`, calls `countAll`, writes
    `data/cuisine-venue-counts.json` atomically (`tmp + rename` so
    a crash mid-write doesn't corrupt the file). Prints summary

- **[KNOWN GAPS]**
  - **No bot UI to surface counts.** The chat `/ver` flow + TMA
    banners DON'T read `data/cuisine-venue-counts.json` yet. If
    the operator wants "55+ cuisines · 612+ venues" in the
    marketing copy, that's a follow-up PR — read the JSON on bot
    startup (or per-request), merge into the existing
    `count-display.substituteCounts` placeholder system, add a
    `{cuisine-venues}` token.
  - **60-result cap on Places.** Saturated cuisines (Italian,
    Japanese, etc.) report `60` not their true SG count. The
    `capped` array surfaces them so the operator knows which
    numbers are floors vs. exact. A "tile-search" workaround
    (split the SG geography into N regions, query each, dedup)
    could push past 60 — but multiplies cost by N. Not done
    here.
  - **Stale-result detection.** Operators who rerun
    `count:cuisines` will overwrite the JSON. There's no rollback
    or history — by design (per operator's "manual-only" call;
    if they want history, the v0.61.166 `count-history` ZSET
    schema is already there to copy).
  - **Privacy verification.** The module fetches `places.id`
    (opaque Google IDs, not names — Field Mask is minimal) but
    the Set + Map data structures hold them transiently in
    memory. The output JSON only has integer counts, no IDs. If
    operator wants a stronger guarantee, the module could
    immediately tally `.length` and discard the array instead of
    using a Set — but loses cross-page dedup.
