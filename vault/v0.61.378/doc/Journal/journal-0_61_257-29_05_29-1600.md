## New

### [HDR] #458 | 16:00 SGT 29-05-29 | v0.61.257 — Durian precision | 3 files | 1 PR | 1 build |

- **[INTENT]** Operator measured <20% precision on Durian + Durian
  Pastry across SG / JB / KL / Putrajaya. Investigation traced the
  pollution to two patterns:

  1. The v0.61.229 `_haystack()` joined `name + area +
     formattedAddress + primaryType + googleSummary.overview + ALL
     review.text` and the keyword check used `.includes()`. A
     single Google review mentioning "durian" was enough to
     promote a generic cafe or bakery.

  2. The v0.61.235 accept lists added VERY broad types (`food`,
     `store`, `market`, `farm`, `garden`, `coffee_shop`,
     `grocery_store`, etc.) to catch real durian sellers Places
     had mis-typed. Combined with (1), generic places with one
     durian review = automatic accept.

  Two-pronged fix:

  1. **DURIAN + DURIAN_PASTRY** keyword check now uses a new
     `_strongHaystack()` that drops `googleSummary` + reviews.
     FRUITS still uses the full haystack (its test suite pins
     googleSummary + review-text matches; the fruits keyword set
     is broader so the same review-pollution loophole doesn't
     apply).

  2. **STRICT_NAME_TYPES gate**: for the broad accept types
     `food`, `store`, `general_store`, `market`, `farm`, `garden`,
     `coffee_shop`, `grocery_store`, `meal_takeaway`,
     `meal_delivery`, `bakery`, `cafe` (DURIAN) — or `food`,
     `meal_delivery`, `snack_bar`, `grocery_store`, `food_court`,
     `hawker_centre`, `hawker`, `restaurant`, `store`,
     `food_store`, `produce_market`, `food_market`, `wholesaler`,
     `wholesale_business`, `juice_shop`, `juice_bar`,
     `fruit_parlor` (DURIAN_PASTRY) — the venue NAME must contain a
     durian keyword (`durian` / `榴莲` / `榴梿`). "99 Old Trees
     Durian" + "Hey!Durian 榴莲说" still pass; a generic 'food'-typed
     cafe does not.

  Canonical durian types (`fruit_and_vegetable_store`,
  `produce_market`, `fruit_parlor`, `food_market`,
  `fresh_fruit_store`, `wholesaler`, `wholesale_business`,
  `wholesale_supplier`) bypass the strict-name gate — they still
  pass via the standard strong-haystack check, so a venue with no
  "durian" in name but address listing "Geylang Durian Wholesale
  District" still surfaces.

- **[DELTA]**

  **1. `special-mode.js`** — three additions:

  - `STRICT_NAME_TYPES_DURIAN` + `STRICT_NAME_TYPES_DURIAN_PASTRY`
    Sets + `_strictNameTypesFor(mode)` selector.
  - `_strongHaystack(v)` helper (name + area + formattedAddress +
    primaryType only).
  - `_nameHasDurian(venue)` cheap check (Latin + Chinese
    durian-keyword scan over `venue.name` lower-cased).

  `isRelevant(venue, mode)` now:
  ```js
  // ... existing pt accept/reject ...
  // ... existing name reject ...

  // v0.61.257 STRICT-name gate for broad accept types
  const strictNameTypes = _strictNameTypesFor(mode);
  if (pt && strictNameTypes && strictNameTypes.has(pt)) {
    if (!_nameHasDurian(venue)) return false;
  }

  // v0.61.257 STRONG-haystack-only for DURIAN + DURIAN_PASTRY
  const useStrong = (mode === SPECIAL_MODES.DURIAN
    || mode === SPECIAL_MODES.DURIAN_PASTRY);
  const hay = useStrong ? _strongHaystack(venue) : _haystack(venue);
  for (const kw of kws) {
    if (kw && hay.includes(kw.toLowerCase())) return true;
  }
  ```

- **[KNOWN GAPS]**
  - A real durian shop whose name contains ONLY a variety
    (e.g. "Mao Shan Wang Stall") with `primaryType=food` will
    still miss — already missed under v0.61.229 by design
    (variety names are extraction-only per the existing
    REGRESSION block in `special-mode.test.js`). To recover
    them, the operator could supply a "variety names with high
    durian-signal weight" sub-catalogue + a second-pass match.
    Deferred.
  - The strict-name gate uses Latin "durian" + Chinese
    "榴莲" / "榴梿". Korean (두리안), Japanese (ドリアン), Thai
    (ทุเรียน), Malay ("durian" already covered) aren't
    explicitly listed in `_nameHasDurian` because the keyword
    set for those scripts isn't in `KEYWORDS[DURIAN]` either.
    If operator wants those tightened too, a follow-up PR can
    extend both sides together.
  - Server-side fix only; no client change. The TMA's
    behaviour is unchanged — only the venue list returned by
    `/api/cuisine/search` (and the chat-side searches) now
    has higher precision.
