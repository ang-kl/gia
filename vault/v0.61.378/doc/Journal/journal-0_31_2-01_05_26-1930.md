## New

### [HDR] #70 | 19:30:00 SGT 01-05-26 | v0.31.2 | n/a kb | n/a lines
- **[INTENT]** Diagnosis-driven hotfix. Human Lead's TMA Diagnostics screenshot showed `D406 Fetch timed out (>25s)` and `D063 Primary fetch failed, trying sendData fallback` on a routine `/cuisine` search. Initial architectural advice (SSE / async-poll / pre-computed cache) was wrong on substance. Pulling the matching Railway log for `D700` at `2026-05-01T11:10:21.059Z` revealed the real root cause: Gemini API rejects `tools: [{googleSearch: {}}]` + `generationConfig.responseMimeType: 'application/json'` in the same call with HTTP 400 "Tool use with a response mime type: 'application/json' is unsupported". The 400 was then needlessly retried — pipeline retry path (D613 relaxed-query), `withRetry` exponential backoff (1+2+4+8 s), and Pro→Flash fallback all chasing the same deterministic client error. Total: **55,525 ms wasted, 0 venues returned, every grounded request failing the same way**.
- **[DESIGN]**
  1. **`pipeline.js#reason`** — when `groundingEnabled` is true, drop `responseMimeType: 'application/json'` from `generationConfig`. Gemini emits JSON-shaped text without the strict mime type; we already have lenient parsing, hardened further here.
  2. **NEW `extractJsonArray(text)` helper at module top** — strips ```json``` markdown fences, locates the first top-level `[ ... ]` array, returns the slice. Falls back to trimmed raw text so the existing `JSON.parse` still surfaces a meaningful error in D612 diagnostics on truly malformed responses.
  3. **`gemini-retry.js#isRetryable`** — explicit allowlist + denylist:
     - `RETRYABLE_STATUSES = {429, 500, 502, 503, 504}` (was `{429, 503}` — adds the rest of the 5xx surface).
     - `NON_RETRYABLE_STATUSES = {400, 401, 403, 404}` checked BEFORE retryable allowlist.
     - Network-error catch (`ECONNRESET`, `ETIMEDOUT`, `ENOTFOUND`, `fetch failed`) only triggers when no status is set.
     - Defense-in-depth: same 4xx/5xx checks against `err.message` regex for SDK-wrapped errors where `err.status` may be missing.
- **[DELTA]**
  - **`pipeline.js`**
    - Top-of-file: NEW `extractJsonArray(text)` helper.
    - `reason()` — `generationConfig` now `{}` when `groundingEnabled`, `{ responseMimeType: 'application/json' }` otherwise.
    - `reason()` JSON parse path: `JSON.parse(extractJsonArray(rawText))` instead of `JSON.parse(rawText)`.
  - **`gemini-retry.js`**
    - `isRetryable` rewritten with explicit non-retryable check first.
    - `RETRYABLE_STATUSES` widened to all 5xx that benefit from a single retry.
    - Network-error retry only when `!err.status` (avoids retrying an SDK error that already carries a 4xx code).
  - **`package.json`** — `version` 0.31.1 → 0.31.2.

- **[STATUS]** PROD — auto-deploys with the next Railway build. Expected impact: this exact request (cuisines=[…], grounding=ON) should either succeed in ~5 s (Reason returns venues) or fail fast in ~1 s (different 400). Never 55 s again.
- **[POST-DEPLOY VERIFICATION]**
  1. Open `/cuisine`, pick 2 cuisines, tap Search.
  2. Railway log should show `D610 Reason call start` immediately followed by `D611 Reason produced N candidates` (success path) — not `D612 ✗ [400 Bad Request]`.
  3. Total `D700` → `D702` should be ≤15 s.
  4. TMA should render cards, not D406.
  5. If grounding ever DOES return malformed JSON, D612 will fire with head/tail snippets and the request returns `venues: []` in <2 s — no more 50 s retry storm.
- **[ROOT-CAUSE TIMELINE]**
  - v0.30.3 (30-04 '26) — added Google Search grounding via `tools: [{googleSearch: {}}]` AND kept `responseMimeType: 'application/json'`. Combination silently incompatible with Gemini API as of 01-05 '26.
  - v0.30.4 (01-05 '26) — added `GROUNDING_ENABLED` env flag (default ON) without testing the off-path. The 400 was masked by a coincidental successful path during initial verification (likely without the cuisines filter).
  - v0.30.5 (01-05 '26) — added Reason-0-candidate retry path (D613). When grounding 400'd, this retry hit the SAME 400 a second time, doubling wasted time.
  - v0.30.6 → v0.31.1 — built features on top of a broken pipeline. Pipeline returning 0 candidates was masked by `geminiCandidates15` legacy fallback path eventually returning *something*. But that fallback also retried 400s 4× before giving up, totalling ~55 s.
  - **v0.31.2 (01-05 '26)** — root cause identified from Railway log; both axes patched.
- **[LESSONS]**
  1. Diagnose before refactoring. Three architectural alternatives (SSE, polling, pre-computed cache) were proposed before pulling the log. None would have helped.
  2. `withRetry` was over-eager — generic "retryable error" classification missed that 400 is fundamentally non-transient. Explicit allowlist + denylist is safer.
  3. Gemini API constraints change with grounding-tool support; combination-tests are needed when adding `tools` to an existing JSON-schema flow.
- **[KNOWN GAPS]**
  - The legacy `geminiCandidates15` path in `cuisine-search.js` was the ultimate fallback that returned the (degraded) results in this trace. With v0.31.2, it should rarely fire because pipeline now succeeds. If it does fire, it benefits from the same `withRetry` fix automatically (no longer retries 400s).
  - No automated test for grounding+JSON combination compatibility. Could add a smoke test that POSTs `/admin/test-pipeline` with `grounding=ON` after every deploy.
  - The 50-s wasted-budget pattern would have surfaced earlier if `D640 Pipeline emit (draft only) :: {"n_final":0}` had triggered an alert. Could add a Redis counter `pipeline:zero-result-streak` and surface it in `/ver`.
