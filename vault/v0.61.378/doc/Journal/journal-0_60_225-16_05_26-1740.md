## New

### [HDR] #193 | 17:40:00 SGT 16-05-26 | v0.60.225 — TMA `🍲 Try ·`: Gemini dish extraction from 4–5★ reviews + regex fallback + glyph standardise | 4 files | 1 PR | 1 build |

- **[INTENT]** The Cuisine TMA result-card `🍲 Try ·` line must carry a genuine dish/dessert name. Operator's final spec: extract it with **Gemini** from the venue's higher-rated Google reviews (5★ rotated down to a 3.5★ floor), fall back to the hardened review-text regex when Gemini finds nothing, and **hide the row** when neither yields a dish. Also: standardise the TMA Try glyph to `🍲`.

- **[REVIEW (operator asked to review before building)]** Traced the data path. The TMA result card is served by the LLM-free `/api/cuisine/search` path; its `dishes` came from `extractDishes()` in `index.js` — a regex over the venue's last 3 Google reviews. The **Google Places API (New) exposes no menu / popular-dishes field** — the "Popular" tags in the operator's Google Maps screenshot are a consumer-app feature, not API data. First operator decision was "harden the regex only" (built as PR #476); the operator then revised to "use Gemini", and via AskUserQuestion chose: Gemini primary, **regex fallback then hide**, and **fold PR #476 + the Gemini layer into one PR**. PR #476 was closed unmerged; its work is carried in this combined v0.60.225.

- **[DELTA]**
  - **`gemini-client.js` — new `extractDishesFromReviews()`.** Batched dish/dessert extraction: takes `{ venues:[{id,name,reviews:[{rating,text}]}] }`, builds **one** prompt covering every result venue (reviews sorted 5★-first, capped at 6/venue, 400 chars each), asks Gemini for a JSON array `[{id,dishes[]}]` of up to 3 genuine dish names per venue. Model chain `gemini-flash-latest → 2.5-flash → 2.5-flash-lite`; 8 s per-attempt `Promise.race` deadline; graceful empty-Map return on no-key / parse failure / timeout. Exported.
  - **`index.js` — Gemini pass on the `/api/cuisine/search` path.** After the existing regex `extractDishes` pass (which now serves as the fallback), a single batched `extractDishesFromReviews()` call runs over the result venues' **4–5★ reviews only** (Google reviews are integer-starred, so the operator's 3.5★ floor admits 4★ and 5★). When Gemini returns dishes for a venue they replace the regex result; the Gemini output is still run through the shared `filterDishNames()` + a venue-name guard + the existing drinks filter. When Gemini returns nothing the regex result stands; when both are empty `v.dishes` is unset and the card row hides itself.
  - **`index.js` `extractDishes()` (the regex fallback) — hardened.** Root cause of `Restaurant Fiz and what`: a **local** `TRAILING_STOPWORDS` regex that predated the v0.60.222 interrogative additions, so a candidate ending in `what` passed. Replaced the local length / category / trailing-stop-word checks with the shared `isDishName()` from `dish-name.js`; removed the dead local consts. Added a `venueName` argument + venue-name guard (drops a capture containing the venue's own name). Both call sites pass `v.name`.
  - **`web/cuisine/src/v2/components/ResultCard.jsx`.** The "what to order" line glyph `🍴` → `🍲` (standardised, parity with the bot-side Try lines unified in v0.60.222). The row already hid when `primaryDish` was empty (`{primaryDish && (…)}`).
  - `package.json` `0.60.224 → 0.60.225`; this Journal entry (#193); `doc/.serial-state.yml` (`journal 192→193`, `commit 199→200`, `build 8→9`, `chat_counter 18→19`; re-anchored 17:40 SGT).
