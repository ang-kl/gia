## Cuisine TMA search: deep pool + per-chatId accumulating exclusion + query-variant escalation

### `pipeline.discover()` — new opt-in params

- `maxPages` (default `1`) — when `> 1` and the cuisine text-search path is taken, after the first `places:searchText` call the function walks the response `nextPageToken` up to `maxPages - 1` more times and concatenates the `places` arrays. Field mask gains `nextPageToken`. Hard-capped at 3 (Google's text-search ceiling — ~60 results). The `searchNearby` path is untouched (no `pageToken` support there). Existing callers (default `maxPages: 1`) are unchanged.
- `queryOverride` (default `null`) — when a non-empty string is passed and cuisines are present, it is used verbatim as the Places `textQuery` instead of the v0.57.15 default `` `${cuisineQuery} cuisine restaurant` ``. Used by the escalation loop to switch phrasings.

### Redis keys (all prefixed with the verified Telegram `chatId`)

| Key | Type | TTL | Purpose |
|---|---|---|---|
| `cuisine:seen:{chatId}:{criteriaHash}` | Set of placeIds | `SEEN_SET_TTL_S` = **12 h** | The accumulating exclusion: every venue ever shown for these criteria this session. Appended (and TTL refreshed) on every 🔍. Cleared by ↺ Start over or a criteria change (different hash). |
| `cuisine:pool:{chatId}:{criteriaHash}:v{variantIdx}` | JSON array of venue objects (raw `discover` output) | `POOL_CACHE_TTL_S` = **20 min** | The cached 3-page pool for one query-variant. First 🔍 of a window builds it (3 Google calls); re-clicks reuse it. If it expires the next click re-paginates the same query → same pool → dedup still works. |
| `cuisine:variant:{chatId}:{criteriaHash}` | integer string | `SEEN_SET_TTL_S` (12 h) | Which of the four query-phrasing variants the user is currently paging through (0…3). Bumped by the escalation loop. |

`criteriaHash` = `computeCriteriaHash({ cuisines, filters, prices, radius, region, freeText })` — sha256 truncated to 16 hex chars. Note it is **location-independent** (no lat/lng), so a coarse area is implied by the cuisine + region only; the 50 km SG-wide `locationBias` makes Google's results roughly SG-wide regardless, and the key is per-chatId anyway.

### Helpers (`index.js`)

- `cuisineSearchVariants(cuisineName)` → `[{ idx: 0, queryOverride: null }, { idx: 1, queryOverride: '<name> restaurant Singapore' }, { idx: 2, queryOverride: 'best <name> restaurant Singapore' }, { idx: 3, queryOverride: 'authentic <name> food Singapore' }]`. Returns `[{ idx: 0, queryOverride: null }]` (escalation off) for an empty name.
- `readSeenSet / appendSeenSet / resetSeenSet(chatId, criteriaHash)` — `sMembers` / `sAdd`+`expire` / `del`. `resetSeenSet` also `del`s `cuisine:variant:…` and `cuisine:pool:…:v0…v7`.
- `readVariantIdx / setVariantIdx(chatId, criteriaHash[, idx])` — `get` / `set … EX SEEN_SET_TTL_S`.

### `POST /api/cuisine/search` flow (single-cuisine path)

1. **`resetSeen` flag** — if `req.body.resetSeen === true`, `resetSeenSet(csChatId, computeCriteriaHash({…}))` before anything else, so the rest of the request starts from variant 0 with an empty seen-set.
2. **Discover branch (single cuisine)** — `cuisineDisplayName = cuisinesForDiscover.length === 1 ? cuisinesForDiscover[0] : ''`; `variants = cuisineSearchVariants(cuisineDisplayName)`; `cuisineSearchHash = computeCriteriaHash({…})`; `cuisineVariantIdx = readVariantIdx(...)`. Then a loop (capped at `variants.length`): for the current variant, fetch its pool — pool-cache HIT reuse (and slide its 20-min TTL); MISS → `pipeline.discover({ maxPages: 3, queryOverride })` + cache. If the *raw* pool has at least one placeId not in the seen-set, **or** it is the last variant → use it and break; else `cuisineVariantIdx++` and retry. Persist `cuisineVariantIdx` via `setVariantIdx`. (Multi-cuisine AND/OR and no-cuisine warm-start paths are unchanged; they set `cuisineSearchHash = ''` ⇒ escalation off, plain dedup downstream.)
3. **Filters** — `venueFilters.passesVenueFilter` + cuisine-name validation + haversine `distanceM` + 80 km gate + distance sort, all on the chosen pool (unchanged from prior versions).
4. **Dedup-slice** — `dedupHash = cuisineSearchHash || computeCriteriaHash({…})`; `seen = readSeenSet(...)`; `unseenVenues = venues.filter(v => v.placeId && !seen.has(v.placeId))`; `atLastVariant = !cuisineSearchHash || cuisineVariantIdx >= cuisineVariantCount - 1`; `dedupExhausted = venues.length > 0 && unseenVenues.length === 0 && atLastVariant`; `top = (unseenVenues.length ? unseenVenues : venues).slice(0, 12)`; `poolCount = |seen ∪ top.placeIds|` (cumulative distinct shown for these criteria).
5. **Enrich `top`** — crowd signal, footfall, dishes, Michelin annotation (unchanged).
6. **Append seen** — `appendSeenSet(csChatId, dedupHash, top.map(v => v.placeId))` (refreshes the 12 h TTL).
7. **Response** — `{ venues: dedupedTop, exhausted: dedupExhausted, poolCount, … }` (the `exhausted`/`poolCount` plumbing is from v0.60.115). Railway log line `D702 discover variantIdx=N/M returned K candidates`.

### Cuisine TMA client (`web/cuisine/src/v2/`)

- `lib/api.js searchCuisine({ …, resetSeen })` → POST body includes `resetSeen: resetSeen === true`.
- `App.jsx runSearch(snap = state, anchor = null, opts = {})` — threads `opts.resetSeen` into `searchCuisine`. The terminal note (rendered when `exhaustedNote && !loading && venues.length > 0`) appends a non-italic underlined "↺ start over" `<button>` that calls `runSearch(state, null, { resetSeen: true })`.
