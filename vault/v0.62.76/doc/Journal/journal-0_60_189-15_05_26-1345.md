Example Nepalese may not have a list of authentic dishes in our database as lookup."* The picker DID filter for has-data since v0.60.181 — but umbrella catch-all entries (European / Mediterranean / Australasia / African / Dessert / Fusion) sneaked through because the lookup tables carried generic entries under those slugs.

## New

### [HDR] #156 | 13:45:00 SGT 15-05-26 | v0.60.189 — /s cuisine picker: exclude umbrella catch-all slugs + raise min-items threshold to 3 | 3 files, ~30 LOC | 1 PR |

- **[INTENT]** A user tapping `🥘 Cooking Methods` or `🍛 Authentic Dishes` then picking a cuisine wants a **country- or region-specific** view. The vault's umbrella entries (slug `european`, `mediterranean`, `australasia`, `african`, `dessert`, `fusion`) carry generic cross-category data — useful for matching ambiguous queries elsewhere in the codebase, but noise in the picker.

  The v0.60.181 picker filter was `length > 0` — which let through the umbrellas because their tables ARE populated (e.g. `cooking-methods.european` has 21 generic European techniques). Operator's correction is to tie the picker more tightly to "specific cuisine with substantive data".

- **[DELTA]**

  **`index.js`** — `_buildCuisinePicker` (line ~4647) gets a two-layer filter:

  1. **`UMBRELLA_SLUGS`** constant: explicit exclusion set of catch-all entries — `australasia`, `european`, `mediterranean`, `african`, `dessert`, `fusion`. Detection rule for these: `slug === categoryId` (the entry is its own category aggregator) PLUS the explicit `mediterranean` exclusion (a region within `european` category, not a country).
  2. **`MIN_PICKER_ITEMS = 3`** threshold: skips thin lookups (≤2 entries). Today's data has no such cases at the country-cuisine level (smallest is 20+ entries), but it future-proofs newly-added cuisines from appearing before they're properly filled in.
