### [HDR] #555 | 09:00 SGT 07-06-26 | v0.61.355 — `location-sync.js` 20 s poller (device GPS + Telegram, fresher wins) → cuisine follows the device | 2 code files | 1 PR | 1 build |

- **[INTENT / ROOT CAUSE]** Every TMA resolves location **once** on mount (server cache → Telegram → GPS → SG fallback) and **deliberately doesn't refresh** (so it won't clobber a deliberate anchor). If the user has **physically moved** since the cached fix, nothing re-checks → the **country flag stays wrong**. The recurring fix: a short load-time poll that follows the device.

- **[MECHANISM]**
  - **`location-sync.js`** (shared) — `startLocationSync({ durationMs:20000, intervalMs:4000, thresholdM:1500, current, onLocation })`: every 4 s for 20 s it reads **device GPS** (`navigator.geolocation`, high-accuracy, 3.5 s, no cache) **and** **Telegram** (`window.Telegram.WebApp.LocationManager.getLocation`) in parallel; the **fresher** reading (by timestamp) wins; when it has moved **> 1.5 km** from the last reported point it calls `onLocation({lat,lng,source,ts})`. The 1.5 km gate means GPS jitter — or a user who picked a city while standing still — is never yanked; only a real move triggers a follow. Returns a `stop()` (effect cleanup).
  - **Cuisine wiring** (`App.jsx`) — a once-on-mount effect starts the sync with `current = userLoc`. On a meaningful move it **follows the device**: `setUserLoc` + region/flag via `coordsToCountry` (SG / JB / OTHER + `countryPref`) + `setLocationAnchor` + `setSearchCenter` + `flyTarget` (map flies to you) + `saveUserLocation` (persist, so other TMAs see it). A `userLocRef` mirror feeds the jitter guard.
