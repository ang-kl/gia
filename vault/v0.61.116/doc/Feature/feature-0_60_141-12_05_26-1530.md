# Feature — soleat v0.60.141 (delta entry)

## New features in this arc

### Free-text: decline question-shaped queries (v0.60.131)

- **What** — A query that reads like a question / instruction rather than a dish or place name ("does Beach Road curry rice sell chiffon cake", "can you find me a place that serves nasi lemak", anything ending in "?") is no longer fed to Google Places `searchText` (which would return a misleading by-rating restaurant dump). Chat replies "🙂 I can't answer questions in free text yet — type a dish or cuisine, or use /cuisine"; the Cuisine TMA returns `{ venues: [], questionDeclined: true }` and shows a decline banner with no result list. Conservative — plain dish / brand names ("fish and chips", "char kway teow", "What The Burger", "Burnt Ends") aren't tripped; "where is `<place>`" still works.
- **Why** — Operator: a sentence-shaped query came back as "12 random fine-dining places".
- **Where** — new `freetext-classify.js` `looksLikeQuestion(text)`; `index.js` chat free-text handler (runs before nation-overlay / R.E.D / misrep / cooking-method) + `/api/cuisine/search` (early `questionDeclined` return); `web/cuisine/src/v2/App.jsx` (`questionDeclined` state + banner); `i18n.js freetext.questionDeclined` (EN/FR); new `__tests__/freetext-classify.test.js`.

### Free-text: dessert / drink terms steer to bakeries · cafés · dessert shops · kopitiams (v0.60.131)

- **What** — When the typed text names a dessert or drink ("chiffon cake", "ondeh ondeh", "egg tart", "kueh", "kopi", "teh tarik", "milo dinosaur", "bubble tea", "matcha latte", …, or anything ending in `…cake/tart/pie/waffle/pancake/macaron/…` or `…latte/frappe/smoothie/…`), the Places query is steered toward bakeries / cafés / dessert shops / kopitiams instead of returning a generic by-rating restaurant list. In chat, the result list is split with a divider — venues that self-identify as the right *kind* of place (bakery / patisserie / kueh shop / café `primaryType`, or a bakery-ish name, or the term in the name) above; the rest below. The Cuisine TMA does the same query-steer and tags `dessert: { term, kind }` on the response.
- **Why** — Operator: "Chiffon cake" → "Beach Road Curry Rice" in the Cuisine picker.
- **Where** — new `dessert-drink-keywords.js` (`DESSERT_DRINK_TERMS` ~150 SG-relevant terms; `looksLikeDessertOrDrink(text)`; `dessertDrinkQuery(hit, cuisineLabel)`); `index.js runFreeTextSearch` (dessert branch — `queryOverride` + a dessert-specific above/below ranking) + `/api/cuisine/search` (replace the query with the steered one when the `freeText` is a dessert/drink term; `dessert` payload field); new `__tests__/dessert-drink-keywords.test.js`.

### Identity-free free-text search-term log + `/ftlog` (v0.60.131; retention 90 d v0.60.132)

- **What** — Every food / dish / cuisine term a user types in chat free-text or the Cuisine "Tell me" box is recorded — **without any chat ID, Telegram user ID, or other user identifier** — in Redis (`freetext:log`, a capped list of the last 5 000 entries; `freetext:log:<YYYY-MM-DD>`, per-day lists; both 90-day TTL, refreshed on each write). Each entry: `{ q (≤ 80 chars), ts, src ('chat' | 'cuisine-tma'), chip (was a cuisine chip active), m (which guard/table matched: misrep / cooking-method / red / red-ambiguous / dessert-drink / question-declined / null), n (result count) }`. A corpus of *what is searched*, never *who searched* — used to extend the misrepresented-dish / cooking-method / dessert-drink tables, tune the question guard, and catch recurring search failures. An owner-only `/ftlog [N]` command (gated by `TELEGRAM_OWNER_CHAT_ID`, like `/ver` — silent no-op for everyone else; open when the env var is unset; default N = 40, max 200) dumps the recent entries.
- **Why** — Operator: "log identity-free … store for 90 days."
- **Where** — new `freetext-log.js` (`logFreeTextQuery(redis, text, meta)`, `dumpFreeTextLog(redis, n)`); `index.js` (logging at the chat free-text decline / R.E.D-ambiguous / cooking-method-pivot returns, before `runFreeTextSearch`, and on the `/api/cuisine/search` payload; new `/ftlog` `bot.onText` gated by `isOwnerChat`); `i18n.js privacy.body` (a "Search terms" bullet, EN + FR — wording iterated to "Search and Selection are kept and expire after 90 days." in v0.60.137); `doc/Legal/legal-0_60_132-12_05_26-0830.md` (the formal Legal record of the log + 90-day retention). Redis-only — no third-party API.

### `/s` + free-text dish search — above-the-line vs below-the-line, on-cuisine "Try X" (v0.60.135 → v0.60.138)

- **What** — A `/s <dish>` or active-conversation chat search now splits its Places results into an **above-the-line** tier (venues that plausibly serve the dish — their name carries the cuisine name, a distinctive dish word, or a cuisine-family demonym; OR their Google `primaryType` is in the dish's coarse cuisine family; OR — for bakery/café dishes like quiche / tart / croissant — the venue is a bakery / café) and a **below-the-line** tier (everything else — Google text-matched your words but the venue is off-cuisine). A `⇩─ Eateries with similar dishes or cuisine ─ ⇩ / ⇩─ not exactly {dish} ─ ⇩` divider sits between them; the "🍽️ Try `<dish>`" card line is shown **only** above the line; when *everything* came back off-cuisine a plain `⚠️ No Singapore eateries clearly serve {dish} — these just matched your search words:` caveat replaces the divider. So `/s goulash dumpling` → Kapitan ("Authentic Slavic Cuisine") above with "Try Czech guláš with bread dumplings", divider, then "Hua Jie Dumpling" / "Dumpling Darlings" / a microbrewery below with no "Try"; `/s Quiche Lorraine` → Choupinette + Tiong Bahru Bakery above, divider, then "Hawkers' Street @ ION" / "Lau Pa Sat" below. The cooking-method fan-out gets the same gate on its "Try `<method>`" line.
- **Why** — Operator, across several rounds: "no separation divider from exact to relevant"; "the 'try' line assumes the dish is available" (a Chinese dumpling house surfaced for "Czech guláš"); then "still no divider" (the first cut only demoted on a confident type contradiction, which Google rarely gives for generically-tagged venues); then `/s Quiche Lorraine` listing hawker food courts ("a French dish at a hawker centre — and quiche is a bakery/café item of *any* cuisine").
- **Where** — new `cuisine-family.js` (`restaurantFamily` / `cuisineFamily` / `isLikelyMismatch` / `familyDemonyms` / `distinctiveDishWords` / `looksLikeBakeryCafeDish` / `venuePlausiblyServes`); `index.js handleSearchTurn` (single-query path: `venuePlausiblyServes`-based split + reorder + divider + per-venue `dishPhrase` + `freetext.allBelow`) + `runCookingMethodFanOut` (the "Try X" gate); `i18n.js freetext.allBelow` (EN/FR); new + extended `__tests__/cuisine-family.test.js`.

### "Please wait" feedback on the free-text chat + `/s` single-query searches (v0.60.139)

- **What** — Typing a dish in chat ("ramen", "chiffon cake") — or `/s <dish>` — now shows "🔎 One moment — searching for eateries for X…" immediately (EN/FR), rotates ("Still searching…", "Almost there…") at 15 s, and shows "🕰️ This is taking longer than usual — did you mean something else?" at 60 s, then deletes the message when the results land. Previously the free-text chat dish search and the `/s` plain-dish path ran a Places call + travel/footfall enrichment (~3–6 s) with no feedback at all; only the `/s` technique / cooking-method / nation-iconic fan-outs had this (since v0.60.112).
- **Why** — Operator: "is there a 'please wait …' reply … in the free-text chat?" — there wasn't.
- **Where** — `index.js runFreeTextSearch` + `handleSearchTurn`'s single-query path now create + `finish()` a `createWaitStatus`; `createWaitStatus` hardened (named `finish`, 4-min self-clean `autoTimer`, `done` guard).

### Cuisine TMA — result cards show the cuisine-type label + a review snippet again (v0.60.140)

- **What** — Each TMA result card again shows a small cuisine descriptor under the venue name ("Thai" / "Sushi" / …) and a `💬 "…"` recent-review snippet below the address — for plain (non-Michelin) venues too. The card component already rendered both (`venue.restaurantType`, `venue.recentReview`); they were just never populated for the TMA's LLM-free search path. Still missing for that path: the "🍴 What to order" line and the `vibe` phrase — those need venue-specific dish data / an LLM, and the operator deferred the re-wire ("status cold, no change").
- **Why** — Operator: "where are the details … in Cuisine TMA? check previous PR."
- **Where** — `pipeline.js` (`places.primaryTypeDisplayName` added to `DISCOVER_FIELD_MASK`; passed through `discover()`'s candidate map); `index.js /api/cuisine/search` (top-venue cleanup loop: `restaurantType` ← `humaniseRestaurantType(primaryTypeDisplayName, primaryType)` with a Michelin-label override; `recentReview` ← the first of the already-fetched-then-discarded `reviews`, ≤ 160 chars).

### Cuisine TMA — the "end" FAB actually closes the Mini App (v0.60.141)

- **What** — The Cuisine TMA's bottom-left "🔚 end" FAB now always calls Telegram `WebApp.close()` (twice, ~350 ms apart, for the clients where `close()` is flaky) instead of, sometimes, doing `history.back()`. Previously the FAB toggled "⬅ Back" / "🔚 Close" on `window.history.length > 1` — and the Cuisine TMA always has `history.length > 1` on entry (the `/app/cuisine` → v2-app redirect, plus the Menu-hub launch path), so the FAB sat in "⬅ Back" mode and a tap meant as "end" did `history.back()` (pop the redirect entry / spin in place), leaving the app open. The native Telegram header back button is unchanged — its "back to the Menu hub" when launched from the hub is intentional.
- **Why** — Operator: "I click 'end' in any TMA, especially Cuisine, it cannot close … is this a Telegram issue?" — mostly an app-side bug (it is also true that `WebApp.close()` itself isn't 100 % reliable on some clients/launch paths — the header X always works).
- **Where** — `web/cuisine/src/v2/components/BackFab.jsx` (`closeOnly` prop); `web/cuisine/src/v2/App.jsx` (`<BackFab inline closeOnly />`).
