## 0. What this project is

**Soleat** (package name `soleat`; product name *Gia4lunch* / "Gia") is a production Telegram bot + five Telegram Mini Apps (TMAs) + an Express server that helps a solo diner in Singapore decide where to eat — and get there. It spans F&B discovery (cuisine picker, hawker centres, Michelin / Bib Gourmand, hidden gems), free-text and cooking-method search, live transport and traffic, carpark availability, weather, and a bilingual (EN/FR) interface. It is a single-operator project built with AI-assisted development, deployed on Railway, and has reached **v0.60.213** across ~190 numbered commits and ~460 pull requests.

The Builder doc records *how* the project is built — the operating lens, the conceptual framework, and the recurring patterns — distinct from *what* it does (Feature), *what it runs on* (Technical), and *who builds it* (Persona).

| # | Framework concept | Description | Origin | Status |

| FW-1 | **Layered architecture — data → policy → surface** | A clean separation: data acquisition (Places / Routes / LTA / NEA / Gemini clients), policy (search classification, cuisine-family plausibility, dish-name validation, ranking), and surface (Telegram message templates + the five React TMAs). | PP-4 | **Cooking-method fan-out** | A free-text technique query (e.g. "en croute") resolves to a curated cuisine, a Gemini one-line explainer, a representative dish, and a fan-out of venues — rendered with a country flag and a "verify" caveat. | v0.60.0 → v0.60.208 | live |
| PP-5 | **Dish-name guard** | A single shared validator (`dish-name.js` — `isDishName` / `filterDishNames` / `CATEGORY_RE`) ensures the "Try" recommendation line only ever carries a genuine dish/dessert name, never a generic category word. | PP-6 | **Defensive card render** | Every venue card is rendered inside a per-item `try/catch` returning a minimal name-only fallback — one malformed venue can never blank the whole reply. | v0.60.112 | live |
| PP-7 | **HTML-then-plain-text retry** | Telegram `parse_mode:'HTML'` sends that fail on tricky punctuation are retried as stripped plain text before surfacing an error. | v0.60.145 | live |
| PP-8 | **Reproduce-by-reference doc delta** | New documentation files reference the prior for unchanged sections, append the delta (FW-6). | v0.60.157 | live |
| PP-9 | **Admin-merge for CI-infra failure** | When CI fails systematically with no execution and local preflight is clean, the failure is diagnosed as infrastructure-side and the PR is admin-merged with the diagnostic recorded — never as a routine shortcut (§17.4). | v0.60.205 | live |
| PP-10 | **Operator-supplied-copy paste** | User-facing legal/privacy copy pasted by the operator lands verbatim in `i18n.js`, is translated paragraph-for-paragraph to FR, and the prior copy is preserved as superseded (§17.2). | v0.60.171 | live |
| PP-11 | **AskUserQuestion at decision forks** | Genuine either/or decisions (UX trade-offs, ambiguous fixes) are surfaced as explicit 2–4-option questions rather than assumed — the operator picks, the choice is recorded as a G3 decision. | full arc | live |

## 4. What this project demonstrates (capability evidence for external readers)

This section is an evidence index for readers assessing the project and its operator — for employment, advisory, AI-collaboration, partnership, or product-development contexts. Each claim is anchored to a verifiable artifact in the repo.

- **Systems thinking** — a clean layered architecture (FW-1), a five-app TMA family on a shared auth + version contract (FW-2), and a self-consistent eight-folder documentation system with its own contract, serial protocol, and confirmation gates (FW-4, FW-5, FW-7). The doc system is itself a designed artifact, versioned to contract v0.0.4.
- **AI understanding** — cost-aware, latency-bounded LLM integration (BL-9): a three-phase Reason–Fetch–Refine pipeline (FW-3), Gemini calls budgeted against a hard 30 s webhook ceiling, model-fallback chains, defensive JSON parsing, and a shared dish-name guard that constrains LLM output to valid dish names (PP-5). LLM enrichment is always best-effort, never load-bearing (BL-4).
- **Execution ability** — ~460 merged PRs to v0.60.213, each preflight-checked, test-covered, and journalled; a unit-test suite at 1865 passing cases; five production React apps; a live Railway deployment.
- **Product reasoning** — UX decisions are evidence-driven (operator screenshots → root cause → fix), trade-offs are made explicitly (PP-11), and bilingual parity is held as a release gate (BL-5). Empty-states, error paths, and degradation are designed, not left to chance (BL-4, PP-6, PP-7).
- **Operational knowledge** — Redis TTL design, Places/Routes/LTA/NEA quota and billing awareness, CI/CD on Railway, GitHub Actions diagnosis (BL-11), security hardening (a Telegram `initData` HMAC auth chokepoint), and a disciplined release/rollback posture (BL-1).
- **Strategic discipline** — a documentation system built to survive hand-off: reproduce-by-reference scalability (FW-6), a cross-team onboarding sequence, and a standing-rules registry so operator decisions bind future sessions.
