- **[EVIDENCE — the log]** Three bare `[set-location] chat=… → <redacted>` lines (label-less,
  region-less SG device coords; 17:45:06, 18:09:40, 18:10:04) — each **replaced** the labelled
  `"Ho Chi Minh City" VN OTHER` pick (correctly written 17:45:44), because
  `location-cache.setUserLocation` replaces the whole payload, never merges.

- **[ROOT CAUSE]** The v0.61.242 boot **auto-detect** effect (App.jsx) — step 5 persisted
  **bare lat/lng** (no label, no region, no `ambient`) and ran on **every** boot once userLoc
  resolved (only the deep-link case skipped it; a labelled server-cache boot did NOT). A coords-only
  cache then boots incoherently: coords adopted, no label → no anchor / no explicit-pick latch,
  no region → **SG default flag**, the MY cascade defaults to its capital → the operator's
  "malaysia>KL + foreign street + 🇸🇬 flag + random-places auto-load" screenshot. This same writer
  class plausibly fed the long location-lock thrash (v0.62.30 era).

- **[FIX — three parts, all EXTENDING the v0.62.30 rule ("a LABELLED cached location is an explicit
  pick on EVERY boot path"), none reversing it]**
  - **A.** Auto-detect **early-returns** when the explicit-pick latch is armed and a **named**
    anchor is installed — no GPS prompt, no Gemini call, no persist. The boot load still fires at
    the cached anchor. Log: `auto-detect: SKIPPED — labelled cached pick "<name>" holds`.
  - **B.** When auto-detect legitimately runs (no pick), its persist now carries **`ambient: true`**
    (the v0.62.31 D787 contract — the server refuses it over a fresh labelled pick, which also
    closes the initData-boot race where the persist fired before the latch armed) **plus the
    resolved label / region / country** — the cache can never be a bare coords-only entry again.
  - **C.** `tryServerCache` now **derives the region from coords** (coordsToCountry → isJbCoords →
    nearestIataCity, mirroring the 20-s follow-sync) when a legacy coords-only cache carries no
    region — a KL anchor can no longer wear a 🇸🇬 flag.

- **[ANSWER to the operator's question]** Yes — first load is **cache-first by design** (boot order:
  hash → initData → server cache → GPS → centroid; a *labelled* cache = your explicit pick). The bug
  was never the order — it was this writer corrupting the cache to coords-only.

- **[NOT touched]** Boot order; the v0.61.409 no-popup policy; `applyAnchorCoherenceChoice`'s
  use-device persist (a deliberate gesture — full overwrite stays correct); /s.
