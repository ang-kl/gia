- **[INVESTIGATION — durian (read-only, 2 Explore agents)]** The v0.61.416 **relaxed fallback**
  (`filterByMode(..., {relax:true})`, fired when the strict durian pool is thin) admitted any venue
  with a durian word **anywhere in the FULL haystack — including reviews/googleSummary** — and skipped
  the accept-type + strict-name gates. Vietnamese chè/vegetarian/coconut venues routinely mention
  durian once in a review → flooded the results. Only "Chè thái sầu riêng" (durian in the NAME) was a
  legit strict match. Contributing: **VN was absent from `LOCAL_SEED_LANG_BY_CC`** (despite being
  belt-allowed since v0.61.413), so the search ran on mostly-English seeds → thin strict pool → the
  loose fallback fired often.

- **[INVESTIGATION — FX]** `currency-format.js` converts via a USD pivot
  (`usdRate(from)/usdRate(to)`), cached 15 d at `fx:usd:<CUR>`. Three compounding defects:
  (1) **Frankfurter omits VND/TWD/MOP/BND** — no fallback source for exactly those currencies;
  (2) **no plausibility guard** — a corrupt/inverted cached leg (the ~0.43 effective multiplier the
  screenshot implies; correct VND→SGD ≈ 0.00005) was used as-is; (3) **`redis.setex` (lowercase) on
  node-redis v4** — silently threw inside its try → **the FX cache NEVER wrote**, so every render
  re-hit Alpha Vantage (25/day free tier) → throttle envelope → null legs. Repo-wide grep confirmed
  every other module uses camelCase `setEx`; this module was the sole straggler. Live `searchText`
  spot-check (THB screenshots) confirmed the bug is currency-specific, not systemic.
