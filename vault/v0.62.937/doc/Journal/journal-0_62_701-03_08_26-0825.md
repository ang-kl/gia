## New

### [HDR] v0.62.701 — O-131: the last tick is locked instead of choosing between two wrong answers

- **[INTENT]** Operator: *"Settle: O-131"*. No direction given, so the call is mine and stated here.

- **[THE QUESTION AS FILED]** O-131 offered two options — fail-open (return everything when nothing
  is selected, which v0.62.700 shipped) or return empty with a message. **Neither is right**, and
  looking again the problem is larger than O-131 recorded:

  | | fail-open | empty |
  |---|---|---|
  | user unticks the last tick | sees **everything** — the tap appears to do nothing (**D-69**) | sees a **blank screen** |

  O-131 described this as an SG/PH problem. It is not. In **every** country, unticking all ticks
  returns everything; SG and PH were only where the *old* build reached zero instead. So both
  options were answers to a question that should never be asked.

- **[DELTA — make the state unreachable]** The **last remaining checked tick is disabled**, exactly
  as D-65 already greys a year with no holders, and for the same reason: a control that cannot
  produce a meaningful result is not offered as though it can. New `soleCheckedKey()` in
  `lib/michelin-years.js`; the drawer locks that tick (accent fill at `opacity-70`, `cursor-default`)
  and shows `michelin.lastTickNote` — *"At least one filter must stay on — turn another one back on
  first."* — so it reads as a floor, not an unresponsive control.

- **[WHAT DELIBERATELY DID NOT CHANGE]** The **server's fail-open guard stays exactly as it is**. Its
  own comment says it exists for a *"stale hash / hand-crafted request"* — and that is now all it
  handles, because the UI no longer produces the state. It is a backstop again rather than the thing
  standing between a user and an empty screen. `soleCheckedKey` returns `null` when everything is
  already off, so a stale URL is left to the server rather than half-repaired by the drawer.

- **[LIVE-TICKS SUBTLETY]** The lock counts **live** ticks only. In Singapore 2026 is greyed, so
  unticking 2025 must lock **Bib** — if the greyed 2026 counted as a second option, the user could
  untick Bib as well and land in exactly the state that produced the blank screen. Covered by a test
  named for that case.

### [HDR] v0.62.701 — O-104 closed: eleven inputs swept, and a guard so it stays closed

- **[INTENT]** Operator: *"Settle: O-104"*. The Register framed closing it as *"either auditing each
  input individually or putting `!important` on the guard"*. **Audit chosen** — D-68 already rejected
  `!important` for a good reason: it forces every input to exactly 16px, shrinking any that
  legitimately want more, as an app-wide restyle inside a bug fix.

- **[THE SWEEP]** Every `<input>` / `<textarea>` / `<select>` across all six TMAs was enumerated with
  its type and size class. **Checkbox / radio / range / color are exempt** — iOS only zooms
  text-entry. That left **11** offenders, now all `text-[16px]`:

  | class | count | where |
  |---|---|---|
  | `text-sm` (14px) | 7 | Cuisine `LocationField` ×2, Cuisine + Clipboard `TellMePanel`, Clipboard `FilterSheet`, Menu `LocationFieldMenu` ×2 |
  | `text-xs` (12px) | 2 | Cuisine + Clipboard `QuickFilters` (custom-rating number field) |
  | `text-[10px]` | 2 | Clipboard `DrawerRow` (inline edit fields) |

  Everything else either inherits — where the element-level guard **does** apply, since nothing
  overrides it — or is an exempt type.

- **[THE PART THAT ACTUALLY CLOSES IT]** `__tests__/ios-input-zoom-guard.test.js`. A sweep is a
  one-time event; without a guard the next `<input className="… text-xs">` reintroduces the bug
  silently, which is **O-103's** pattern precisely. The test walks `web/_shared` + all six
  `web/*/src` trees, reads each text-entry control's **className value**, and fails with file:line
  for anything under 16px.

- **[TWO THINGS THE TEST ITSELF CAUGHT]**
  1. **My own sweep had a hole.** I globbed `web/*/src`, which does **not** cover
     `web/_shared/components/`. The guard flagged `StationLocationField.jsx` on its first run — the
     one file I would have sworn was correct, because v0.62.698 fixed it.
  2. **That flag was a false positive**, and instructive: the match was inside the JSX comment
     *explaining O-104*, which quotes `text-xs`. The first draft scanned the whole opening tag. A
     guard that fails on its own documentation is a guard someone deletes, so it now reads the
     `className` value with comments stripped.

- **[MUTATION-CHECKED]** The guard was proven to fail, not merely to pass: reverting one input to
  `text-xs` produced `web/cuisine/src/v2/components/TellMePanel.jsx:113 <input type=text> text-xs`,
  and restoring it went green. A second test asserts the scan sees ≥25 controls, so a scan that
  silently walked the wrong tree cannot pass forever — the same failure class the guard is about.

- **[VERIFICATION (sandbox)]** Cuisine + Menu + Clipboard builds green. `.opacity-70`,
  `.cursor-default`, `.text-[16px]` confirmed **emitted** in each app's compiled stylesheet
  (D-22…D-28). Full suite **160 files / 3,959 tests** green (was 159/3,951): +6 for `soleCheckedKey`,
  +2 for the zoom guard. i18n locale-coverage suite green with the two new keys.
