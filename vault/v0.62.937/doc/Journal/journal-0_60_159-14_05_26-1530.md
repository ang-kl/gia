# Journal — soleat v0.60.159

> Two operator-reported issues on Cuisine TMA / Michelin Criteria, fixed in one PR. (1) **UI**: `🍴 Try · X` line duplicated the first dish from the rest-of-menu list directly below it, plus the two lines were rendered at different font sizes (12px vs 11px). (2) **Functional**: Michelin list resumed mid-catalogue (`seen=84`) on what should have been a fresh TMA mount — Railway log evidence pinned the cause to the v0.60.155 mount-time wipe being gated on `verifyInitData`, which 401s during the brief window before Telegram WebApp populates `initData` on a cold launch, so the wipe silently skips. Fix: lazy session-meta wipe at the `/api/cuisine/search` route entry — once initData IS valid (which is when the user can actually search), detect a missing `cuisine:session-meta:<chatId>:started_at` and perform `startSession()` + `cuisine:seen:<chatId>:*` wipe inline before any seen-set read. Idempotent and cheap (one HGET per search; subsequent searches in the same session skip the wipe).

  **`web/cuisine/src/v2/components/ResultCard.jsx` (line 153–185)** — two coupled fixes inside the IIFE that builds the primary dish + rest-of-menu lines:

  1. **Filter duplicate** — `restDishes` was `venue.signatureDish ? venue.dishes.slice(0, 3) : venue.dishes.slice(1, 4)`. When `signatureDish` is set (which the v0.60.153 force-fill guarantees for Michelin / Bib-Gourmand entries — `dishes[0]` equals `signatureDish` in that path), the `slice(0, 3)` branch re-included `dishes[0]` → both `🍴 Try · dishes[0]` and the rest line `dishes[0] · dishes[1] · dishes[2]` rendered, with `dishes[0]` duplicated. New logic: `venue.dishes.filter((d) => norm(d) && norm(d) !== norm(primaryDish)).slice(0, 3)` (case-insensitive trim normalisation) — drops any rest-list entry that matches `primaryDish` regardless of whether the dupe came from the LLM, force-fill, or upstream curation.

  2. **Match font size** — the rest line was `text-[11px] text-tg-hint`; the primary `🍴 Try · X` line was `text-[12px] text-tg-text`. Per operator screenshot the size mismatch read as a visual glitch. New: rest line is `text-[12px] text-tg-hint` — same size as the primary line, hint colour retained so the secondary-list semantic stays.

  **`index.js` `/api/cuisine/search` route entry (~line 8776, right before the `JB_CBD` constant)** — new lazy session-meta + seen-set wipe block. Why it's here and not in `handleMichelinSearch`: the same `cuisine:seen:<chatId>:<criteriaHash>` SET drives dedup for BOTH the curated Michelin path AND the regular cuisine-chip path, so the fix at the route entry covers both. Flow:

  ```js
  if (csChatId && redis?.isOpen) {
    try {
      const startedAt = await redis.hGet(`cuisine:session-meta:${csChatId}`, 'started_at');
      if (!startedAt) {
        console.log(`[Cuisine-Session] lazy start for chatId=${csChatId} (mount POST missed initData); wiping seen-set`);
        await cuisineSession.startSession(redis, csChatId);
        try {
          const seenKeys = await redis.keys(`cuisine:seen:${csChatId}:*`);
          if (seenKeys && seenKeys.length) {
            await redis.del(...seenKeys);
          }
        } catch (err) {
          console.warn('[Cuisine-Session] lazy seen-set wipe failed:', err.message);
        }
      }
    } catch (err) {
      console.warn('[Cuisine-Session] lazy session-meta check failed (non-fatal):', err.message);
    }
  }
  ```

  Cost on the happy path (mount POST DID fire successfully — `started_at` exists): one `HGET` per search. The wipe block doesn't execute. Cost on the recovery path (mount POST 401'd): one `HGET` + one `HSET` (inside `startSession`) + one `KEYS` + one `DEL`. Bounded — fires AT MOST once per session (the `HSET started_at` inside `startSession` ensures the guard short-circuits on every subsequent search in the same session). 30-min `cuisine:session-meta` TTL means a long-backgrounded TMA naturally re-fires the wipe when the user returns, which matches the operator's mental model of "fresh re-open = fresh list".
