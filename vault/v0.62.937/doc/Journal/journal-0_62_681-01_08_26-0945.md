## New

### [HDR] v0.62.681 — two device-reported Cuisine regressions, both from guessed-instead-of-measured values

- **[INTENT]** Operator, with two device screenshots (iPhone, v0.62.679): *"(1) when I first time open
  the Cuisine TMA, it should fire 'first load…' like before. I think the audit to make it consistent
  remove it. (2) first-time-loaded carousel card position (see picture) is much closer to the
  recommended strip (which is above the footer) than the second-time-loaded carousel card. I want it
  consistent to be just 2 tiny spacing above the strip of recommendation."* On the follow-up question
  about what appears instead on first open, the operator answered: *"Back to originally planned
  'finding eateries…' and the results."*

- **[#1 — first-load wait message]** The operator's hypothesis (an audit removed it) was checked and
  **disproved before any code was written**: the overlay's condition (`loading && !funFact`) has not
  changed since v0.62.484, and none of the three recent audits touched it — v0.62.671 (M3 Tier 0)
  changed exactly one line in Cuisine's `App.jsx` (the Widen-switch thumb offset, `1.15rem` →
  `1.25rem`), and v0.62.674–678 / v0.62.679 changed nothing loading-related. Also verified intact:
  `loadingReason` still defaults to `'initial'` and only a user-initiated search flips it to
  `'rotating'`/`'refresh'`; fun-facts are explicitly suppressed while `firstLoadPending`; `loading`
  itself is initialised `true`; and `runSearch` has no `await` before its `setLoading(true)`. So the
  message the boot path *would* render was already the right one — `t('loading.initial')` =
  "Finding eateries" + the separately-rendered blinking `…` span.
  **What was never guaranteed is that it stays on screen long enough to READ.** The splash gate
  (`App.jsx`'s `locationGateOpen` early-return) opens the gate and fires the one boot load in a
  single commit, so a boot search that settles fast — warm response cache, small pool — flips
  `loading` back to false within a frame or two and the wait message flashes past: the TMA reads as
  jumping straight from "Confirming your location…" to results. Added `bootOverlayHold`, a
  minimum-dwell flag armed *only* on the gate's boot-load branch (the saved≠device mismatch branch
  deliberately opens an EMPTY TMA with no hourglass — v0.61.409 — and is untouched), cleared by a
  900 ms timer that always fires, and also cleared by 🛑 Stop so a manual stop still feels
  immediate. Overlay condition widened to `(loading || bootOverlayHold) && !funFact`. Net effect: a
  first open always reads "Finding eateries…" → results, which is the originally-planned behaviour
  the operator asked for.

- **[#2 — carousel card vs. the recommendation strip]** Root cause: `ResultDrawer.jsx`'s bottom
  offset was a hardcoded **guess** — `bottom: calc(${hasFilters ? '6rem' : '4.5rem'} + 2px)` — a
  leftover from v0.62.186, when the active-filter chips genuinely rendered as their OWN full-width
  row above the dock and made the footer ~1.5 rem taller. Since v0.62.192/281 those chips live
  INSIDE the dock as the inline "Criteria (N) ▾" pill, so the footer's real height no longer changes
  when filters exist — but the drawer still lifted an extra 1.5 rem (24 px) whenever any criteria
  did. That is exactly the reported asymmetry, and both screenshots confirm it: the first-open shot
  has no "Criteria (N)" pill in its footer (→ the 4.5 rem branch, card landing nearly flush with the
  "S$30 ~ 100 · 3 gems | ★ 11PenangLane Bistro" strip), the later shot shows "Criteria (1)" (→ the
  6 rem branch and its roomier gap). Fixed by **measuring instead of guessing** — the same fix shape
  as v0.62.674's footer-height reserve: a `useLayoutEffect` in `App.jsx` reads the strip's real top
  edge and publishes `stripLiftPx`, which `ResultDrawer` turns into `bottom: ${stripLiftPx + 2}px`,
  holding the card a consistent 2 px above the strip in every state (criteria or not, back-FAB row
  or not, Michelin pager or not, locale reflow). The strip is found via `.insight-glass`
  (`InsightStrip`'s inline root — the single place that class is used) scoped to the footer ref the
  component already holds, following the v0.62.657 precedent of matching a selector guaranteed to
  keep matching rather than a hand-written one that can silently match nothing. Two deliberate
  details: the effect takes **no dep array** (it runs after every render and bails when the value is
  unchanged, so it can never go stale against a flag declared later in this component — the TDZ trap
  `tma-hook-deps-tdz.test.js` already caught once on the `listPeekPx` effect), and the last good
  measurement is **retained** while the strip is unmounted (💬 composer expanded, picker/region
  overlays open) so the card never jumps mid-interaction. The old `calc()` stays as the
  pre-measurement first-paint fallback only, unchanged — one guess is not traded for another.
