- **[INTENT]** When the user **picks** a new search area in the Cuisine TMA and returns to chat, send one message naming the area. The original parked text is honoured verbatim.

- **[FINDING that shaped it]** `saveUserLocation` (web/cuisine) POSTs `/api/cuisine/set-location` from **4** paths — including **boot / auto-detect** (`App.jsx` 216 / 1212 / 1548), not just user picks. A naïve "fire on every write" would spam on app-open. The boot calls send **no label**; the deliberate-pick path (`:2272`) does. So the operator confirmed: **only on a deliberate pick AND an actual change**.

  - **`web/cuisine/src/v2/App.jsx`** (`:2272`, the deliberate-pick path) — adds `notify: true`. The boot / auto-detect calls omit it, so they stay silent.
  - **`i18n.js`** — new bot key `loc.searchArea.set` (en + fr); `{label}` is HTML-escaped.
  - **`index.js`** — new module fn `notifySearchAreaSet({ chatId, prev, lat, lng, label })`: fires **only** when `req.body.notify === true` **and** the area actually changed vs the previous set-location (haversine > 1000 m **or** the label differs). Resolves the name (`opts.label` → `reverseGeocodeAddress` → coords), `resolveLang`, sends via `bot.sendMessage` (HTML); fire-and-forget. `/api/cuisine/set-location` reads `prevLoc` (`getUserLocation`) **before** persisting, then calls it on `notify`.
  - *"return to your previous search area"* = **/location**, which already surfaces the recents quick-picks — so the text is actionable without a new button.
