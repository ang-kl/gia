## New

### [HDR] v0.62.667 — restore Singapore's 2 "dropped" Bib Gourmand rows as 2025-only historical entries

- **[INTENT]** Operator, after v0.62.666 shipped: *"Actually don't drop 2025. I didn't tell you to keep 2025
  even though is dropped."* Read together with the clarifying question I asked and the operator's answer
  ("Restore SG's 2 deleted Bib Gourmand rows"): the v0.62.665 decision to DELETE "Eminent Frog Porridge &
  Seafood" and "Soon Huat" entirely from `SG-michelin.js` when their Bib Gourmand distinction lapsed in 2026 was
  never actually requested — the operator's original spec asked for dropped-vs-retained to be reflected
  honestly in the display, not for the underlying 2025 record to be destroyed. I had made that deletion call
  myself (recorded, with a Confirmation Gate G2 flag, in the v0.62.665 Journal) reasoning that "this file has no
  historical/dropped-listing mode" — that premise was WRONG, and the operator's correction is the proof: a
  category entry holding only past years and no current one *IS* a historical-listing mode, it just hadn't been
  used yet. Notably, I had ALREADY built the correct pattern one entry later, for Taiwan (v0.62.666, Register
  D-34) — 12 non-retained Taiwan rows were kept as 2025-only historical entries rather than deleted, specifically
  because that schema "is explicitly designed to retain full award history including dropped venues." The
  operator's correction makes the SAME reasoning apply to Singapore's flat schema too — the schema difference
  between the two files was never a reason to delete in one and retain in the other.

- **[THE FIX]** Restored both entries into `SG-michelin.js`'s `BIB_GOURMAND` array, in their original
  alphabetical positions, with the EXACT address text they carried before the v0.62.665 deletion (recovered from
  `git show f01fd08 -- SG-michelin.js`, not reconstructed from memory) and `awardYears: ["'25"]` — 2025-held,
  not retained in 2026. This is the identical shape every other 2025-only entry in this file already has (e.g.
  a brand-new 2026 debut carries `["'26"]` only); "held in the past, not now" and "held now, not yet in the
  past" are the same kind of fact, rendered by the same one mechanical rule (`formatMichelinLine`) with no code
  change required. Verified `formatMichelinLine` on the restored entries renders "✳️ Bib Gourmand · '25" — a
  plain historical badge, no "'26", no dangling comma.

- **[A REAL CORRECTNESS CONSEQUENCE, FIXED IN THE SAME PASS]** Restoring these 2 rows means
  `BIB_GOURMAND.length` is now 99, not 97 — but only 97 of those 99 currently hold the 2026 award. One call site
  in `index.js` (the Michelin criteria tile's description string, `"Singapore Michelin Guide: N Bib Gourmand"`)
  read that raw array length directly; left unchanged, restoring the 2 rows would have made this user-facing
  count silently WRONG (99 instead of the true current 97). Fixed by filtering to entries whose `awardYears`
  includes `"'26"` at that one call site — the smallest change that keeps the description accurate without
  altering how `BIB_GOURMAND`/`ALL`/`getByCategory('bib-gourmand')` are consumed anywhere else (search/seed
  behaviour is unchanged, matching how Taiwan's venue-centric pool already includes dropped venues in
  `visitableVenues()` without a "held this edition" gate).
