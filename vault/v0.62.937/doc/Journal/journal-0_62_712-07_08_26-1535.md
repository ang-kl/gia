# Journal — v0.62.712 (Item 2: the location picker learns to fold — Malaysia, China, and a generalized mechanism)

_(№ 1,051 — 07-08 '26 15:35 SGT)_

## New

### [HDR] v0.62.712 — generalize the AU-only region-grouping picker to Malaysia + China (pilot), France data-prep

- **[INTENT]** Third and final item of the operator's original three-item "next build" message (O-144 and
  the Michelin 2026 update shipped earlier this arc). Original spec asked to extend Australia's
  state-grouped disclosure-triangle picker to the rest of the OTHER-country city list, give China a
  curated "Popular provinces" lead section, and confirm Singapore's placement in the Others list. Plan
  mode (this session) scoped it to a pilot — Malaysia + China fully built, France data-prepped only,
  11 other countries left flat for a later pass — with two structural decisions locked by the operator
  during planning: Johor keeps its existing whole-state row as an always-visible 16th entry; China's
  fold reuses the existing simple province-level mechanism rather than a new nested per-province
  toggle. One item was left open at plan-approval time — which 3 of China's real 5 autonomous regions
  to include (the operator's spec said "3", real China has 5) — and the operator later delegated that
  decision directly: *"Proceed to do (Location picker rework), including China's autonomous-region and
  Popular-province lists."*

- **[THE DECISION MADE ON DELEGATED AUTHORITY]** Used the complete, factually correct set of 5
  autonomous regions (Guangxi, Inner Mongolia, Ningxia, Tibet, Xinjiang) rather than an arbitrary
  3-of-5 cut with no principled basis for which two to drop. The Popular-provinces manifest kept the
  plan's own placeholder (Guangdong, Beijing, Shanghai, Zhejiang, Jiangsu, Sichuan) — reasonable given
  no population/tourism data source exists anywhere in this repo to derive a ranking from — with one
  adjustment: Beijing moved to the FRONT of that set (see the `[0]`-capital discovery below).

- **[A REAL BEHAVIOURAL CONSTRAINT DISCOVERED BEFORE IT COULD BREAK]** `App.jsx`'s boot-anchor
  fallback (~line 1877) reads `CITIES_BY_COUNTRY[cc][0]` as the country's default pin when no device
  GPS is available — it depends on element `[0]` being the national capital. Following the plan's
  "Popular provinces first" ordering literally (Guangdong first, since it was listed first in the
  plan's placeholder) would have put Guangzhou at `CITIES_BY_COUNTRY.CN[0]`, silently changing China's
  no-GPS fallback anchor from Beijing to Guangzhou. Caught by grepping every `CITIES_BY_COUNTRY[`
  call site before restructuring the data, not after. Fixed by ordering Beijing first within the
  Popular set — satisfies both "Popular provinces lead" and "element `[0]` is the capital" without
  touching the `[0]`-dependent code itself. Malaysia's existing "Kuala Lumpur first" already satisfied
  this; the FT group ordering was chosen to preserve it explicitly rather than by accident.

- **[A SECOND BUG THAT WOULD HAVE SHIPPED SILENTLY]** `collapsedStates` (now `collapsedRegions`) was
  seeded once via `useState(() => new Set())` on mount and never reset — harmless while only AU carried
  a `state` field, since switching to any other country just rendered flat. The moment MY/CN/FR also
  carry `region`, that stale-Set bug becomes real: switching from AU (some groups toggled) to CN would
  carry AU's leftover state codes into CN's collapse Set, and CN's "non-Popular starts collapsed"
  seeding would silently never apply on a genuine country switch (since `CityDropdown`/`CityDropdownMenu`
  are NOT remounted when `countryCode` changes — same component instance, new prop, confirmed by
  reading the parent's JSX for a `key` prop and finding none). Fixed with a `useEffect` that reseeds
  `collapsedRegions` from `defaultCollapsedRegions(countryCode)` whenever `countryCode` changes.

- **[THE GENERALIZED MECHANISM — §2.0]**
  - `state` renamed to `region` throughout AU's 33 rows in both `cities.js` files (mechanical; nothing
    outside these two files + the two dropdown components read the literal key `state`, confirmed by
    grep before renaming).
  - `REGION_LABEL_BY_COUNTRY` — `{ AU: 'State', MY: 'State', CN: 'Province', FR: 'Région' }`, kept for
    aria-label use only; the visible group divider stays terse (just the region name), matching AU's
    existing convention.
  - `CN_POPULAR_PROVINCES` + `defaultCollapsedRegions(countryCode)` — the latter computes CN's
    non-Popular set from the LIVE data (`CITIES_BY_COUNTRY.CN`) rather than a hand-maintained second
    list, so the two can never drift apart.
  - `computeGroupedRows(list, { collapsedRegions, currentRegion })` — the disclosure-triangle logic
    (`groupStart`/`folded`/`open_` in the old inline version) extracted into a pure, testable function
    returning `{ type: 'divider', region, open, key }` / `{ type: 'row', city, index, folded }`
    descriptors. Both `CityDropdown` (Cuisine) and `CityDropdownMenu` (Menu) now render from the
    identical function instead of two hand-maintained copies of the same boolean logic — the exact
    failure mode this file's own header comment already warns about ("kept in sync only by comment
    convention").
  - Menu's `CityDropdownMenu` previously had **zero** grouping (33 AU cities rendered flat) and the
    older `(idx+1) % len` wraparound keyboard nav. Both ported: full disclosure-triangle rendering, and
    Cuisine's `step`/`edge` keyboard helpers that skip collapsed-row `null` holes in `itemRefs` — without
    this, arrow keys would have silently stranded focus on a folded row the moment Menu's picker gained
    its first foldable country.

- **[MALAYSIA — §2.1]** Restructured from 16 flat rows (all state/FT capitals) into 16 region groups
  (13 states + 3 Federal Territories), up to 5 real cities each, capital-first: **62 rows total**.
  Every new row reuses an already-vetted IATA code (from this file's own pre-existing rows or from
  `web/_shared/lib/iata-cities.js`) rather than asserting a new one, per the standing v0.61.242
  non-inventive rule — confirmed by re-running `__tests__/iata-cities.test.js`'s existing "cities.js
  only references codes that exist in iata-cities.js" invariant, which passed unchanged against every
  new row. Sabah and Sarawak are the exception: both already had 3-4 *distinct* vetted codes each
  (BKI/SDK/TWU; KCH/SBW/MYY/BTU) before this change, so their new rows use real per-city codes rather
  than reusing the capital's. **"Johor state" (the existing 120 km whole-state row) keeps its exact
  position and behaviour, deliberately given NO `region` field** — `computeGroupedRows()` only folds
  rows that carry one, so it stays an always-visible 16th-of-Johor row for free, with no special case
  needed in the grouping logic itself, exactly as the plan specified.

- **[CHINA — §2.2]** 31 region groups (22 provinces + 4 municipalities + 5 autonomous regions,
  HK/Macau/Taiwan excluded as already-separate country codes): **78 rows total**, Popular-first
  ordering, non-Popular ordered alphabetically. Every code likewise reuses a vetted IATA metro code
  (province/municipality capitals) or that capital's own code for a same-province satellite city — the
  existing `Suzhou → SHA` reuse already in this file before this change is the precedent this follows.
  Beijing/Shanghai/Tianjin/Chongqing's extra rows are well-known DISTRICTS (Chaoyang, Pudong, etc.),
  not separate satellite cities — administratively correct for a municipality, and mirrors how this
  file's existing HK block already lists districts under one shared code.

- **[FRANCE — §2.3, DATA-PREP ONLY]** `region` (French région) added to the existing 12 FR rows.
  Zero visible effect: `countries.js`'s FR picker entry stays commented out (v0.62.473, catalogue not
  settled) in both apps, confirmed unchanged by this entry. Validates the generic `region` mechanism
  against a 3rd real administrative structure (accented names — `Île-de-France`,
  `Provence-Alpes-Côte d'Azur`) before further rollout.

- **[SOURCING METHOD]** City names, capitals, and approximate coordinates for both Malaysia and China
  came from general geographic knowledge (well-established, stable facts — unlike volatile data such
  as Michelin awards, which this repo's own governing comments explicitly warn against guessing from
  memory). IATA codes were NOT invented from memory at any point — every code was cross-checked against
  `web/_shared/lib/iata-cities.js`'s existing vetted table before use, and the pre-existing automated
  invariant test (`__tests__/iata-cities.test.js`) that enforces this rule passed unchanged against
  every new row.
