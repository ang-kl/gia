## New

### [HDR] #4 | 23:10:00 SGT 29-04-26 | v0.4.1 | n/a kb | n/a lines
- **[INTENT]** Patch fix. Tapping a venue card in Telegram chat (sent via `bot.sendVenue`) was opening Google Maps at raw coordinates instead of the Place page. Reported by Human Lead with example URL `…/place/1°16'48.9"N+103°51'15.0"E/@1.280246,…` — the canonical "Telegram-built coords-only deep link" symptom. Same root cause affected the TWA "Open in Maps" link.
- **[DELTA]**
  - **`vibe.js`** — added `places.primaryType` to FIELD_MASK; mapped `primaryType` (default `'restaurant'`) onto each cached listing.
  - **`vibe-suggest.js`** — same addition for the Gemini-validated path.
  - **`index.js` `safeVenue`** — accepts `opts` and forwards to `bot.sendVenue(..., opts)`. `deliverPicks` now passes `{ google_place_id, google_place_type }` so Telegram's native venue card deep-links to the Place page on Google Maps.
  - **`public/app.js`** — InfoWindow "Open in Maps" link now built from `place_id` via `https://www.google.com/maps/place/?q=place_id:<id>`. Falls back to `googleMapsUri` only if `placeId` missing.
  - **`package.json`** — version → 0.4.1.
- **[RISK]** Low — patch-level UX fix. Telegram and Google Maps both honour the standard `google_place_id` and `q=place_id:` schemes; if either ever rejects the ID, behaviour falls back to the prior coords-only link, which is what we already had.
- **[STATUS]** PROD — auto-deploys with the next Railway build.
- **[TEST]** Manual — Human Lead to retap a venue card after redeploy and confirm the Maps page opens with the venue name + Place sheet (rather than coords).
- **[NEXT]** Phase 4 — GrabID PKCE for live quietness signal (Register Open #6).
- **[ADVICE]** Telegram's `sendVenue` is one of those APIs where the optional fields are doing 90% of the work. Always pass `google_place_id` when you have one; the fallback URL is hostile to non-power users.
