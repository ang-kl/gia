## New

### [HDR] #35 | 15:45:00 SGT 30-04-26 | v0.21.2 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead:
  > Issue: `[GoogleGenerativeAI Error]: Error fetching from https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-pro:generateContent: [503 Service Unavailable] This model is currently experiencing high demand. Spikes in demand are usually temporary`.
  > Resolution: wrap `generateContent` calls in retry-with-exponential-backoff (1s, 2s, 4s) — a simple loop won't suffice; 503s often clear within seconds.
- **[DELTA]**
  - **`gemini-retry.js`** (NEW) —
    - + `withRetry(fn, { delays = [1000, 2000, 4000], label = 'gemini' })` — runs `fn`, retries up to 3 times on 429/503, sleeping `delays[attempt]` ms between attempts. Other errors bubble immediately.
    - + `isRetryable(err)` — returns true if `err.status` is 429 or 503, or if the error message contains `[429 …]` / `[503 …]` (the SDK surfaces status both ways).
    - Worst-case added wait per call: 7 seconds. Fits inside Telegram's ~30 s server-side reply timeout.
  - **`gatekeeper.js classify()`** — `model.generateContent(...)` wrapped in `withRetry(..., { label: 'Gatekeeper' })`.
  - **`vibe-summary.js`** — same wrap, `label: 'Vibe-Summary'`.
  - **`vibe-suggest.js pickValidated()`** — same wrap, `label: 'Vibe-Suggest'`.
  - **`consultant.js findHiddenSanctuary()`** — same wrap, `label: 'Consultant'`.
  - **`ver.js`** — INTENTIONALLY unchanged. The `/ver` Gemini probe is a single-shot health check; retrying would mask transient 503s and produce false-green readings.
  - **`package.json`** — version 0.21.1 → 0.21.2.
- **[ROOT-CAUSE NOTE]** Gemini 2.5 Pro/Flash 503s are routine during regional capacity spikes (typically 10–60 s). Without retry, a single 503 propagates straight back to the user as "Sorry, I can't reach the model right now." With three retries on 1s/2s/4s, the call clears 80–95 % of transient capacity events while preserving fail-fast behaviour for actual errors (auth, depleted credits, malformed requests).
- **[RISK]** Low —
  - User-perceived latency on a 503 hit: +1 s (best case) to +7 s (worst case before final raise). Acceptable; users would see the same delay or longer if they retried manually.
  - Cost impact: each retry is a billable Gemini call. 503 retries are charged. Mitigation: 60 s SHA-256 cache in gatekeeper, 7-day Redis cache in vibe-summary, single-shot in vibe-suggest/consultant per `/eat` invocation. Worst-case extra spend: 4× normal Gemini cost during a sustained capacity event — but the alternative is total failure.
  - Health-probe accuracy preserved by NOT wrapping ver.js — `/ver` will still report 🔴 on a live 503, which is what we want.
- **[STATUS]** PROD — auto-deploys with the next Railway build.
- **[TEST]**
  1. `/eat` → share location → if Gemini returns 503, Railway log shows `[Vibe-Suggest] retryable error (attempt 1/4) — waiting 1000ms: …` and the user still gets picks within ~7 s of normal latency. Bot does NOT show "Sorry" message.
  2. Free-text "what should I eat" → if Gemini 503s, `[Gatekeeper] retryable error …` log + user still gets the normal classifier reply.
  3. `/ver` → if Gemini is currently 503, the Gemini row shows 🔴 with the actual error text (no retry hides the failure).
- **[NEXT]** None. If Gemini 503 rate becomes routine despite retries, the next escalation is a fallback to `gemini-2.5-flash` when Pro is selected and 503s twice in a row.
