## New

### [HDR] #24 | 11:30:00 SGT 30-04-26 | v0.16.0 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead doc + screenshot showing Google Maps opened at raw coords (`1°16'49.9"N 103°51'01.4"E`) — adopt Places API (New) `googleMapsLinks` structured field across all Place fetches and use Google's authoritative URLs (`directionsUri`, `placeUri`, `reviewsUri`, `photosUri`) instead of constructing Maps URLs ourselves.
- **[DELTA]**
  - **`vibe-suggest.js validateWithPlaces`** — added `places.googleMapsLinks` to FieldMask. Returns `directionsUri`, `reviewsUri`, `photosUri` on each venue object alongside the existing `url` (now prefers `googleMapsLinks.placeUri` with `googleMapsUri` fallback).
  - **`vault.js verifyOpenNow`** — Place Details FieldMask gains `googleMapsLinks`. Returns the four link fields on each open vault pick.
  - **`vault.js queryVault`** — surfaces stored `placeUri / directionsUri / reviewsUri / photosUri` from the `gia:place:*` hash on each pick.
  - **`consultant.js nearbyAnyOperational`** — same FieldMask addition. Hidden Sanctuary venues now propagate the four link fields.
  - **`sync-vault.js`** — Place Details FieldMask gains `googleMapsLinks`. `vaultUpsert` writes `placeUri / directionsUri / reviewsUri / photosUri` into the `gia:place:<id>` hash so they're available on every Vault read.
  - **`index.js deliverPicks`** — Directions inline button now uses Google's authoritative `p.directionsUri` when available, falls back to the constructed Search-action URL only if missing. Authoritative URL routes more reliably through iOS / Android Maps app handlers.
  - **`package.json`** — version → 0.16.0.
- **[WHY THIS MATTERS]** Per Places (New) docs, `googleMapsLinks.placeUri` ≡ legacy `googleMapsUri`, but the new field also exposes `directionsUri` (driving directions deep link), `reviewsUri` (reviews tab), `photosUri` (photos tab), and `writeAReviewUri`. Google's URLs are guaranteed-canonical and route correctly via Universal Links on iOS / App Links on Android. Constructing URLs ourselves (the prior `&query_place_id=` Search-action pattern) works most of the time but can degrade to coords-only on edge cases.
- **[SCREENSHOT NOTE]** The user's screenshot showed `https://www.google.com/maps/place/1°16'49.9"N+103°51'01.4"E/...` — that's Telegram's coords-only fallback URL when a venue card is tapped without a `google_place_id`, OR when the user-shared location pin is tapped (user-pins always lack place IDs by definition). Bot-sent venue cards already include `google_place_id` since v0.4.1; the user-pin behaviour is intrinsic to Telegram and cannot be changed bot-side.
- **[RISK]** Low —
  - `googleMapsLinks` is optional in field-mask responses; missing = empty strings, fall-throughs preserve existing behaviour.
  - Adds modest payload size to each Place Details / searchText response.
  - No new env vars, no schema migration; the Vault hash gains 4 new keys but old entries without them just return empty strings.
- **[STATUS]** PROD — auto-deploys with the next Railway build.

  2. Vault re-import (`sync-vault.js`) populates the new fields. Existing entries retain their old data without those keys; future runs add them.
