## New

### [HDR] v0.62.674 — footer-overlap peek gap + the pager's always-N/N denominator

- **[INTENT]** Operator did the real-device check on v0.62.673 (two screenshots) and reported two Cuisine
  TMA bugs: *"1. On loading first time, cards should have gaps to the footer as the Normal cards"* and
  *"2. The total pages in pagination for Michelin Stars should be calculated and then state. Right now
  is <1/1> <2/2> instead of <1/6>. Formula is the total count of Michelin Star/Bib Gourmand <2/6>."*

- **[BUG 1 — first-load peek flush against the footer]** Traced to `listPeekPx` (App.jsx ~:735-742,
  originally from v0.62.655/657): measured purely from card geometry (`cardHeight + 44px handle band`),
  with zero awareness that a SEPARATE `fixed bottom-0 z-30` footer stack paints ON TOP of whatever the
  `BottomSheet` reveals at its own bottom edge (same z-index; footer renders later in DOM, so it wins
  paint order). Fully-scrolled list content was never affected — `BottomSheet`'s own `footerPad` prop
  already reserves space for scrolled content — but the collapsed FIRST-LOAD peek height had no such
  reserve, so the footer visually ate into the gap the peek was supposed to leave. Fixed by measuring the
  footer's own real rendered height (new `footerRef`, same measurement technique already used for card
  height) and adding it into the peek reserve; a `ResizeObserver` on the footer keeps this correct
  whenever the footer's real height changes for any reason, chosen specifically to avoid adding
  `criteriaSummary`/`isMichelinMode`/`pages` to this effect's dependency array — all three are declared
  LATER in this same giant component, and this exact file already caught one TDZ crash from that shape
  of mistake (`tma-hook-deps-tdz.test.js`, v0.62.655's own Journal entry).

- **[BUG 2 — pager always showed N/N]** The denominator was `pages.length` — the count of batches
  actually FETCHED — which is, by construction, always exactly equal to the numerator (`cursor + 1`) at
  the cache tip. It could never have displayed anything but "1/1", "2/2", "3/3"… Switched to a new
  `michelinTotalPages`, derived from `michelinRemaining.total` (the server's own Michelin Star/Bib
  Gourmand count for the current criteria, already sent on every search response — no new field needed)
  divided by 12, the per-batch size `ResultPanel.jsx`'s own `PAGE_SIZE` constant already uses for this
  exact batch concept — matching the operator's stated formula exactly ("total count of Michelin Star/Bib
  Gourmand ÷ page size"). `Math.max` against `pages.length` is a defensive floor only. The pager's
  visibility gate moved to this real total too: it now appears from the very FIRST batch (once the
  server has reported more than one page's worth exists) instead of only after the user has already
  stepped forward once — a real improvement, not just a cosmetic fix, since the old gate meant the very
  first search never showed any page indicator even when 6 pages were known to exist.
