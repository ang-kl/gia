# Journal — soleat v0.60.166

Operator turn — three coupled UX fixes folded into one PATCH:

> 1. *"After typing in the location in the Search Criteria, instead of waiting for me to tap 'search' FAB or 'search' button. It fires and didn't register the new set location. This is an old PR error."*
>
> 2. *"First time loading the 'cuisine' tma, should grey off any selection until it is loaded. As the experience to click and interfere by the search result is annoying. This including clicking the 'edit search' or dropdown Search criteria."*
>
> 3. *"Correction on the text: 🐾pet allowed should be: 🐾Pet allowed"* (capital P on the chip label — v0.60.165 shipped lowercase per the first review pass; this is the second pass).

**Fix 1 — LocationField pick no longer auto-fires the search.** Picking a place in the Cuisine TMA's `LocationField` (tap on an autocomplete suggestion or Enter on the input) was wired in `App.jsx`'s `onSelect` callback to call `runSearchAt(p.lat, p.lng, p.label)`. That helper does two things in the same tick — `setLocationAnchor({…})` AND `runSearch(state, { lat, lng })` — so picking a location auto-fired a search instead of waiting for the user's explicit 🔍 Search tap. The same-tick `runSearch` also raced the React state update, occasionally running with the *previous* `locationAnchor` — which the operator saw as the new pick being "ignored". Fix: commit the anchor only — `setLocationAnchor({ lat, lng, name })` + `saveUserLocation(...)` — and stop calling `runSearchAt` from the LocationField `onSelect`. The user's explicit Search FAB tap (the existing handler at `App.jsx:413-415`) still reads `locationAnchor` and fires the search with the freshly-committed coords. `runSearchAt` itself is untouched — the map's "Search this area" control (`onSearchHere={runSearchAt}` at `App.jsx:942`) still wants the immediate fire.

**Fix 2 — First-load greyed-off overlay.** The previous in-flow "⏳ Please wait while loading list…" banner just sat inside the layout — every interactive element around it (Edit-search pill, Search-criteria dropdown chevron, the cuisine chips, the FAB) stayed tappable while the warm-start fetch was in flight. Operator reported repeatedly bumping into the partially-rendered UI and triggering unwanted state during the first 1-3 second window. Fix: replace the in-flow banner with a `fixed inset-0` viewport overlay (`z-50`, semi-transparent `bg-tg-bg/60`, `cursor-wait`) that covers the full screen, captures all pointer events, and centres the same "Please wait…" message in a card. Disappears the instant `firstLoadPending=false && loading=false`.

**Fix 3 — `Pet allowed` (capital P).** Operator's second-pass review on v0.60.165's chip label. The v0.60.165 first-pass said "🐾pet allowed" (lowercase); this pass says "🐾Pet allowed" (capital). i18n key `filter.petFriendly` updated: EN `"pet allowed" → "Pet allowed"`, FR `"animaux acceptés" → "Animaux acceptés"`.
