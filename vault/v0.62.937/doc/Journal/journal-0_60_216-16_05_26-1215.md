## New

### [HDR] #184 | 12:15:00 SGT 16-05-26 | v0.60.216 — free-text chat food-relatedness gate + `venue` intent | 5 files | 1 PR |

- **[INTENT]** When a user typed non-food text into the bot's free chat, the path handed the verbatim text to Google Places `searchText` → an off-topic message ("tell me a joke", "weather in Tokyo") returned a misleading restaurant list; and plain greetings ("hi", "thanks") got **no reply at all** (the v0.58.27 noise-guard silently `return`ed). Operator wants any non-food input to immediately get the polite *"🍛 Please try a dish name, cooking method, or food term…"* nudge.

- **[DELTA]** `index.js` — the free-text chat handler (`bot.onText` catch-all), two insertions:

  1. **Greeting / chat-noise → nudge.** The noise-guard (`looksLikePlaceQuery` reject) previously `return`ed silently. Now: a real chat-noise WORD (`FREE_TEXT_NOISE` member — "hi", "thanks", "menu", …) gets the `freetext.questionDeclined` nudge; truly degenerate input (emoji-only, punctuation-only, <3 chars, digit-only) stays silent — no point replying to "👍".

  2. **Food-relatedness gate (Option A).** Inserted after the deterministic food-detectors (nation-overlay / R.E.D disambig / misrepresented-dish / cooking-method) and before the raw `runFreeTextSearch`. When R.E.D did **not** resolve the query (`!disambigDisclosureFT`), it is classified once via `classifySearchIntent` (Gemini Flash — no Haiku, no cache). Verdict `dish` / `ingredient` / `tool` → food → proceeds to the search. Verdict `ambiguous` → non-food → the `freetext.questionDeclined` nudge, logged `non-food-declined`, no search. **Fail-open** — a classifier error logs a warning and proceeds to the search, so a Gemini outage never blocks a real food query.

  Placement rationale: running the gate *after* the deterministic detectors means a known SG dish/drink ("milo dinosaur", "kaya toast") routed by nation-overlay, an R.E.D-resolved ambiguous dish ("goulash dumplings"), or a cooking-method pivot are never gated — the LLM gate only judges text that no deterministic detector recognised, which is exactly the "might be off-topic" population. It also limits the Gemini call to that population.

  3. **`venue` intent added to `classifySearchIntent`** (`gemini-client.js`). Operator follow-up in the same turn — *"Include venue name in the lookup for searchintent."* The classifier previously had only `dish` / `ingredient` / `tool` / `ambiguous`, so a bare restaurant name with no dish word ("Newton Food Centre", "Burnt Ends") fell to `ambiguous` and the gate declined it. A new `venue` intent — *"a restaurant, café, bar, bakery, kopitiam, hawker centre, or food court … proper-noun place names of eateries even when they contain NO dish word"* — is added to the prompt's intent list, the output-JSON shape, a `WHEN A VENUE IS NAMED` searchTerm rule, and the return-shape coercion whitelist (`['dish','ingredient','tool','venue','ambiguous']`). A venue name now classifies `venue` → not `ambiguous` → the gate proceeds to the Places search. `__tests__/gemini-client.test.js` — 3 new `classifySearchIntent` tests (venue preserved, unknown intent → ambiguous, dish/ingredient/tool intact).

  Plus `package.json` `0.60.215 → 0.60.216`; this Journal entry (#184); `doc/.serial-state.yml` (`journal 183→184`, `commit 190→191`; re-anchored).
