## Amendments

### `cuisineSearchVariants` — accept multi-cuisine array

> Prior (≤ v0.60.117 → v0.60.145): `cuisineSearchVariants(cuisineName)` accepted a single string only; the call site at `/api/cuisine/search` gated the helper with `(cuisinesForDiscover.length === 1)`, so multi-cuisine returned the no-cuisine fallback `[{ idx: 0, queryOverride: null }]` — effectively NO variant escalation, and the pool topped out at the first Places search. This is the root of the operator's "Japanese + Korean stuck after 3–4 clicks" report.
>
> Change (v0.60.146): the helper accepts an array of cuisine names; they are joined with " + " for the variant prompts ("best Japanese + Korean restaurant Singapore", …). The call-site gate at line ~8706 is `length >= 1`. Single-cuisine behaviour is unchanged.

### `/api/cuisine/search` dedup fallback at line ~8951

> Prior (≤ v0.60.145): `const top = (unseenVenues.length ? unseenVenues : venues).slice(0, 12)` — when the per-criteria `unseenVenues` was empty (every venue in the current variant's pool already in the seen-set), the handler **silently fell back to `venues.slice(0, 12)`**, re-serving 12 venues the user had already seen. `exhausted: true` only flowed when `atLastVariant` was also true, which depended on the variant count being correctly set for multi-cuisine (it wasn't — see the `cuisineSearchVariants` amendment above). End result: the TMA kept rendering the same 12 cards.
>
> Change (v0.60.146): the outer session-clipboard 80-cap (`cuisine:session-seen:<chatId>`, reset on TMA launch) filters again — `trulyUnseen = unseenInCriteria.filter(v => !sessionSeen.has(v.placeId))`. The new `top = trulyUnseen.slice(0, 12)`; when empty, `top = []` and `exhausted: true` flows from `dedupExhausted = (… && trulyUnseen.length === 0 && atLastVariant) || sessionFull`. The TMA's existing terminal-note path therefore takes over instead of looping on stale cards.

### `handleMichelinSearch` — joins the session clipboard

> Prior (≤ v0.60.145): Michelin path managed its own per-criteria seen-set (`cuisine:seen:<chatId>:<criteriaHash>`) but had no per-session ceiling. The operator's note "sensitive with Michelin criteria" pointed at the asymmetry: closing & re-opening `/cuisine` should reset everything visible in the same session, including Michelin.
>
> Change (v0.60.146): after `appendSeenSet(csChatId, criteriaHash, …)`, also fire-and-forget `cuisineSession.recordPage(redis, csChatId, …)` with a slim Michelin venue payload. The response gains `sessionFull` + `pageStackDepth` so the TMA's ⇠ Prev FAB and the terminal-note path behave identically on Michelin and cuisine-chip results. The per-criteria seen-set still drives Michelin's own "all N curated venues shown" terminal.
