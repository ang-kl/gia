## New

### [HDR] #73 | 22:00:00 SGT 01-05-26 | v0.34.0 | n/a kb | n/a lines
- **[INTENT]** Third leg of the v0.32-v0.36 roadmap. Per the original ask:
  > "Third, construct the /recognised Global Excellence Database. Build a high-priority 'Hall of Fame' table in Redis containing restaurants, hawkers, and cafes that have received accolades over the past 8 years. Specifically scout and store data for the World Culinary Awards, UNESCO Intangible Cultural Heritage listings, The Best Chef Awards, Michelin Stars, and Michelin Bib Gourmand recipients."
  
  And per the AskUserQuestion answer this session: **Gemini drafts; user verifies via redis-cli before promotion to live**. So v0.34.0 ships the *schema + seeder + admin endpoints*, NOT the user-facing `/recognised` slash command — that lands in v0.35.0 once the curated data exists.

- **[DESIGN]**
  1. **Two-stage data flow**:
     - **Staging** (`recog:staging:<placeId>` HASH + `recog:staging:list` SET) — Gemini-drafted entries land here for human review.
     - **Live** (`recog:venue:<placeId>` HASH + `recog:venues:geo` GEO set) — promoted entries available for nearest-N geo queries.
     - **Rejected** (`recog:rejected:<placeId>` HASH, 90-day TTL) — kept for audit; ineligible for live but visible if Gemini re-scouts.
  2. **6 award categories supported**:
     - `michelin-star` (1/2/3 levels) — 8-year window, ~60 SG winners
     - `bib-gourmand` — 8-year window, ~80 entries
     - `asia-50-best`
     - `world-culinary-awards`
     - `best-chef-awards`
     - `unesco-ich` — special-cased: 2020 inscription of Singapore Hawker Culture; we curate the iconic centres most cited as exemplars
  3. **Multi-award merge** — when a Gemini scout for `bib-gourmand` produces "Hill Street Tai Hwa Pork Noodle" and a later scout for `michelin-star` produces the same venue (same placeId), the new award is APPENDED to the existing staging entry's `awards` array rather than overwritten. So one venue can carry many accolades.
  4. **Honest Gemini framing** — the seeder prompt explicitly says "Include only venues you are confident are real. If unsure, OMIT the entry. DO NOT invent venues. DO NOT fill in years if you don't know." Combined with the manual promotion gate, this is the right architectural shape for hallucination-tolerant data ingestion.
  5. **Auth-gated admin endpoints** — same `ADMIN_SYNC_SECRET` + timing-safe compare as v0.28.2 `/admin/sync-vault`. No new env var needed.

- **[DELTA]**
  - **NEW `recognised-store.js`** — pure Redis CRUD. Functions: `setStaging`, `listStaging`, `getStaging`, `promote`, `reject`, `getLive`, `listLive`, `nearestLive`, `counts`. Validates entries via `validateEntry()` (placeId, name, lat/lng, ≥1 award with valid category). `nearestLive` uses raw `GEOSEARCH FROMLONLAT BYRADIUS` since node-redis exposes `sendCommand` for that.
  - **NEW `recognised-seeder.js`** — Gemini-driven scout. `CATEGORIES` map (6 entries). `buildScoutPrompt(category)` returns the per-category prompt. `scoutCategory(category)` calls Gemini Flash with `responseMimeType: application/json` (no grounding tools — same v0.31.2 lesson) and lenient JSON parse. `resolvePlaces(rawEntries)` runs `geocodeQuery()` (existing helper from `vibe-suggest.js`) per entry with concurrency 3 to fetch placeId + lat/lng. `runSeed({redis, category})` orchestrates per-category scout → resolve → setStaging. `runSeedAll({redis, categories?})` runs all 6 categories sequentially.
  - **`index.js`** — three new admin endpoints:
    - `POST /admin/seed-recognised?secret=<x>&category=<one|all>` runs the seeder, returns `{results, totals, counts}`.
    - `GET /admin/list-staging?secret=<x>&limit=<n>` returns pending entries for redis-cli inspection.
    - `POST /admin/promote-recognised?secret=<x>&placeId=<id>&decision=accept|reject` moves staging → live or to rejected (with reason).
    - Helper `adminAuth(req, res)` extracted to dedupe the timing-safe compare.
  - **Versions** — package.json + web/cuisine/package.json + web/menu/package.json bumped 0.33.0 → 0.34.0.

- **[KNOWN GAPS]**
  - **Gemini hallucination risk is real.** The whole point of staging+promote is to catch this. Spot-check sample entries before promoting in bulk.
  - **No batch-promote endpoint.** Each placeId requires its own `/admin/promote-recognised` call. For a one-time bulk acceptance after an initial seed, consider piping `list-staging` through `jq -r '.entries[].placeId' | xargs -I{} curl ...`.
  - **`asia-50-best` award category coverage is thin** in Gemini's training data; expect <30 entries even with target=30.
  - **`unesco-ich` is special** — UNESCO inscribed Singapore Hawker Culture (2020) as a cultural practice, not a list of venues. The seeder pattern of "iconic centres most cited as exemplars" produces a small list of well-known centres; this overlaps with the v0.33.0 hawker dataset and is acceptable.
  - **No de-duplication across categories during a single seed run** — `runSeedAll` runs categories sequentially, so a venue scouted in `michelin-star` and again in `bib-gourmand` will correctly merge (same placeId → existing staging found, awards array appended). But within a single category, if Gemini returns the same venue twice (with different years), only the first is kept; the second triggers `existing` branch and appends. Acceptable.
  - **Geocoding cost.** Each Gemini-drafted name triggers one Google Places `searchText` call (~$0.017/call). A full seed across 6 categories with ~200 raw entries costs ~$3.40 — one-time spend. Future re-seeds for refresh would add the same.
  - **`recog:venues:geo` GEOSEARCH compatibility** — node-redis v4 may need `sendCommand(['GEOSEARCH', …])` instead of a wrapper. Verified syntax in this implementation; if it fails on the live Redis, the fallback is to fetch all live entries via `listLive` and haversine-sort client-side.
