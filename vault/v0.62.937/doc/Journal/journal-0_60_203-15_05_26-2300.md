  ### Explanation surfaced to operator (recorded here for posterity)

  **"Good window"** is from `headOutLine()` in `weather.js:331` — a 3-state heuristic:
  - `☔ Raining around …` when current rainfall > 0.2 mm at the nearest NEA station.
  - `🌦️ Dry now, but …` when currently dry but NEA's 2-hour forecast for the user's area contains wet-weather keywords.
  - `✅ Good window — … looks dry for the next 2 hours.` when currently dry AND 2-hour forecast is also dry. Means: safe to head out for ~2 h.

  **"@ S129"** is the NEA weather station ID of the nearest physical sensor to the user's lat/lng. `nearestStation()` in `weather.js:142` picks the closest station from each NEA realtime feed (air-temp, humidity, rainfall, wind dir, wind speed) by haversine distance. The S-codes are NEA's own internal station IDs (`S60` Sentosa, `S109` Ang Mo Kio Ave 5, `S129` near the user's recent location, etc.); we surface them as attribution so users know the reading comes from a specific physical sensor.

  ### TMA load-speed audit findings (no-fix; operator decides)

  **Bundle sizes** (gzipped, on-the-wire):
  | TMA | Raw | Gzipped | Cellular 3G ≈ |
  |---|---|---|---|
  | Menu | 155 KB JS + 8.7 KB CSS | ~50 KB | ~0.4 s |
  | Cuisine | 147 + 73 + 32 KB JS + 16 KB CSS | ~85 KB | ~0.7 s |
  | Hawker | 158 KB JS + 8.6 KB CSS | ~50 KB | ~0.4 s |
  | Train (in Menu hub) | inline panel | — | — |
  | Oversight | 99 KB JS | ~30 KB | ~0.3 s |

  Bundle sizes are modest — not the bottleneck.

  **Primary slowness: missing cache headers on static asset routes.** `index.js:8204, 8216, 10928, 10935, 10944` mount `express.static(...)` for `/app/menu`, `/app/cuisine`, `/app/hawker`, `/app/transport`, `/app/oversight` without a `maxAge` option. Result: NO `Cache-Control` header on the hashed JS/CSS bundles. Every TMA open re-validates with the server (300-800 ms 304 round-trip on cellular). Vite's content-hashed filenames (e.g. `index-DqeRTlrw.js`) make these PERFECT candidates for `Cache-Control: public, max-age=31536000, immutable` — they never change at the same URL; a code change re-hashes the filename. Fix would be a one-line change per `app.use`. Estimated user-felt speedup: 0.3-1 s per TMA open on warm browser cache.

  **Secondary slowness factors (gating first paint)**:
  - **Cuisine TMA**: fetches `/api/cuisine/catalogue` on mount, then `/api/cuisine/warm-start` (geolocation 5-s timeout). Total time-to-first-result ≈ 1-3 s after JS executes.
  - **Hawker TMA**: loads 122 hawker centres + geocodes from `/api/hawker/...`. ~1-2 s.
  - **Menu TMA**: pulls Train status `/api/train` on mount. ~0.5-1 s.
  - **Cuisine search results**: BestTime footfall enrichment + travel-times + price-range can add 3-5 s on cold cache. Already best-effort but blocks the response.

  **Railway cold start**: if no traffic for ~30 min, the first request after dormancy includes ~3-8 s of container spin-up. Not a code issue; addressable via Railway "always-on" config.

  Recommended one-line wins (operator-decide): add `maxAge: 31536000` + `immutable: true` to all five `express.static` mounts for `/app/*`. Zero-risk change because the filenames are content-hashed (Vite default). Expected effect: warm TMA opens drop from "perceptible" to "instant".
