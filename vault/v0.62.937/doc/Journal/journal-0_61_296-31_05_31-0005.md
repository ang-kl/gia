> v0.61.296 ships the chat-surface integration the v0.61.285 + v0.61.295 fun-facts work was preparing for. New file `bot-fun-facts.js` is the server-side selector + message-sender. The cuisine TMA modal (in-app) and the bot DM "💡" message (chat) now both surface from the same 52-fact catalogue.
>
> Architecture:
>
> - **Selector logic stays in `web/cuisine/src/v2/lib/fun-facts.js`** — that's the single source of truth (v0.61.293's lesson). `bot-fun-facts.js` (CJS) loads `_pickFact` from the cuisine TMA lib via dynamic `import()`. No logic duplication.
> - **Anti-repeat persistence**: per-chat-id Redis list `funfact:lastSeen:<chatId>`, 1-day TTL, 10-entry cap. Independent of the TMA's `localStorage` dedup — same fact can appear in both surfaces, that's fine.
> - **Wire point**: `runCuisineFlow` (line 1385) — right after `deliverPicks` returns, fire a follow-up "💡" via `sendFunFactReply`. Best-effort: a Redis or Telegram error never blocks the cuisine result.
> - **Scope**: `/c <cuisine>` DM flow only. Other entry points (`/s` free-text, `/hidden`, `/cuisine` opens TMA) untouched in Phase 2B per operator's implicit acceptance of my proposal.

- **[DELTA]**

  **1. `bot-fun-facts.js` (NEW, ~120 lines)** — top-level CJS module.
  - `_loadLib()` — dynamic `import()` of the cuisine TMA's `lib/fun-facts.js`, cached. Returns `{ _pickFact }`.
  - `_readLastSeen(redis, chatId)` — reads up to 10 fact IDs from Redis list `funfact:lastSeen:<chatId>`. Returns `[]` when Redis is closed.
  - `_persistLastSeen(redis, chatId, factId)` — `LPUSH` + `LTRIM 0 9` + `EXPIRE 86400`. Best-effort.
  - `pickFunFactForChat({ redis, chatId, cuisines, region, countryPref })` — builds `ctxTags`, reads `lastSeen`, calls `_pickFact`, persists the picked ID. Returns the fact or `null`.
  - `_formatHtml(fact, lang)` — produces `<b>💡 Did you know?</b>\n\n<body>\n\n<a href>Source: NLB</a>` HTML for Telegram parse_mode='HTML'. Escapes body content. EN/FR + EN fallback.
  - `sendFunFactReply({ bot, redis, chatId, lang, cuisines, region, countryPref })` — orchestrates pick + format + `bot.sendMessage`. Best-effort; logs and returns `null` on any failure.

  **2. `index.js:runCuisineFlow` (line 1385)** — after `deliverPicks(chatId, meal.label, venues)`, a new `try/catch` block:
  ```js
  try {
    const { resolveLang } = require('./user-prefs');
    const ffLang = await resolveLang(redis, chatId, null).catch(() => 'en') || 'en';
    const { sendFunFactReply } = require('./bot-fun-facts');
    await sendFunFactReply({
      bot, redis, chatId, lang: ffLang,
      cuisines: cuisineType ? [String(cuisineType).toLowerCase()] : [],
      region: null, countryPref: null
    });
  } catch (err) {
    console.warn('[runCuisineFlow] funfact append failed:', err && err.message ? err.message : err);
  }
  ```
  Region + countryPref are `null` for now — the bot has no region context for the `/c` flow. The selector falls through to Tier-3 (full pool) when there's no cuisine match. Cuisine tag (`cuisineType`) lowercased to match the data file's tag conventions.

  **3. `__tests__/bot-fun-facts.test.js` (NEW, ~150 lines)** — 14 assertions covering:
  - `_formatHtml`: EN/FR/unknown-lang/null-fact/HTML-escape/missing-sourceUrl.
  - Redis anti-repeat: closed-Redis no-op, lPush+lTrim trimming to 10, falsy-factId no-op.
  - `pickFunFactForChat`: returns the picked fact even when Redis is closed (best-effort contract); persists on success; non-repeating across consecutive calls.
  - `sendFunFactReply`: calls `bot.sendMessage` with HTML body + correct opts; returns `null` + doesn't throw when `bot.sendMessage` rejects.
