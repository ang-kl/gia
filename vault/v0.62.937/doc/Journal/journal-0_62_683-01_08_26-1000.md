## New

### [HDR] v0.62.683 — two free-text fields unified; the v0.62.678 iOS zoom guard turns out to be inert

- **[INTENT]** Operator, with cropped side-by-side screenshots of both fields: *"compare the two
  free-text-entry-fields (search versus location). i want search's free-text-entry-field to follow
  exactly the location's (font, font size, border shape, border colour, border size) to be
  consistent."*

- **[COMPARISON — three of the five already matched]** Read both components rather than judging from
  the screenshots (the two crops are at different zoom levels, so relative text size in them is not
  evidence). `TellMePanel.jsx`'s composer wrapper vs `LocationField.jsx`'s resting field (its
  `hasLoc` branch):

  | Property | Location field | Search field (before) | Verdict |
  |---|---|---|---|
  | font family | inherited | inherited | already same |
  | font size | `text-sm` (14px) | `text-sm` (14px) | already same |
  | border shape | `rounded-md` | `rounded-md` | already same |
  | border **size** | `border` (1px) | `border-2` (2px) | **differed** |
  | border **colour** | `border-tg-border` | `border-tg-hint/60` | **differed** |

  So the fix is one line: `border-2 border-tg-hint/60` → `border border-tg-border`. Worth recording
  that the *apparent* difference in the screenshots was largely something else — in both crops the
  visible blue stroke is a STATE effect, not the resting border: the location shot catches the
  `editBlink` `ring-1 ring-tg-accent` ("tap to change" affordance) and/or the shared P1-c
  `:focus-visible` outline, and the search shot shows a focused input (text caret present) wearing
  that same 2px accent focus outline. Neither is the resting style, and neither was changed.

- **[DELIBERATELY NOT CHANGED]** `bg-tg-card` and `px-3` on the composer. Neither is in the
  operator's five-property list, and both are load-bearing here: the composer floats OVER the map, so
  it needs the opaque card fill (the location field's `bg-tg-bg/40` sits on the page background and
  would read as translucent over map tiles), and `px-3` is tuned to this bar's icon+input+FAB row
  rather than the location field's flag+text row. Flagged rather than silently harmonised.

- **[FINDING — the v0.62.678 iOS auto-zoom guard is inert, and it is mine]** While confirming the
  font sizes, found that `styles.css`'s guard — `input, textarea, select { font-size: 16px; }`,
  shipped by me in v0.62.678's Phase A to stop iOS zooming the viewport on input focus — **does
  nothing on the inputs it was written for.** Both rules are present in the compiled CSS:
  `input,textarea,select{font-size:16px}` (element selector, specificity 0,0,1) and
  `.text-sm{font-size:.875rem}` (class, specificity 0,1,0). The class wins regardless of source
  order, so every Cuisine text input carrying `text-sm` — including TellMePanel's, the exact input
  the v0.62.678 comment names as the motivation — still renders at 14px and will still trigger iOS
  auto-zoom on focus. The comment in `styles.css` asserts a fix that the CSS cascade never delivered.
  **Not fixed in this entry, deliberately:** every route to fixing it (`!important`, a
  higher-specificity selector, or changing the inputs to `text-base`) raises those inputs to 16px,
  which would directly contradict the font size the operator has just asked to keep aligned with the
  location field. Surfaced to the operator with options instead of resolved unilaterally. Tracked as
  **O-104**.
