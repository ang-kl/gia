- **[INTENT]** The operator reported the SG Michelin listing (a) didn't start from 3★ and (b) had no paging controls. The read-only trace proved the server order is correct (3★→2★→1★→shuffled Bib, `index.js` `stars.sort(TIER_ORDER)` + `ordered=[...stars,...bib]`, no downstream re-sort, TMA `ResultPanel` renders in received order) — so page 1 of a fresh walk **does** start at 3★. The real defect: `michelinSummary.remaining` is hardcoded `0`, so the TMA's "📚 N more to explore — Tap 🔍 for next batch of 12" hint (gated on `michelinRemaining.remaining > 0`) **never appears**; with no page indicator, a re-tap silently advances the seen-set walk past the already-served 3★ slice, which reads as "the list stopped starting from 3 stars". Both complaints = this one line.

- **[MECHANISM]** The `remaining: 0` hardcode dates to **v0.60.195**, set when the seen-set walk was DISABLED. **v0.60.198 RESTORED** the walk (the `michelin-walk.js` seen-set + `recordWalk` advance every tap) but never updated this summary line, leaving an inconsistent state: pagination advances server-side while the UI is told there is nothing more. The fix computes the honest remaining over the tier-ordered `ordered` pool the walk actually paginates: `remaining = exhausted ? 0 : Math.max(0, ordered.length - totalServedThisWalk)`. `totalServedThisWalk = walkState.seen.size + newKeys.length` (already computed just above for `walkExhausted`), so the value is consistent with `exhausted` by construction — when the walk ends (or `filteredVenues.length < 3`), `remaining` is `0` and the `<3-result` / walk-end recycle UX is unchanged. The `michelinSummary` object still ships on every Michelin response (never null), so the TMA's `michelinRemaining`-truthy gate that suppresses the combo-`<12` autoReset hint is preserved.
