# Journal — v0.62.708 (O-144: the cap was truncating a string, not the object it came from)

_(№ 1,047 — 07-08 '26 09:00 SGT)_

## New

### [HDR] v0.62.708 — fix `clip-store.js`'s venue JSON truncation (O-144)

- **[INTENT]** Operator, in a "next build" list of three independent items: *"O-144 (venue JSON
  truncated as a string, silently dropping coordinates — a real data bug in the store)"*. O-144 was
  logged as a Register open item during the itinerary-map session (v0.62.704 arc) and had carried
  forward unchanged through v0.62.705–707. This entry closes it.

- **[THE BUG]** `normaliseRecord()` wrote a structured venue as `JSON.stringify(record.venue).slice(0,
  6000)` — the cap was applied to the **stringified result**, after `JSON.stringify` had already run.
  Slicing a JSON string at an arbitrary byte offset can land mid-token (mid-string, mid-number,
  mid-escape) and produce text that is no longer valid JSON. `denormaliseRecord()`'s matching
  `JSON.parse` then threw, was caught, and silently returned `undefined` — indistinguishable from "no
  venue was ever attached." A card with a genuinely oversized venue would drop its coordinates with no
  log trail explaining why. Confirmed likely dormant in practice (a fully-populated venue serialises to
  ~1.5KB against the 6000-char cap) but real: `vibe`, `nameGloss`, `nameReading`, and `signatureDish`
  are all free-text LLM output with no explicit upstream length cap.

- **[THE FIX]** Two changes, both in `clip-store.js`:

  1. **`normaliseRecord`** — validate the FULL stringified length *before* deciding what to write,
     rather than truncating after the fact. If the JSON fits under the cap, write it whole; if it
     doesn't, drop venue entirely (`venue = ''`) — the same path already taken when `record.venue` is
     absent. A dropped venue degrades to a text-only card, exactly as before v0.62.429 ever added
     structured venues; a truncated one degrades to nothing, silently, which is strictly worse. Cap
     raised 6000 → 10000 for headroom over the realistic payload.

  2. **`denormaliseRecord`** — the venue `JSON.parse` catch block was the one catch in this
     635-line file that swallowed its error silently. Every other catch in the file logs via
     `console.warn('[Clip-Store] <fn> failed:', err.message)`; this one now matches that convention,
     so a future corrupt-venue case (e.g. a pre-v0.62.708 clip written under the old buggy cap) leaves
     a trace instead of looking identical to "nothing was ever there."

- **[DELTA]** (2 files)
  1. `clip-store.js` — `normaliseRecord`'s venue branch (validate-then-drop, cap 6000→10000);
     `denormaliseRecord`'s venue branch (`console.warn` on parse failure). Both sites carry a
     v0.62.708 comment explaining the mid-token-truncation failure mode.
  2. `__tests__/clip-store.test.js` — new `describe` block (4 tests): normal-size venue round-trips;
     an oversized venue (12000-char `signatureDish`) degrades to `venue: ''` on write / `undefined` on
     read without throwing; a venue string corrupted directly in the fake Redis hash degrades to
     `undefined`, without throwing, and triggers the new `console.warn`; existing no-venue cases
     (absent / `null` / non-object) are unaffected. This field had **zero** test coverage before this
     entry, despite the file covering every other cap.
