# Journal — v0.62.705 (the footer's cabinet became switchable)

_(№ 1,044 — 04-08 '26 14:25 SGT)_

## New

### [HDR] v0.62.705 — long-press footer tab 2 to switch cabinet

- **[INTENT]** Operator: *"the second button in the footer which shows default cabinet should be
  switchable"*.

- **[WHAT WAS THERE]** Footer tab 2 renders the **default** cabinet's emoji + name
  (`footerCabinetLabel` ← `state.defaultCabinetId`) and taps through to it. Changing which cabinet
  that is required Cabinets → open a cabinet → tap ★: three screens away from the button it
  controls, and the button gave no hint the setting existed.

- **[TWO READINGS, BOTH PUT TO THE OPERATOR]** "Switchable" could mean *set which cabinet is
  pinned* or *jump to another cabinet without disturbing the pin* — materially different, since the
  first writes `defaultCabinetId` (which also drives the header title and the next app open) and the
  second does not. And the gesture was a separate choice. Both were asked rather than guessed:

  | question | ruling |
  |---|---|
  | interaction | **Long-press the tab → picker.** Tap keeps today's behaviour. |
  | semantics | **Switching sets the default** — the same write ★ makes, not a rival notion. |

- **[DELTA]**
  - **`web/clipboard/src/lib/long-press.js`** (NEW) — the timing half of press-and-hold, pure and
    framework-free: 500 ms delay, 10 px movement tolerance, and `consumeClick()`. `setTimer` /
    `clearTimer` are injected so the tests drive time directly instead of sleeping.
  - **`web/clipboard/src/components/CabinetSwitchSheet.jsx`** (NEW) — the picker. Bottom sheet, not
    a popover: it is a footer control, there can be up to 12 cabinets, and the app already has
    exactly this shape in `LocationSheet` / `FilterSheet` (same `.sheet` / `.sheet-scrim`, same
    `z-50`, same `useDialog` contract for Escape and outside-tap). Each row carries the **same ★**
    the cabinet header uses, so the two controls read as one setting.
  - **`web/clipboard/src/components/Shell.jsx`** — `FooterTab` gains an **optional** `onLongPress`.
    Only tab 2 passes it; a plain tap is byte-identical for every tab.
  - **`web/clipboard/src/App.jsx`** — `switchOpen` state; picking navigates first, then persists.
  - **`web/clipboard/src/lib/i18n.js`** — 4 new keys × 8 locales.
  - **`__tests__/long-press.test.js`** (NEW) — 13 tests.

- **[THREE ROUTES INTO ONE ACTION]** A hold is touch-only, and a gesture no keyboard can perform is
  not a feature. So the same picker opens on **press-and-hold** (phone), **right-click / context
  menu** (desktop, and the semantic equivalent of a hold), and **ArrowUp** while the tab has focus —
  advertised through `aria-haspopup="dialog"` and `aria-keyshortcuts="ArrowUp"`.

- **[THE TWO THINGS THAT WOULD HAVE BITTEN ON A DEVICE]** Both are invisible in a screenshot and
  both are now tested:
  1. **A press that drifts is a scroll.** The footer sits at the bottom of a scrolling screen; a
     finger that lands on tab 2 and drags is scrolling, not holding. Drift is measured from the
     **origin**, not the previous move — otherwise a slow crawl of 4 px steps never trips the
     tolerance and the sheet fires mid-scroll.
  2. **The click after a hold must be swallowed.** The browser still sends a click on release, so
     without `consumeClick()` one hold would open the picker *and* navigate — the sheet appearing
     over a screen the user never asked for. It clears on read, so the next genuine tap is never
     eaten, and `fired` is set *after* the callback so a throwing callback cannot leave the tab
     permanently unable to navigate.

- **[KNOWN GAPS]**
  - **Not verified on a device.** The probe is headless Chromium driving a mouse; a real thumb on a
    real iOS WebView is a different thing, and Telegram's own long-press handling (text selection,
    the native context menu) is not reproduced here. `WebkitTouchCallout: 'none'` and
    `touchAction: 'manipulation'` are set defensively but unproven on hardware.
  - **500 ms is inherited, not measured.** It matches Cuisine's map long-press so the app is
    internally consistent, but no one has been timed holding it.
  - The picker lists cabinets in `state.cabinets` order — the same order the Cabinets grid defaults
    to — with no sort control. With the cap at 12 that is probably fine; it is not a decision anyone
    has made.
