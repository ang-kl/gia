# Journal — soleat v0.60.194

> Operator: Michelin selection in Cuisine TMA has regressed since v0.60.172. Diagnosed as the v0.60.188 `autoResetOnLowCount` logic spilling into the Michelin paging flow (which has its own deterministic 130-venue pool + walk-through indicator). Fix: suppress auto-reset + the visible <12 hint when `michelinRemaining` is set.

## New

### [HDR] #161 | 17:20:00 SGT 15-05-26 | v0.60.194 — Michelin pagination: suppress autoReset + <12 hint while michelinRemaining is set | 3 files, ~10 LOC | 1 PR |

- **[INTENT]** Triangulated via diff `ebe6ca8` (v0.60.172, last operator-confirmed stable) → `cdd4af2` (v0.60.193). Four Michelin-touch PRs across the window; one regression source:

  - PR #437 / v0.60.188 added `autoResetOnLowCount`: when `venues.length < 12 && !exhaustedNote`, the next 🔍 tap auto-fires `resetSeen: true`. **No Michelin exception was wired** — and `handleMichelinSearch` never sets the `firstBatch` flag that v0.60.191 added for the cuisine-chip path, so the threshold stayed at 12 for Michelin too.

  - Trace on current main: Michelin's 130-entry catalogue paginates as 10 × 12-venue batches + 1 × 10-venue tail. The 10-venue tail (tap 11) has `10 < 12`, `firstBatch=false`, `exhaustedNote=false` (server's `exhausted` flag fires only when `< 3`). So `autoResetOnLowCount = true` arms silently. **Tap 12** then sends `resetSeen=true` → `handleMichelinSearch` wipes the seen-set → returns the first 12 Michelin venues again. The user's pagination state is destroyed without warning.

  - Same loop fires earlier for combo searches (e.g. Michelin + Japanese) that trim the slice below 12 on tap 1 — exactly the v0.60.191 cuisine-chip first-batch loop pattern, just unpatched on the Michelin side.
