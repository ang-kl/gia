## New

### [HDR] v0.62.657 — the device check that O-56 asked for, and what it turned up

- **[INTENT]** Operator, with a screenshot (`IMG_3693`) of the Cuisine list mode: *"i pull down the drawer
  handle to make it smaller, instead the whole TMA pull down. i wanted only 1 card height instead of current
  50% of the map which i cannot see the map"*

- **[THIS IS THE O-56 DEVICE CHECK]** v0.62.655 shipped the Cuisine over-the-map drawer with an explicit,
  written caveat: *"the drawer's rendered state is UNVERIFIED… this is the change most likely to need a
  second pass."* This message **is** that pass, and it confirms the caution was warranted — the shipment was
  **broken in two independent ways**, neither of which threw an error or failed a test.

- **[BUG 1 — dragging the handle drags the whole Mini App]** `web/cuisine/src/api/tg.js` never called
  `disableVerticalSwipes()`. Hawker and Transport both call it (v0.62.610) because **Telegram's own
  vertical swipe-to-minimise gesture competes with a draggable `BottomSheet` handle for the same downward
  drag — and, being native, always wins.** Cuisine never needed this before v0.62.655 because it never had a
  draggable drawer; the moment it gained one, it inherited the exact bug the other two apps had already
  fixed. Now wired identically, feature-detected for Bot API 7.7+.

- **[BUG 2 — the drawer never actually collapsed to a card height]** The peek-height measurement used the
  selector `'[data-venue-card], article, .skeuo-card'` — and **none of the three exist anywhere in
  `ResultCard.jsx`**, grep-verified. Its root is a plain
  `<button data-pid={venue.placeId} className="w-full text-left rounded-lg border …">`. `listPeekPx` was
  therefore **permanently `null`** in production, and the sheet was always on its `0.80` **fallback fraction**
  — nowhere near "1 card". That is exactly what the operator's own screenshot showed: a drawer covering
  roughly half the map instead of a one-card peek.

  Fixed to `[data-pid]` — the same selector `ResultPanel.jsx` **already uses** for its own scroll-into-view
  logic, so it is the one place in the codebase guaranteed to keep matching a real card if this markup
  changes again. The multiplier also drops **1.5 → 1** per the operator's revised ask ("only 1 card height").

- **[THE LESSON — this is the same failure class, again]** A declaration or selector that **matches nothing**
  fails silently and degrades to a fallback that *looks like a design choice* rather than a bug. This is the
  fourth occurrence of that shape this arc (see the three Tailwind silent-drops in `technical-0_62_655`,
  T-61.1 / Register D-22–D-24) — and, like those, it was found only by a human actually touching the
  feature, not by any test. That is precisely why O-56 was tracked as an **open register item** rather than
  assumed fine on the strength of construction and unit tests.
