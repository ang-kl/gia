## New

### [HDR] #85 | 03:30:00 SGT 02-05-26 | v0.41.0 | n/a kb | n/a lines

- **[INTENT]** Ship Fix 3 (pipeline inversion: Google Places-first discovery, Claude as ranker/narrator) and Fix 5 (cross-user response cache) per the architectural review. Restores `/cuisine` reliability on sparse anchors (Pasir Panjang, far-west HDB, sub-CBD) by removing the LLM hallucination layer. v0.40.1 fixed the prefill 400 — that was a hard blocker; v0.41.0 fixes the 0-candidate failure class that the prefill bug was masking.

- **[ARCHITECTURAL SHIFT]** The legacy pipeline was Reason → Validate: Claude *invents* 15 venue names, Google Places *verifies* each. ~30-60% hallucination rate on sparse anchors → drop in validation → empty results. The inversion: Google Places *discovers* 20 real venues, Claude *picks 5 and narrates*. No invention; selection + narrative only. This matches what LLMs are actually good at (pattern-completion over a structured input) and what Places API is authoritative on (real venue facts).

- **[DESIGN]**

  1. **NEW `response-cache.js`** — Redis-backed cross-user response cache.
     - Key: `cuisine-cache:<lat3>:<lng3>:<cuisinesSorted>:<mealPeriod>:<dow>` where `lat3`/`lng3` are lat/lng rounded to 3 decimal places (~110m bucket in Singapore latitudes).
     - TTL: 30 minutes. Long enough to absorb rush-hour bursts (12:00–13:00 SGT weekday), short enough that openNow/queue/weather don't go stale.
     - Stores discovery output only — Refine pass still runs per-request so weather/traffic/carpark copy stays fresh.
     - Telemetry counters: `cuisine-cache:metric:hit`, `:miss`, `:write`. Fire-and-forget so cache failures never block real requests.
     - Honest caveat: `radius` and `specialRequest` are NOT in the key (would balkanise the cache too much). The cache is keyed on the choices that move the candidate set most.

  2. **NEW `pipeline.discover()`** — Google Places-first venue retrieval.
     - With cuisines: `searchText` with `"<cuisine1> OR <cuisine2> restaurant"` (better recall than `searchNearby` includedTypes).
     - Without cuisines: `searchNearby` with broad type set + `rankPreference: 'POPULARITY'`.
     - Returns up to 20 normalised candidates with `placeId`, `name`, `rating`, `userRatingCount`, `priceLevel`, `openNow`, `primaryType`, `lat/lng`, `googleMapsLinks`, `googleSummary`.
     - Filter: only `businessStatus === 'OPERATIONAL'`; closed/permanently-closed dropped.
     - Diagnostic codes `D710` start, `D711` ok, `D712` failed.

  3. **NEW `pipeline.rankAndNarrate()`** — Claude picks top-N from real Places candidates and adds vibe/dishes/cost.
     - Prompt structure: short structured input list with `[placeId] name — area — rating — price — open status — type` per row, plus vault snapshot for narrative grounding.
     - Output schema: array of `{placeId, vibe, signature_dish, dishes[], queue_min_estimate, booking_required, cost_estimate_sgd}`.
     - **Defensive placeId validation**: every output `placeId` must match an input candidate; hallucinated IDs are dropped silently. The model cannot invent venues — only narrate over real ones.
     - **Deterministic fallback**: if Claude fails, returns null, returns invalid placeIds, or returns nothing usable, falls back to `deterministicFallback()` — top-N sorted by `openNow` first then rating desc. Guarantees non-empty result whenever Places returned candidates.
     - Diagnostic codes `D720` start, `D721` ok, `D722` failed (with fallback).

  4. **MODIFIED `pipeline-task.js#runCuisineTask`** — split into `runCuisineTaskInverted` (new default) and `runCuisineTaskLegacy` (preserved verbatim). Dispatcher reads `PIPELINE_INVERSION_ENABLED` env (default ON; set to `'false'` for rollback to v0.40.1 behaviour).
     - New stages: `cache_lookup` → `discovering` → `narrating` → `ranking` → `refining`.
     - Old stages preserved when legacy path runs: `building_prompt` → `reasoning` → `validating` → `ranking` → `refining`.
     - Cache lookup fires before discover. Cache write happens after rank, before refine — refine is per-request.
     - Diagnostic codes `D700` cache HIT, `D701` cache MISS, `D702` cache WRITE.

  5. **OUT OF SCOPE for v0.41.0** (deferred to v0.42.0 per the spec discussion):
     - Fix 4 — vault-first warm-anchor short-circuit (waits on Tranche B vault data).
     - Fix 6 — rain → vault venue substitution (waits on Tranche B + vault `tags: ['outdoor']` enrichment).
     - `/surprise` slash command unchanged — already Places-first via `surprise.js#findSurprise`.
     - `/api/surprise-search` endpoint stays on legacy path — unused by any TMA; risk-free to defer.
     - `cuisine-search.js#searchCuisine` synchronous fallback unchanged — serves users who can't poll (corp MDM, ancient Telegram); changing it risks regression for them.

- **[KNOWN GAPS]**
  - **No `output_config.format` schema** — relying on system-prompt instruction + `extractJsonArray` + `stripJsonFences` for JSON output enforcement. Robust in practice; not bulletproof. Future patch can add per-caller schemas if drift observed.
  - **`searchText` cuisine query is keyword-based.** "Korean OR Japanese restaurant" works but isn't a structured cuisine filter — Places API doesn't expose one. Recall is good empirically; precision relies on Claude's filtering in `rankAndNarrate`.
  - **GenerativeSummary block depends on Places coverage.** Singapore venues have spotty coverage; we surface it when present, fall through cleanly when absent.
