# Journal — v0.62.711 (a 9ms loss shouldn't be a hard failure, but the fix has a ceiling of its own)

_(№ 1,050 — 07-08 '26 15:05 SGT)_

## New

### [HDR] v0.62.711 — raise `extractDishesFromReviews`'s PER_ATTEMPT_MS/DEADLINE (O-166)

- **[INTENT]** Operator, closing the loop on O-166 (logged in the prior entry): *"make the
  PER_ATTEMPT_MS/DEADLINE change."* The triggering evidence was a single production log line —
  `[Extract-Dishes] gemini-flash-latest failed: per-attempt timeout 6s` — paired with the same
  request's `enrichSlow` timing breakdown showing `dishes=6009ms`: the real call took 6009ms against
  a 6000ms cap, losing the race by about 9 milliseconds. That's not evidence of a broken key or a slow
  model tier — it's a cap sized with essentially zero margin for an otherwise-healthy call.

- **[THE FIRST DRAFT WAS WRONG, CAUGHT BEFORE SHIPPING]** The immediately obvious fix — bump
  `PER_ATTEMPT_MS` 6000→10000 and `DEADLINE` 12000→20000 in step — was written first and then checked
  against the rest of the call chain before being kept. `extractDishesFromReviews` runs as one step
  inside `cuisine-enrich.js`'s `enrichSlow`, which itself runs inside `index.js`'s Cuisine search
  route — and that route has its own hard ceiling: `_SEARCH_DEADLINE_MS = 20000` (the "D706" deadline,
  named and complained-about in three separate operator-driven fixes already in this codebase:
  v0.62.482, v0.62.483, v0.62.31). `enrichSlow` also runs crowd-signal, translate, review-cache,
  travel, sanctuary, and footfall enrichment around the dish-extraction call. A 20000ms DEADLINE on
  dish-extraction ALONE would have let this one step consume the entire route budget, starving every
  other enrichment step and very plausibly reintroducing the exact D706 degraded-response failure mode
  three prior versions were written to prevent — the opposite of what this fix was meant to do.

- **[THE ACTUAL FIX]** `PER_ATTEMPT_MS` 6000ms → **10000ms** (real headroom over the observed 6009ms
  near-miss). `DEADLINE` 12000ms → **14000ms**, not 20000ms — kept comfortably under half the route's
  20000ms ceiling, leaving room for the other `enrichSlow` steps (crowd-signal alone was 2451ms in the
  same log sample) plus whatever ran before `enrichSlow` even started. A timeout is still terminal —
  the v0.60.226 design (a timed-out attempt breaks the whole fallback chain rather than retrying the
  next model, because a slow Gemini response means Gemini itself is slow, not that a different model
  would be faster) is unchanged; this raise only gives the single attempt more time to succeed before
  that terminal give-up fires.

     to match `PER_ATTEMPT_MS` × 2 without checking the outer route budget).
