# Journal — soleat v0.60.167

> Operator: *"To prevent hacker, how to harden the pipeline, API keys, etc."* → after I listed three priorities (Telegram-auth gate, API-key budget caps, per-chatId rate limiting), operator picked **#1**: Telegram WebApp `initData` auth on `/api/cuisine/*`.

Existing state — `twa-auth.js` already exports `verifyInitData()` (HMAC-SHA-256 of the data-check-string with `secret_key = HMAC_SHA256(bot_token, "WebAppData")` per Telegram spec) and `requireInitData()` (header-only middleware reading `X-Telegram-Init-Data`). 19 inline `verifyInitData(req.body?.initData, …)` calls across 17 `/api/cuisine/*` routes already verify per-handler. Gaps:

1. **GET endpoints unguarded** — `/api/cuisine/catalogue` and `/api/cuisine/user-language` (GET) have no inline verify. The catalogue is read-only static data so the cost of an open endpoint is low, but it's still a free probe surface for fingerprinting + warming caches.
2. **Coverage relies on every handler remembering** — any new POST that forgets `verifyInitData(req.body?.initData, …)` is silently open. The v0.60.165 → v0.60.166 hotfix exposed exactly this class of miss (filter-key wiring); the same risk exists for auth gates.
3. **Timing-leak in the hex compare** — `computedHash !== hash` ran a non-constant-time compare. Low impact in practice (HMAC-SHA-256 over a 32-bit network is not realistically timeable from outside), but the fix is a one-liner.

Hardening landed in this PR:

- **New `requireInitDataFromBodyOrHeader` middleware** in `twa-auth.js` — reads from `X-Telegram-Init-Data` header OR `req.body.initData`, accommodating both the older `/api/cuisine-search`-style header pattern AND the v2 TMA's `postJson` body-stuffed pattern in `web/cuisine/src/v2/lib/api.js:15`. Single chokepoint.
- **Mounted as `app.use('/api/cuisine', requireInitDataFromBodyOrHeader)`** in `index.js` directly before the first route declaration (line ~7838). All 17 routes + the two GETs now inherit the gate; future routes inherit it automatically.
- **Constant-time hash compare** (`crypto.timingSafeEqual`) replacing the `===` string compare in `verifyInitData`.
- **Dev bypass env `SKIP_INIT_DATA_AUTH=true`** for Railway preview deploys + local dev — attaches a synthetic `req.tg = { user: null, devBypass: true }` so handlers downstream can detect dev mode if they need to. Strict equality on the string `"true"` (so `"1"`, `"yes"`, truthy garbage all reject).
- **Auth-failure logging** — `[twa-auth] 401 <method> <path> ip=<ip> ua=<user-agent>` on every reject, capped at 80 chars of UA, so abuse spikes are visible in Railway tail.
- **Generic 401 body** (`{ error: 'invalid initData' }`) — same for tampered / expired / missing-hash / missing entirely, so a probing caller can't distinguish failure modes.
- **17 new unit tests in `__tests__/twa-auth.test.js`** covering: happy-path verify, tampered-hash, wrong-bot-token signature, missing-hash, expired auth_date, missing auth_date, null inputs, malformed user JSON, both middlewares' accept/reject paths, header-vs-body precedence, dev-bypass enable + strict-string check. Suite now 57 files / 1757 tests (was 56 / 1740).
- **Inline `verifyInitData(...)` calls left in place** — defense in depth, zero risk of regression in the 19 existing handlers, simplification deferred to a future cleanup pass.

  **`twa-auth.js`** —

  *Added* `requireInitDataFromBodyOrHeader(req, res, next)`:
  ```js
  function requireInitDataFromBodyOrHeader(req, res, next) {
    if (process.env.SKIP_INIT_DATA_AUTH === 'true') {
      req.tg = { user: null, devBypass: true };
      return next();
    }
    const initData = req.headers['x-telegram-init-data'] || req.body?.initData || '';
    const verified = verifyInitData(initData, process.env.TELEGRAM_BOT_TOKEN);
    if (!verified) {
      const ip = req.headers['x-forwarded-for'] || req.socket?.remoteAddress || 'unknown';
      const ua = (req.headers['user-agent'] || 'unknown').slice(0, 80);
      console.warn(`[twa-auth] 401 ${req.method} ${req.path} ip=${ip} ua="${ua}"`);
      return res.status(401).json({ error: 'invalid initData' });
    }
    req.tg = verified;
    return next();
  }

  module.exports = { verifyInitData, requireInitData, requireInitDataFromBodyOrHeader };
  ```

  *Hardened* the existing `verifyInitData` hash compare:
  ```js
  // Before:
  if (computedHash !== hash) return null;

  // After (constant-time):
  let hashOk = false;
  try {
    hashOk = crypto.timingSafeEqual(Buffer.from(computedHash, 'hex'), Buffer.from(hash, 'hex'));
  } catch { hashOk = false; }
  if (!hashOk) return null;
  ```
