# Journal — soleat v0.62.524 (Cuisine TMA — fix: stalled result stream hung forever on slow phones)

> Operator: *"the UI results experience, sometimes slower phones are not populating the details
> and caused a letdown."* Traced (not guessed) to source: the operator's own working hypothesis —
> a documented 6s client timeout racing detail-fetch — was WRONG; that constant doesn't exist in

> mattered.

## New

### [HDR] #880 | 12:03 SGT 10-07-26 | v0.62.524 — Cuisine stream stall-timeout + degraded notice | 2 files | PR #(pending) |

- **[INTENT].** Fix slow-phone/flaky-network searches where the pick list paints but per-card
  details (photos, address, rating, hours, walk-minutes) never populate and the loading spinner
  never clears — no error, no retry, just a permanently half-painted UI.

- **[ROOT CAUSE].** `web/cuisine/src/v2/lib/api.js` `postJsonStream()` reads the progressive
  NDJSON result stream in an unbounded `for (;;) { await reader.read(); }` loop with **no
  deadline**. On a connection that stalls — stops delivering bytes without erroring or closing,
  common on flaky mobile networks — `reader.read()` never resolves. The `searchCuisine()` promise
  therefore never settles: `App.jsx`'s `finally { setLoading(false); }` never runs, and any card
  whose `patch` event hadn't landed yet stays on base-only fields forever. No fallback/retry UI
  existed for this state.

- **[DELTA].**
  - `web/cuisine/src/v2/lib/api.js` — added `STREAM_STALL_TIMEOUT_MS = 15000`. Each
    `reader.read()` now races a per-CHUNK stall timer (reset on every chunk received, not an
    overall deadline — a merely-slow-but-flowing stream is never cut off; only a genuine stall
    is). On stall: `reader.cancel()`, break the loop, and resolve with the best-effort partial
    result (`assembleFinal(...)`) tagged `streamStalled: true`, instead of hanging indefinitely.
    15s chosen with headroom above the documented `<12s p95` end-to-end (`doc/Technical/
    Technical.md`).
  - `web/cuisine/src/v2/App.jsx` — wired the result into the **existing but previously dead**
    `degradedNotice` state + its already-8-language-authored (en/fr/ru/de/zh/ja/es — see
    `[KNOWN GAPS]`) "↻ Search hiccup — tap 🔍 to try again" banner
    (`degradedNotice && !loading`, amber border + icon, colour-blind-safe per the operator's
    standing accessibility rule). `setDegradedNotice(false)` resets it at the top of each new
    search attempt; `setDegradedNotice(true)` fires when `r.streamStalled` comes back true.
    Added one `console.log('[Cuisine-TMA-v2] stream stalled — showing degraded notice')` line for
    basic observability (v2 has no `[Cuisine-Diag]` D-code system — see `[KNOWN GAPS]`).

- **[WHY THE 6s-TIMEOUT HYPOTHESIS WAS WRONG].** The operator's own read of the symptom named a
  documented "6s TMA fetch timeout" (`doc/Technical/Technical.md:31`) as the likely cause. A
  read-only trace found no such constant anywhere in `web/cuisine/src` — the only 6000ms constant
  in the codebase is server-side in `footfall-signal.js`, unrelated, and already tightened to
  3500ms in v0.62.229. The doc line is stale relative to the live client. Not corrected in this
  PR (out of scope — a Technical-doc line, not a code defect); flagged in `[KNOWN GAPS]`.
