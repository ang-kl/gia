## `/weather` expansion (v0.60.118)

- **Cached fetchers** (Redis-keyed, so the NEA feed is hit ≤ once per window regardless of pick/search volume): `getNowcastCached` (`nea:2h-nowcast`, 300 s), `getRainfallCached` (`nea:rainfall`, 60 s), `get24hCached` (`nea:24h-forecast`, 1800 s); new `fetch24hForecast()`.
- **Pure helpers**: `inSgBounds({ lat, lng })` (lat > 1.48 ⇒ a JB pick — skip NEA caveats); `WEATHER_ZONE_CENTROIDS` (W/N/C/S/E) + `zoneKeyFor(lat,lng)` / `zoneLabelFor(key)`; `resolveArea(text)` (free-text → `{ lat, lng, label }`: matches the ~47 NEA nowcast area names first, then the 5 broad zones + synonyms); `rainAlertFor(venue, { nowcast, rainfall })` (per-venue: "raining near {area} now" from a > 0.2 mm station, or "{desc} in {area}'s 2h outlook" when the nowcast for the nearest area is wet, else `null`); `headOutLine({ nowcast, rainfall })` (the interpreted lead line — raining / showery / good window); `tonightOutlookFor(venueOrZone, twentyFourH)` (picks the evening 24h period for the zone → "Tonight in the {zone}: {desc}"); `attachRainAlerts(redis, picks, lang, isRainSensitiveVenue, tn)` (best-effort: mutates `v.rainAlert` on rain-sensitive venues; any failure → no alerts, never blocks delivery).

### `venue-filters.js`

- `isRainSensitiveVenue(v)` → true for `primaryType` `food_court` / `market`, or a name/address match on `hawker` / `food centre` / `market` / `kopitiam` / `al-fresco` / `outdoor` / `rooftop` / `riverside` / `quay` / `waterfront` / `esplanade` / `pasar malam` / etc. Ordinary (likely-indoor) restaurants get no caveat — a rain line there is just noise.

### `venue-templates.js`

- `formatVenueBlock` renders `p.rainAlert` (one line, after the footfall row, before travel-time) when present.

### `index.js`

- `/weather` regex now captures an optional `<area>` → `runWeatherCommand(chatId, lang, areaArg)`. With an arg: `weather.resolveArea(areaArg)` (else a "I don't know that area …" reply); without: the cached pin (or SG centroid). The reply gains: a "— for {area} —" sub-line (when an area was given), the `headOutLine` lead, the existing temp / humidity / rain / wind / 2h lines, the 24h "🌙 Tonight in the {zone}" line, and the `tempC ≥ 33` air-con nudge.
- `deliverPicks` + `deliverSurprise` call `weather.attachRainAlerts` (best-effort) before formatting.

### `i18n.js`

## Free-text dish-search relevance + divider (v0.60.122 → v0.60.127)

### `index.js deliverPicks` — optional section divider

- New `opts.dividerAfter` (integer N) + `opts.dividerText` (string): when both are set and `0 < N < blocks.length`, the rendered list is split — `blocks[0..N)` then `dividerText` then `blocks[N..]`. No-op for every other `deliverPicks` caller.

### `index.js runFreeTextSearch` — `opts.cuisine` / `opts.dishLabel` / disambiguated ranking

- New `opts.cuisine` / `opts.dishLabel` (passed from the message handler when R.E.D's `disambiguateTerm` resolved the query, e.g. "goulash dumplings" → "Czech guláš with bread dumplings", European). When disambiguated: `pipeline.discover({ ..., queryOverride: text, maxResults: 15 })` feeds Places the anchored phrase verbatim (don't append `" cuisine restaurant"` on top of `"… restaurant Singapore"`); keep up to 20 survivors; score each venue:
  - **STRONG keywords** = the cuisine name + `getDishKeywords(cuisine)` (curated per-cuisine dish/demonym vocabulary) — a hit on the **venue name** (or a `<cuisine>_restaurant` `primaryType` match) ⇒ the venue self-identifies as that cuisine ⇒ **above the line** (`exact = true`).
  - **WEAK keywords** = generic words pulled from the dish *label* that aren't already strong ("bread", "dumplings" from "Czech guláš with bread dumplings") — a hit on these *alone* is a bare word-match (a Chinese 灌汤包 also "has dumplings") ⇒ **below the line**, where it just orders the tier (soft score). A strong word found only in a *review* is also a soft signal, not an above-the-line ticket.
  - `above` sorted rating → distance; `below` sorted soft-score → rating → distance; `venues = [...above, ...below].slice(0, 8)`; if `above.length > 0 && above.length < venues.length` → `dividerAfter = above.length`, `dividerText = trnBot('freetext.divider', lang, { dish: cleanDish })`.
  Plain free text (no disambiguation) keeps the distance order `filterFreeTextResults` produced, just shows up to 8 instead of 5.

### `cuisine-dish-keywords.js` — `european` keyword list

- New `european` entry: the broad category R.E.D assigns to Central/Germanic dishes (goulash → "Czech guláš with bread dumplings", schnitzel, …) — goulash-family dishes + accented variants + the relevant nationality / region demonyms (`czech, czechia, bohemian, moravian, slovak, hungarian, magyar, austrian, german, bavarian, polish, slavic, balkan, croatian, serbian, romanian, bulgarian`) + signature dish words (`knedlik, bread dumpling, svickova, trdelnik, kolache, langos, palacinky, schnitzel, spaetzle, pierogi, kielbasa, bratwurst, sauerkraut, pretzel, currywurst, rouladen, bigos, pelmeni, apfelstrudel, sachertorte, tafelspitz`) + distinctively Central/Germanic *eatery* name-words (`hospoda, pivnice, pivovar, brotzeit, gasthaus, gasthof, bierhaus, brauhaus, biergarten, ratskeller, csarda, bierstube`).

## `misrepresented-dishes.js` — data/*.md-backed lookup table #1 (v0.60.128)

- **Source** — `data/Misrepresented Dish Dessert Drink.MD` (operator-authored; 759 entries `Name - often assumed X, but actually Y.`; the first line is a usage note, not an entry — filtered by requiring a space-hyphen-space separator + a short name).
- **Module** — reads the .md once at `require` time; `parseFile()` → `{ entries: [{name, desc}], byKey: Map<normalised-key, entry>, prefix: Map<first-word, [entries]> }`. `norm(s)` = NFD → strip combining diacritics → strip apostrophes → lowercase → punctuation→space → collapse. `singularizeLastWord(s)` = drop a trailing `s`/`es` on the last word (with `ss`/`us`/`is`/`ous` guards) so "goulash dumplings" matches "Goulash dumpling" and "fortune cookie" matches "Fortune cookies" — entries are indexed under both their normalised name and its singularised form.
- **Lookup** — `lookupMisrepresentedDish(query)` → `{ name, note }` or `null`. Bails if the normalised query is blank, > 48 chars, or > 6 words. (1) exact / singularised exact `byKey` match; (2) a single-word query → the **unique** entry in `prefix` whose name starts with that word ("goulash" → "Goulash dumpling"). Never throws (the data file is read defensively).
- **Wiring** — `index.js` chat free-text handler: after the R.E.D pre-step (skipped if R.E.D produced a disclosure) and the misrep step, `safeSend` an HTML `ℹ️ <b>{name}</b> — {note}` line (caller HTML-escapes name + note), then continue to `runFreeTextSearch` (the note doesn't change the search). `index.js /api/cuisine/search`: after the `chipDisambig` probe, if `req.body.freeText` matches and R.E.D didn't fire, `misrepNote = lookupMisrepresentedDish(ftRaw)`; `misrepresentation: misrepNote` on the payload. `web/cuisine/src/v2/App.jsx`: `misrepNote` state from `r.misrepresentation`; banner above `<ResultPanel>` (cleared on error). `i18n.js misrep.note` (EN/FR; `{note}` payload stays English).
- **Tests** — new `__tests__/misrepresented-dishes.test.js` (parse count ≥ 700; exact / singular-plural / single-word-prefix lookup; accent/punctuation normalisation; junk guards). +11 (1607 → 1618).

## `cooking-methods.js` — the .md merge + multi-match (v0.60.129 → v0.60.130)

- **Baseline (v0.60.12, unchanged on disk)** — `COOKING_METHODS` = a hand-curated `{ slug: [~30 method strings] }` literal for 70 cuisines; `tokenize` / `stripDiacritics` helpers; `isOrderedPrefix`; `findCookingMethod(text, opts)` (first hit; sticky-cuisine bias); `slugToLabel` / `getMethodsForCuisine` / `getCuisineSlugs`.
- **Merge (v0.60.129)** — at module load: `parseCookingMethodsMd()` reads `data/cooking method reference by cuisine.md` (sections `Cuisine — method1, method2, …`; the file's header sentences have no em-dash separator so they're naturally excluded). `MD_LABEL_TO_SLUG` maps the .md cuisine labels to the dict's slug convention (e.g. `'Sichuan' → 'sichuanese'`, `'Hong Kong' → 'hong-kong'`, `'Northeastern Chinese' → 'northeastern-chinese'`). `mergeMdCookingMethods()` (an IIFE): for each section, UNION the .md method list into `COOKING_METHODS[slug]` — existing tokens kept (existing wins on display order), new tokens appended, deduped by normalised (diacritic-stripped, lowercased, trimmed) form. **`MD_BARE_VERB_STOPLIST`** — a single-token .md term whose only token is a generic English cooking verb (`steaming`, `smoking`, `frying`, `pickling`, `roasting`, `braising`, … ~50 words) is dropped: a bare single-token entry false-matches any input containing the verb (the matcher's single-token rule is `userLower.includes(token)`). Multi-token compounds (`tea-smoking`, `deep-frying`, `charcoal grilling`) are unaffected (they tokenize to ≥ 2 tokens and require all to appear). Net: 94 cuisine slugs (was 70); per-cuisine method counts vary (≥ 20 — new .md-only cuisines like European / Dessert lose a few to the stoplist). New slugs: `hokkien, teochew, hainanese, hakka, shanghainese, hunan, northeastern-chinese, northwestern-chinese, hong-kong, macau, taiwanese, bengali, gujarati, jordanian, uzbek, eurasian, dessert, fusion, european, mediterranean, australasia`.
- **`findCookingMethodMatches(text, opts) → Array<{ slug, cuisineLabel, term }>`** — same matching rules as `findCookingMethod` (substring on a single-token term; all-tokens or ordered-prefix on a multi-token term; sticky-cuisine first), but collects ALL plausible cuisine hits — one entry per slug, in scan order (sticky first). Bails on blank / < 3-char / no-token input → `[]`. `findCookingMethod` is now `findCookingMethodMatches(text, opts)[0] ?? null` (semantics preserved — same first hit). New module exports: `findCookingMethodMatches`, `_MD_LABEL_TO_SLUG`, `_parseCookingMethodsMd` (alongside the existing `COOKING_METHODS`, `findCookingMethod`, `getMethodsForCuisine`, `getCuisineSlugs`, `slugToLabel`, `_stripDiacritics`, `_tokenize`).
- **Pivot wiring (`index.js`)** — `buildCookMethodKeyboard(text, matches, lang)` → an inline keyboard: ≤ 5 cuisine buttons (2 per row), `callback_data = \`cookm:${idx}:${encodeURIComponent(text.slice(0,40))}\``, then a tail row `[{ text: t('cookmethod.literalBtn', lang), callback_data: \`cookm:L:${enc}\` }]`. Text capped at 40 chars before encoding so the callback_data stays well under Telegram's 64-byte limit; the handler re-derives the match list from the round-tripped text. Used by:
  - **Chat free-text handler** — after the R.E.D + misrep steps, if `findCookingMethodMatches(text).length > 0` (and R.E.D didn't disclose), `safeSend` the `cookmethod.didYouMean` prompt with the keyboard and `return` (no literal search yet).
  - **`handleSearchTurn` (`/s`)** — `cmMatches = findCookingMethodMatches(userText, { stickyCuisine })`; `verbatim = cmMatches.length === 1 && tokenize(userText).join(' ') === tokenize(cmMatches[0].term).join(' ')`. Verbatim ⇒ `runCookingMethodFanOut(...)` directly (pre-v0.60.129 path). Else ⇒ the pivot keyboard.
  - **`/api/cuisine/search`** — after the `chipDisambig` probe, if `req.body.freeText` matches and R.E.D didn't fire, `cookMethodMatches = { query, matches: hits.slice(0,6).map(h => ({ slug, cuisine, method })) }`; `cookingMethod: cookMethodMatches` on the payload.
  - **New `bot.on('callback_query')` branch** — `data.startsWith('cookm:')`: parse `cookm:<idx-or-L>:<encoded-text>`; decode (try/catch fallback); `L` ⇒ `runFreeTextSearch(chatId, text, { lang })`; an index ⇒ `findCookingMethodMatches(text)[idx] ?? [0]`, then `sc.setLastCuisine(redis, chatId, 'cooking-method', hit.slug, hit.term)` + `runCookingMethodFanOut({ chatId, userText: text, hit, lang, center, sc })` (center = the cached pin or SG centroid). Any failure → `runFreeTextSearch` fallback.
  - **`web/cuisine/src/v2/App.jsx`** — `cookMethodPivot` state from `r.cookingMethod`; banner above `<ResultPanel>` with cuisine chip-`<button>`s — a chip does `setState({ ...state, cuisines: [slug] })` + `runSearch(next)` (reuses the existing cuisine-chip pivot path; no new endpoint). Cleared on error / next search.
  - **`i18n.js`** — `cookmethod.didYouMean` (v0.60.130 polite wording) + `cookmethod.literalBtn` (EN/FR).
- **Tests (`__tests__/cooking-methods.test.js`)** — the v0.60.12 exact-count shape assertions ("exactly 70 cuisines × 30 methods = 2100") relaxed to floors (≥ 70 cuisines; ≥ 20 methods each; ≥ 2100 entries); +11 new tests for the merge (label→slug map; new slugs present; baseline vocabulary preserved; bare-verb stoplist; `findCookingMethodMatches` multi-/single-match + empty cases; `findCookingMethod` backward-compat). +11 (1618 → 1629).
