## T-64.1 — A single-quote assumption inflated one file's gap by roughly 20×

The initial audit script parsed i18n key/value pairs with a single-quote-only regex. Cuisine's `i18n.js`
mixes `'key':` and `"key":` styles across its overlay blocks (apparently from different authoring passes over
time) — the script silently skipped every double-quoted entry when counting what a locale ALREADY had,
making Cuisine's Russian/German gap look like 216 keys when the true number, confirmed by rewriting the parser
to walk brace-depth and skip any of `'`/`"`/`` ` ``-quoted strings uniformly, was 10. This was caught two
ways: independently, by two of the six translation agents actually reading the live file and noticing most of
their "missing" worklist already existed; and directly, by re-running the corrected extractor and diffing
against the agents' claimed counts. Lesson, consistent with this arc's greatest hits (T-61.1, T-63.2): a
regex tuned against one sample of a file's style will silently under- or over-count the moment that style
isn't uniform across the whole file — worth grepping for BOTH quote styles before trusting a "N missing" number
in a codebase old enough to have been touched by more than one authoring pass.

## T-64.2 — Merge safety: verify against the live file, not against what an agent was told

Six translation agents were each given a "missing keys" worklist computed BEFORE the quote-style bug was
found — meaning Russian and German's worklists for Cuisine were inflated 20×. Rather than trust each agent's
self-reported completeness, the merge step re-derived the TRUE missing set from the corrected extractor at
merge time and used it as an allow-list: only keys genuinely absent from the live file were inserted,
regardless of what any agent produced. This meant the ~400 redundant "translations" of already-shipped
strings (which several agents dutifully reused verbatim, correctly recognizing they already existed) were
simply discarded rather than merged as duplicate keys. The general principle: when a worklist was computed
from a source later found to be buggy, re-derive the ground truth at the point of consequence (here, the file
write) rather than propagating the original list's assumptions forward.

## T-64.3 — A missing-trailing-comma assumption broke the first merge attempt, caught immediately by the build

The first merge pass spliced new object-literal lines directly before each overlay block's closing `}`,
assuming the preceding entry already ended in a comma. Cuisine's file doesn't consistently do this — one block
ended without one — producing `"a": "b"` immediately followed by `"c": "d"` with no separator, a syntax error
`vite build` caught on the very first attempt. Fixed by having the merge script look backward past whitespace
from the insertion point and add a comma itself when the preceding character isn't already one, rather than
assuming the file's own formatting convention holds everywhere. Reverted the botched write via `git checkout`
before re-running with the fix, so no partially-broken state was ever committed.
