### 3. Memory — Redis Schema additions

| Key | Type | TTL | Writer | Readers |
| :--- | :--- | :--- | :--- | :--- |
| `loc:<sha256(chatId).slice(0,16)>` | JSON `{lat, lng}` | 1800 s (30 min) | `setUserLocation` (`/eat` location handler) | `getUserLocation` (`/eat` cache check) |
| `loc:pending:<hash>` | string (mealId) | 300 s (5 min) | `setPendingMeal` | `consumePendingMeal` |

`vibe:summary:<placeId>` (Phase 3a) and `vibe:listings`, `lta:train_status` (earlier) unchanged.

**Zero-Server Mandate breach (accepted by Human Lead):** the `loc:*` keys store transient user lat/lng on Railway. Mitigations:
- Chat ID is SHA-256 hashed (16 hex chars), not stored in plaintext.
- TTL strictly enforced (30 min and 5 min, never extended).
- No append/history; `setEx` overwrites every call.
- One-line rollback (skip `setUserLocation`, re-prompt every `/eat`) is documented in Phase 3c Risk.

### 6. Build constraints additions

- **Places `searchText` quota.** Each `/eat` invocation issues up to 5 calls (one per Gemini candidate). At 200 m acceptance and Gemini's typical accuracy, ~3 hit; the rest 200-m miss and are dropped without further calls.
- **Maps JavaScript API quota.** Frontend loads the Maps SDK once per TWA session. Map loads + marker placement count toward Places quota under the JS SDK billing line.
- **Bot menu button** auto-registers on every boot when in webhook mode. Switching to a new domain requires a fresh boot — no manual `@BotFather` step.
