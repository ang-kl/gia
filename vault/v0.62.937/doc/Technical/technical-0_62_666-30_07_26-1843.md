## T-66.1 — A dropped venue in the venue-centric schema is "no new award," not "delete the row"

`SG-michelin.js` (v0.62.665) handles a dropped Bib Gourmand entry by removing the row entirely, because that
file has no historical-listing mode — it's a flat "current roster" snapshot. `TW-michelin.js` (and the other 10
venue-centric country files) is built differently: `awardsDiff(venue)` already derives `droppedAfter` from
`venue.status === 'closed' || latest.year < MAX_EDITION_YEAR` — meaning a venue that simply doesn't gain a
current-edition award is automatically treated as dropped, with its full award history preserved. This entry's
12 non-retained Taiwan rows (2 one-star + 10 Bib Gourmand) therefore needed ZERO new code: they were left with
only their 2025 award, and the existing `awardsDiff`/`editionVenues` machinery correctly classifies them as
dropped without a single line changing. The lesson generalises: in a schema already designed to retain history,
"drop" is an ABSENCE (no new award this edition), not an ACTION (delete/mark-closed) — `status:'closed'` is
reserved for the narrower, different fact "this business no longer operates," which is not established for any
of these 12 rows (they may simply have lost the distinction while remaining open).

## T-66.2 — A "verbatim from source-of-record" contract needs the source updated too, not just the mirror

`TW-michelin.js`'s header declares it "Loaded VERBATIM" from `instruction/Taiwan.js`, with an explicit
instruction not to auto-generate or AI-fabricate data into the mirror file. Reading the declared source
confirmed it was byte-identical 2025-only content — updating only `TW-michelin.js` would have created a silent
provenance fork: a future session trusting the header's claim and re-syncing from `instruction/Taiwan.js` would
overwrite this update without warning. The fix was mechanical, not architectural: apply the identical
text-transform to both files and verify entry/award counts match exactly afterward (`grep -c` on both files).
This is a narrower instance of the general principle already applied to Michelin work this session — when a
file's own header makes a promise about where its data comes from, honouring that promise means keeping BOTH
ends of the promise true, not just the one file currently being edited.

## T-66.3 — Scale (183 rows) is a case for a verified mechanical transform, not 183 manual edits

Adding a same-category 2026 award to 183 already-correct rows is a pure mechanical operation once the set of
exceptions (12 drops + 1 promotion) is fully verified — doing it as 183 individual tool-mediated edits would
have been slow and error-prone for zero benefit over a small, auditable Node script performing targeted string
substitution keyed on each row's existing `id`. The script never decided any fact — every retained/dropped/
promoted classification was established via the WebSearch research first, and the script's own console output
(retained/promoted/dropped counts) was checked against the expected numbers before trusting the result. This is
the same discipline as writing a migration script for a database: verify the facts, then let a script apply
them exactly, then verify the result — not "let the script figure out what to do."
