### [HDR] #322 | 12:41 SGT 24-05-26 | v0.61.121 — chat free-text place-anchored search + "✨ Top eateries nearby" button | ~14 kb | 5 files | 1 PR | 1 build |

- **[INTENT]** Add a place-anchored search path to the Telegram chat
  free-text handler: when Gemini's `classifySearchIntent` returns
  `intent='venue'`, resolve the text to a SG anchor (deterministic
  MRT/hawker first, geocode fallback), run Places at that anchor's
  coords with a per-kind radius, reply with `📍 <place> — found N
  eateries here` + the venue cards, append an opt-in
  `✨ Top eateries nearby` inline button that fans out into a wider
  composite-scored alternatives list.

- **[DELTA]**
  - **`+ place-detector.js`** (~200 lines, new module). Three-tier
    detection ladder (cheapest → most-general, first hit wins):
    1. **MRT/LRT** — exact whole-word match (with optional
       `mrt`/`lrt`/`station`/`stn`/`interchange` suffix stripped)
       against `data/mrt-coords.json` (operational stations only).
       MRT first because the hawker fuzzy matcher sometimes prefers
       an obscure block over an obvious station for queries like
       `"Tanjong Pagar"`. The 400 m MRT radius covers any adjacent
       hawker centre anyway.
    2. **Hawker** — `hawker-vault.findByName` (exact → substring →
       edit-distance ≥ 0.75). Uses the centre's geocoded lat/lng.
    3. **Geocode fallback** — `vibe-suggest.geocodeQuery` (Places
       searchText with `" Singapore"` appended). Catches malls /
       buildings / restaurants / postal codes / etc.
    Per-kind radii: hawker **150 m**, MRT **400 m**, geocoded **300 m**,
    nearby button **1500 m**.
  - **`+ __tests__/place-detector.test.js`** (~120 lines, 5 describes
    / 18 specs covering MRT exact / suffix / case / negatives; hawker
    exact / fuzzy / negatives; MRT-vs-hawker ordering for
    `"Tanjong Pagar"`; helpers + radius sanity).
  - **`index.js`**
    - New `placeAnchorKey(place)` — sha256 of
      `lat.toFixed(4),lng.toFixed(4),kind` → 10-char hex. Used as the
      Redis cache key suffix so callback_data stays under 64 bytes.
    - New `runPlaceAnchoredSearch(chatId, place, opts)` — calls
      `pipeline.discover` at `place.lat/lng` with the per-kind radius,
      filters by haversine to the radius, takes top 12, enriches with
      travel-times + crowd + footfall, replies via `deliverPicks` with
      the `place.foundN` header, caches the anchor
      (name + coords + originalPlaceIds for dedupe) in Redis at
      `place:anchor:<chatId>:<key>` (30 min TTL), appends a separate
      message with the `✨ Top eateries nearby` inline button.
    - New `runNearbyAlternatives(chatId, anchor, lang)` — wider 1500 m
      `pipeline.discover`, dedupes against the original at-place
      placeIds, scores each candidate
      `rating·0.4 + michelin·0.3 + rarity·0.2 + (1−crowdCost)·0.1`,
      sorts desc, takes top 12, enriches the final set only, replies
      via `deliverPicks` with the `place.nearbyHeader` header.
    - Chat free-text gate (`~7738`) — when `cls.intent === 'venue'`,
      calls `detectPlaceName` and branches into
      `runPlaceAnchoredSearch` on a hit. Logs
      `[free-text] D774 place-anchored — "<text>" → <kind>: <name> (<lat>,<lng>, r=<radius>m)`.
    - `bot.on('callback_query')` — new branch for
      `place:nearby:<key>` callback. Reads the cached anchor; on miss
      sends the `place.expired` nudge; on hit fires
      `runNearbyAlternatives`.
  - **`i18n.js`** — 6 new keys (en + fr): `place.foundN`,
    `place.foundEmpty`, `place.nearbyBtn`, `place.nearbyHeader`,
    `place.nearbyEmpty`, `place.expired`.
  - **`package.json`** — `0.61.120 → 0.61.121` (PATCH).
