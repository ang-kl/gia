>
> The v0.61.299 + v0.61.300 arc added Gemini-cache support for 7 Slavic / EE cuisines (`russian`, `polish`, `ukrainian`, `czech`, `hungarian`, `bulgarian`, `romanian`). v0.61.303 extends the same pattern to 21 more cuisines covering the rest of the operator's "Common Here" + "South Asian Specialists" + "European" categories:

> |---|---|---|

>
> Total mode allow-list grows 10 → **31 keys** (3 special modes + 7 Slavic/EE + 21 new). Same architecture as v0.61.282 + v0.61.294 + v0.61.299 — `PROMPT_CONFIG` entry + `GEMINI_CACHE_KEYS` Set entry per cuisine.
>
> Cross-contamination guards are the design focus this round. The South Asian set has high overlap risk (Bengali → North Indian, Sri Lankan → South Indian, Pakistani → Mughlai); each prompt has an explicit "not a generic <broader>" caveat. The European set similarly disambiguates Italian → Mediterranean, Greek → Mediterranean, Austrian → German, etc.
>
> Two broad catch-alls (`european`, `mediterranean`) are deliberately permissive — they describe a STYLE rather than a national kitchen, so the prompts allow restaurants that identify "broadly continental" / "Mediterranean-style".

- **[KNOWN GAPS]**
  - **The two broad catch-alls** (`european`, `mediterranean`) may have lower precision than the cuisine-specific entries. Gemini's verdict on "is this restaurant European-style?" is fuzzier than "is this restaurant Bengali specifically?". Initial cache fills may need prompt-tuning if the operator finds borderline cases. Worth measuring after a few weeks of real traffic.
  - **No variance script extension.** Unlike Slavic/EE (where the v0.61.297 variance was the entry point), these cuisines have established Places coverage — Italian / Japanese / Indian variants are well-indexed. Skipping the up-front variance saves ~$3 of API quota; the auto-warming D703f path will fill the cache organically.
  - **Slug-vs-name mismatch risk.** Each `GEMINI_CACHE_KEYS` entry must exactly match the `cuisineMetas[0].slug` that `cuisines-vault.js` produces. The slugs are derived from cuisine names via `lowercase + hyphenate` per cuisines-vault.js line ~12. I cross-referenced against `doc/Feature/cuisines_js.MD` — all 21 new keys are correctly slug-shaped.
  - **No DVG_LABEL entries** for any of these in the bot `/ver` UI. All 31 cached modes/cuisines are auto-warming-only; the bot UI still only exposes durian + durian-pastry for bulk pre-warm. Adding more to `/ver` is a separate UX decision.
  - **Indian sub-cuisine quality risk.** Bengali / Gujarati / Nepalese / Sri Lankan / Pakistani / North Indian / South Indian all share menu items at the border (e.g. samosas exist in many). The "not a generic <neighbour>" caveat helps but Gemini may classify borderline venues as `occasional` rather than `specialist`. Worth a spot-check after the cache warms.
  - **The two East Asian cuisines (japanese, korean)** are highly mainstream in SG/MY — the cache will warm quickly. Cross-contamination risk is lower than the South Asian or Slavic/EE sets; the prompts mainly guard against sushi-fusion / pan-Asian misclassification.
