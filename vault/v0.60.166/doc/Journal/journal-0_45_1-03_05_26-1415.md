## New

### [HDR] #93 | 14:15:00 SGT 03-05-26 | v0.45.1 | n/a kb | n/a lines

- **[INTENT]** v0.45.0 was supposed to fix the "Location is using Apple map" issue across all venue cards. Production trace from `/p m halal ramen` revealed two bugs the v0.45.0 changes didn't catch:
  1. **`/p m` had no Singapore location bias** — search returned NYC, Houston, Texas, IL results because Places API `searchText` was unconstrained. soleat is a SG-only bot.
  2. **`googleMapsUrl()` fallback chain was still wrong** — when `googleMapsLinks.placeUri` was absent (which Places API does for some venues), the helper preferred `googleMapsUri` (cid URL — Apple-Maps-on-iOS source) OVER the synthesised `place_id:` deep-link. The synthesised deep-link was buried at position 4 in the chain; the cid URL was position 3. Wrong order. Defeated the entire v0.45.0 fix for any venue without `googleMapsLinks`.

- **[DESIGN]**

  1. **`maps-url.js` — fallback chain reordered**:
     - **OLD** (v0.45.0): placeUri → place.url → googleMapsUri (cid) → synthesised place_id → directionsUri → coords → null
     - **NEW** (v0.45.1): placeUri → **synthesised place_id** → place.url → googleMapsUri (cid) → directionsUri → coords → null
     - Why: when `place.id` exists (which it does for every Places API response we touch), we can ALWAYS construct an iOS-friendly URL. The cid URL should be the absolute last resort — we'd rather fall to `https://www.google.com/maps/place/?q=place_id:<id>` than a cid-based URL that may route to Apple Maps.
     - The fix is one line of code reordering, but it's the difference between v0.45.0 working only for venues-with-placeUri and v0.45.1 working for any venue with a place_id.

  2. **`prompt-query.js#viaMaps` — Singapore locationBias**:
     ```js
     const SG_BOUNDS = {
       rectangle: {
         low:  { latitude: 1.13, longitude: 103.59 },
         high: { latitude: 1.47, longitude: 104.10 }
       }
     };
     // ... locationBias: SG_BOUNDS in the searchText body
     ```
     - **`locationBias` (soft)**, not `locationRestriction` (hard). If user explicitly types "halal ramen Tokyo", Places will still return Tokyo. SG just gets prioritised when the query is ambiguous (which is the common case for a SG bot).
     - Bounds chosen are Singapore's bounding box rounded to 2dp. Covers the entire island, all surrounding waters, and parts of Johor/Riau — slightly generous, but harmless (those regions don't have many F&B results that overlap with SG queries).
     - Affects only `/p m`. The discovery pipeline used by `/cuisine` (in `pipeline.js`) already passes `locationRestriction` from the user's actual coordinates — no change needed there.

  3. **Tests** — 2 new tests (128 total, was 126):
     - "v0.45.1: synthesises place_id deep-link BEFORE falling to cid URL" — directly asserts the bug fix. Pre-v0.45.1 this test would have failed.
     - "place.url is also rejected if it has no http(s) scheme" — defensive coverage for the new ordering's interaction with non-http url fields.
     - Existing 5 tests for the helper updated to reflect new fallback order (the assertions about which URL wins changed).

```js
// 4. place.googleMapsUri              (cid URL — last resort)
// 5. place.directionsUri              (directions-mode last resort)
```
