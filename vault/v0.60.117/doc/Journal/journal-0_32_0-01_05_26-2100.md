## New

### [HDR] #71 | 21:00:00 SGT 01-05-26 | v0.32.0 | n/a kb | n/a lines
- **[INTENT]** Major architectural shift per Human Lead instruction:
  > "take selection first from the TMA, put into a database record, then run Gemini @ railway to construct a prompt, keep the prompt in same database row, then plumb at the server. Before returning the result. This may resulted in two or more round of tokens"
  
  Decoded: request persistence + two-stage Gemini (Stage A constructs the executor prompt → Stage B executes) with TMA polling for completion. This becomes the foundation for v0.33-v0.36 (`/hawker`, `/recognised`, `/heritage-food`, carpark-as-footfall).
  
  Three concurrent UX changes ride along: (1) `/cuisine` results converge on a single shared "🗺 View all on map" button instead of N per-card map links; (2) `📤 Save to chat` button per card lets users push individual picks into chat for persistence/sharing; (3) `/surprise` becomes a multi-venue list (5 hidden gems) with rating window 4.0-4.3, <50 reviews, launched within 90 days, and day/night temporal switch — final prompt syntax provided verbatim by Human Lead.

- **[DESIGN]**
  1. **Request store** (`request-store.js`) — Redis HASH `cuisine-request:<reqId>`, 1 h TTL. Fields: chatId, userId, payload, status, stage, prompt_constructed, candidates, venues, diag, error, timestamps. Single source of truth for an in-flight or completed request.
  2. **Stage A — `prompt-builder.js`** — Gemini Flash call (~2 s, no grounding tools) takes user filters + neighbourhood/meal/holiday context and constructs the OPTIMAL executor prompt as `{system, user, schema, relaxations, reasoning}`. Static fallback prompt when Gemini unreachable.
  3. **Stage B — `pipeline.reasonExecute(prompt)`** — refactored from `pipeline.reason()` to accept a pre-built prompt object instead of internally constructing. Same lenient JSON parser; no grounding tools (kept the v0.31.2 fix). Returns `{candidates, rawText, meta}` instead of just `candidates`.
  4. **Background runner — `pipeline-task.js`** — orchestrates Stage A → Stage B (with relaxation retry on 0 candidates) → place validate → rank → refine. Writes stage transitions to the request row at every step. `runCuisineTask` and `runSurpriseTask` share the same skeleton; surprise applies extra gates (rating 4.0-4.3, <50 reviews, launch within 90 d, day/night temporal).
  5. **HTTP routes** —
     - `POST /api/cuisine-search` now returns 202 + `{reqId, pollUrl}` and spawns background `runTask` (was: synchronous response with full venues).
     - `GET /api/cuisine-search/:reqId` returns the row state (status, stage, venues, diag).
     - `POST /api/surprise-search` + `GET /api/surprise-search/:reqId` mirror cuisine for the new TMA-driven `/surprise` flow.
     - `PIPELINE_TASKS_ENABLED=false` env reverts the POST endpoint to v0.31.x synchronous behaviour as rollback.
  6. **TMA submit + poll** (`web/cuisine/src/api/search.js` + `App.jsx`) — replaces the 25 s fetch with `submitSearch(payload)` + `pollUntilDone(reqId, …)` polling every 1.5 s. Banner shows current stage label (`Stage A — building prompt`, `Stage B — reasoning`, `Validating venues`, …). Dual-channel sendData fallback retained for hostile webviews.
  7. **Single shared map button** — `ResultsGrid.jsx` adds footer `🗺 View all N picks on map` button. Tapping opens `/app/map#venues=<base64-json>`. `public/app.js` decodes the hash and renders all venues as AdvancedMarkerElement pins on one map. Per-card 📍 Google Maps button removed from `VenueCard.jsx`.
  8. **Save to chat** — `VenueCard.jsx` adds `📤 Save to chat` button per card. Calls `Telegram.WebApp.sendData({cmd: 'save-pick', placeId, name})`. `index.js routeMenuCommand` handles `save-pick` (alias for `cuisine-pick`) by posting that single Sanctuary read to chat. Backward-compatible with older bundles still emitting `cuisine-pick`.
  9. **/surprise multi-venue** — `runSurpriseCommand` now uses pipeline-task (kind=`surprise`) and delivers 5 venues via `deliverPicks` instead of 1 via `deliverSurprise`. Final prompt syntax (Human Lead, this turn): rating window 4.0-4.3, <50 reviews, **launched within last 3 months** (verifiedOpeningDate ≥ today-90d, soft-fallback to 180d if 0 venues), 2-4 dishes per venue with reviewer-praise framing, day/night temporal switch (day: openNow + closesIn≥2h; night: openNow + closesIn≥4h OR opensWithinHours≤12 for breakfast pivot). Old `findSurprise` retained for `PIPELINE_TASKS_ENABLED=false` rollback.

- **[KNOWN GAPS]**
  - **Stage A model is hard-coded to Gemini 2.5 Flash.** Could be `GEMINI_STAGE_A_MODEL` env-overridable for experimentation; not done in v0.32.0 to keep deployment surface tight.
  - **Polling interval is fixed at 1.5 s.** A backoff schedule (1.5 s for first 10 s, 3 s after) would reduce poll-load on long-running pipelines but adds complexity without a measured need yet.
  - **`/api/tma-map` token-based map handoff** considered and rejected: URL hash works, costs $0/render, no extra Redis state.
  - **`requestStore.pushDiag` is read-modify-write** (HGET diag → JSON.parse → push → HSET). Not atomic but fine because there's only one writer (the background task).
  - **Reqid-ownership check** uses `String(req.tg?.user?.id) === row.userId`. If TMA initData fails to parse user ID for any reason, the check is skipped (`tgUserId` empty → permissive). This is intentional for sandboxed tests; production deploys always have initData.
  - **Surprise temporal gate** uses `closesInHours` and `opensWithinHours` fields that are NOT yet populated by `validateWithPlaces`. Until those are populated, the gate becomes permissive (allows venues without closing-time data). Future work: extend `validateWithPlaces` to compute these from Places API `currentOpeningHours.periods`.
