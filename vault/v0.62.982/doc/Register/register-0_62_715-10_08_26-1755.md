## Decisions (new this entry)

| # | Decision | Rationale |
| :--- | :--- | :--- |
| D-103 | **A cost guard fails OPEN; its alerting fails CLOSED.** `readSpend` returning `ok` on a broken cost read means a monitoring outage never silently degrades the product for every user at once. `shouldAlert` returning `false` on a broken Redis latch means a Redis hiccup never produces an alert loop DMing the operator on every request. The two directions look inconsistent until you name what each protects; both are pinned by name in the test file so a refactor can't quietly flip either. | v0.62.715 |
| D-104 | **A mutation that stays GREEN is a finding about the test, not a clean bill of health — investigate it, don't wave it through.** Two of three mutations this entry survived: (a) flipping fail-open to fail-closed, because `api-cost.getCostSummary` absorbs Redis errors internally and returns a zeroed summary, so `readSpend`'s own catch was never reached by any test; (b) removing the unknown-step allow-list guard, because the test set `SPEND_HARD_USD=1` while leaving soft at its default 10 — and `levelFor` deliberately ignores a `hard < soft` config, so the reading was `soft` and the test passed **vacuously**. Both tests would have shipped green while asserting nothing about the properties they named. Fixed (hostile-client case; both thresholds set + an explicit precondition assert), then re-run to confirm red. | v0.62.715 |
| D-105 | **Degrade the product before refusing it, and only ever at the edges.** The sheddable set is confined to additive polish (sanctuary read, footfall, LLM dish extraction, `/hidden`). Places search, venue cards, and `/cost` are never gated; an unknown step name is always allowed so a typo can't silently disable enrichment that was never meant to be sheddable. | v0.62.715 |

## Note

Three of the four planned phases are now built (A: visibility, B: one confirmed leak removed, C: acting
on the number). O-174's remaining scope is Phase D alone — extending `rate-limit.js`'s Redis-counter
pattern to the Telegram bot commands, which today have **no** per-user cap at all (the existing limiter
covers only 12 HTTP `/api/cuisine/*` endpoints). Note the division of labour between C and D: Phase C
caps what the *system* spends in a day; Phase D caps what any *one user* can trigger. Neither
substitutes for the other — a single user could exhaust the daily cap under C alone, degrading the
product for everyone else, which is precisely the hole D closes.

D-104 is the entry worth carrying forward as a habit: two mutations here stayed green, and in both cases
the correct read was "the test is broken", not "the code is fine".
