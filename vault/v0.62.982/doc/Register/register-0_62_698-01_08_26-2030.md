## Decisions (new this entry)

| # | Decision | Rationale |
| :--- | :--- | :--- |
| D-68 | **A size that must reach the element goes ON the element.** The iOS guard `input, textarea, select { font-size: 16px }` is specificity (0,0,1) and was competing with Tailwind's `text-xs` at (0,1,0) — a contest it can never win, for six versions. Where a value has to beat a utility class, set it at the same level as the thing that would override it. `!important` on the guard was rejected: it would force every input in the app to exactly 16px, shrinking any that legitimately want to be larger — an app-wide restyle inside a one-field bug report. | v0.62.698 |
| D-69 | **A control that appears interactive must do something.** Re-tapping the active zone pill called `setActiveRegion` with the value it already held; React bailed and nothing moved. It now re-frames the zone. Same reasoning as D-65 (a control that cannot change the result must not be offered), applied to one that simply did nothing. | v0.62.698 |

## Note

O-104 is the interesting one. It sat open for six versions with a correct diagnosis and no fix,
because the fix was framed as a tradeoff against "the 14px parity" — and nobody had felt the cost of
*not* fixing it. A device report settled in one sentence what six versions of deliberation had not:
the page zooming is worse than a field being 4px larger.

The mechanism is worth keeping visible. The guard was not missing, and it was not wrong; it simply
could not win. `input { font-size: 16px }` is (0,0,1) and `.text-xs` is (0,1,0), so the rule was
inert from the moment any input picked up a Tailwind size class — which every one of them has. It
would have looked correct in every code review, and it did, repeatedly.

That is the same shape as the compiled-CSS grep in D-62: a check that reads as a guarantee and is
actually a statement about something adjacent. The guard says what it wants in a comment; CSS decides
what it gets.
