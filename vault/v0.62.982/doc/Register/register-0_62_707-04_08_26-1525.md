## Decisions (new this entry)

| # | Decision | Rationale |
| :--- | :--- | :--- |
| D-88 | **A unit test asserts the model; only the real thing tests the join between the model and the platform.** The ramp was correct, fully covered by 19 passing tests, and produced **0 px of movement in the browser** with the card held just inside the zone boundary. `scrollTop` quantises to whole pixels: a 0.1 px/frame delta assigned `before + 0.1`, landed back on `before`, and the fraction was discarded every frame. Anything under ~0.5 px/frame was dead, which silently pushed the rest band ~14 px past its designed end and made the shipped feel disagree with the tested one. No test of the pure function could have found it, because the pure function was right — the loss happened where the model met the DOM. Where a computed value is handed to a platform API, the platform's own quantisation is part of the contract. | v0.62.707 |
| D-89 | **When a complaint is about feel, check first whether something is simply broken.** "Too smooth to move around" reads as a tuning request, and half of it was. The other half was a missing movement guard: `dnd.js` had no `onPointerMove` at all, so every attempt to scroll the list by swiping on a card started a drag. Tuning the ramp without finding that would have produced a differently broken interaction and a second round of the same complaint. A feel report is evidence that something is wrong, not evidence about *what*. | v0.62.707 |

## Open (new this entry)

| # | Item | Note |
| :--- | :--- | :--- |
| O-158 | **The scroll lock is unproven on touch, which is the only place it matters.** The probe drives a synthetic **mouse**, and mouse pointers never trigger the native touch-scroll arbitration that the entire `touch-action` argument turns on. Whether setting `touch-action: none` mid-gesture actually holds in Telegram's iOS WebView — and whether the browser has really not yet committed to a scroll after 280 ms of stillness — is exactly what has not been tested. |
| O-159 | **72 px zone, 14 px/frame ceiling and curve 2 are chosen, not measured.** They give a ~130:1 ratio between a nudge and a commitment in the probe, which reads right. Nobody has dragged a card on a phone with them. |
| O-160 | **`scrollParent` returns `null` for a list that is not currently overflowing**, so a short list gets no lock and no edge scroll. Correct in itself, but it means the interaction's behaviour changes as content grows, and nothing surfaces that. |
| O-161 | **The horizontal catch-all strip is untouched.** This model is vertical only. Dragging a card out of the horizontal strip still has whatever behaviour it had. |

## Note

`createLongPress` was written three versions ago for a completely different control — the footer tab
— and it dropped into the card drag unchanged, tolerance aside. That is the second consumer of a
module that could easily have been written inline in `Shell.jsx`, and it arrived with its drift rule
already tested. Worth noticing, because the drift rule is exactly the thing that was missing from
`dnd.js` and had been missing since the drag was first written.

The more uncomfortable item is D-88. The scroll ramp had 19 passing tests and was **still wrong in
the browser** — not subtly, but completely dead across the slow half of its range. The tests were
not weak; they asserted the right things about the right function. The defect was one layer down, in
the assumption that assigning a fractional value to `scrollTop` moves anything. Three of the last
four versions have now been rescued by driving the real built app rather than by reasoning about it,
and O-157 records that none of those probes has touched a device.
