## Note

Two things worth recording about the catch-up itself.

**The PR listing's `merged` boolean cannot be trusted.** Every PR in the API listing came back
`"merged": false` — including #1666–#1671, which are already in the ledger *as merged*, and #1684/#1685,
which this session merged by hand minutes earlier. `merged_at` was populated and correct throughout.
Taking `merged` at face value would have appended fourteen rows marked unmerged and quietly skewed
every merged/unmerged statistic on the hosted page. The field that was checkable against known
ground truth is what caught it.

**O-105 grew while it waited.** It was opened at a 10-PR gap and closed at 14. The ledger has no
mechanism that notices it has fallen behind — regeneration is a manual step in the root `CLAUDE.md`
standing rule, and a busy arc is exactly when it gets skipped and exactly when the most rows accrue.
Nothing is proposed here; it is noted so the next gap is read as normal rather than as an anomaly.
