| D-409 | A location picked in the Cuisine-TMA Search-criteria builder is the durable search anchor AND becomes the user's `/location` — but only an explicit place pick persists | 11-05 '26 | Operator: "I change the location in Search Criteria … it should lock in." So an explicit pick routes through the never-nulled `locationAnchor` state and also `POST /api/cuisine/set-location`. A `×` clear, a map pan, and "Search this area" deliberately do **not** persist to `/location` — casual map exploration mustn't clobber the saved pin. |

The old `transport:bus:route` callback / text path is kept for anyone hitting it directly. |
| D-411 | Free-text dish search keeps everything, sorts "actually serves it" above a divider, looser matches below — never drops results | 11-05 '26 | Operator, re-testing "Goulash dumplings": "don't drop anything — sort exact → possibilities, with a divider line, ≥~7 shown." A venue is "above the line" only if its **name** (or `primaryType`) self-identifies as the cuisine — a strong word found only in a review is a soft ordering signal, not an above-the-line ticket. |
| D-412 | The Cuisine-TMA "Tell me" free-text box folds into the Places query as a qualifier; Enter does not fire a search | 11-05 '26 | Operator: typing in the box then picking a cuisine ran the search with only the cuisine — the typed text was being dropped from the Places query (it only fed the criteria hash + the R.E.D probe). Enter shouldn't fire a search either (search is via the → button / 🔍 buttons / FAB). |
| D-413 | The two operator reference tables (`Misrepresented Dish Dessert Drink.MD`, `cooking method reference by cuisine.md`) are consumed at module load from `data/*.md`, not pre-baked into JS, and not editing the source files | 11-05 '26 | Keeps the operator's plain-text tables editable in one place; the modules parse them defensively (never throw if a file is missing/garbled) — same pattern as the existing `data/mrt-coords.json` etc. read at startup. The misrep table is informational only (it never steers the search; that's R.E.D's job); the cooking-method table merges INTO the existing `cooking-methods.js` dict (per the operator's "combine with existing") rather than living separately. |
| D-414 | The cooking-method "did you mean" pivot is always-on for any match in chat / Cuisine TMA; `/s` keeps a verbatim-single-cuisine fast path | 11-05 '26 | The .md note: "Better to check with user if he/her meant this." So chat / TMA always show the pivot when a cooking-method match exists (even an unambiguous one — it shows one cuisine chip). `/s` is a power-user surface: a *verbatim* single-cuisine method (the user typed the exact chef compound) still fans out directly, preserving the pre-v0.60.129 behaviour; ambiguous / non-verbatim → pivot. Recorded in Deferred below as a tunable boundary. |
| D-415 | Bare single-token common cooking verbs from the operator .md are dropped at merge time, not added to `COOKING_METHODS` | 11-05 '26 | A bare "steaming" / "smoking" / "pickling" entry would false-match any input containing the verb (the matcher's single-token rule is `userText.includes(token)`). `MD_BARE_VERB_STOPLIST` (~50 verbs) filters them; multi-token compounds ("tea-smoking", "deep-frying", "charcoal grilling") are unaffected. The pre-existing matcher's ordered-prefix quirk (`'smoking'` → 'smoking with cypress' → Sichuanese) predates this arc and is not fixed here. |
