## New

### [HDR] #367 | 12:00 SGT 27-05-27 | v0.61.166 — Periodical cadence + 6h scheduler tick (PR 3/3) | 6 files | 1 PR | 1 build |

- **[INTENT]** Make the Periodical lever fully autonomous. Today
  every recount is operator-tap (via the v0.61.165 chat UI).
  v0.61.166 lets the operator set a per-item cadence:
  - `manual` (default): never auto; operator tap only.
  - `4-monthly`: re-count when ≥ 120 days since the latest history
     entry.
  - `yearly`: re-count when ≥ 365 days.
  - `off`: never auto AND silent in logs (operator explicitly
     suppressed).
  A 6h tick (`setInterval`) walks all 14 items each tick and
  runs `recountOne` for any due item. The interval check uses
  the history's newest ts, so container restarts don't double-
  count.

- **[DELTA]**
  - **`count-cadence.js`** (NEW, ~90 lines).
    - **`VALUES = ['manual', '4-monthly', 'yearly', 'off']`**;
      **`DEFAULT_VALUE = 'manual'`**.
    - **`DAYS_4_MONTHLY = 120`, `DAYS_YEARLY = 365`** —
      operator-confirmed thresholds.
    - **`isValidValue(v)`** — strict membership.
    - **`getCadence(redis, item)`** — returns the stored value
      or `'manual'`. Defensive against closed Redis.
    - **`setCadence(redis, item, value)`** — validates + writes;
      returns boolean.
    - **`listAll(redis, items)`** — batch read into a `Map`. The
      scheduler calls this once per tick to avoid 14 sequential
      `getCadence` round-trips.
    - **`intervalMs(value)`** — returns ms duration for
      `'4-monthly'` / `'yearly'`, or `null` for `'manual'` / `'off'`
      (never auto). Pure helper used by the scheduler.
    - **Storage**: `count:cadence:<item>` Redis string. No TTL.
  - **`count-scheduler.js`** (NEW, ~50 lines).
    - **`runDueRecounts(redis, opts)`** — the only exported fn.
      Reads the cadence map via `listAll`, then for each item:
      - Skip if cadence is `manual`/`off` (intervalMs returns null).
      - Read the newest history entry's `ts`.
      - If `(now - ts) ≥ interval` (or no history at all → seed
         run), call `recountOne(redis, item, { source: cadence,
         notes: 'scheduler tick at <iso>' })`.
      - Per-item failure caught + logged; loop continues.
      - Returns the array of `{item, n, source}` for items that
         actually re-counted.
    - **`opts.now`** lets tests inject a synthetic clock.
  - **`__tests__/count-cadence.test.js`** (NEW, 14 tests):
    constants, isValidValue, intervalMs (manual/off/4M/Y/unknown),
    getCadence default, set+read round-trip, invalid-value
    rejection, defensive (null/closed redis), listAll Map
    contract.
  - **`__tests__/count-scheduler.test.js`** (NEW, 10 tests):
    cadence gating (manual/off skips), seed run for items with
    no history, 120-day interval gate for 4-monthly, 365-day
    gate for yearly, history source = cadence label, synthetic
    `opts.now` clock, multi-item walk (only due items fire).
  - **`index.js`** (3 wiring edits):
    1. **`ownerPeriodicalItemPanel`** header now shows the
       current cadence: `📊 <b>Cuisines</b> · cadence: <i>4-monthly</i>`.
       A new row of 4 cadence buttons (M / 4M / 1Y / Off) sits
       between Re-check and Revert; the active value gets a `✓`
       prefix. Each button fires `per:set-cadence:<item>:<value>`.
    2. **`callback_query`** dispatch adds a `per:set-cadence:*`
       handler that calls `setCadence`, surfaces a warning on
       invalid input, then re-renders the panel.
    3. **Startup wiring** — a new `setInterval` near the existing
       24h LTA bus-stops refresh:
       ```
       setInterval(() => {
         if (!redis?.isOpen) return;
         require('./count-scheduler').runDueRecounts(redis)
           .then((r) => r.length && console.log('[Periodical] tick: ran N due recount(s) ...'));
       }, 6 * 60 * 60 * 1000);
       ```
       6h tick = 4 ticks/day; items still re-count only when
       their cadence interval has elapsed (no over-counting).

- **[KNOWN GAPS]**
  - **TMA "{n}+ cuisines" string template** is filed as a
    follow-up. The data layer + scheduler now have the live
    count; wiring the TMA template (probably a
    `/api/cuisine/counts` GET that returns `{ cuisines, hawker,
    michelin, … }` + a Cuisine TMA banner update) is a ~15-min
    follow-up. Splitting it from this PR keeps the scope tight
    enough to review.
  - **6h tick interval** is arbitrary. 4-monthly / yearly items
    only ever recount once per cadence period, so any tick
    cadence < 1 day is fine. 6h was picked to balance "fresh
    log on every Railway redeploy" against "minimal background
    work". Tunable via `PERIODICAL_TICK_MS`.
  - **No cadence-change confirmation step.** Tapping a cadence
    button writes immediately. Acceptable for an owner-only menu;
    if the operator wants a confirm modal, it's an extra
    callback state.
  - **No "next scheduled run" estimate** in the panel header.
    The operator can compute it manually: `latestTs +
    intervalMs(cadence)`. Future enhancement: panel shows
    `next: 2026-09-24` next to the cadence label.
