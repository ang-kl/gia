  only the `‹` (previous-page) button was switched to `.gia-hit-y`; the `›` (next-page) button kept

  important of the two, and the reported symptom would have survived the "fix". Verified by grep
  before and after (`App.jsx:5782` and `:5793` now both `.gia-hit-y`). Recorded as a correction to
  C-93 rather than a new item: the O-92 root-cause analysis was right, the application was
  incomplete. Worth noting the shape — a fix verified by *reasoning about the root cause* but never
  by *checking every site the root cause applies to*; the same class of gap as the v0.62.671
  git-add incident (O-90) and D-22…D-28, and again caught by an outside check rather than by
  anything in the verification I ran (build + tests are both blind to which class a button carries).

- **[Card gap — quantified, then decided by the operator]** Built the before/after table from the
  CSS rather than from eyeballing the screenshots, separating exact from derived:
  | State | Drawer `bottom` | Gap above strip top | Δ vs. second-load |
  |---|---|---|---|
  | First open (no criteria) | `calc(4.5rem + 2px)` = **74px** | ~**−16px** (card overlaps the strip's top edge) | **−24px** |
  | After a search (criteria present) | `calc(6rem + 2px)` = **98px** | ~**+8px** | baseline |
  | v0.62.681 as shipped | measured strip top + 2px ≈ **92px** | **+2px** | **−6px** |
  The 74/98 offsets and the 24px delta are exact (straight from the ternary); the strip's top edge
  (~90px from the viewport bottom — dock ≈53.5px + `gap-1.5` 6px + safe-area padding ≈19px, plus the
  strip's own `self-end -mb-2` pull-down) is derived and device-dependent. The card's internal bottom
  padding adds the same constant to all three rows, so **the Δ column is exact even where the
  absolute gaps are not** — which is what made the table decision-grade.
  This surfaced a real conflict worth putting to the operator instead of assuming: a literal 2px
  (the v0.62.650 ask) is **tighter** than the +8px second-load state the operator had just pointed at
  as the one that looked right. Asked; answer: *"Split it — ~4-5px."* Implemented as
  `STRIP_GAP_PX = 5` in `ResultDrawer.jsx` (module-level named constant, not an inline literal —
  this is the third time this number has moved), the exact midpoint of 2 and 8, applied to the
  MEASURED offset so it is a true 5px on every device. The first-paint `calc()` fallback keeps its
  own historic +2px, unchanged.
