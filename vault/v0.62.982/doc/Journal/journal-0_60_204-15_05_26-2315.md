> Operator: *"Want me to ship DF-105 (cache headers) as v0.60.204"* (confirming my offer from v0.60.203's audit). Five `/app/*` TMA static mounts now serve their Vite-bundled assets with `Cache-Control: public, max-age=31536000, immutable`; entry-point HTMLs continue to receive `no-store, no-cache` so a new deploy is picked up on the next TMA open.

## New

### [HDR] #172 | 23:15:00 SGT 15-05-26 | v0.60.204 — TMA static-bundle cache headers (DF-105) | 3 files, +24 LOC | 1 PR |

- **[INTENT]** Close DF-105 from v0.60.203's audit: every TMA open re-validated bundle assets with the server (300-800 ms 304 round-trip on cellular) because `express.static('/app/<tma>')` had no `maxAge`. Vite's content-hashed asset filenames make immutable caching trivially safe — a code change re-hashes the filename, so stale hashes can never resolve. Entry-point HTML files keep `no-cache` so users always see the latest manifest.

- **[DELTA]**

  **`index.js`** — new `STATIC_OPTS` constant defined just after the existing `noCacheHtml` helper (line 8215):
  ```js
  const STATIC_OPTS = {
    maxAge: '1y',
    immutable: true,
    setHeaders(res, filePath) {
      if (filePath.endsWith('.html')) {
        res.setHeader('Cache-Control', 'no-store, no-cache, must-revalidate, max-age=0');
      }
    }
  };
  ```
  Applied to five mounts:
  - `app.use('/app/menu', express.static(…, STATIC_OPTS))`
  - `app.use('/app/cuisine', …)`
  - `app.use('/app/hawker', …)`
  - `app.use('/app/transport', …)`
  - `app.use('/app/oversight', …)`

  The `app.use('/static', express.static(…))` catch-all at line 8118 is left unchanged — it's before the `STATIC_OPTS` definition and serves miscellaneous public files (icons, the v0.4.0 vanilla-JS map TMA), not the per-TMA Vite bundles. Not the bottleneck.

  HTML entry points are protected two ways: (a) the explicit `app.get('/app/<tma>', …)` routes already wrap their `sendFile` in `noCacheHtml`; (b) the `setHeaders` callback in `STATIC_OPTS` strips long-cache from `.html` if someone hits it directly via the static middleware (e.g. `/app/cuisine/index.html`).

- **[TEST]** Post-deploy, on a phone with browser dev-tools (or the new TMA-debug session):
  1. First TMA open (cold cache) → 200 responses for `index-<hash>.js` + `index-<hash>.css` (as before). Response carries `Cache-Control: public, max-age=31536000, immutable`.
  2. Close TMA, re-open → bundle requests are served from disk cache instantly (no network round-trip, no 304). User-felt speedup: 0.3-1 s.
  3. Deploy a new version → Vite re-hashes the bundle filenames → browser sees a brand new URL → fresh download. Old hash URLs may persist in cache, harmless (they're addressable but no longer linked from any HTML).
  4. `index.html` requests always return 200 with `no-store` — operator-facing copy / chip-label changes propagate instantly.

  Use Telegram WebApp's Inspect (long-press the TMA → "Inspect Element" on iOS) to confirm Network panel shows `from disk cache` on the second open.
