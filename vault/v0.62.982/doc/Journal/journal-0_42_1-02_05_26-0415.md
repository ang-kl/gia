## New

### [HDR] #87 | 04:15:00 SGT 02-05-26 | v0.42.1 | n/a kb | n/a lines

- **[INTENT]** Fix three real bugs from the outstanding-bugs audit: B1 (voice handler honest fallback), B3 (Telegram polling/webhook error handlers), B4 (request idempotency). All small, all visible to users.

- **[B1 — voice handler honest fallback]**
  - **Pre-fix behaviour:** v0.40.0 stubbed `classifyVoice()` to return `null`. The voice handler in `index.js` already caught `!cls` and replied "Sorry, I couldn't transcribe that...", but FIRST sent "🎙 Heard you — transcribing…" which was misleading — transcription was disabled, not failing.
  - **Fix:**
    - `voice-input.js` — added `isAvailable()` predicate (today always `false`; flip when Whisper / AssemblyAI / Deepgram is plumbed). `classifyVoice()` now returns `{ disabled: true, reason: 'voice_transcription_unavailable' }` instead of `null` so the handler can branch deterministically.
    - `index.js#bot.on('voice')` — short-circuits on `!voiceAvailable()` BEFORE the misleading "transcribing…" tease. Sends a single honest message: *"🎙 Voice transcription is temporarily unavailable — please type your question instead."*
    - The cls-error branch also handles the new `cls.disabled` shape for belt-and-braces.
  - **Verification:** Send a voice note → bot replies once with the honest message + verbose log shows `D760-B1`.

- **[B3 — Telegram polling/webhook/bot error handlers]**
  - **Pre-fix behaviour:** No `bot.on('polling_error')` or `webhook_error` registered. A transient Telegram outage (502, polling drop, ECONNRESET) caused node-telegram-bot-api's internal loop to fall over silently. Bot went dark until Node process restart. Operator noticed only when users complained.
  - **Fix:**
    - Added three handlers right after bot init in `index.js`: `bot.on('polling_error')`, `bot.on('webhook_error')`, `bot.on('error')`.
    - All three log via pino (`logger.warn` for polling/webhook, `.error` for bot) and capture to Sentry via `captureWithReqId(err, null, { kind: 'telegram_*' })`.
    - The `beforeSend` hook in `sentry.js` continues to drop `ETELEGRAM 429/502` and `EFATAL.*AggregateError` noise; only meaningful errors reach the inbox.
    - The SDK auto-recovers polling on its own — these handlers are observability, not recovery. Recovery (process restart on N consecutive fails) deferred to v0.43.0+.
  - **Verification:** Force a Telegram outage simulation by setting an invalid bot token briefly — observe pino warn + Sentry capture (if DSN set).

- **[B4 — request idempotency on /api/cuisine-search]**
  - **Pre-fix behaviour:** A double-tap on Search in the TMA fired two `pipeline-task#runCuisineTask` invocations for the same `(chatId, payload)`. Cheap on Sonnet 4.6 (~$0.02 each) but wastes Anthropic + Places quota under burst load.
  - **Fix:**
    - Added Redis SETNX-style idempotency in the `/api/cuisine-search` POST handler: key = `idem:cuisine:<chatId>:<sha256(payload).slice(0,16)>`, TTL 30s.
    - On request: `redis.get(key)` first. If hit → return existing `reqId` with `idempotent: true` flag in the 202 response.
    - Otherwise: create new request, write `(key → reqId)` with EX=30, fire pipeline-task.
    - 30s window matches typical TMA polling-tap cadence; longer would cause stale results, shorter wouldn't dedup human double-taps.
    - New diagnostic codes: `D713 idempotent`, `D714 idempotency-key write failed` (non-fatal — request still proceeds).
  - **Verification:** Tap Search twice rapidly in TMA → second response shows `idempotent: true` with same `reqId`.
