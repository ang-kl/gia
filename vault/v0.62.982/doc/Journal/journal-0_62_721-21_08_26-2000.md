# Journal — soleat / Gia4lunch v0.62.721

## New

### [HDR] v0.62.721 — Copy-all: a relative URL in a button that took the whole message down

- **[INTENT]** Operator: *"what is happening. i am getting upset"* — and they were right
  to be. O-192 had sat open for days at the top of this session's own priority list while
  five PRs of scaffolding went past it. Each time it came up, this session offered a
  hypothesis and asked the operator to run a two-tap test instead of debugging it. That
  was the actual failure: generating work for the operator rather than doing the work.

- **[ROOT CAUSE — two faults compounding]**
  1. `buildMapHashUrl` falls back to a **relative** URL when `webhookDomain` is empty:
     `soleat.net` → `https://soleat.net/app/map#venues=…`, but `''`/`undefined` →
     `/app/map#venues=…`. Telegram requires absolute `https` for both `web_app.url` and
     `url` and rejects the entire `sendMessage`, not just the button.
  2. The retry path re-attached the **same** `reply_markup`:
     `if (sendOpts.reply_markup) plainOpts.reply_markup = sendOpts.reply_markup;`
     It was written for parse-mode and message-length failures, and it is useless against
     the one failure it could have rescued. A refused button failed identically twice →
     `500 send_failed` → the TMA's "Couldn't send to chat", and nothing in the user's chat.

  Together these turn a cosmetic problem (no map button) into a total one (no message).
  Single-venue 📋 Copy has no button, which is why only *Copy all* broke — the asymmetry
  that was sitting in the code the whole time.

- **[DELTA — `index.js`]**
  - A non-absolute `mapUrl` is now treated as no URL at all: logged, button dropped, and
    the existing `pick.mapUnavailable` footer appended.
  - The plain-text retry no longer copies `reply_markup`. Picks without a map button beat
    no picks.

- **[VERIFICATION (sandbox)]**
  - Reproduced before fixing: `buildMapHashUrl(venues, { webhookDomain: '' })` returns a
    string that does **not** start with `https://`.
  - `node --check index.js` clean; `npx vitest run` — **171 files / 4,186 tests, 0 failures.**
  - 5 regression tests appended to `__tests__/copy-all-html.test.js`, including one that
    reproduces the relative-URL defect directly rather than asserting the fix.
  - `package.json` 0.62.720 → 0.62.721. No `web/` change.

- **[NOT VERIFIED — the honest limit]** Whether `webhookDomain` is actually empty in
  production is **unconfirmed**. The boot log reports `hasPrimary: true` and
  `[Updates] Webhook registered: https://soleat.net/webhook`, which argues it is set. So
  this fix may harden a path that was not the live trigger. What is certain is that the
  retry-keeps-markup bug made *any* button rejection fatal, and that is fixed regardless
  of which rejection was firing. The Railway log line
  `[Cuisine] copy-all sendMessage failed (HTML mode): <description>` will name the real
  one the next time it happens — and now, when it does, the user still receives their
  venues.

- **[RELATED, SAME SESSION — the embedded map]** Operator: *"the embedded map cannot be
  loaded"*. Different surface, same rotated credential. `gmaps-loader.js:69` loads
  `maps.googleapis.com/maps/api/js?key=…&libraries=marker`, which is **Maps JavaScript
  API** — a different API from the Places/Routes calls the server makes — and the loader's
  own comment (line 24) records that the key is **domain-restricted** in Cloud Console. A
  freshly-rotated key has neither the JS API enabled nor a referrer allow-list by default.
  Diagnosis handed to the operator with the two console errors that discriminate
  (`ApiNotActivatedMapError` vs `RefererNotAllowedMapError`). No code change: nothing here
  is wrong in the repo.
