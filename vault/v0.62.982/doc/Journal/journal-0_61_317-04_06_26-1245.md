# Journal — soleat v0.61.317 (recents drawer: resolve coords → place name on save)

> Operator (04-06 '26, screenshot of the Cuisine TMA recents drawer): rows like *"1.2722, 103.8113"*, *"1.4912, 103.7665"*, *"1.3029, 103.7660"*, *"2.9264, 101.6964"* showed raw coordinates instead of place names. Quote: *"the location are saved as coordinates which is meaningless to user, can you resolve this when save"*.
>
> Root cause: the Cuisine TMA's `/api/cuisine/set-location` write to the recent-locations LRU passed `label: opts.label || ''`. When the app POSTs coords-only (GPS auto-detect, map tap, "search this area"), the label is empty and the drawer falls back to rendering `<lat>, <lng>`. The screenshot's named rows (VivoCity, Raffles City Shopping Centre, West Coast Plaza, Mount Austin) came in *with* a label; the coordinate rows did not.
>
> Fix: reverse-geocode the coords into a human-readable name before storing (the `reverseGeocodeAddress` helper already exists, 24h-cached on a ~10m grid). Also forward `country` + `region` so the drawer row shows the right flag instead of the generic 🌍 globe seen on every row in the screenshot.
>
> Commit 531 / journal 518 / build 320, on branch `claude/v0.61.317-recents-resolve-label` off `main` at v0.61.316 (sha `9b77c29`).

- **[INTENT]** Make every recents-drawer row human-readable. No more bare `lat, lng` rows for coordinate-only saves; resolve a place name at save time, and surface the correct country flag.

- **[DELTA]**

  **1. `index.js`** — single edit inside the `/api/cuisine/set-location` handler (`index.js:13179` block, the v0.61.197 LRU push):
  - **Before**: `addRecentLocation(redis, String(userId), { lat, lng, label: opts.label || '' }).catch(() => {});`
  - **After**: a fire-and-forget async IIFE that:
    1. starts from `opts.label` / `opts.country` (whatever the client supplied);
    2. when no label, calls `reverseGeocodeAddress(lat, lng)` (defined at `index.js:201`, 24h Redis cache on a 4-dp grid) and uses its `.name`;
    3. **bare-country guard**: rejects a `.name` of "Singapore" / "Malaysia" (or a name equal to the resolved country long-name) — `reverseGeocodeAddress` falls back to the country when no finer feature exists, and that's as meaningless as raw coords, so the label stays empty (drawer falls back to coords) in that edge case;
    4. derives `country` (SG / MY) from the geocode when the client didn't send one;
    5. calls `addRecentLocation(...)` with `label` + `country` + `region`.
  - The IIFE runs AFTER `res.json({ ok: true })` semantics are unaffected — the HTTP 200 isn't delayed by the geocode round-trip (the existing `setUserLocation` await already completed; the LRU push was always fire-and-forget).

  **2. `package.json`** — `0.61.316 → 0.61.317`.

  **3. `doc/.serial-state.yml`** — commit 530→531, build 319→320, journal 517→518; re-anchored 04-06 '26 12:45 SGT.

- **[KNOWN GAPS]**
  - **Existing rows not migrated.** The screenshot's current coordinate rows won't retro-resolve; they update when re-anchored. A one-off backfill pass over each user's LRU was considered and deferred (more cost + complexity for a cosmetic gain on stale rows).
  - **Country mapping is SG/MY-only.** The geocode→ISO map covers Singapore + Malaysia (the bot's regions). A pick in Thailand/Indonesia via the OTHER picker already carries `opts.country` from the client, so it's covered there; a bare coordinate in a third country resolves a name but may show 🌍 (no ISO mapping) — acceptable.
  - **One extra reverse-geocode per unique coords-only save.** Bounded by the 24h `revgeo:addr:v2:<4dp>:<4dp>` cache; repeat saves at the same ~10m grid cell are free. Cost ≈ $0.005 per fresh cell per day (per `api-cost.js` rate card). Not instrumented in `/cost` yet (that path tracks place-autocomplete + place-resolve only).
  - **`reverseGeocodeAddress` needs `GOOGLE_MAPS_API_KEY`.** Unset → returns null → label stays empty → drawer falls back to coords (same as before). No regression.
