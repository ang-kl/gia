- **[INTENT]** Three bundled changes per operator's request:
  1. **Backend cap 12 → 19.** The v0.60.191 split (6 first tap /
     12 follow-up) is unified to 19 across both branches. The
     TMA's existing `ResultPanel` PAGE_SIZE=12 then paginates
     19 venues as 12 + 7 with the existing ◀ / ▶ strip — no new
     pagination machinery needed.
  2. **`Results (X/Y)` header always renders.** Previously the
     header only showed `(X/Y)` for Michelin (when `totalCount`
     was set) and plain `(X)` otherwise. v0.61.163 always renders
     the ratio: visible-on-current-page / total-loaded. So a
     19-venue search displays `Results (12/19)` on page 1,
     `Results (19/19)` after tapping ▶. Michelin's larger
     `totalCount` (~130) still slots in.
  3. **Friendlier zero-state.** Replaces the generic "No matches
     yet — pick a cuisine or use 💬 Tell me above." with
     "No results. Suggest changing the search criteria, or
     leaving it blank." (FR equivalent).

## Amendments

- **`FIRST_TAP_SLICE = 6` / `FOLLOW_UP_SLICE = 12`** (v0.60.191) —
  unified to `RESULT_SLICE = 19`. The first-tap latency saving
  is sacrificed for the operator's pagination indicator UX. If
  the latency hit shows up as a real problem in deploy logs,
  the constants can be re-split without rolling back the
  header / zero-state changes.
- **`ResultPanel.jsx` header** — was `Results (N)` plain or
  `Results (N/total)` only when Michelin's `totalCount` prop
  was set. Now always `Results (visibleOnPage/total)`. Behaviour
  for Michelin preserved (denom uses `totalCount` when set);
  cuisine search gets the same UX with `total = venues.length`.
- **Zero-state copy** — was "No matches yet — pick a cuisine or
  use 💬 Tell me above." Now the operator's preferred
  "No results. Suggest changing the search criteria, or leaving
  it blank." (EN / FR).
