## New

### [HDR] v0.62.713 — Phase A of the cost-audit remediation plan: instrument every real Gemini + Maps call site

- **[INTENT]** Operator raised a direct concern: *"serious concern over the use of tokens, i would like
  to know like how many request, how much information received like eateries (each eatery uses for what
  type of information received), or train or hawker or query. And firing model, per user and if there
  are leaks."* A full code-level audit (three parallel research agents + direct spot-verification of the
  two most consequential claims) found `/cost`'s existing tracker (`api-cost.js`) was nearly blind: 0 of
  ~10 real Gemini call sites fed `recordGeminiUsage`, only 2 of ~25 real Maps call sites fed
  `recordMapsCall`, and Routes API spend was untracked *and* unpriced (no `routes` entry in
  `PRICES.maps` at all). One initial finding was self-corrected before reaching the operator: the search
  cache's `skipCache = true` (index.js) is a **deliberate, documented v0.60.11 operator decision**
  (restores always-fresh results after a "clicking = same cached list, feels broken" complaint), not a
  bug — excluded from remediation. Operator chose the full 4-phase plan ("draft") over a two-item quick
  fix, then explicitly said **"remember to link to my telegram account via env.var. Start with Phase A"**
  — `TELEGRAM_OWNER_CHAT_ID` already exists and gates `/cost` + other owner-only commands, so it's noted
  for Phase C's future spend-alert DMs rather than inventing a new env var; this entry is Phase A only
  (pure instrumentation, the lowest-risk phase, first PR in the sequence).

- **[WHAT PHASE A DOES]** Adds a fire-and-forget `recordGeminiUsage`/`recordMapsCall` call immediately
  after every real, production Gemini `generateContent()` and Google Places/Routes `axios` call this
  session could find and safely thread a `redis` client into — zero behaviour change to any response,
  only visibility. Two upstream fixes were needed to make the tracking itself correct, not just present:
  1. `api-cost.js`'s `PRICES.maps` had no `routes` entry — Routes spend was unpriceable even where
     tracked. Added a `$0.005`/element point estimate (Google's Compute Route Matrix "Essentials" tier
     is volume-banded $2-$7/1,000 elements; exact tier needs a Cloud Console billing-export confirmation
     — flagged as a known gap, not guessed further).
  2. `recordMapsCall(redis, endpoint)` only ever incremented by 1 — but Routes bills per **element**
     (origins × destinations), and `travel-times.js` calls `computeRouteMatrix` with 1 origin × N
     candidate venues per mode, not 1×1. Recording it as "1 call" per mode would have silently
     undercounted every search by up to ~10-20x on the Routes line. Added an optional `count` parameter
     (default 1, so all ~30 existing single-request call sites are unaffected) and pass
     `candidates.length` explicitly at the one call site that needs it.

- **[THE REDIS-THREADING PATTERN]** Most instrumented functions don't have a `redis` client in scope —
  `gemini-client.js`, `translate-name.js`, `hidden-verify.js`, etc. are `require`d modules, not
  `index.js` itself. Rather than reach for a global singleton, every touched function gained an
  **optional `redis = null` parameter** (or reused an existing one already threaded for caching, e.g.
  `translate-review.js`/`translate-name.js`/`name-gloss.js` already took `redis` for their own 30-day
  cache and needed no signature change at all). `recordGeminiUsage`/`recordMapsCall` already no-op
  safely on a null/missing client (confirmed in `api-cost.js`'s own `_connect()` guard), so a caller that
  can't reach a redis client degrades to "untracked," never to a thrown error. Functions defined directly
  inside `index.js` (e.g. `nearestLandmark`, `fetchSinglePlaceForPick`) needed no parameter at all — they
  close over `index.js`'s module-level `const redis` automatically.

- **[HIGHEST-VALUE SINGLE FIX]** `pipeline.js`'s `discover()` is the single highest-volume Places call
  site in the app by a wide margin — it's the core `/api/cuisine/search` fetch, called from ~15 sites
  across `index.js`, `cuisine-search.js`, `pipeline-task.js`, and `vibe-suggest.js`. Instrumented its 4
  internal `axios.post` sites (fan-out seed loop, first page, page-walk pagination, dessert-mode
  `searchNearby`) and threaded `redis` through every live caller — including two call sites that inject
  `pipeline.discover` itself as a bound function reference (`cuisine-special-mode-widen.js`,
  `cuisine-nearby-refetch.js`), wrapped as `(opts) => pipeline.discover({ ...opts, redis })` at the
  injection point rather than touching either library file, since both already take an injected
  `discoverFn` and don't need to know redis exists.

- **[DEAD-CODE CHECK BEFORE THREADING]** `pipeline.js`'s legacy v0.26.0 `runPipeline()`
  (Reason-Fetch-Refine) has zero live callers anywhere in the codebase — confirmed by grep before
  spending effort threading `redis` through its `fetchClusterContext` → `nearestMrtStations` chain.
  Left untouched; `transport.js`'s `nearestMrtStations` still gained the `redis` param and instrumentation
  because its OTHER caller (`index.js:5912`) is very much live.
