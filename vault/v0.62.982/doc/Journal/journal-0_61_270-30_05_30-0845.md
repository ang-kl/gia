### [HDR] #471 | 08:45 SGT 30-05-30 | v0.61.270 — Phase 2 writer parity + country round-trip | 5 files | 1 PR | 1 build |

- **[INTENT]** Bring `/api/cuisine/set-location` to parity with `/api/menu/set-location` so Cuisine TMA picks persist the full anchor metadata (label, country, region, street, building, postal). Surface the persisted `country` in `/api/cuisine/user-location` responses. Sync `state.countryPref` from the cached anchor's country on Cuisine TMA mount + visibility-restore so the round-trip closes.

- **[DELTA]**

  **1. `location-cache.js`** — add `country` opt handling in `setUserLocation`

  Pre-v0.61.270, Menu's `/api/menu/set-location` route had been passing `{ country: cc }` to `setUserLocation` since v0.61.192, but the helper's opts processing only enumerated `region / radiusCapM / label / precinctId / street / building / postal` — `country` was silently dropped at the boundary. Now persisted with ISO 3166-1 alpha-2 validation + uppercase normalisation.

  **2. `index.js`** — two route changes

  - `/api/cuisine/user-location` GET response now includes `country` when persisted (line ~13119). This closes the read-side leak: Menu writes country → Cuisine reads country.
  - `/api/cuisine/set-location` POST handler now accepts the full payload (`label`, `country`, `region`, `street`, `building`, `postal`, `radiusCapM`) and forwards every populated field to `setUserLocation` via opts. Region is whitelist-validated against `/^(SG|JB|OTHER|MY-PUT)$/`; country must match `/^[A-Z]{2}$/i`. Response now includes the `persisted` opts so callers can log/verify what stuck.

  Both routes remain backwards-compatible. A pre-v0.61.270 client that POSTs `{ lat, lng }` only still works — the opts dict stays empty, and `setUserLocation` writes a lat/lng-only payload as before.

  **3. `web/cuisine/src/v2/lib/api.js`** — extend `saveUserLocation` signature

  `saveUserLocation({ lat, lng, label?, country?, region?, street?, building?, postal? })`. Only sends a field when it's truthy. Backwards-compatible for any caller still invoking the v0.60.120 `{ lat, lng }` shape.

  **4. `web/cuisine/src/v2/App.jsx`** — three call sites

  - `onLocationSelect` now forwards `label`, `state.region`, and (when `state.region === 'OTHER'`) `state.countryPref` to `saveUserLocation`. So every cuisine-side pick persists the full metadata, matching Menu TMA's writes.
  - `tryServerCache` consumes the new `r.country` field: when present AND the cached anchor's region is OTHER/MY-PUT, `state.countryPref` is synced. The Menu TMA's Thailand pick now opens the Cuisine TMA OTHER picker on TH instead of the stale `state.countryPref` default ('MY').
  - `refetchAndFlip` mirrors the same country-sync logic on the visibility-restore path.

  **5. `__tests__/location-cache.test.js`** — +6 tests

  - persists country with valid ISO 3166-1 alpha-2
  - uppercases lowercase input
  - drops invalid country (length ≠ 2)
  - drops non-string country
  - documents replace-payload semantics on subsequent writes (no implicit carry-forward — operator caller must re-pass on every write, matching `/api/menu/set-location`'s existing behaviour)
  - coexists with all other opts (region, label, street, building, postal, radiusCapM)
