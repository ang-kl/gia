## New

### [HDR] #64 | 16:30:00 SGT 01-05-26 | v0.30.6 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead screenshot of v0.30.5 result — five returned venues were **completely off-cuisine** for a Peranakan/Indonesian/Korean query:
  - "Kopi Near Me International Plaza" (coffee shop)
  - "Nom Singapore" (coffee/café)
  - **"The Coffee Bean & Tea Leaf"** (explicitly named in our negative-constraint list — Gemini ignored it)
  - "The Wizard's Brew" (coffee/bar)
  - "Old Amoy Chendol" (Singaporean dessert, not the requested cuisines)
  Two compounding bugs: meal-period bias overrode cuisine intent, AND server had no defense-in-depth chain filter.
- **[ROOT CAUSES]**
  1. **Meal-period bias**: at 4:33 PM `whenToMealHint` returned `{label: 'afternoon', hint: 'afternoon tea, coffee, light bites'}`. The prompt rendered this as `Period: afternoon snack (afternoon tea, coffee, light bites)` which actively biased Gemini toward coffee/dessert venues regardless of the user's explicit cuisine ask.
  2. **Negative-constraint compliance is unreliable**: the prompt enumerated "McDonald's, KFC, Subway, Burger King, Starbucks, Coffee Bean & Tea Leaf, …" as exclusions. Gemini still returned Coffee Bean & Tea Leaf. The bot had no server-side enforcement.
- **[DELTA]**
  - **`pipeline.js#buildReasonPrompt`** —
    - + `hasCuisines` flag (true when `query.cuisines.length > 0`).
    - + `periodLine` — when `hasCuisines`, period framing softened to `"Time of day (informational only — DO NOT bias toward generic snack/café venues): <label>"`. The "afternoon tea, coffee, light bites" hint no longer pulls Gemini off-cuisine.
    - + `cuisineEnforcement` — when `hasCuisines`, prompt appends an authoritative clause: `"AUTHORITATIVE CUISINE CONSTRAINT: Every venue you return MUST primarily serve one of [<cuisines>]. Coffee shops, dessert specialists, generic cafés, kopitiams, and bakeries DO NOT QUALIFY unless they specialise in the named cuisines. If you cannot find venues matching the cuisines + area + recency, return fewer (or zero) — DO NOT pad with off-cuisine venues."` Pairs with v0.30.5's relaxed-retry fallback (D613/D614) so we still degrade gracefully on truly empty searches.
  - **`cuisine-search.js`** —
    - + `FAST_FOOD_CHAIN_PATTERNS` regex array — McDonald's, KFC, Subway, Burger King, Starbucks, Coffee Bean (& Tea Leaf), Domino's, Pizza Hut, Jollibee, Texas Chicken, Wendy's, Popeye's, Shake Shack, Five Guys, Taco Bell, Long John Silver's, Carl's Jr. Conservative — does NOT touch SG-local chains (Toast Box, Ya Kun, Killiney, Old Chang Kee) where users may genuinely want them.
    - + `isFastFoodChain(name)` and `excludeChains(venues)` helpers. `excludeChains` logs each dropped venue with `[Cuisine-Search] D709 chain-filter dropped "<name>"` for traceability.
    - `searchCuisine` post-pipeline filter chain now ends with `excludeChains(filtered)` — defense-in-depth runs AFTER `applyPostFilters` and queue-tolerance filter, so even if Gemini lets a chain through, our code blocks it.
- **[VERIFICATION (sandbox)]**
  ```
  node --check on pipeline.js, cuisine-search.js, index.js → OK
  cd web/cuisine && npm run build → vite v5.4.21 ✓ in 2.75s
  ```
- **[STATUS]** PROD — auto-deploys with the next Railway build.

  - Cuisine validation is still prompt-only at the Reason layer. A future refinement could use Places `primaryType` (`korean_restaurant`, `peranakan_restaurant`) as a server-side cross-check, but Places coverage is incomplete (most show generic `restaurant`).
