## New

### [HDR] #68 | 17:30:00 SGT 01-05-26 | v0.31.0 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead "Fix … I" — Buddy Level 2: live solo-dining match. v0.25.0 shipped Buddy Level 1 (share-a-pick deep links). Level 2 is the harder version: two opted-in users heading to the same venue in the next 60 min get the option to mutually-confirm and exchange first names + Telegram handles. Multiple safety controls baked in to keep the pilot defensible.
- **[DESIGN — safety controls]**
  1. **Opt-in only.** `/buddy on` to enable. OFF by default. 30-day TTL on opt-in (forces monthly re-consent).
  2. **Mutual confirmation.** First name + Telegram handle revealed ONLY after both parties confirm. Either can `🚫 Decline` the offer (30-min expiry) at any point.
  3. **No PII reveal.** No phone, no last name, no exact GPS. Telegram handle only if user has one set.
  4. **Block list.** `/buddy block <chat_id>` per user. Blocked counterparts never matched. Cap at 50 blocks per user.
  5. **Daily cap.** 5 successful connections per user per 24 h. Hits both initiator and responder.
  6. **60-min intent window.** ZSET self-prunes on every read.
  7. **Auto-block on report.** `/buddy report <chat_id> <reason>` logs to admin Redis LIST AND auto-blocks the reported user from your matches.
  8. **"Meet in public" reminder** on every match offer + every successful connection.
  9. **No women-only flag in v1.** Requires identity verification we don't have. Documented as future scope.
- **[DELTA]**
  - **NEW** `buddy-match.js` — full storage + business logic:
    - `isOptedIn / optIn / optOut` — `buddy-optin:<chatId>` STRING with 30-day TTL.

    - `dailyCount / bumpDailyCount` — `buddy-day:<chatId>:<YYYYMMDD>` INT with 24h TTL.

    - `findCounterparts` — returns OTHER opted-in chatIds at the same place, excluding requester + symmetric blocks.
    - `createOffer / loadOffer / setOfferStatus` — `buddy-offer:<token>` STRING (JSON) with 30-min TTL. State machine: `pending_to → declined | mutual_confirmed | expired`.
    - `report` — appends to `buddy-reports` LIST capped at 1000 entries.
  - **NEW** `prompt-templates/buddy-level-2-policy.md` — explicit user-facing safety policy + storage shape + slash-command reference + future scope.
  - **`index.js`** —

- **[TEST RUNBOOK]**
  Two-account flow (need a second Telegram account):
  1. Both users send `/buddy on`.
  2. User A runs `/cuisine` (or any food query) and gets picks.
  3. User B runs same area within 60 min — picks include `👥 Connect (1 other diner)` button on the same venue.
  4. User B taps Connect → User A receives "Match offer from <fromName>" with Accept / Decline.
  5. User A taps Accept → both see mutual-confirm message with first names + chat IDs + safety footer.
  6. Either tests `/buddy block <other_id>` to verify they no longer match.
  7. Either tests `/buddy report <other_id> bad behaviour` — reported user is auto-blocked + entry appears in `buddy-reports` Redis LIST.
  8. `/buddy status` shows daily count.
- **[KNOWN GAPS]**
  - First names come from `q.from?.first_name` — Telegram only sends this when the user has set one. If they haven't, we fall back to "a fellow soleat user".
  - No in-bot encrypted chat — once handles are revealed, conversation moves outside soleat. Future scope.
  - No moderator UI for reviewing `buddy-reports`. Admin tails the list manually for now.
  - `/buddy block` requires the chat ID. We surface chat IDs in mutual-confirm messages so the user can copy-paste. Future patch could let users pick from a list.
  - Daily cap is per-user not per-pair. Two users could match each other 5 times if they both keep heading to different venues; deduping per-pair is future scope.
