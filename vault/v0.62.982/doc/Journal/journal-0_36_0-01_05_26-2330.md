## New

### [HDR] #76 | 23:30:00 SGT 01-05-26 | v0.36.0 | n/a kb | n/a lines
- **[INTENT]** Final leg of the v0.32-v0.36 roadmap. Per the original ask:
  > "First, implement the Enhanced Carpark & Movement Layer. Integrate the LTA DataMall Carpark Availability API to serve as a high-fidelity proxy for local footfall. When a user requests a location, the bot must fetch live occupancy rates for both malls and HDB carparks within a 500m radius. If availability is below 10%, Gemini 2.5 Flash must adjust the 'Wait Time' advice to reflect a high-crowd state."

  Shipped as an **A/B-tested hypothesis** under `FOOTFALL_PROXY_ENABLED=on|off` env flag (default `off`). Honest framing: this is a *cars-not-diners* proxy with documented bias against CBD walk-in venues. The A/B test is whether the signal helps suburban / drive-to F&B searches enough to justify always-on.

- **[DESIGN]**
  1. **Schema reality check** — LTA's `CarParkAvailabilityv2` API returns `AvailableLots` only, no total capacity. Therefore "availability ratio < 10%" (per the original ask) cannot be computed. Pivoted to **absolute thresholds** on median lots across the nearest 3 carparks.
  2. **`computeCrowdSignal(carparks)` helper** in `pipeline.js`:
     - Inputs: array of carpark records with `availableLots`.
     - Returns: `{level, medianLots, sampleSize}` where level ∈ `'high' | 'medium' | 'low'`, OR `null` if fewer than 2 carparks have data.
     - Thresholds: median <15 lots → `high`, >150 → `low`, else `medium`.
  3. **`fetchClusterContext` writes `crowdSignal` to every cluster** (always — computation is cheap; surfacing is gated). No additional API calls; uses the existing `carpark.nearest(lat, lng, 3)` already in the per-cluster fetch.
  4. **`summariseClusterCtx` surfaces the signal in the refine prompt only when `FOOTFALL_PROXY_ENABLED=on`**. When OFF (default), the refine prompt sees the cluster context exactly as v0.35 — no behavioural change. When ON, the prompt receives a bracketed tag `[footfall (carpark proxy, n=3, median=8 lots): high]`.
  5. **Refine prompt directive** updated to handle the new tag:
     - When `footfall: high` → mention "lunch crowd peak — arrive 15 min early or go takeaway"
     - When `footfall: low` → mention "quiet right now — easy to walk in"
     - Explicit honesty clause: "The signal is a CARPARK proxy (cars-not-diners) so do NOT cite it as authoritative for CBD walk-in venues."
     - `queue_min_estimate` may be adjusted UP when footfall=high, in addition to traffic/carpark.
  6. **Env flag is one-way safe** — `FOOTFALL_PROXY_ENABLED=on` enables the surface; anything else (including unset) keeps it off. No restart needed; lives in the runtime env check inside `summariseClusterCtx`.

- **[KNOWN GAPS / HYPOTHESIS CAVEATS]**
  - **Cars ≠ diners.** CBD lunch crowd at Maxwell / Lau Pa Sat / Amoy / Newton is overwhelmingly walk-in or MRT-arrivals. Carpark fullness will under-detect crowd at these venues. The refine prompt explicitly tells the model not to cite the signal as authoritative for CBD walk-in venues.
  - **No total-capacity data.** LTA `CarParkAvailabilityv2` only exposes `AvailableLots` (currently free), not total spaces. Absolute thresholds (15 / 150 lots) are calibrated by inspection, not by ratio. Adjust if the A/B test surfaces persistent mis-calibration.
  - **Cluster centroid drift.** The carpark sampling is anchored to the cluster centroid (500 m grid cell), not the venue itself. If a cluster contains venues at opposite corners of its cell, the carpark signal may be noise. Mitigation: 500 m cells are tight enough that this rarely matters in practice.
  - **No A/B telemetry yet.** This version ships the toggle and the signal; we don't yet log per-search "footfall_signal=X, user_complaint=Y" so the decision to keep the flag ON requires manual subjective review. Future v0.36.x could add a one-key Redis counter `footfall:signal-fired:<level>` for visibility.
  - **HDB carpark coverage is good; private mall carpark coverage is sparse.** LTA includes most HDB and government carparks but private malls (e.g. Marina One) often aren't in the feed. This biases the proxy toward HDB heartland.
  - **Time-of-day correlation isn't modelled.** A "high" signal at 11pm probably means low overall demand, not "diners are queuing." We rely on the model's reasoning to combine the signal with the user's `mealPeriod`. May warrant explicit time-gating in v0.37.
