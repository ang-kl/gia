### [HDR] v0.62.704 — an itinerary map for the Sketchbook cabinet

- **[INTENT]** A five-round design conversation, then a build instruction. The opening ask was:
  *"do you think the sketchbook cabinet can be improved? as an itinerary cabinet shall we have a map
  of the pins. pins coloured by different drawer with numbered. objectives: (1) print/pdf/share/copy
  map with a list of location-pins and pin-details and separate by drawers"*.

  Four refinements followed, each one narrowing the design:
  1. *"the challenge is that different drawer could mean travelling different places. should it be
     link to previous and next drawer"*
  2. *"change the mockup buttons to follow exactly like the one in the Sketchbook… and make it as a
     layer over the drawers like the drawer in other 3 TMA… pull-out with different friction
     standards like Cuisine/Train/Hawker TMA"*
  3. *"badge shows mappable stops only, keep 📍 on active cabinet. 4 drawers means 4
     concentrated-circle with the drawer name in the centre (user can toggle disply on/off with
     checkbox what to show and not to show)"*
  4. *"ugly checkbox not following m3 material, checkbox's alignment and groupings lacking and not
     following realistic drawer's purpose. i am not looking for general purpose checkbox"*

  Then: *"before generate a .MD file and upload to the instruction folder then build. note the map —
  is it google map that can have embedded buttons and zoom like the rest or is this a svg."*

- **[THE QUESTION WAS THE MOST IMPORTANT PART OF THE ROUND]** The mockup's map was an SVG — a
  hand-rolled equirectangular projection with no basemap, no zoom, no pan and no controls. That was a
  mockup convenience (no API key, no async loader, instant render), and it had quietly become a
  design position without ever being argued for. Shipping it would have made Clipboard the only TMA
  whose map does not behave like the other three.

  **Ruling: both, with the SVG demoted to print.** Operator picked *"Google Maps + SVG for print"*.

  | | screen | print / PDF |
  |---|---|---|
  | renderer | Google Maps JS, `AdvancedMarkerElement` | inline SVG |
  | zoom / pan | yes | no — fixed fit |
  | basemap | Google tiles | none; 1 km scale bar |
  | offline | `nokey` placeholder | always works |

  The print half is not a reuse of anything: **this repository had no print path at all** before
  today — no `@media print`, no `window.print`, no Static Maps call anywhere in source. A live map is
  a WebGL canvas of raster tiles; browsers routinely print it blank or as grey boxes, and Google's
  terms restrict reuse of captured tiles. Both renderers now draw from one geometry module so the
  printed page cannot drift from the screen.

- **[THE COLOUR SCHEME WAS WRONG AND THE OPERATOR'S FOURTH NOTE IS WHAT EXPOSED IT]** The mockup
  coloured pins by `segments.js`'s day-part. `segments.js` puts `teaBreak`, `earlyDinner` **and**
  `dinner` all in `evening`, so three drawers rendered the identical `#ff6b6b` — and "which drawer is
  this pin" is the only question the colour exists to answer. It survived four rounds of review
  because the demo cabinet only ever had two evening drawers and the pin *numbers* disambiguated
  them.

  Fixed by making the **family** the day-part and the **shade** the drawer's ordinal within it. A
  test now asserts every colour in a cabinet is distinct.

- **[THE LAYER PANEL — "not following realistic drawer's purpose"]** The first cut was a flat wrapped
  row of native checkboxes. The rewrite takes the note literally: a Sketchbook drawer **is** a time
  slot, so the control is the day.

  - Drawers in clock order, nested under their day-part, each part with its **own parent tick**.
  - A partly-ticked part goes **indeterminate**. That third state is the whole reason it is needed: a
    half-ticked Evening must not read as "Evening is off".
  - A part with no drawers is **not rendered** — never an empty row waiting to be filled.
  - Each part's span is **computed from its members**, so it stays true when drawers change.
  - `wholeDay` is classified `night` by `segments.js` but reads *"Anytime"*. It is not on the clock,
    so it gets its own trailing section and is excluded from leg sequencing. (The `segments.js`
    classification itself is left alone and filed as O-147.)
  - The leading mark on a drawer row is the map's actual pin — same fill, same number, same circle.
    A neutral swatch would have been a second vocabulary to learn.

  Checkboxes are M3 to spec: 18×18 / 2dp radius / 2dp outline, a **drawn** checkmark
  (`stroke-dashoffset`, 150 ms, `cubic-bezier(.2,0,0,1)`), a 40dp state layer, and every box in its
  own 40px column so parents, children and map layers share vertical centrelines.

- **[A FALSE ALARM I RAISED ON MYSELF, WORTH RECORDING]** The first browser measurement reported the
  indeterminate state as *not applying* — transparent fill, bar offset 9px — while `:indeterminate`
  matched and the rule was demonstrably present in the compiled CSS. Ten minutes went into hunting a
  minifier bug that did not exist. The cause was the probe: it set `indeterminate` and read
  `getComputedStyle` in the same tick, i.e. at t=0 of the box's own 100 ms `background-color`
  transition. The `:checked` control read correctly only because that input carried `checked` in the
  HTML and had never transitioned. Waiting 400 ms produced the right numbers. **A measurement of an
  animated property is a measurement of a moment, and the moment has to be chosen.**

- **[CI WENT RED, AND IT WAS RIGHT]** The first push failed `Vitest unit tests` with
  *"Failed to load url react (resolved id: react) in web/clipboard/src/lib/i18n.js"* — while the
  full suite had been green in the sandbox minutes earlier. The worst shape a failure can take.

  **The import was the defect, not the test.** `itinerary.js` opens by claiming *"no React, no
  Google Maps, no DOM"* and then imported `./i18n.js`, which imports React for its `useLocale` hook.
  So the "pure" module pulled the whole renderer in behind a name that gave no hint of it. It
  resolved locally only because React lives in `web/clipboard/node_modules` and Vite resolves bare
  specifiers by walking up from the **importer**; the root `npm ci` the unit job runs installs no
  TMA dependencies.

  Fixed by taking the one thing it needed as an argument: `buildItinerary(payload, lang, translate)`
  and `toPlainText({ …, translate })`, defaulting to an identity that returns the key. The header's
  claim is now true.

  Reproduced locally first, by hiding `web/clipboard/node_modules/react` — same error, same file.

- **[AND A GUARD, BECAUSE THIS WILL RECUR]** `__tests__/test-import-graph-guard.test.js` walks the
  relative-import graph of every `web/` module the root tests pull in and fails on any bare specifier
  the repo root cannot resolve. Mutation-checked by re-adding the exact import: it fails with
  `__tests__/itinerary.test.js → … → web/clipboard/src/lib/i18n.js imports "react", which the repo
  root cannot resolve`. Several root tests already reach into `web/_shared/lib/`, so the next such
  import is a matter of time — and it now fails on the developer's machine instead of on the runner.
