# Journal — v0.62.663 (auto-maximize on Telegram Desktop, for the two Mini Apps that never got it)

_(№ 1,186 — 30-07 '26 13:42 SGT)_

## New

### [HDR] v0.62.663 — Menu, Clipboard, and Oversight join Cuisine/Hawker/Transport's desktop auto-fullscreen

- **[INTENT]** Operator: *"Can you implement automatic resizing for the Telegram Desktop TMA? ... Detect
  whether the Telegram Desktop TMA window is not maximized. If the window is minimized or opened at a
  smaller-than-full-screen size, automatically resize or maximize it. Perform this check when the TMA
  finishes loading."*

- **[WHAT'S ACTUALLY POSSIBLE — AND ALREADY SHIPPED]** A Telegram Mini App is a web page inside an iframe;
  it has no privilege to query or resize the actual OS-level Telegram Desktop application window (no
  "is minimized" flag, no "maximize the window" call exists in the Bot API). The one real lever is
  `requestFullscreen()` (Bot API 8.0) — Telegram's own API for expanding the MINI APP's rendering area to
  fill what Telegram gives it, gated on `w.isFullscreen` (Telegram's own flag, the closest available proxy
  for "is this already maximized") so it doesn't re-fire on every reload. **Cuisine, Hawker, and Transport
  already do exactly this on Telegram Desktop** — it's been live since the "auto-fullscreen saga"
  (v0.60.52 → v0.62.286 removed it → v0.62.617 restored it for desktop → v0.62.623 removed the desktop
  branch → v0.62.624 restored it again, "why I cannot expand in telegram desktop"). Confirmed by reading all
  three apps' `tg.js`: identical `platform === 'tdesktop' || 'macos'` gate, `isFullscreen` early-return,
  `fullscreenFailed` listener, called from the init step run right after `w.ready()` on load.

- **[THE REAL GAP]** Auditing the other Mini Apps found two genuinely missing and one already covered:
  - **Menu** (the hub) had the auto-fullscreen step, but scoped to `platform === 'ipados'` ONLY — explicitly
    excluding desktop (the v0.60.52-era gate, never updated when Cuisine/Hawker/Transport re-added desktop at
    v0.62.617/624). Users landed on the windowed hub even though every app it links to opens maximized.
  - **Clipboard** and **Oversight** had NO fullscreen step at all — just `w.expand()` (height only, no width
    on desktop, per the standing "auto-fullscreen saga" note in every other file).
  - **About** was checked and correctly excluded: it's a public marketing page (links OUT to "Open on
    Telegram"), not itself a Mini App — no `tg.js`, nothing to fix.

- **[THE FIX]** Menu's existing gate widened to also allow `tdesktop`/`macos` (iPad behaviour untouched);
  Clipboard and Oversight each gained a new `fullscreen` init step, copied verbatim from the canonical
  Cuisine/Hawker/Transport pattern (desktop-only — neither app has an established tablet-responsive story
  the way the three map apps do, so this stays scoped to exactly what was asked: Telegram Desktop).

- **[KNOWN GAPS / caveats]**
  - **Not device-verified.** Same standing caution as every Telegram-host-API change this arc — confirmed
    only by reading the code path, not by opening Menu/Clipboard/Oversight in a real Telegram Desktop client.
  - **This cannot detect or fix a "minimized" window at all.** `requestFullscreen()` operates on the Mini
    App's rendering area within Telegram's own window; if the user has minimized TELEGRAM ITSELF to the
    taskbar, no Mini App JS runs to request anything until Telegram is restored — there is no API surface
    that could intervene there, and none was invented to paper over that gap.
