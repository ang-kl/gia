# Journal — v0.62.673 (Michelin footer-centre pagination)

_(№ 1,196 — 31-07 '26 11:07 SGT)_

## New

### [HDR] v0.62.673 — a compact page indicator for Michelin results, reusing 100% existing machinery

- **[INTENT]** Operator: *"Do this: https://github.com/ang-kl/gia/blob/main/instr/GIA_Michelin_Footer_Pagination_AI_Prompt.md"* —
  a fully-specified instruction file (footer-centre-only pagination for Michelin Guide results,
  Year Filter → Sort → Paginate pipeline, its own explicit §16 working method requiring investigation
  and file-report before code, and a stop-and-explain clause on repo conflicts). Per that clause, a
  pre-implementation investigation surfaced a real conflict between the spec's assumed data model
  (a complete local result array, sliced client-side) and this app's actual architecture (one server
  batch fetched at a time via a `pages`/`cursor` history stack, capped at 11 Michelin batches) —
  reported to the operator rather than guessed past. Operator resolved it directly: **"'page' is
  already-fetched server batch. I need to just show then tap to next page to fetch."**

- **[EVIDENCE BASE]** A dedicated investigation (file:line evidence throughout) established: `venue.
  michelinCategory`/`venue.michelinAwardYears` already reach the frontend untouched — no backend
  plumbing needed; there is no canonical "Michelin mode" flag (~10 ad hoc `state.cuisines.includes
  ('michelin')` checks instead); the footer is hand-rolled `flex justify-between` (not the shared
  FooterNav), with a conditionally-present "Criteria" pill already occupying the one existing centre-ish
  slot; there is no client-side filter/sort pipeline anywhere — `venues` is raw server output; and,
  critically, the codebase's own comment on `ResultPanel.jsx`'s internal pager explicitly frames
  "Michelin pagination" as already server-side (its `onLastPageNext` prop already calls `runSearch(state)`
  to fetch a fresh batch when the user reaches the end of what's loaded).

- **[DELTA]** (single commit `77cca13`, `web/cuisine/src/v2/App.jsx` only)
  - New `isMichelinMode` derivation, matching the existing ad hoc check pattern exactly (no new
    canonical flag introduced, per the instruction's "use existing state" rule).
  - Footer row 1 converted from `flex justify-between` to an explicit 3-column CSS grid
    (`grid-cols-[1fr_auto_1fr]`) so the centre region is genuinely centred regardless of left/right
    cluster width — the spec's own explicit requirement, and its own suggested technique.
  - New Michelin pager in that centre cell (alongside — not replacing — the pre-existing Criteria
    pill; either, both, or neither can be present): `‹ {cursor+1} / {pages.length} ›`. **Reuses 100%
    of existing state**: Prev/replay-Next just move `cursor`; the app's own `useEffect` keyed on
    `cursor`/`pages` (~App.jsx:946) already restores every piece of page state reactively; fresh-Next
    (at the cache tip) calls the exact same `runSearch(state)` `ResultPanel`'s own `onLastPageNext`
    already uses (App.jsx:5210) — no new fetch mechanism, no parallel result system.
  - The pre-existing "Next list" button (left region) is now hidden specifically when the new pager
    is also showing (`isMichelinMode && pages.length > 1`) — its replay case is a strict subset of the
    new pager's Next, so keeping both would duplicate forward navigation for Michelin results; every
    non-Michelin search keeps it exactly as before.
  - Full accessible labels (8 locales, matching this file's own established inline-ternary convention)
    on both pager buttons, correct `disabled` states (Prev at `cursor===0`; Next only when the server
    has confirmed exhaustion AND there's no cached page ahead), `aria-live="polite"` page announcement,
    `.gia-hit` invisible touch-target extension (the Phase-1 pattern, v0.62.668).

- **[KNOWN, DELIBERATE DEVIATION]** The existing "Back"/"End" button (right region) can *also* step
  `cursor` backward for Michelin results, overlapping with the new pager's `‹`. Left untouched rather
  than risk that control's separate "close the Telegram WebView on the oldest page" behaviour — a
  judgment call between two imperfect options (duplicate a benign action vs. touch a safety-relevant
  one), reported explicitly per the instruction's own §16 requirement to disclose deviations.
