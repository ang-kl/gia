# Journal — soleat v0.61.282 (online verify-then-cache for OTHER regions + JSON seed script)

> Operator (30-05 '26 ~16:50 SGT, Railway log from a durian-pastry search in Surabaya):
> *"i selected durian, at Indonesia, Surubaya. it shows steak house. do you think each places than the one we search need more analysis for durian fruits and durian pastry."*
>
> Root cause: v0.61.275 Plan B cached Gemini labels at `dgv:labels:<mode>` (populated by the `/ver → 🤖 Gemini verify` job). The bulk verify only covered SG + JB + Putrajaya + KL; Indonesian / Vietnamese / Thai / etc. placeIds had no labels, so the v0.61.275 D703e post-filter passed every unlabelled venue through (heuristic-keyword fall-through). The keyword filter at `special-mode.js filterByMode` lets some venues through when "durian" appears in adjacent metadata (formatted address, area name) — Places searchText for "Durian Pastry" in Indonesia returned a steak house whose address presumably contained "Durian" as a street/area name.
>
> Operator asked for a *better strategy* than the four obvious options (pre-cache more cities; real-time-only; hybrid; tighten Places query). v0.61.282 ships the proposed answer: **auto-warming online verify-then-cache**.
>
> v0.61.282:
>
> 1. **`scripts/seed-dgv-labels-from-json.mjs` (NEW).** One-shot loader that reads the operator's `/ver` JSON outputs (e.g. `~/Downloads/durian-pastry-gemini-verified-2026-05-30_1659.json` + `~/Downloads/durian-gemini-verified-2026-05-30_1657.json`) and bulk-`hSet`s each labelled venue's `(placeId → {label, confidence, reason, verifiedAt, seededFrom, region})` into the same `dgv:labels:<mode>` Redis hash the bot's `ownerDurianGeminiRun` writes. 30-day TTL. Idempotent (re-running overwrites the same fields). The operator's two latest verify runs total ~5,200 placeIds across SG/JB/Putrajaya/KL — importable in one shot without burning another ~$1 of Gemini quota.
>
> 2. **Inline online verify-then-cache** in `/api/cuisine/search` D703f (new step after the existing D703e cache lookup). When the cache didn't cover all venues AND `GEMINI_API_KEY` is set, the search calls the same `_processBatch` the `/ver` job uses on the unlabelled subset (max 30 venues per batch), drops `unrelated`, and writes the verdicts back to `dgv:labels:<mode>`. Subsequent searches anywhere in the world hitting the same placeIds get the cached label for free.
>
> 3. **Public export** of `_processBatch` from `durian-gemini-verifier.js` (was private; v0.61.275 only exported `verifyKeptVenues` which requires the `/ver` report shape).
>

- **[INTENT]** Make durian / durian-pastry searches precision-bounded ANYWHERE (not just SG+JB+Putrajaya+KL). Self-warm the dgv:labels cache from real user queries. Provide a path to import existing `/ver` JSON outputs without re-running Gemini.

- **[DELTA]**

  **1. `scripts/seed-dgv-labels-from-json.mjs` (NEW, ~110 lines).**
  Standalone Node script (ESM). Reads N JSON files, detects each `report.mode` (`durian` | `durian-pastry`), bulk-`hSet`s `dgv:labels:<mode>` with one entry per labelled venue with a placeId. 30-day TTL. Per-file per-region counts printed to stdout. Requires `REDIS_URL` in env.

  **2. `index.js:/api/cuisine/search` D703e+f (~line 14117).**
  - The existing v0.61.275 cache-lookup block (D703e) gains an `unlabeledVenues` accumulator that collects the venues whose placeId had no cached label.
  - New D703f step: if `unlabeledVenues.length > 0` AND `GEMINI_API_KEY` is set, build a `_processBatch`-shaped batch (`{id, placeId, region, name, primaryType, address, reviewSnippets}`) from those venues (slice to 30 max), call `_processBatch` with model `gemini-2.5-flash-lite` and the active `specialMode`, drop venues labelled `unrelated`, and `hSet` all returned labels back into `dgv:labels:<mode>` with the same 30-day TTL the bulk `/ver` job uses.
  - Best-effort: all Redis writes are `.catch(() => {})`; a Gemini timeout / error logs but doesn't fail the search (the v0.61.275 unlabelled-pass-through semantics still apply).
  - New log line: `[Cuisine-Search] D703f online verify-then-cache (<mode>): batched=N, labels written=M, dropped=K unrelated (X → Y)`.

  **3. `durian-gemini-verifier.js`.**
  Added `_processBatch` to `module.exports`. No source change to the function itself — was already used internally by `verifyKeptVenues`. Public export documented with a v0.61.282 comment.

- **[KNOWN GAPS]**
  - **Inline latency.** A cold-cache OTHER search adds one Gemini batch call (~2–5 s for 20 venues with `gemini-2.5-flash-lite`). Subsequent searches against the same placeIds are free. The 6 s `PER_CALL_TIMEOUT_MS` inside `_callGemini` bounds the worst case.
  - **Quota usage.** Each new placeId costs ~$0.0001 of Gemini quota. After ~2 weeks of normal traffic in any popular OTHER city, the inline path stops firing — the cache covers everything.
  - **`reviewSnippets` not available** in the search-route venue shape. The inline prompt sends `name + primaryType + address` only. The bulk `/ver` path enriches with reviews. Precision is therefore slightly lower for inline-verified venues than for bulk-/ver'd venues, but still much higher than no Gemini at all.
  - **Batch size cap at 30.** Above 30 unlabelled venues, the extras pass through unlabelled (and the next search at the same coords picks them up). In practice the search returns ≤20 venues so the cap never hits.
  - **No `_processBatch` test.** The existing `__tests__/durian-gemini-verifier.test.js` covers `verifyKeptVenues` end-to-end. The new export reuses the same code path; no regression risk.
