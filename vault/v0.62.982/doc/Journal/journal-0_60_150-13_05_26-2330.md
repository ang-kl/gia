### [HDR] #115 | 23:30:00 SGT 13-05-26 | v0.60.150 | n/a kb | 1 PR

- **[INTENT]** Operator: *"Later Michelin List — HTTP 502. Investigate."* The first Michelin tap worked (~10–15 s end-to-end after v0.60.149's slice 40→12), but the next ▶ tap returned `HTTP 502` from Railway's edge proxy. 502 = upstream timeout — Express handler didn't respond inside Railway / Telegram's webhook ceiling (~30 s).

- **[DELTA]**

  **Root cause** (diagnosed via Phase-1 Explore agent against `handleMichelinSearch` at `index.js:5713–5812`): the **12 × Places `searchText` lookups ran in a serial `for (const entry of slice) await axios.post(...)` loop**, each with a **6 s** timeout. First-tap batches returned 3★ / 2★ flagships (Odette, Burnt Ends, Les Amis, …) — popular venues with hot Google indexes, ~1–2 s per call → ~15 s total → inside the budget. Later batches dipped into the **Bib Gourmand** tier (89 stalls + obscure eateries — Places is genuinely slower on these, 3–5 s per call sometimes hitting the 6 s timeout) → 12 × 4 s = 48 s → exceeded Telegram's 30 s webhook ceiling → Railway returned 502. No response-level cache at the Michelin sub-path (the cuisine-chip `cuisine:search:*` cache is bypassed when `cuisines` includes `michelin`), so every ▶ tap re-ran the full ~48 s loop.

  **Fix — three coupled changes in `handleMichelinSearch`** (`index.js:5713–5812`, lowest-risk → highest-payoff):

  1. **Parallelize the 12 Places lookups.** Replaced the serial `for` loop with `Promise.allSettled(slice.map(async (entry) => ({ entry, placesData: await resolveEntryPlace(entry) })))`. Worst case **72 s → 4 s** in one change. (Google Places API rate is 600+ QPM per project for `searchText`; 12 parallel requests is well within budget. `pipeline.discover` uses similar concurrency for the cuisine-chip path.) The venue-object construction loop downstream is unchanged — it just iterates the resolved results instead of slicing fresh axios responses.

  2. **Per-entry Redis cache for the Places resolution.** Key `michelin:place:<slug(entry.name)>`, 24-h TTL via `setEx`. The curated Michelin entries change rarely (annual Guide refresh); Places `id` / `location` / `rating` / `reviews` / `editorialSummary` for "Odette" or "Hill Street Tai Hwa Pork Noodle" is stable for hours. Cache HIT = ~1 ms Redis read; cache MISS = the 4 s axios call. Once the catalogue is warmed (~1–3 sessions), subsequent ▶ taps for any covered entry are near-instant. Negative-cache marker `{ __null: true }` for "Places returned no match" so dead venues don't get re-hit every session.

  3. **Cut per-call axios timeout 6 s → 4 s.** Fail-fast: a Places call that takes > 4 s is almost certainly going to fail anyway; the curated entry's fallback payload (`name`, `michelinCategory`, `michelinCuisineLabel`, no `placeId`) ships either way. Aligns with the cuisine-chip `pipeline.discover` budget.

  **Diagnostic latency log.** Added a one-line `[Michelin] handler ms={n} cacheHits={h} cacheMisses={m} venues={k}` `console.warn` at the response site, fired only when `ms > 10000`. Next regression of this class will be visible in Railway logs without another investigation cycle.
