## New

### [HDR] #63 | 16:15:00 SGT 01-05-26 | v0.30.5 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead `/log on` trace screenshot (after v0.30.4 shipped). Trace revealed two compounding bugs:
  1. **Search anchored at user's GPS, not the location they typed.** User's prompt mentioned "Tanjong Pagar or Raffles Place MRT" but `runNLFlow start lat=1.2722 lng=103.8112` shows Pasir Panjang/West Coast. Classifier wasn't extracting the location anchor from prompt text.
  2. **Reason returned 0 candidates in 60 s.** With Google Search grounding ON + strict combined query (4 cuisines + 1 km of CBD MRT [user not nearby] + Nov 2025-May 2026 + no chains), the model couldn't find anything. No fallback retry to relax constraints.
- **[DELTA]**
  - **`nl-intent.js`** —
    - Schema adds `"location_override": "<Singapore place name explicitly mentioned>"` field. Classifier returns `"Tanjong Pagar MRT"`, `"Raffles Place"`, `"Bishan"` etc. when the user says "near X" / "1 km of X". Empty string when no override.
    - 4 new examples in the few-shot prompt covering location-override extraction.
    - Console log line now includes `location_override="..."` for debugging.
  - **`index.js#bot.on('message')` NL branch** —
    - When `cls.location_override` is non-empty, geocodes it via existing `geocodeQuery(text + " Singapore")` and uses the resolved lat/lng for the search instead of cached GPS.
    - Diagnostic codes added:
      - **D708** geocoding location_override
      - **D709** geocoded successfully (logs resolved coords + place name)
      - **D710** geocode failed → falls back to cached GPS
    - Verbose-log emits `Search anchored at <override "X" → Place (lat, lng)>` or `<cached GPS (lat, lng)>` so the user sees which coords actually drove the search.
    - When neither override geocodes nor cached GPS exists, location-share keyboard prompts (existing path) — pending state now also includes `locationOverride` for the resume.
  - **`pipeline.js#runPipeline`** —
    - When Reason returns 0 candidates AND query has either `recencyDays` or `specialRequest`, retry once with both relaxed (set to null/empty). New diag codes:
      - **D613** retry with relaxed query
      - **D614** relaxed retry yielded N candidates
    - Avoids the "0 venues in 60 s" empty-handed UX. Trade: slightly less precise match on the recency / qualifier when relaxation kicks in, but better than empty result.

- **[KNOWN GAPS]**
  - Geocoding the override adds ~500 ms before the pipeline starts. Acceptable trade for searching at the right place.
  - Override resolution only happens for chat-side NL search; TMA Search button still uses the user's GPS exclusively (TMA has no free-text input). If we want override in the TMA, that's a separate feature.
  - Relaxed retry drops both `recencyDays` AND `specialRequest`. If only one is the offender, we lose information. Two-step relaxation (drop recency first; if still 0, drop specialRequest) would be a future refinement.
  - Pipeline's 60s ceiling (combined Pro retry + Gemini search + retries) is unchanged. If grounding genuinely hangs, we still wait out the full window. Future patch could add a server-side `Promise.race` with a 30s soft cap.
