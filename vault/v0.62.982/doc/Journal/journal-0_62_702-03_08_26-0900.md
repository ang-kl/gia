# Journal — v0.62.702 (O-130: writing the z-stack down found a bug in it)

_(№ 1,041 — 03-08 '26 09:00 SGT)_

## New

### [HDR] v0.62.702 — O-130 closed, and two dialogs that were losing to the footer

- **[INTENT]** Operator: *"do next work"*. Next in the queue was **O-130** — *"the z-stack is
  undocumented and app-specific"*, the condition that produced the v0.62.699 regression and the one I
  had recommended taking.

- **[THE JOB AS FILED]** Write down each TMA's tiers so the next port is checkable. Documentation.

- **[WHAT THE FIRST SCAN GOT WRONG]** The enumeration regex was `\bz-(\[[0-9]+\]|[0-9]+|auto)\b`. The
  trailing `\b` after `]` can never match — `]` and the following space are both non-word — so
  **every arbitrary `z-[NN]` was silently dropped**, including the `z-[35]` overlays that O-130 is
  *about*. The first table looked complete and omitted 17 sites. Re-scanned without it.

- **[THE TABLE — four apps, three footer tiers]**

  | role | cuisine | hawker | transport | clipboard |
  |---|---|---|---|---|
  | header | `z-30` | `z-20` | `z-20` | `z-10` |
  | card strip | `z-30` | `z-30` | `z-[38]` | `z-30` |
  | **footer dock** | **`z-30`** | **`z-40`** | **`z-40`** | **`z-20`** |
  | expanded map | **`z-20`** | **`z-[35]`** | **`z-[35]`** | — |

  Each map-overlay value is correct for its own app and wrong for the other two. That row is D-70 in
  one line.

- **[THE BUG THE TABLE EXPOSED]** Cuisine has two dialogs at **`z-30`** —
  `MichelinFilterDrawer.jsx:68` and `CuisineCategoryDrawer.jsx:131` — the **same tier as Cuisine's
  footer dock** (`App.jsx:5591`). There are no portals anywhere in the app, and the footer renders at
  line 5591 while `CuisineDrawer` renders at 4592. **At equal z, document order decides.** The footer
  won: it stayed visible and tappable over dialogs declaring `aria-modal="true"`.

  `CuisineCategoryDrawer` is worse. Its root is `fixed` *with* a z-index, so it opens a stacking
  context — a fact already written in that very file at line ~97 — which means its nested dish pop-up
  (`z-40`) and dish detail (`z-50`) were **clamped to the root's `z-30`** and lost to the footer too.
  Three layers, one root.

- **[MEASURED, NOT INFERRED]** A hit-test probe was built from the **compiled** Cuisine stylesheet
  with the exact class strings and the real DOM order:

  | tap target, dialog open | at `z-30` | at `z-40` |
  |---|---|---|
  | the footer band | **footer chips** ❌ | **dialog scrim** ✅ |
  | the dialog card | dialog card ✅ | dialog card ✅ |
  | the scrim above the footer | dialog scrim ✅ | dialog scrim ✅ |

  Identical at 390×844 and 1280×900.

- **[DELTA]**
  - `MichelinFilterDrawer.jsx` `z-30` → **`z-40`**, `CuisineCategoryDrawer.jsx` root `z-30` →
    **`z-40`**. Re-derived against Cuisine's own neighbours, **not** copied (D-70): above the `z-30`
    chrome tier, below the `z-50` loading / fun-fact overlays that should cover a dialog. The FAB
    clusters at `relative z-40` live inside the footer's own `z-30` context and cannot escape it, so
    the dialogs cover them too.
  - `doc/Technical/technical-0_62_702-03_08_26-0930.md` (**NEW**, № 70) — the full per-app table,
    shared-component values, rules **R-Z1…R-Z5**, and a checklist for adding a layer.
  - `__tests__/z-stack-registry.test.js` (**NEW**) — pins each app's chrome tier and the three map
    overlays, and enforces the one rule that generalises: **a dialog must strictly outrank its own
    app's `chromeTop`**.

- **[THE GUARD PASSED A MUTATION IT SHOULD HAVE CAUGHT]** Reverting both dialogs to `z-30` left the
  test **green**. The cause is worth keeping: the scanner extracted the opening tag *then* stripped
  comments, and the comment I had just written to explain this fix contains **`(5591 > 4592)`** —
  whose `>` terminated the tag early, so `role="dialog"` was never reached and both dialogs were
  skipped entirely. My own documentation made the guard blind to the thing it guards. Comments are
  now **blanked** (spaces, newlines kept, offsets intact) **before** the tag is located; the mutation
  now fails with both file:line entries, and restoring goes green.

- **[VERIFICATION (sandbox)]** Cuisine build green; `.z-40` / `.z-30` / `.z-20` confirmed emitted in
  the compiled stylesheet. Full suite **161 files / 3,964 tests** green (was 160/3,959).

- **[STATUS]** DRAFT — branch `claude/handover-july-11-49uzvf`.

- **[KNOWN GAPS]**
  - **The guard reads source.** It knows a dialog's declared z and its app's chrome tier; it does
    **not** know DOM order or ancestor stacking contexts — those were measured by hand here. Green
    means "nothing is declared below its app's chrome", not "the stack is correct".
  - **Not seen on a device.** The probe uses the real stylesheet and the real class strings, but it is
    not the running app (O-93).
  - `chromeTop` is a hand-maintained registry. If a footer moves and someone updates only the app,
    the pinning test fails — which is the intent — but nothing checks the *table in the doc* against
    the test's `APPS` constant.
  - **`_shared/FooterNav.jsx` is `z-50`**, above every app's chrome *and* above Cuisine's `z-40`
    dialogs. Deliberate for a floating nav, but it means a dialog cannot cover it. Filed as O-138.
