# Journal — v0.62.676 (Michelin: independent Year + Bib Gourmand ticks)

_(№ 1,199 — 31-07 '26 12:15 SGT)_

## New

### [HDR] v0.62.676 — 3 independent ticks under the Michelin chip: 2026 / 2025 / Bib Gourmand

- **[INTENT]** Operator, following the v0.62.675 divisor correction, asked for the Michelin year
  sub-criterion flagged as Open item O-94: *"Michelin star. Bib Gourmand becomes a group like the
  rest of Cuisine group. Below will have multiple tick for 2026, 2025, Bib Gourmand like the
  rest."* Per this session's standing rule (visible/structural UI changes get explicit per-item
  confirmation, not spec-guessing), two design forks were resolved directly with the operator
  before any code was written:
  1. **Chip structure** — asked whether Michelin Star and Bib Gourmand should become two
     independent top-level cuisine chips, or stay one "Michelin" chip with 3 ticks revealed below
     it. Operator: *"One 'Michelin' chip, 3 ticks below it."*
  2. **Walk reset on tick change** — asked whether changing a tick should reset the Michelin
     pagination walk (the pool size changes). Operator: *"Yes, reset (Recommended)."*

- **[DELTA]**
  - **`index.js`** (`handleMichelinSearch`) — new `michFilterIn` read from
    `req.body.michelinFilter` (`{ year2026, year2025, bib }`, each `!== false` so an absent/legacy
    request defaults all three ON — today's pre-v0.62.676 all-inclusive behaviour, unchanged for
    every existing caller). `michYearMatches(e)` applies UNION semantics across 3 parallel
    categories (Bib Gourmand is its own bucket, not cross-filtered by year — matches the
    operator's own framing, "3 independent ticks, like the rest [of the cuisine tag chips]", not a
    year × category matrix): a Bib Gourmand entry passes iff `michIncludeBib`; a star entry passes
    iff its `awardYears` intersects the ticked year(s). All-three-off (a stale hash / hand-crafted
    request) fails OPEN rather than silently returning zero, the same convention already used for
    a null `michelinCuisines` allow-list elsewhere in this file. Applied once, to `allEntries`
    itself, right after it's built — every downstream consumer (`pool`, `stars`/`bib`, `ordered`,
    `michelinSummary.total`/`threeStar`/`twoStar`/`oneStar`, the city breakdowns) is a filtered
    derivative, so nothing else needed touching for the total to reflect the active ticks.
  - **`michelin-walk.js`** — `computeCriteriaHash` gained a `michYears` param (a compact `"110"`-
    style 3-bit string), included in the hashed `norm` object so a tick change resets the walk, per
    the operator's explicit "yes, reset" answer. Backward compatible (default `null`, existing
    call sites/tests unaffected).
  - **`web/cuisine/src/v2/lib/state.js`** — new `state.michelinFilter = { year2026: true,
    year2025: true, bib: true }` in `defaultState()`; hash read/write only persists the OFF ticks
    (`michY26=0` / `michY25=0` / `michBib=0`), mirroring the existing QUICK_FILTERS convention
    (all-ON stays implicit).
  - **`web/cuisine/src/v2/lib/api.js`** — `searchCuisine` forwards `michelinFilter` in the request
    body when present (harmless when Michelin isn't selected — server only reads it inside the
    Michelin branch).
  - **`web/cuisine/src/v2/App.jsx`** — `runSearch` forwards `snap.michelinFilter`; `CuisineDrawer`
    gets the new `michelinFilter`/`onMichelinFilterChange` props, wired to `state`.
  - **`web/cuisine/src/v2/components/CuisineDrawer.jsx`** — new tick row, rendered only when
    `'michelin'` is in `selected` (Michelin stays ONE chip, unchanged from before): three small
    pill buttons (`role="checkbox"`, `aria-checked`), labelled `2026` / `2025` / the localised
    "Bib Gourmand" term, all checked by default. Untouched cuisine-chip grid/drill-down logic
    otherwise identical.
  - **`web/cuisine/src/v2/lib/i18n.js`** — 3 new keys (`michelin.filterHeader`,
    `michelin.bibLabel`, `michelin.yearAria`) across all 8 locales (en/fr/id/ru/de/zh/ja/es).
    "Bib Gourmand" kept untranslated in en/fr/de/es (matches `cat.michelinBib`'s existing
    convention) and given each locale's own established term in id/ru/zh/ja (also matching
    `cat.michelinBib`'s existing per-locale translations for the same phrase).
