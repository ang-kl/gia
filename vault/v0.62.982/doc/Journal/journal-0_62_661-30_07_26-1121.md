# Journal — v0.62.661 (iPhone landscape + list mode reverts to the static split, across all three map TMAs)

## New

### [HDR] v0.62.661 — the landscape-iPhone carve-out, built (not just recommended)

- **[INTENT]** Operator, confirming the v0.62.660 recommendation: *"okay, please to revert back for iPhone
  size landscape + list mode"* — after asking, in the prior turn, "did we ever build iPhone landscape + list
  mode, long time ago", which a research pass answered in detail (see that turn's findings, summarized below).

- **[WHAT "REVERT" MEANS HERE]** A below-the-map, independently-scrollable list in landscape phone + list
  mode did exist in all three apps, but never as a purpose-built "landscape iPhone" feature — it was simply
  what phones got in EVERY orientation before each app, one at a time, moved its list into the shared
  over-the-map `BottomSheet` drawer: Cuisine since `v0.62.138` until `v0.62.655` (28-07), Hawker's landscape
  case specifically retired at `v0.62.590` (18-07), Transport's at `v0.62.639` (25-07). So this entry
  reintroduces something that used to exist by omission (no orientation check), scoped down to exactly the
  one case the operator asked for — every other case (portrait phone, any tablet/desktop orientation) keeps
  the drawer exactly as v0.62.655–660 left it.

- **[HAWKER]** Already had the exact right layout SITTING UNUSED: `portraitTabletPanel()` — map anchored in a
  fixed top box, a separate `flex-1 overflow-y-auto` list panel below it, own header/footer — was built for
  portrait tablets at v0.62.550, deliberately orphaned (not deleted) at v0.62.642 specifically "so the
  two-panel can be restored in one line if wanted." It needed zero internal changes — it was already
  device/orientation-agnostic. Only the dispatcher changed: `viewMode==='list'` now checks
  `vp.deviceClass==='mobile' && vp.orientation==='landscape'` first and routes there; every other case still
  calls `drawerLayout()` as before.

- **[TRANSPORT]** Had no orphaned equivalent to revive (its `viewMode==='list'` block was always one inline
  function, never split out). New branch added inside it, built to the same shape as Hawker's
  `portraitTabletPanel`: `headerEl` (shrink-0) → map bounded to `h-[38vh]` (shrink-0, `mapBlock(true)` so it
  fills that box rather than going full-bleed) → the SAME `listBody` already computed for the drawer case, now
  in a plain `flex-1 min-h-0 overflow-y-auto` panel instead of inside `<BottomSheet>`. Reuses `listScrollRef`/
  `onListScroll` directly — no new refs, no duplicated list-rendering logic.

- **[CUISINE — the trickiest of the three]** Cuisine's vertical list has no separate "layout function" to
  branch at all; it's one long render with props that vary by condition. Investigating `fill`/`frameHeight`
  turned up a real, pre-existing inconsistency: `frameHeight` (a compact ~40vh framed-map override) has been
  DEAD since v0.62.655 made `fill` unconditionally `true` for every device — `MapPanel`'s own style calc only
  reads `frameHeight` when `!fill`, so the portrait-tablet "compact map, list gets the rest" comment has
  described a state that hasn't actually been reachable for two weeks. Not fixed here (out of scope, no
  operator report against it, and touching a live tablet layout unprompted is exactly the kind of scope creep
  this repo's CLAUDE.md warns against) — logged as O-68 below.

  For THIS entry's actual case, a new `staticSplitList` flag
  (`vp.deviceClass === 'mobile' && vp.orientation === 'landscape' && drawerMode === 'vertical'`) is OR'd into
  three existing, already-conditional props, reusing the exact mechanism portrait-tablet already had (even
  though that mechanism's `frameHeight` half was dormant — my case is the first one where `fill` genuinely
  varies, so `frameHeight` will actually take effect for it):
  1. The sticky-map wrapper condition (was `portraitWide && drawerMode==='vertical'`).
  2. `boundList` (was `portraitWide && …`) — the "freeze the header, scroll the columns independently, map
     stays put" behaviour already built for portrait tablets at v0.62.594.
  3. `MapPanel`'s `frameHeight`/`onExpandFull`/`onCollapse` (were `portraitWide` only).
  4. `MapPanel`'s `fill` prop itself — changed from the unconditional `fill` shorthand to `fill={!staticSplitList}`,
     the ONE place `fill` varies again post-v0.62.655, and specifically for phones, which the v0.62.574
     remount-key comment already anticipated tolerating cheaply ("Phones … keep a CONSTANT key so their
     picker-open fill flip stays a cheap in-place resize with no remount flash").
  5. `ResultSheetShell`'s `active` prop gained `&& !staticSplitList` — the one place that actually skips the
     drawer wrapper and renders the list in plain page flow instead.

- **[DELTA]** (3 files)
  1. `web/hawker/src/App.jsx` — dispatcher routes landscape-phone list mode to `portraitTabletPanel()`
     (function itself untouched); its docstring comment updated to note the second caller.
  2. `web/transport/src/App.jsx` — new static-split branch inside the `viewMode==='list'` block, reusing
     `headerEl`/`mapBlock`/`listBody`/`listScrollRef`/`onListScroll`/`popups`/`footerBar`.
  3. `web/cuisine/src/v2/App.jsx` — `staticSplitList` flag; OR'd into the sticky-map wrapper, `boundList`,
     `MapPanel`'s `frameHeight`/`onExpandFull`/`onCollapse`, and `fill`; `ResultSheetShell`'s `active` excludes it.

- **[KNOWN GAPS / caveats]**
  - **Not device-verified.** Same standing caution as every viewport-conditional change this arc — nobody has
    rotated a real iPhone to landscape, opened list mode, and confirmed the map+list split renders as
    intended rather than, say, both panels collapsing to zero height on some specific viewport quirk.
  - **O-68 (new): Cuisine's portrait-tablet `frameHeight` has been dead code since v0.62.655.** `fill` being
    unconditionally `true` for that device class means the "compact ~40vh framed map" comment at
    `MapPanel.jsx`'s style calc has described unreachable code for two weeks; portrait tablets have actually
    been getting the same full-bleed-behind-drawer treatment as everyone else. Not fixed in this entry —
    no operator report against tablet behaviour, and fixing it means changing what a **currently-shipped,
    unremarked-upon** tablet layout looks like, which is a different risk profile than adding a new
    landscape-phone-only branch nobody has used yet. Flagged for an explicit go-ahead before touching it.
  - **The expand/collapse map button's dead branch, on portrait tablets, is now a live branch for landscape
    phones.** `MapPanel`'s `(fill ? onCollapse : onExpandFull)` click logic was unreachable for portrait
    tablets (`fill` never varied, so only the `onCollapse` arm ever fired, even in carousel mode) — for the
    new landscape-phone case, `fill` genuinely toggles, so BOTH arms are live for the first time. This should
    behave as originally designed (⇲ expands to carousel, ⇱ collapses back), but it is new-territory behaviour
    for code that has sat dormant since v0.62.655, so it's called out rather than assumed correct.
