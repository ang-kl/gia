## New features in this arc

### Cuisine TMA — search results never repeat: deep pool + accumulating exclusion + query-variant escalation (v0.60.114 → v0.60.117)

The headline feature. Re-tapping 🔍 Search with unchanged criteria now behaves the **opposite of Google Maps** (which re-shows page 1 every time): it skips the venues you've already been shown and serves the *next* unseen ones, advancing through an ever-deeper pool, and once the obvious pool is used up it automatically widens the search. Built in four steps:

- **v0.60.114/115 — dedup-exhaustion terminal state.** Per-chatId seen-set (`cuisine:seen:{chatId}:{criteriaHash}` in Redis): each 🔍 filters out previously-shown placeIds for this chat + criteria. When nothing new remains, the server stops resetting/reshuffling (which used to re-serve the same list in a new order with no clear end) and instead returns `exhausted: true` + `poolCount`; the TMA renders a sticky terminal note ("That's all N places matching these criteria…"). A criteria change uses a different criteria-hash → fresh round implicitly.
- **v0.60.116 — deep paginated pool + per-chatId pool cache.** `pipeline.discover()` gains an opt-in `maxPages` param; for the Cuisine single-cuisine path it walks Google Places `searchText`'s `nextPageToken` up to 3 pages (~60 raw → ~30–50 after the brand / dish-tail throttle) so there's a real pool to advance through. That pool is cached in Redis (`cuisine:pool:{chatId}:{criteriaHash}`) so re-clicks within the window don't re-pay for 3 Google calls each. `top` becomes the next 12 *unseen* venues from that pool (was: first 12, then a dedup pass on those 12).
- **v0.60.117 — auto-escalation to wider query phrasings.** Once a phrasing's pool is fully seen, the *next* 🔍 inline-escalates to the next of four ordered phrasings — `"<cuisine> cuisine restaurant"` → `"<cuisine> restaurant Singapore"` → `"best <cuisine> restaurant Singapore"` → `"authentic <cuisine> food Singapore"` — fetches that variant's 3-page pool, dedups it against the accumulated seen-set, and serves the fresh batch on the *same* click. ≈100–130 distinct venues across the four phrasings before the genuinely-terminal state. The variant the user is currently paging through is tracked in `cuisine:variant:{chatId}:{criteriaHash}`; each variant's pool is cached separately (`…:v{idx}`). The exclusion set must **not** reset mid-session — the Redis TTL is now 12 h (pure hygiene, not the reset trigger); the only early resets are a **↺ Start over** link on the terminal note (re-fires the search with `resetSeen`, wiping the seen-set + variant index + variant pool caches) or a criteria change.
- **Why** — Operator 2026-05-11, iteratively: "Same problem… are you able to cache the results per ChatID active session, and then ensure the next set of results are new, store up 60 and clear them"; "I want to be different from Google map, to exclude previous search results"; "intelligence enough to know that it wants new searching after seeing 60 eateries"; "Fresh round should be after the last N places are listed regardless of TTL". Identification needs nothing new — the seen-set / pool / variant keys are already prefixed with the verified Telegram `chatId` (HMAC-validated `initData` via `twa-auth.js` on every `/api/cuisine/search`).
- **Where** — `pipeline.js discover()` (`maxPages`, `queryOverride`); `index.js` (`cuisineSearchVariants()`, `readSeenSet/appendSeenSet/resetSeenSet`, `readVariantIdx/setVariantIdx`, `SEEN_SET_TTL_S`, `POOL_CACHE_TTL_S`, the single-cuisine escalation loop, the `resetSeen` flag, the dedup-slice block); `web/cuisine/src/v2/lib/api.js` (`searchCuisine({ resetSeen })`); `web/cuisine/src/v2/App.jsx` (`runSearch(snap, anchor, { resetSeen })`, the ↺ start over link); `web/cuisine/src/v2/lib/i18n.js` (`result.startOver`, reworded `result.exhausted*` EN + FR).
- **Scope note** — single-cuisine path only; multi-cuisine AND/OR keeps the v0.60.116 behaviour (plain dedup, no escalation). The no-cuisine warm-start path keeps its rotating seeds. Follow-ups: same escalation for the multi-cuisine path; a richer per-cuisine phrase dictionary (alias / iconic-dish queries instead of the four programmatic phrasings); a cron pre-warm of top-cuisine pools so Google calls are bounded by *cuisines* not *users* at scale.
