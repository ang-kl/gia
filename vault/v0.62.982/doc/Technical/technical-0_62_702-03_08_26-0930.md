## 1. Why this document exists

**The six TMAs do not share a z-index scale.** Nothing recorded that, and it has cost two versions:

- **v0.62.691 → v0.62.699.** `z-[35]` was carried from Hawker into Cuisine *together with its
  justification* — *"clears the carousel while staying under the footer dock (z-40)"*. True in
  Hawker. False in Cuisine, whose footer is `z-30`. The expanded map covered the card strip and the
  footer, exactly as the operator reported. **D-70** came out of it: *a z-index is a statement about
  ONE app's stack; port the check, not the number.*
- **v0.62.702 (this entry).** Two Cuisine dialogs sat at `z-30` — the same tier as Cuisine's footer
  dock, which renders **later in the DOM**. At equal z, document order decides, so the footer painted
  over dialogs that declare `aria-modal="true"`. Found by writing this table, not by a report.

A z-value is only meaningful relative to its neighbours. This is the neighbour list.

## 3. Rules

**R-Z1 — a z-index is a statement about one app's stack.** Never port a value between apps. Port the
*check*: list the neighbours in the destination, then choose. (D-70)

**R-Z2 — a comment may assert only what was verified in the file it lands in.** The v0.62.699 bug
survived review because a sentence about Hawker was sitting in a Cuisine file and read as
verification.

**R-Z3 — a dialog must strictly outrank its own app's `chromeTop`.** Equal z is decided by document
order, and chrome usually renders last. Enforced by `__tests__/z-stack-registry.test.js`.

**R-Z4 — `fixed` + a z-index opens a stacking context, and children cannot escape it.** A nested
`z-50` inside a `z-30` root is `z-30` as far as the rest of the app is concerned. Already recorded
in-code at `CuisineCategoryDrawer.jsx:~97`, and the direct cause of half of §4.

**R-Z5 — shared components must clear the highest host `chromeTop`, not the current one.**

## 5. What the guard can and cannot see

`__tests__/z-stack-registry.test.js` reads **source**. It knows each dialog root's declared z and each
app's registered `chromeTop`. It does **not** know DOM order or ancestor stacking contexts — those
were measured. Green means *"no dialog is declared below its app's chrome"*, not *"the stack is
correct"*.

It is **mutation-checked**: reverting both dialogs to `z-30` must fail it with file:line. That check
earned its keep immediately — the first draft **passed** the mutation, because it extracted the
opening tag before stripping comments, and the comment added to explain this very fix contains
`(5591 > 4592)`, whose `>` ended the tag early so `role="dialog"` was never reached. Comments are now
**blanked** (spaces, newlines preserved, offsets intact) **before** the tag is located.

## 6. Adding a new layer — checklist

1. Find the host app's row in §2 and its `chromeTop`.
2. Decide what must be above it and what below, **by role**.
3. Check for an ancestor with `position` + `z-index` (R-Z4) — if there is one, your value is scoped
   inside it and the ancestor's value is what the rest of the app sees.
4. Write the comment to say only what you checked, in this app (R-Z2).
5. If it is a dialog, confirm it clears `chromeTop` (R-Z3) — the test does this for you.
6. If the value lives in `web/_shared/`, clear the **highest** host `chromeTop` (R-Z5).
7. Update §2 and the `APPS` registry in the test.
