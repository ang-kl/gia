## T-69.1 — The audit inverted the premise: most "hard-coded colours" are decisions, not debt

Of 435 classified sites, only 3 were mechanically safe to migrate. The other ~430 fall into documented
deliberate choices (amber-only advisories for the operator's red/green colour-blindness; Google-Maps-white
map chrome; InfoWindows fixed light since v0.61.47 for sunlight readability; CVD-curated brand accents;
two subtrees that deliberately REBIND `--tg-*` to force a light surface). A token bridge that "fixed" these
would have vandalised the design system it claims to serve. The bridge's real deliverables were therefore
NAMES (`tg-warn`, `.gia-map-btn`) and a decision list (Register O-85), not mass substitution.

## T-69.2 — Two traps any future colour migration must respect

(1) **No `--tg-link` exists** — not in `tg-colors.js`, any tailwind config, or any `tg.js`. Emitting a
`tg-link` class produces the classic silent-drop (class referenced, no rule emitted). (2) **Local
rebinding**: `ResultCard`'s focused card and cuisine's `.folio--manila`/`.folder-drawer` re-declare
`--tg-*` inline to force light surfaces, so inside those subtrees a "token" is not the app theme — swaps
there change rendering even when the token names match. Both subtrees are out of bounds for mechanical
migration.

## T-69.3 — Fixed-value role tokens are legitimate bridge output

`tg-warn: '#f59e0b'` is a Tailwind colour, not a CSS variable, on purpose: the advisory role must not
follow themeParams (a red-tinted custom theme must never turn advisories red — the entire point is the
operator's no-red rule). Likewise `.gia-map-btn` holds fixed values because its background is the map
tiles, not the app surface. The bridge maps ROLES to values; only roles that should track the Telegram
theme go through `--tg-*`.
