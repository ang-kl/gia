## 3. New decisions

### D-401 — R.E.D dictionary is deterministic, NO LLM in the disambiguation pipeline

**Decision (v0.60.4):** `disambiguateTerm` runs entirely off `AMBIGUOUS_DISHES` + `PARENT_CUISINES`. No Gemini / Anthropic call. Predictability and zero cost per turn outweigh expressiveness.

**Rationale:** R.E.D pre-step runs on EVERY /s and free-text turn. An LLM call there would compound spend at the highest-frequency surface. The dictionary suffices for the dishes that matter; uncovered dishes fall through to the standard Places searchText path.

**Trade-off accepted:** dictionary maintenance cost. New ambiguous dishes get added by Human Lead via PR.

### D-402 — Locale is physical location, NOT user nationality

**Decision (v0.60.4):** `disambiguateTerm`'s `ctx.locale` (default 'SG') biases `defaultIn[]` matching for ambiguous-dish entries. It does NOT override an explicit modifier (HIGH-confidence interpretation always wins). Language of the user's text is never a nationality signal.

**Rationale:** A Singaporean typing "Sautage" wants French food in SG; the French word doesn't make the user French. Routing on language would be wrong for tourists, multilingual diners, or domain-specific terms.

### D-403 — NATION_OVERLAY caps: 30 per cuisine, 200 special exception for Singaporean

**Decision (v0.60.5/v0.60.20):** `iconicDishes[]` capped at 30 entries per cuisine. Singaporean exception: 200 entries (food + drinks). Drinks (kopi/teh, herbal teas, MJ/calamansi/bandung/Milo dinosaur, etc.) count as iconic entries for SG.

**Rationale:** SG cuisine breadth + drinks vocabulary is materially deeper than other cuisines. Once seeded, the SG list MUST NOT be silently restructured/dropped/replaced — Human Lead is warned before any change.

### D-404 — /hidden tier ladder + MIN_SURVIVORS=1

**Decision (v0.60.26 + v0.60.33):**
- Tier 1: Gemini grounded (default 100m–2km band)
- Tier 2: Gemini wider (1.5–3 km, fires only when allDropped)
- Tier 3: Claude Sonnet + web_search (gated `HIDDEN_CLAUDE_TIER3=true`, default OFF since v0.60.35)
- `MIN_SURVIVORS = 1` — deliver any verified survivor; only escalate when zero survive

**Rationale:** Production logs showed Gemini frequently surfaces 6 candidates and Places verification trims to 1 survivor after CLOSED_PERMANENTLY + address-mismatch rejection. With MIN_SURVIVORS=2 the 1 survivor still triggered tier 2 + tier 3 (180 s wait) without improving truth.

### D-405 — /hidden hallucination guard (two-layer)

**Decision (v0.60.31 + v0.60.33):**
- **Pre-Places:** parseBlocks extracts `claimedDistanceM` from "approx X km" prose. Drop blocks > radius * 1.2 BEFORE Places lookup.
- **Post-Places:** haversine of resolved coords. `dropBlocksByName` strips out-of-radius blocks from delivered text + rewrites "I found N hidden gems" prefix count.

**Rationale:** v0.60.29 prompt hardening alone didn't stop Gemini from fabricating addresses for "near anchor" venues that resolve to far away. Need a verifier guard at both layers.

### D-406 — Anthropic spend gating

**Decision (v0.60.35):** Claude tier 3 `/hidden` fallback gated on `HIDDEN_CLAUDE_TIER3=true` env (default OFF). All other Anthropic surfaces (Haiku for /cuisine NL, Sonnet for /vibe, etc.) remain default-on but at lower cost classes.

**Rationale:** $30/day spend audit traced peak to /hidden tier 3 firing during the Coconut Club hallucination test cycle. Each tier 3 call ~$0.05–0.10 (Sonnet + web_search + ~4 K output tokens). Default-OFF removes the spike vector while preserving the escape hatch for users who want it.

**Verification:** Anthropic dashboard target ≤ $5/day post-deploy (vs $30 baseline).

### D-407 — Michelin sliceCap progression

**Decision (v0.60.30 → v0.60.39, settled):**
- Pure Michelin: `sliceCap = 130` (full curated SG dataset)
- Combo Michelin + cuisine: `sliceCap = pool.length` (every entry that survives `cuisineTagMatches`)

**Rationale:** Initial v0.60.32 cap of 12 was set for token-burn relief but blocked the in-response pagination strip. Restored to 24 (v0.60.34) for browseability, then to 130 (v0.60.37) for full coverage, then combo also uncapped (v0.60.39) so "Chinese + Michelin" doesn't lose tail entries.

**Trade-off:** per-click Places spend rises proportionally to filter survivors. `Places searchText` is much cheaper than Anthropic, and the v0.60.32 "Please wait while loading list…" toast already covers latency UX.

### D-408 — Hawker coords as static JSON (not lazy / not Redis)

**Decision (v0.60.40):** Hawker centre lat/lng lives in `data/hawker-coords.json` committed to repo. Generated once by `node scripts/fetch-hawker-coords.js` against data.gov.sg.

**Rationale:** Dataset is stable. Lazy geocoding adds runtime API cost + first-request latency. Redis caching adds dependency. A static commit is simpler and aligns with the existing `data/list-of-hawker-centres.md` shipping in repo.

**Out-of-band action:** Human Lead runs the script once on Railway (or any internet-reachable machine) post-merge.

### D-409 — HawkerMapPanel: build slim, don't fork cuisine MapPanel

**Decision (v0.60.41):** New `web/hawker/src/components/HawkerMapPanel.jsx` written from scratch (~180 LoC) rather than copying cuisine `MapPanel.jsx` (~400 LoC) and stripping.

**Rationale:** ~40 % of cuisine MapPanel is cuisine-specific (focused-card sync, drift "search here", footfall colours, ratings, travel times, placeId identity). Hawker domain is deterministic, no ranking, no enrichment. Slim build is cleaner than lift + strip and easier to maintain alongside cuisine MapPanel.

**Reused conventions:** `/maps-key` fetch, async script injection with `__giaMapsReady`, AdvancedMarkers + PinElement, phone min(420, 50vh) / tablet min(560, 55vh) height policy.
