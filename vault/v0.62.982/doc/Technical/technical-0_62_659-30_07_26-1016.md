## T-62.1 — `StationLocationField.jsx`: search the dataset you already fetch, don't call an API per keystroke

Cuisine's `LocationField.jsx` (address search) calls a server-proxied Google Places Autocomplete on every
keystroke, 5-minute Redis-cached. The new Train/Hawker station-search field solves a narrower problem —
picking one of ~209 known stations, not resolving an arbitrary address — so it fetches
`/api/transport/stations` once on mount and filters client-side. No new server route, no new billing surface,
no debounce needed. This is the correct trade specifically because the candidate set is small and closed
(MRT/LRT stations don't get added mid-session); it would be the wrong choice for anything with an open-ended
or large candidate set.

## T-62.2 — "Not operating" vs "future" are different filters, and the UI must not conflate them

The operator's clarification ("If the train station is not operating (aka don't be confuse with future
station), still allow to type") maps onto two independent fields in `/api/transport/stations`'s response:
`status: 'future'` (not yet built — has an `opensYear`) is a structural property of the station; a live
service disruption is a property of the *line*, tracked entirely separately
(`/api/transport/status`'s `affectedCodes`/`statusByLine`, unrelated to the station dataset). `nearest()` in
the new component filters out `status==='future'` (a station that doesn't physically exist yet can't be the
one nearest you); the search filter does **not** filter on status at all — every station, operating, future,
or mid-disruption, is typeable and shows up, with only future ones getting the `· opens <year>` tag. Getting
this distinction backwards (e.g. hiding "future" stations from search, or hiding disrupted stations from
"nearest") would have reintroduced exactly the kind of silent, plausible-looking-but-wrong default this arc's
Register keeps flagging (D-22–D-24, D-28).

## T-62.3 — Reusing `location-sync.js` for a one-shot read

`startLocationSync({ durationMs: 0, onLocation })` still runs its first `tick()` immediately regardless of
`durationMs` (only the *re-schedule* is gated on the duration elapsed) — so passing `durationMs: 0` gives a
clean one-shot dual-source (device GPS + Telegram LocationManager, fresher wins) read without duplicating the
polling logic already shared by Cuisine/Hawker/Menu. `StationLocationField` calls `stop()` (the returned
cleanup) on unmount either way, since a one-shot call still schedules nothing further once `durationMs` has
elapsed — this is defensive, not currently load-bearing.

## T-62.4 — Two explicit decision reversals, both operator-directed, both logged rather than silently applied

Per this repo's Recipe (AU-1/AU-7): a later decision that contradicts an earlier one is recorded pointing at
