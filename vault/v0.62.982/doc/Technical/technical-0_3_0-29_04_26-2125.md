### 1.1 Stack additions

### 3.1 Memory — Redis Schema additions

| Key | Type | TTL | Writer | Readers |
| :--- | :--- | :--- | :--- | :--- |
| `vibe:summary:<placeId>` | string | 7 days (`604800s`) | `vibe-summary.js` `getOrCacheSummary` | `/lunch` handler |

**Invariants:**
- Key keyed by Google `placeId`, not by user — multiple users share the same cache.
- No PII anywhere (Place Details review text is public, attached to Google account display name only; we discard reviewer metadata before caching).
- Per-summary TTL of 7 days bounds storage growth: at 25 cached venues, max ~25 keys at any time.

### 5.1 R005 grep list — extended

Pre-commit grep adds `GEMINI_API_KEY` to the existing list. Updated complete list:

`TELEGRAM_BOT_TOKEN`, `LTA_ACCOUNT_KEY`, `GOOGLE_MAPS_API_KEY`, `REDIS_URL`, `WEBHOOK_DOMAIN`, `TELEGRAM_WEBHOOK_SECRET`, `GEMINI_API_KEY`.

### 6.1 Build Constraints additions

- **Gemini API quota.** Free tier: 15 RPM / 1M tokens-per-day for `gemini-1.5-flash`; `gemini-3-flash` quota and pricing per Google docs (could not verify from sandbox). At our usage with 7-day cache: cold start = 25 cached venues × 1 call = 25 calls; steady state ≈ 0–3 calls per `/lunch` invocation. Well under any reasonable threshold.
- **Place Details quota.** New SKU per call vs `searchNearby`. Lazy fetch model means we only spend when a user actually invokes `/lunch` *and* the cache misses. Bounded by `MAX_LISTINGS=25` × 7-day TTL.
