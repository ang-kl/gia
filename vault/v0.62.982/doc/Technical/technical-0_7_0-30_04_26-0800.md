### 2. Pending-state interaction with Gatekeeper

| Order | Behaviour |
| :--- | :--- |
| 1 | User sends `/eat`. Pending = `'food'` (5 min TTL). |
| 2 | User types `Chinatown`. Free-text handler reads pending, treats text as place query. |
| 3 | `geocodeQuery('Chinatown')` → `{ lat: 1.282, lng: 103.844, name: 'Chinatown', placeId: 'ChIJ…' }`. |
| 4 | `setUserLocation(redis, chatId, lat, lng)` (30-min cache). `runFlow(chatId, lat, lng, 'food')`. |
| 5 | Gatekeeper does NOT fire because pending was consumed in step 2. |

If the user types unrelated text WITHOUT a pending flow, the free-text handler falls through to the Gatekeeper as in v0.6.0.

If `geocodeQuery` returns null (no match), the pending flag is **restored** so the next text from the user retries. The user gets a hint: *"I couldn't place X. Try a building or street name, or tap 📍 Share my location."*

### 3. New external API call pattern

| Places `searchText` for typed place name | `vibe-suggest.js geocodeQuery` | None (per-typed-message). Result is one Place lookup. |

This is one additional Places call per "type a place" interaction. At single-user scale negligible; the existing G4 confirmation for Places quota covers it.
