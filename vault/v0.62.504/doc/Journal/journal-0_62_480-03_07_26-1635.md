## New

### [HDR] #834 | 16:35 SGT 03-07-26 | v0.62.480 — /language spans all 8 locales (en/fr/id/ru/de/zh/ja/es) | 4 files | PR #(pending) |
- **[INTENT].** The `/language` command exposed only EN + FR. Extend it to every locale the
  app supports, so a chat-side pick localises the Mini-App surfaces.
- **What the pick actually drives (traced before editing).** `/language` writes a per-user
  Redis pref (`user:{chat}:lang`, 1-year TTL) that is **shared** across chat and every TMA.
  `user-prefs.js` `normaliseLang` gates it. **Caveat surfaced to the operator:** the bot's own
  chat `i18n.js` carries **en/fr strings only**, so the extra locales localise the **Mini-App
  UI**, not the chat replies. A zh/ja/es chat reply still resolves to EN.
- **[DELTA] (4 files).**
  - `user-prefs.js` — `SUPPORTED` `['en','fr','id','ru','de']` → **+`zh`,`ja`,`es`** (8). This
    single array is the one source of truth the regex + callback now validate against.
  - `index.js` — (1) `/language` regex widened to `(en|fr|id|ru|de|zh|ja|es|auto)`; (2)
    `runLanguageCommand` accepts **any** `SUPPORTED` arg (was hardcoded en/fr) and builds an
    **8-button** inline keyboard — flag + endonym, **2 per row** (4 rows, thumb-friendly); (3)
    the `language:set:*` callback generalised from the two-literal check to any `SUPPORTED`
    locale (`setUserLang`→`normaliseLang` is the guard, so a spoofed code no-ops); (4) `/start`
    intro line + handler doc-comment updated to reflect the 8 options + the EN/FR-chat caveat.
  - `i18n.js` — added `bot.lang.set.{id,ru,de,zh,ja,es}` (native-language acks) +
    `language.btn.{id,ru,de,zh,ja,es}` (flag + endonym labels, same EN/FR keys by design).
  - `__tests__/user-prefs.test.js` — `SUPPORTED` equality → 8; the two cases that used `zh`
    as an "unsupported" example reworked to use **`ko`** (Korean), since `zh` is now supported
    and a zh Telegram locale now **auto-resolves to zh**.
- **[VERIFICATION (sandbox)]** `node --check` clean on `index.js`, `user-prefs.js`, `i18n.js`.
  `t()` smoke-test: all 8 `language.btn.*` + `bot.lang.set.*` resolve to native strings. The
  three changed `user-prefs.test.js` assertions re-verified in a standalone node harness
  (SUPPORTED=8, `ko` rejected, `zh` accepted+stored, `ko`→en fallback, `ja` Telegram→ja).
- **[STATUS]** PROD — bot redeploys on merge (Railway). Verify on Telegram: `/language` → an
  8-button keyboard; tap 🇮🇩/🇷🇺/🇩🇪/🇨🇳/🇯🇵/🇪🇸 → native ack + the Cuisine TMA opens in that
  language; chat replies stay EN/FR (documented caveat).
- **[TEST]** Full vitest via CI (unit-covered: `user-prefs` round-trip / reject / resolve).
- **[KNOWN GAPS]** Bot **chat** text is still EN/FR only — localising it to id/ru/de/zh/ja/es
  is a separate, larger job (operator declined it this round; option was offered). The
  `language.current` prompt header falls back to EN for non-EN/FR display locales (the buttons
  carry the meaning via flag + endonym).
