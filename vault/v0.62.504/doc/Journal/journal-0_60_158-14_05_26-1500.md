- **[KNOWN GAPS]**

  **Operator's functional question — Michelin list start position**: surfaced and investigated separately on PR #400's body. Summary:

  - **Storage**: Stored by `chatId + criteriaHash` at `cuisine:seen:<chatId>:<criteriaHash>` (Redis SET, no TTL until explicit reset). The Michelin handler's `criteriaHash` excludes `radius` (per v0.60.153) so the slider drift no longer changes the hash mid-session.
  - **TMA-mount wipe (v0.60.155)**: `POST /api/cuisine/session/start` route at `index.js:7935` deletes every `cuisine:seen:<chatId>:*` key on TMA mount. This SHOULD make a fresh re-open start at list #1.
  - **Suspected race condition**: `App.jsx:281` fires `startSession().catch(...)` **fire-and-forget** (no `await`). A user tapping Michelin search quickly after mount can race the wipe — the Michelin handler reads the seen-set BEFORE the wipe completes server-side, so it filters out entries the wipe is about to remove.
  - **Diagnostic**: `index.js:5679` logs `[Michelin] tap chatId=… hash=<8> seen=N combo=[…]` on every Michelin tap. If `seen > 0` on the very first Michelin tap of a fresh TMA mount, the race is confirmed.
  - **Proposed fix (deferred — awaiting operator decision)**: gate the FIRST `runSearch` of a TMA session behind `startSession()` completion via a `sessionReady` ref (~5 lines in `App.jsx`). Subsequent searches are unaffected. Alternative: server-side lazy-wipe in `handleMichelinSearch` (~10 lines in `index.js`).
