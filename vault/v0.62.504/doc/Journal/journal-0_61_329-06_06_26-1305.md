> Operator (06-06 '26, live v0.61.328, Railway log as proof): the Menu TMA showed a 🇸🇬 flag over a Malaysian address. Railway: `[menu/set-location] D776 ... text="legoland" region=SG → LEGOLAND Malaysia (1.4272,103.6295)` — typing "legoland" while the anchor was `region=SG` resolved to **Legoland Malaysia** (Johor coords) but stored the anchor with `region: SG`. The Menu pill flag reads `anchor.region`, so it showed 🇸🇬 over a Johor address.

Fix: the resolved point is the source of truth. SG bbox → SG, Johor extent → JB, else → OTHER (country MY for the SG/MY-biased text geocode). Contained bug fix; auto-merge squash **armed**. ### [HDR] #530 | 13:05 SGT 06-06-26 | v0.61.329 — Menu set-location re-derives region from RESOLVED coords (🇸🇬-over-MY-address bug) | 3 files | 1 PR | 1 build |

- **[INTENT]** In the Menu TMA, typing a text location (e.g. "legoland") while the anchor's region is SG could resolve to a Malaysian place (Legoland is in Johor, `1.4272,103.6295`). The geocode returned the correct Johor coords, but the stored anchor kept `region: SG`, so the Menu pill rendered 🇸🇬 over a Malaysian address. The region must be derived from **where the resolved point actually is**, not from the request/cached region (which is only a geocode *bias*).

- **[MECHANISM]** The text branch of `/api/menu/set-location` builds `effectiveRegion = requestedRegion || cached?.region || 'SG'` and uses it as the **geocode bias** for `geocodeQueryRegion`. That is correct as a bias. The bug was downstream: the only place `setOpts.region` was set was a `preserveRegion` guard that fired solely when the *cached* region was JB/MY-PUT/OTHER **and** equalled `effectiveRegion`. For an SG anchor that path never ran, so `setOpts.region` stayed unset and the response fell through to `region: setOpts.region || 'SG'` → SG. The fix re-derives region from the **resolved** `r.lat/r.lng` after the geocode: `coarseGate` (SG centroid radius) → SG; else a Johor-extent bbox (`isJbCoords`) → JB; else OTHER. For non-SG it also stamps `country` (`r.country` uppercased, else `MY` for the SG/MY-biased geocode). The radius cap is preserved only when the **derived** region matches the cached region.

- **[DELTA]**

  **1. `location-mode.js`** — `isJbCoords` did not exist on `main` (only `isFarFromJB`, a distance-from-JB_CBD test with the opposite polarity, and `classifyByCountry`, which needs a geocoded admin-area string). Added a pure coordinate-only Johor-extent gate and exported it:

    ```js
    function isJbCoords(input) {
      if (input == null) return false;
      const { lat, lng } = input;
      if (!Number.isFinite(lat) || !Number.isFinite(lng)) return false;
      return lat >= 1.20 && lat <= 2.55 && lng >= 102.50 && lng <= 104.50;
    }
    ```

    Added `isJbCoords` to `module.exports` (next to `isFarFromJB` / `coarseGate`). Legoland `1.4272,103.6295` is inside the bbox → JB. No existing export/const changed.

  **2. `index.js`** — `/api/menu/set-location`, the **text** branch (was ~line 13005-13017). Replaced the `preserveRegion`-only region logic with a re-derivation from the resolved coords:

    ```js
    const { coarseGate, isJbCoords } = require('./location-mode');
    let resolvedRegion;
    if (coarseGate({ lat: r.lat, lng: r.lng })) resolvedRegion = 'SG';
    else if (isJbCoords({ lat: r.lat, lng: r.lng })) resolvedRegion = 'JB';
    else resolvedRegion = 'OTHER';
    const setOpts = { label: r.name || text.trim(), region: resolvedRegion };
    if (resolvedRegion !== 'SG') {
      setOpts.country = (typeof r.country === 'string' && r.country) ? r.country.toUpperCase() : 'MY';
    }
    if (cached?.region === resolvedRegion && Number.isFinite(cached?.radiusCapM)) {
      setOpts.radiusCapM = cached.radiusCapM;
    }
    ```
