## New

### [HDR] #48 | 12:30:00 SGT 01-05-26 | v0.27.0 | n/a kb | n/a lines
- **[INTENT]** Outstanding-list item #3: 60-second per-chat pick cache. v0.26.0 noted ~$0.07/search end-to-end (Reason + Validate + Refine = 2 Gemini + ≤15 Place Details + 1 Routes Matrix). Tap-spam (user taps Search, sees results, taps again to confirm, mucks with sliders, taps a third time) currently bills 3× full pipeline. The cache deduplicates near-identical requests within a 60 s window for ~80% cost cut on the spam pattern.
- **[DELTA]**
  - **NEW** `pick-cache.js` — Redis-backed cache with `get/set/keyFor/TTL_S`. Cache key folds:
    - `chatId` (per-user, prevents cross-tenant leakage)
    - `lat/lng` snapped to a 100 m grid (0.0009° lat-deg) — typo-tolerant within a city block
    - `radius`, `recencyDays`, `queueMaxMin`, `mode`, `when`, `preset`
    - `cuisines` lower-cased + sorted + pipe-joined
    Smoke-tested: two requests with `(1.2839, 103.8517)` vs `(1.28391, 103.85171)` and `[Japanese, Korean]` vs `[Korean, Japanese]` collapse to the same key.
  - **`index.js#POST /api/cuisine-search`** — cache lookup before pipeline dispatch; cache write-through after a successful response with non-empty venues. Diag codes:
    - **D705** cache HIT (returns cached payload + `{cached: true}` flag, ~50 ms instead of ~9 s)
    - **D706** cache STORE (TTL = 60 s)
  - **`web/cuisine/src/state/diagnostics.js`** — added D705 and D706 to the enum so the front-end logger can mirror them.
  - **`web/cuisine/src/App.jsx`** — when `result.body.cached === true`, records D705 in the local diag log so power-users (long-press → diag ON) see when they've hit cache.
  - **`web/cuisine/src/main.jsx`** — `D040 bundle loaded version=0.27.0`.
- **[VERIFICATION (sandbox)]**
  ```
  node --check on index.js, pick-cache.js → OK
  node -e "keyFor smoke" → both variants collapse to same key ✓
  cd web/cuisine && npm run build → vite v5.4.21 ✓ in 1.12s
    → public/cuisine/assets/index-*.js  168.18 kB (gzip 54.56 kB)
  ```
  Live cache-hit measurement requires Railway round-trip; expected behaviour: first tap ~9 s (full pipeline + D706), second tap within 60 s ~50 ms (D705).
- **[STATUS]** PROD — auto-deploys with the next Railway build.
- **[TEST]**
  1. Tap Search → first response in ~9 s with cards. Railway logs `D700 → D702 OK <ms> venues=N` and `D706 cache STORE ttl=60s`.
  2. Tap Search again within 60 s with the same controls and ~same location → response in ~50 ms. Railway logs `D700 → D705 cache HIT <ms> venues=N`. TMA Diagnostics (long-press → diag ON) records `D705 Server cache hit (60s pick cache)`.
  3. Move location ≥ 100 m → next tap misses cache (different grid cell), full pipeline runs, fresh `D706 cache STORE`.
  4. Wait 60+ s → next tap misses cache (TTL expired), full pipeline runs.
  5. Change ANY slider (radius / recency / queue) → cache key changes, fresh pipeline run.
- **[KNOWN GAPS]**
  - Cache key includes `lat/lng` *snapped to a 100 m grid* but does NOT include precise location, so two users in the same building share cache. That's intentional for cost — the picks are area-based, not personalised. If we ever add user-personalised picks (favourites, history bias), drop the snap and key on raw `lat/lng`.
  - Cached response carries the older Refine timing — if it just rained heavily 30 s after a cache write, the user gets stale weather advice for up to 60 s. Acceptable trade for the cost cut; could be tightened to 20 s if weather staleness becomes noticeable.
