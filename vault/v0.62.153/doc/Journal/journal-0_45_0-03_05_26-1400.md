## New

### [HDR] #92 | 14:00:00 SGT 03-05-26 | v0.45.0 | n/a kb | n/a lines

- **[INTENT]** Per Human Lead, restore the v0.1-era "5 map locations on one map" UX. **First half of investigation: that feature is already built** (cuisine TMA `ResultsGrid.jsx` has the footer button, `/app/map` reads `#venues=<base64>` hash, `deliverPicks` calls `sendGoogleMapsContainer` for chat-side multi-stop directions). The actual gap is that the URL construction logic is **scattered across 7 files with subtly different fallback chains** — meaning the v0.44.2 iOS Apple-Maps fix only landed in `/p m`, while `/eat` / `/drink` / `vibe.js` paths still routed users to Apple Maps because they used `googleMapsUri` directly without the place_id deep-link fallback.
- **Centralise it.** One helper module (`maps-url.js`), three exports, used everywhere. Plus add the multi-marker map link to `/p m` output (which previously had per-card URLs but no shared map link).

- **[DESIGN]**

  1. **NEW `maps-url.js`** — single source of truth for Google Maps URL construction. Three exports:
     - `googleMapsUrl(place)` — single-venue URL with explicit fallback order:
       1. `place.googleMapsLinks.placeUri` (place_id-explicit deep-link, opens Google Maps app on iOS via Universal Links)
       2. `place.url` (already-constructed URL from upstream)
       3. `place.googleMapsUri` (cid-based; sometimes routed to Apple Maps)
       4. Synthesised `https://www.google.com/maps/place/?q=place_id:<id>` from `place.placeId` or `place.id`
       5. `place.directionsUri`
       6. `https://www.google.com/maps/search/?api=1&query=<lat>,<lng>` from coords
       7. `null`
     - `googleMapsContainerUrl(places, opts)` — multi-stop directions URL (destination + up to 4 waypoints, 5 venues max — Google Maps URL hard limit). Walking by default. `opts.travelmode` and `opts.origin` overridable.
     - `buildMapHashUrl(venues, opts)` — TMA hash URL `/app/map#venues=<base64>` mirroring the format produced by `web/cuisine/src/components/ResultsGrid.jsx`. With `opts.webhookDomain` returns a fully-shareable `https://<domain>/app/map#venues=...` URL.
     - All three handle `null` / empty / missing-coords inputs defensively. Reject `javascript:`-style URLs in the `place.url` fallback path.

  2. **Sweep across 7 venue-card codepaths** to use `googleMapsUrl(place)` instead of inline ternary chains:
     - `vibe.js:65` — **REAL BUG FIX**: was using `p.googleMapsUri ?? ''` only (no `placeUri` fallback, no place_id deep-link synthesis). vibe-cached venues used by `/eat` and `/drink` were the actual source of the iOS Apple-Maps reports. Field mask also extended to request `googleMapsLinks`.
     - `surprise.js:332`, `vibe-suggest.js:179`, `pipeline.js:450`, `consultant.js:136`, `vault.js:81` — already had correct precedence inline; switched to helper for consistency. No behavioural change, but means future fixes propagate everywhere automatically.
     - `index.js#deliverPicks` (the chat-side reply button at line ~488) — was synthesising the place_id URL inline; switched to helper.
     - `prompt-query.js#viaMaps` — already fixed in v0.44.2; switched to helper for consistency.

  3. **NEW: multi-marker map link on `/p m` output** — previously each `/p m` venue had its own URL but no shared map link. Now the response footer includes `🗺 View all 5 on map: https://<webhookDomain>/app/map#venues=...` which opens the existing TMA at `/app/map` with all 5 venues as numbered markers. Reuses the same `buildMapHashUrl()` helper the cuisine TMA uses.

  4. **NEW `__tests__/maps-url.test.js`** — 21 tests covering:
     - `googleMapsUrl`: null/empty handling, all 7 fallback levels, encoding, javascript:-URL rejection.
     - `googleMapsContainerUrl`: empty handling, place_id vs coord destination, 4-waypoint cap, travelmode + origin overrides.
     - `buildMapHashUrl`: empty handling, no-coords filtering, base64url encoding (no `+` `/` `=`), `webhookDomain` shareability.
     - Total tests: 105 → 126.

- **[REUSED]**
  - `Buffer` for base64 encoding in `buildMapHashUrl` (server side; replaces the `btoa(unescape(encodeURIComponent(...)))` browser-side dance in `ResultsGrid.jsx`).
  - The same `place_id-explicit` URL format the cuisine TMA's footer button has used since v0.32.0.
  - Existing `/app/map` vanilla JS at `public/app.js` already reads `#venues=<base64>` hash — no TMA changes needed.

## Amendments

**Prior (v0.44.2 vibe.js URL extraction at line 65):**
```js
url: p.googleMapsUri ?? '',
```

```js
// v0.45.0: prefer place_id deep-link over cid URL — fixes iOS

url: googleMapsUrl(p) ?? '',
googleMapsLinks: p.googleMapsLinks ?? null,
googleMapsUri: p.googleMapsUri ?? null,
```
Also extended field mask to request `places.googleMapsLinks`.

**Prior (v0.44.0 surprise.js / vibe-suggest.js / pipeline.js / consultant.js / vault.js — repeated 5×):**
```js
url: place.googleMapsLinks?.placeUri ?? place.googleMapsUri ?? '',
```

**v0.45.0 amendment:** consistent helper:
```js
url: googleMapsUrl(place) ?? '',
```
Behavioural-equivalent for places with `googleMapsLinks` (placeUri preferred); behavioural improvement when `googleMapsLinks` absent (now synthesises place_id deep-link from `place.id`).
