- **[BUG — JB sub-location results far from the pick (root cause)]** The cuisine-search route
  (`index.js:~14388`) and the warm-start path (`~12861`) tested "is this coordinate in Singapore?" with
  an **old inline FLAT SG bbox** (lat 1.15–1.50, lng 103.6–104.1). That box **over-claims JB
  sub-locations** (Legoland 1.4296/103.6321, Bukit Indah 1.4773/103.6645, Southkey 1.4912/103.7665) as
  "inside SG". The search center is then
  `searchCenter = isJB ? (insideSG ? JB_CBD : { lat, lng })` — so for a region=JB pick whose coords
  *looked* SG, the picked chip coords were **replaced by the JB CBD centroid** (1.4927/103.7414). Result:
  the pin sat on Legoland but the venues came from JB CBD / Mount Austin. (Mt Austin 1.5252 is north of
  1.50 → already worked; CBD == JB_CBD → coincidentally fine.)

- **[DELTA — fix: port the client's carve-out to the server]** The **client already solved this** in
  v0.61.281 (`web/cuisine/src/v2/lib/coords-to-country.js` `_inSgBbox`): **west of lng 103.70** the SG
  north cap drops to **lat 1.42** (Tuas Second Link), so Iskandar Puteri / Legoland / Bukit Indah
  classify as JB. The **server never got that fix.** Added **`location-mode.insideSgBbox`** mirroring it
  (`SG_BBOX`: east/central cap lat 1.47, west cap 1.42 below lng 103.70) + exported it, and replaced
  **both** inline flat-bbox sites with it.
  - Verified: Legoland / Bukit Indah / CBD / Southkey / Mt Austin → `insideSgBbox = false` (coords
    honoured → search centres on the chip). Orchard / Woodlands / Changi / SG-centroid → `true`
    (genuine SG stays SG, so a region=JB pick made from inside SG still snaps to JB CBD as before).

- **[KNOWN GAPS — Problem 2 STILL DUE (surfaced, not shipped)]** The 4th screenshot: device GPS (SG ·
  Katong) **silently overrides** the user's saved labelled pick (MY · (Mount) Austin) at boot. Root
  cause: `App.jsx:~889` — when Telegram initData carries device GPS, the boot **short-circuits
  `tryServerCache()`** (`~893`), so the saved pick is never loaded into `locationAnchor` and the existing
  anchor/device prompt never has data to compare. The keep/use banner UI (`App.jsx:2660`) is **dead code**
  (`setAnchorMismatch` is only ever called with `null`, `~1434`). Operator chose **"prompt, don't
  auto-switch"** — BUT investigation found that exact keep/use popup was **deliberately removed**:
  **v0.61.407** ("the shared set-location is authoritative — keep it, don't ask") and **v0.61.409**
  ("saved ≠ device → no popup, empty TMA, tap 🔍"). Re-adding it **reverses that twice-made policy** and
  **touches the fragile boot gate** (`modalPendingRef`), which the location-reconciliation rules say to
  confirm before changing. So it was **surfaced for operator confirmation** rather than silently
  reversed — to be done in a follow-up PR once the exact behaviour is chosen.
