# Feature — soleat v0.60.130 (delta entry)

> Per `doc/CLAUDE.md` §3 + AU-1: supersedes `feature-0_60_117-11_05_26-1600.md` by reference. All prior feature catalogue entries stand; this entry adds the v0.60.118 → v0.60.130 features. ## New features in this arc

### `/weather` expansion — rain caveat on open-air picks · `/weather <area>` head-out window · 24h "tonight" line · hot-day air-con nudge (v0.60.118)

- **What** — `/weather` with no argument now leads with an *interpreted* head-out line (raining / showery / good window to head out), keeps the existing temp / humidity / rain / wind / 2-hour lines, adds a `🌙 Tonight in the {zone}: …` line from the NEA 24-hour forecast, and a "≥ 33 °C — find air-con" nudge when it's hot. `/weather <area>` (e.g. `/weather tampines`, `/weather east`) resolves the area against the ~47 NEA nowcast area names then the 5 broad zones (+ synonyms) and prepends a "— for {area} —" sub-line with that area's outlook; an unknown area gets a friendly "I don't know that area …" reply. Separately, **`/eat` / `/surprise` picks now carry a rain caveat** on rain-sensitive (open-air) venues — a one-line "🌧️ raining near {area} now — covered seating helps" / "{desc} in {area}'s 2h outlook" rendered after the footfall row; ordinary (likely indoor) restaurants get no rain line.
- **Why** — Operator, from the NEA-feeds discussion: a rain caveat on open-air picks, a `/weather <area>` "good window to head out?" answer, the `tempC ≥ 33` nudge, and a 24h "tonight" line.
- **Where** — `weather.js` (cached fetchers `getNowcastCached` / `getRainfallCached` / `get24hCached`, new `fetch24hForecast`; pure helpers `inSgBounds`, `WEATHER_ZONE_CENTROIDS` + `zoneKeyFor`/`zoneLabelFor`, `resolveArea`, `rainAlertFor`, `headOutLine`, `tonightOutlookFor`, `attachRainAlerts`); `venue-filters.js` `isRainSensitiveVenue`; `venue-templates.js formatVenueBlock` (renders `p.rainAlert`); `index.js` `/weather` regex + `runWeatherCommand(chatId, lang, areaArg)`, `deliverPicks` + `deliverSurprise` call `weather.attachRainAlerts` (best-effort); `i18n.js` `weather.areaUnknown` / `weather.forArea` / `weather.headOutRaining|Showery|Good` / `weather.hotNudge` / `weather.tonight` / `weather.rainNowNear` / `weather.rainSoonNear` (EN + FR); new `__tests__/weather.test.js` + `__tests__/venue-filters.test.js`.
- **Scope note / follow-ups** (recorded in the PR, not in this PR): a 🌧️ rain chip on the Cuisine / Hawker TMA `VenueCard` (needs `rainAlert` plumbed into `/api/cuisine/search` + `/api/hawker/...`); radar-image-derived "rain in exactly N min" precision + rain-trend; wider multi-cuisine coverage.

### Cuisine TMA — a location picked in Search Criteria locks in + updates the banner + the bot's `/location` (v0.60.119 → v0.60.120)

- **What** — Picking a place in the Search-criteria location field now (a) stays the search anchor across criteria-card collapses / nav-FAB taps / TMA background-restore (no more reverting to the device / `/location` pin); (b) updates the "📍 {neighbourhood} · N places nearby" banner under the TMA title to show the picked place; and (c) becomes the user's `/location` server-side — persisting across TMA sessions and into chat commands (`/eat`, `/weather`, `/transport`, …). A `×` clear snaps back to the device pin (and does **not** re-save anything); a map pan / "Search this area" updates the banner + search anchor but does **not** touch `/location`.
- **Why** — Operator: "I change the location in Search Criteria (Cuisine TMA), it should lock in as the new location — it is reset to the location last set at `/location` or the device"; then "after picking 'Alexandra Retail Centre' the banner still said Yishun and `/location` wasn't updated either."
- **Where** — `web/cuisine/src/v2/App.jsx` (`locationAnchor` is now the durable source of truth — nothing nulls it on background; `runSearch` anchor chain `anchor || searchCenter || locationAnchor || userLoc`; `runSearchAt` also `setLocationAnchor`; banner `locationName` effect keys on `locationAnchor ?? userLoc`); `web/cuisine/src/v2/components/LocationField.jsx` (accepts `anchor`; resting label / `×`-clear visibility track the anchor); `web/cuisine/src/v2/lib/api.js` (`saveUserLocation`); `index.js` new `POST /api/cuisine/set-location` (`initData`-verified; `setUserLocation(redis, chatId, lat, lng)`).

### Bus — arrivals sorted by ETA in the map InfoWindow · "Plan a route" opens Google Maps directly (v0.60.121)

- **What** — The `/transport bus → Nearest stops` map's per-stop InfoWindow now lists services soonest-first and band-grouped (`№ 145, 273, 120 — ≤5 min` before the `≤10 min` line) the same way the chat reply does. The Bus menu's "🗺 Plan a route" button **is** the Google Maps link now — a direct `https://www.google.com/maps/dir/?api=1&travelmode=transit` URL button (origin = the device's current location in Maps; the user types the destination) — instead of posting an intermediate message with an "Open Google Maps" button.
- **Why** — Operator: "View bus stops — arrivals weren't sorted by time in the map popup"; "Plan a route should just open Google Maps."
- **Where** — `transport.js busArrivals()` (returns services sorted by next-bus ETA; ties broken numerically; no-live-reading sinks to the bottom); `public/app.js` (bus-stop InfoWindow band-grouping); `index.js` (the `transport:bus:route` button → direct Maps URL; the callback / `/transport busroute` text path still works).

### Free-text dish search — "actually serves it" above the line, looser Google matches below (v0.60.122 → v0.60.127)

- **What** — When a one/two-word chat query is disambiguated by R.E.D into a dish + cuisine (e.g. "goulash dumplings" → "Czech guláš with bread dumplings", European), the result list is no longer sorted by distance only — it splits into an **above-the-line tier** of venues that *actually* read as that cuisine / serve that dish, then a **divider**, then the **below-the-line tier** of looser Google text-matches (e.g. a Chinese 灌汤包 place for "bread dumplings"). Nothing is dropped; ~7–8 shown. The above-the-line test went through three iterations: v0.60.124 split keywords into STRONG (cuisine name + curated dish/demonym vocabulary + `*_restaurant` `primaryType`) vs WEAK (generic words from the dish *label*); v0.60.125 tightened "above" to require the **venue name** (or `primaryType`) to self-identify as the cuisine — a strong word found only in a review is a soft signal that just orders the below tier. The divider copy was reworded across v0.60.122 → v0.60.130 (see the Amendments / Behavioural-changes notes); v0.60.127 made it two lines with the dish name on its own line.
- **Why** — Operator, re-testing "Goulash dumplings": the results were a mixed bag (a Chinese "Jiangsu Restaurant", a Nordic spot, only one Slavic place) because the bare-free-text path sorted by distance with no relevance check; chosen fix: "don't drop anything — sort exact → possibilities, with a divider line, ≥~7 shown."
- **Where** — `index.js deliverPicks` (`opts.dividerAfter` + `opts.dividerText`); `index.js runFreeTextSearch` (`opts.cuisine` / `opts.dishLabel`; `queryOverride` to feed Places the anchored phrase verbatim; the STRONG/WEAK scorer; the above/below split + slice; the divider emit); `cuisine-dish-keywords.js` (new `european` keyword list — goulash-family dishes + Central/Germanic demonyms + distinctive eatery name-words `hospoda`/`pivovar`/`brotzeit`/`gasthaus`/…); `i18n.js` `freetext.divider`.

### Cuisine TMA — the "Tell me" free-text box feeds the criteria search; Enter no longer searches (v0.60.126)

- **What** — Typing a qualifier in the Cuisine-TMA "💬 Tell me" box (e.g. "Goulash Dumplings") now actually carries into the 🔍 criteria search instead of being silently dropped when you also pick a cuisine — `cuisine=Portuguese + freeText="goulash dumplings"` → server query `"Portuguese goulash dumplings"`; with no cuisine selected the free text becomes the whole query (capped 80 chars). Pressing **Enter** in the box no longer fires a search — search is via the → button or the 🔍 Search buttons / FAB only.
- **Why** — Operator: typing in the free-text box then selecting a cuisine ran the search with only the cuisine; and Enter shouldn't fire a search.
- **Where** — `web/cuisine/src/v2/components/TellMePanel.jsx` (controlled input; Enter→submit removed); `web/cuisine/src/v2/App.jsx` (`nlText` state, pre-fillable from a `/cuisine` deep-link's `freeText`; `runSearch` passes `freeText: nlText.trim()`); `web/cuisine/src/v2/lib/api.js searchCuisine` (forwards `freeText`); `index.js /api/cuisine/search` (folds `req.body.freeText` into the Places query).

### Misrepresented-dish note on the free-text dish-search paths (v0.60.128)

- **What** — Typing one or two words that name a "misrepresented" dish / dessert / drink — from the operator-authored `data/Misrepresented Dish Dessert Drink.MD` (759 entries: `Name - often assumed X, but actually Y`) — now surfaces the "actually it's …" context line alongside whatever search runs. In chat it's an `ℹ️ <b>{Name}</b> — {note}` line before the results; in the Cuisine TMA it's a banner above the result list. Examples: `ramen` → "sometimes assumed ancient Japanese, but it has Chinese noodle roots…"; `carbonara` → "Roman carbonara traditionally does not use cream"; `nachos` → "the dish is Tex-Mex / border cuisine"; `butterbeer` → "the popular version is a fictional Harry Potter-themed beverage". Informational only — it doesn't change which venues are returned. Distinct from `/s` and from R.E.D's `disambiguateTerm` (which steers the Places query); the chat note is skipped when R.E.D already disclosed (no double note).
- **Why** — The .md's embedded note: "tabulate them in table. Whenever a user types one or two words in free type chat or in the free text chat in cuisine TMA. Not to be confused with /s command."
- **Where** — new `misrepresented-dishes.js` (parses the .md at module load → `{ name, note }` map; `lookupMisrepresentedDish(text)` = exact-normalised match + last-word singular/plural fold + single-word prefix-disambiguation; bails on >6 words / >48 chars; never throws); `index.js` chat free-text handler + `/api/cuisine/search` (`misrepresentation: { name, note }` on the payload); `web/cuisine/src/v2/App.jsx` (banner); `i18n.js` `misrep.note` (EN/FR; `{note}` stays English — source data is English-only); new `__tests__/misrepresented-dishes.test.js`.

### Cooking-method "did you mean" pivot, merging the operator's cuisine→method reference (v0.60.129 → v0.60.130)

- **What** — Typing one or two words that name a cooking method — from `cooking-methods.js` (the existing chef-English dict) **plus** the operator-authored `data/cooking method reference by cuisine.md` (~70 cuisine sections of traditional verbatim terms: `agemono`, `tadka`, `wok hei`, `dum`, `nimono`, `hongshao`, …) merged into it — now triggers a polite tap-to-pivot: "🙂 Were you perhaps after a cooking method? Tap a cuisine below, or search literally." with one button per cuisine that uses that method (`tadka` → South Indian / North Indian / Pakistani / …; `wok hei` → Singaporean / Cantonese / Sichuanese / Hong Kong / …) plus a "🔍 Search literally" escape. Tapping a cuisine runs the rich-card fan-out for that cuisine; tapping "🔍 Search literally" runs a plain Places search on the raw text. Wired on three surfaces: the chat free-text handler (after the R.E.D + misrep steps; skipped when R.E.D disclosed); `/s` (a *verbatim single-cuisine* method still fans out directly — the pre-v0.60.129 power-user path; ambiguous / non-verbatim → pivot); and the Cuisine-TMA "Tell me" box (banner with cuisine chips above the result list; a chip prefills that cuisine into the criteria and re-runs the search).
- **Why** — The .md's embedded note: "tabulate them in table. Whenever a user types one or two words in free type chat or in the free text chat in cuisine TMA. Use with /s command as well. Better to check with user if he/her meant this." Operator scope: "combine with existing cooking-methods.js + wire 'do you mean' pivot." Then v0.60.130: "ask in polite tone rather than 'did you mean'."
- **Where** — `cooking-methods.js` (parses + UNION-merges the .md at module load — existing tokens kept, new appended, deduped; bare single-token common verbs filtered via `MD_BARE_VERB_STOPLIST`; ~24 new cuisine slugs → 94 total; new `findCookingMethodMatches(text, opts)` returning all per-slug matches; `findCookingMethod = …Matches(text)[0]`); `index.js` (`buildCookMethodKeyboard`; the chat free-text pivot; `handleSearchTurn` verbatim-vs-pivot branch; `/api/cuisine/search` `cookingMethod: { query, matches }` payload; new `bot.on('callback_query')` `cookm:<idx>:<text>` / `cookm:L:<text>` handler — text capped 40 chars, handler re-derives the match list); `web/cuisine/src/v2/App.jsx` (banner with cuisine chip-buttons); `i18n.js` `cookmethod.didYouMean` / `cookmethod.literalBtn` (EN/FR); `__tests__/cooking-methods.test.js` extended.
