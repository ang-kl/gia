### [HDR] #45 | 11:30:00 SGT 01-05-26 | v0.26.3 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead 4-part repair spec restating the bridge failure ("Search button currently fails to deliver the user's prompt to the server, resulting in no response"). The escalation past v0.26.1's pre-flight ping + chat receipt names a real Telegram WebApp gap I underestimated:

  > "verify the launch context of the TMA; if the app is launched via a KeyboardButton, configure the Search button to use Telegram.WebApp.sendData() to pass the search string back to the bot as a service message. If launched via an inline button, refactor the Search button to use a standard POST request to the /api/search endpoint on Railway, ensuring CORS is enabled on the server."

  Per the Telegram WebApp spec, `sendData()` is documented as usable **only** when the WebApp is launched from a KeyboardButton or chat-menu button — it throws on inline-button or direct-link launches. Conversely, fetch+initData works in every context but requires the in-app webview to allow same-origin XHR + initData population (some Android Telegram builds + corporate-MDM webviews silently block).

  v0.26.1 picked a single channel (fetch). v0.26.3 picks **both** — primary fetch, fallback to sendData on any HTTP failure, with full simulation logging at every step.

- **[KNOWN GAPS]**
  - Telegram never exposes "you were launched from KeyboardButton/inline/menu/direct" as a clean enum. We probe and fall back rather than guess.
  - The `D730` inbound payload preview is capped at 240 chars; very long payloads (15-pick + dishes + reviews) will be truncated in the log. Acceptable — the TMA payload to `cuisine-search` is bounded to lat/lng/cuisines/sliders, ~150 chars typical.

  - If both channels fail, we surface the failure in the Diagnostics panel rather than silently retrying. Explicit failure > infinite spinner.
