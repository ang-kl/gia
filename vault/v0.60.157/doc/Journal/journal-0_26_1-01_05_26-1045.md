## New

### [HDR] #43 | 10:45:00 SGT 01-05-26 | v0.26.1 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead 3-part TMA bridge audit ((№ 138)) explicitly naming the failure mode as "disconnection between the front-end event listener and the bot's API endpoint on Railway". Three asks:
  1. **Front-end trigger audit** — verify the Search button actually fires the fetch and points at the right URL.
  2. **Backend listener audit** — verify the route receives + parses TMA payloads and dispatches into the Reason–Fetch–Refine sequence.
  3. **Visual feedback loop** — TMA shows "Sensing…" *and* the backend pushes a "Sensing the vibe…" status message back to the Telegram chat.
- **[AUDIT FINDINGS]**
  - Front-end (`web/cuisine/src/App.jsx#onSearch`): button is `<button onClick={onSearch}>`, fires `searchCuisine(payload)` from `api/search.js`, which `fetch('/api/cuisine-search', POST, headers: {Content-Type, X-Telegram-Init-Data})`. Same-origin (TMA served from `/app/cuisine`, API at `/api/cuisine-search` — both under `webhookDomain`). **No fetch call missing; no listener missing.** D400–D406 already record every step.
  - Backend (`index.js#POST /api/cuisine-search`): route exists, `requireInitData` middleware verified, dispatches into `searchCuisine` → `runPipeline` → reason/fetch/refine. **Wired correctly.**
  - **Real risks identified during audit:**
    - **CORS** — same-origin today, but if a future preview deploy ever serves the TMA from a different host, the fetch would be silently blocked. No `Access-Control-Allow-Origin` was set.
    - **No pre-flight indicator** — if the bridge IS broken (auth misconfigured, route missing in a partial deploy, env vars unset), the only way the user finds out is by tapping Search and getting a delayed failure. Better: ping a tiny endpoint at TMA mount and show a green/red dot up front.
    - **No backend chat receipt** — visual feedback was TMA-only. If the TMA's loading state doesn't paint (network blip / Telegram in-app webview quirk), the user sees nothing happen.
- **[DELTA]**
  - **`index.js`** —
    - + `const pkgJson = require('./package.json')` for surfacing the running version on the diag endpoint.
    - + Permissive CORS on `/api/*` routes: `Access-Control-Allow-Origin: *`, methods `GET, POST, OPTIONS`, allowed header `X-Telegram-Init-Data`. Safe under wildcard because auth is via header (no cookies cross the boundary). OPTIONS pre-flight returns 204.
    - + `GET /api/diag/cuisine` — auth-free pre-flight ping. Returns `{ok, version, pipelineEnabled, envPresent: {TELEGRAM_BOT_TOKEN, GOOGLE_MAPS_API_KEY, GEMINI_API_KEY}, vaultIndexLoaded, webhookDomain, timestamp, diag: 'D710'}`. Auth-free by design — its purpose is to confirm "the bridge is up" *before* initData is even available.
    - + `POST /api/cuisine-search` now extracts `tgUserId = req.tg?.user?.id` (set by `requireInitData`) and fires-and-forgets a `safeSend(tgUserId, '🌿 Sensing the vibe… (Cuisine Picker)')` chat message at the very top of the handler. Throttled by `isProcessing` flag so a fat-fingered user can't spam. Cleared in the `finally` block.
    - + New diag code D704 — chat receipt failure (logged only, never blocks).
  - **`web/cuisine/src/api/search.js`** — added `diagPing()` returning `{status, ok, body, elapsedMs}`. Auth-free `GET /api/diag/cuisine`.
  - **`web/cuisine/src/state/diagnostics.js`** — added codes D050 (bridge ping), D051 (bridge ok), D052 (bridge fail), D053 (pipeline disabled on server).
  - **`web/cuisine/src/App.jsx`** —
    - On mount: `console.log('[Cuisine-Diag] API base = <origin>/api/cuisine-search')` so the dev can verify routing in the TMA's webview console.
    - On mount: fires `diagPing()`, records D050 → D051/D052/D053, sets `bridge` state.
    - New visible **connectivity badge** rendered just below the Header: `● online v0.26.1` (green) / `● offline` (red) / `… checking` (grey). Adds `(pipeline OFF)` when `PIPELINE_ENABLED=false` server-side so the user knows why advice is back to legacy shape.

- **[TEST]**
  1. Open `/cuisine`. Connectivity badge shows `● online v0.26.1` within ~500 ms of paint. Telegram in-app console logs `[Cuisine-Diag] API base = https://<host>/api/cuisine-search` and `[Cuisine-Diag] ✓ D051 Bridge OK`.
  2. If Railway is down or the route is wrong: badge shows `● offline` red, Diagnostics panel auto-opens showing `✗ D052 Bridge unreachable :: status=0` (network) or `status=404` (route missing).
  3. Tap Search → user should *also* receive a Telegram chat message "🌿 Sensing the vibe… (Cuisine Picker)" within 1–2 seconds. Confirms the bridge from TMA to backend is alive even if the TMA loading state never paints.
  4. Set `PIPELINE_ENABLED=false` in Railway → badge reads `● online v0.26.1 (pipeline OFF)`, Diagnostics panel records `✗ D053 PIPELINE_ENABLED=false on server`.
  5. CORS smoke test: `curl -i -X OPTIONS https://<host>/api/diag/cuisine -H "Origin: https://example.com"` → 204 with `Access-Control-Allow-Origin: *`.
- **[KNOWN GAPS]**
  - The chat receipt arrives in the chat *while* the user is still inside the TMA webview — they may not see it until they close the TMA. That's acceptable: it's a fallback signal, not the primary feedback. Primary remains TMA "Sensing…".
  - Pre-flight ping has no retry; a single transient failure paints the badge red. Keeping it strict on purpose so the user sees the real connectivity state without false greens.
  - Auth-free `/api/diag/cuisine` is intentional and exposes only non-secret info (boolean env presence, version string). No tokens leak.
  - CORS wildcard is intentionally broad. If we ever start using cookies for auth (we don't today), this becomes unsafe and must be tightened to a specific origin allowlist.
