## T-61.1 — The silent-drop failure family (three occurrences in one arc)

The defining technical lesson of this arc. Three separate build-time failures where **something was
discarded without an error**, each shipping a visibly broken UI while every unit test stayed green.

| # | Version | What was dropped | How it looked | Caught by |
|---|---|---|---|---|
| 1 | v0.62.648 | Every `/NN` **opacity** colour utility | The bottom sheet's drag handle was an invisible 48×6 box — for two releases | Reading the built stylesheet by hand |
| 2 | v0.62.649 | Every **bare** colour utility | Loading card had no fill; its accent border fell back to `currentColor` | Operator screenshot |
| 3 | v0.62.654 | The entire arbitrary min/max **breakpoint variant family** | iPad mini and iPad landscape lost their third column | The ten-profile browser smoke |

**Root causes, all Tailwind, all different:**

1. A colour declared as a raw `var()` string has nowhere to put an alpha, so Tailwind **discards the
   utility** rather than warning.
2. The fix for (1) assumed `opacityValue` was numeric. Tailwind passes the literal string
   `'var(--tw-bg-opacity)'` for the **bare** utility; `Number()` of that is `NaN`, producing
   `color-mix(… NaN%, transparent)` — invalid CSS, dropped by the browser. **The fix was worse than
   the bug.**
3. A template interpolation inside a file in the `content` glob made Tailwind read a **mixed-unit
   `screens` config** and disable the whole variant family. Writing the offending pattern in an
   explanatory **comment re-triggered it** — the scanner reads comments too.

**Decision T-61.1a:** *A Tailwind colour function must treat `opacityValue` as an arbitrary CSS token,
not a number.* Non-finite → return the plain value. Enforced by `__tests__/tg-colors.test.js`.

**Decision T-61.1b:** *Never interpolate into a Tailwind class string in a scanned file — not even
inside a comment.* Enforced by `__tests__/viewport-breakpoints.test.js`, which asserts the
`LIST_GRID_CLASS` declaration line contains no `${`.

**Decision T-61.1c (the durable one):** *Assert on computed style or built output, never only on a
class string.* Every one of the three was caught by something that measured what the browser actually
did; none was caught by a unit test asserting on source. The repo now carries both kinds of guard.

## T-61.2 — One definition of "wide"

Two competing answers had grown up independently: `classify-viewport.js` (tablet ≥ 700, desktop
≥ 1024) and Tailwind breakpoints chosen ad hoc in each app's grid. At ~1000 px — a half-screen
Telegram Desktop window — the CSS said "wide enough for three columns" while the classifier said
"mobile".

`GRID_BREAKPOINTS`, `LIST_GRID_CLASS` and `gridColumnsForWidth()` are now exported from
`classify-viewport.js` as the declared contract, with a guard test asserting each app's grid carries
the literal and reintroduces neither `md:` nor `lg:` `grid-cols`.

**Decision T-61.2a:** *CSS breakpoints must agree with `TABLET_MIN_EDGE`, not with Tailwind's
defaults.* The 3-column step is **700 px, not `md` (768)** — the iPad mini is 744 px wide in portrait
and a 768 breakpoint silently drops it to two columns.

**Decision T-61.2b:** *Grid class strings stay literal in the JSX.* Tailwind's JIT scans source text,
so an imported constant emits nothing. The constant is the contract; the test is the link.

## T-61.3 — Layout is driven by viewport width, not device class

Device-class buckets cannot answer "how many cards fit", and no device guess re-flows when a desktop
window is dragged. Column counts and carousel card widths are now pure CSS breakpoints. The classifier
survives only for things that genuinely are about the device (pointer type, safe-area handling).

Carousel ladders were also capped twice over — the per-card `basis` stopped at `md`, **and** the track
itself was capped (`max-w-6xl` = 1152 px on Transport). Both had to lift before an ultrawide showed
more cards; fixing either alone moved nothing.

## T-61.4 — Auto-expand: listen, don't guess

`useViewport` had been re-measuring after `requestFullscreen()` via three hard-coded timers
(250/700/1500 ms). Telegram announces the transition exactly, via `fullscreenChanged` and
`viewportChanged`, and nothing was subscribed — so a transition slower than 1500 ms left the layout on
its pre-expand classification for the whole session.

**Decision T-61.4a:** *Where a platform emits an event, subscribe to it; timers are a fallback, never
the mechanism.*

## T-61.5 — `BottomSheet.peekPx`: pixels, not fractions

The shared sheet's collapsed snap can now be a real pixel height instead of a viewport fraction.
Rationale: the operator's spec was "1.5 card height", and **1.5 cards is a fact about the card, not
about the screen** — a `vh` fraction is right on one device and wrong on every other. Callers measure
their own first rendered card and pass the number; the fraction remains the fallback.

## T-61.6 — Wrap in place, don't relocate

Cuisine's ~350-line `ResultPanel` became a drawer by being **wrapped** by a conditional shell
(`ResultSheetShell`) rather than moved. Every existing ref, scroll handler, pagination hook and
flash-highlight kept working untouched, and the non-drawer path stayed byte-for-byte identical. In a
5,000-line file this is the difference between a reviewable diff and a rewrite.

## T-61.7 — Stacking contexts and JSX comments (recurring, still unlinted)

Two long-running foot-guns, both now with a body count:

- **`z-index` on a full-bleed map wrapper** creates a stacking context that traps `fixed` descendants
  — three occurrences (v0.62.630, v0.62.639, v0.62.646).
- **A `{/* … */}` comment as the first token of a parenthesised JSX expression** is a syntax error —
  **six** occurrences (v0.62.640, v0.62.646, ×2 at v0.62.650, v0.62.651, v0.62.652).

Both remain **unenforced by lint**. `__tests__/tma-hook-deps-tdz.test.js` catches the second by
parsing every TMA `App.jsx`, which is a backstop rather than a rule.
