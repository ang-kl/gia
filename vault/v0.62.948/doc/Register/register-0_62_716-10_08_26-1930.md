## Note — what merging did and did not settle

The operator's concern — *"serious concern over the use of tokens… And firing model, per user and if
there are leaks"* — now has code in production answering every clause of it. That is worth stating
plainly, and so is its limit: **merging is not verification.**

Four separate Open items (O-175, O-176, O-179, O-182) say the same thing from four angles — not one
line of this work has been observed against real traffic. Before the merge that was a caveat on
unshipped code. After the merge it is a caveat on *running* code, which makes it more urgent rather
than less: the spend guard is live and has never been seen to fire; the rate limits are live and have
never refused a real request; the instrumentation is live and no one has read `/cost` since.

The cheapest possible next step is also the highest-value one: **run `/cost` against the deployed
build.** It costs nothing, needs no code, and either confirms Phase A's ~35 newly-instrumented call
sites are reporting or reveals in one message that they are not. Everything else in the tuning
backlog (O-180's cap values, O-172's Routes price) should wait behind that reading rather than be
guessed a second time.
