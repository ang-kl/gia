## Decisions (new this entry)

| # | Decision | Rationale |
| :--- | :--- | :--- |
| D-55 | **SG geocoding goes to OneMap, not Google Places.** The repo already had a working, cached, rate-limited Places autocomplete pair that could have been reused in an afternoon. Rejected on three counts: Places is **billable** (a new caller is a G4 spend decision, default no) where OneMap's `common/elastic/search` is free and keyless; Places has **no road-only type filter** where OneMap returns `ROAD_NAME`/`BLK_NO`/`POSTAL` as first-class fields; and OneMap is **already the project's SG-authoritative source** (`scripts/fetch-hawker-coords.js`, the v0.62.519 MRT coord curation) and **already legally cleared** in `doc/Legal` with the "Source: OneMap / SLA" attribution. The feature is SG-only by construction, so OneMap's SG-only coverage costs nothing. | v0.62.690 |
| D-56 | **The address list de-duplicates by NAME, not by coordinate.** Coordinate dedup is the obvious choice and is insufficient: a live "Jalan Kayu" query returns six rows all titled "Jalan Kayu Estate" at six different coordinates. The accepted cost is that two genuinely distinct same-named places collapse ("Bishan Loft" at blocks 31 and 33, ~60 m apart). Correct for an **inspection** overlay answering "roughly here"; would be wrong for a booking flow. | v0.62.690 |
| D-57 | **ERP gantries are filtered out of address results.** They are returned as ordinary rows and are toll points, not destinations — three of the first six live "Orchard Road" results were gantries. | v0.62.690 |
| D-58 | **The new endpoint is unauthenticated, on a neutral `/api/geo/` prefix.** It matches `/api/transport/stations` and `/api/hawker/centres-by-region`, which the same field already calls unauthenticated: public catalogue data, no per-user payload, no billable upstream. `/api/cuisine/*` would have bought free auth but misstated ownership — the consumer is a shared component used by two other TMAs. | v0.62.690 |

## Amendment

**D-61.63 — "the sandbox cannot reach OneMap"** (`register-0_61_76-21_05_26-0944.md:82`) is **narrowed,
not overturned**. It is accurate for `public/nearbysvc/getNearestBusStops`, which requires
`ONEMAP_API_KEY`. It does not generalise: `common/elastic/search` is keyless and was verified
reachable from this sandbox on 01-08 '26. The full quoted prior text and rationale are in
`journal-0_62_690-01_08_26-1500.md` under Amendments, per AU-7.

## Note

The two defects that mattered in this arc were both found by running **live** payloads through the
parser, and neither would have failed a build, a lint or a test: six identical-looking "Jalan Kayu
Estate" rows, and three toll gantries in the top six for "Orchard Road". The unit tests written
*before* the fixtures were captured all passed against the broken behaviour, because they tested what
the parser was specified to do rather than what the upstream actually returns. Every fixture in
`__tests__/onemap-search.test.js` is now trimmed from a real response for exactly that reason.

Worth pairing with the D-61.63 amendment. A previous session recorded a true fact about one OneMap
endpoint; read a year later as a fact about OneMap, it would have pushed this arc toward a paid
geocoder. The lesson is not that the note was wrong — it was right — but that a constraint recorded
without its scope tends to widen on re-reading.
