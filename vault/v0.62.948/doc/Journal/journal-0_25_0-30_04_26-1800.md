## New

### [HDR] #40 | 18:00:00 SGT 30-04-26 | v0.25.0 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead question "Major feature is: interact with other use, can this be done?" → Claude proposed two levels in plan-mode. Level 1 (share-a-pick) accepted in the "complete 1 to 4" rollout. Level 2 (live solo-dining match) deferred pending safety/abuse policy work.
- **[DELTA]**
  - **NEW** `share.js` — Redis-backed share-token store.
    - `saveShare(redis, payload)` → 10-char base64url token, 7-day TTL, key `share:<token>`.
    - `loadShare(redis, token)` → payload or null. Token is reusable within the TTL (multiple buddies can claim the same link).
  - **`index.js`** —
    - + `botUsername` cached at boot via `bot.getMe()`. Falls back to `process.env.BOT_USERNAME || 'gia_bot'` if API offline.
    - + `cacheBotUsername()` called in the boot IIFE before `registerCommandsMenu`.
    - + `trimPickForShare(p)` and `trimSurpriseForShare(v)` — strip transient fields before Redis save (placeId, name, area, lat, lng, rating, openNow, primaryType, url, directionsUri, vibe, signatureDish, googleSummary for picks; dishes, whyOrdered, bookingRequired added for surprises).
    - + `deliverPicks` per-pick inline keyboard now appends `{ text: '👋 Send to buddy', callback_data: 'share:<token>' }` next to 🚗 Directions. Token generated synchronously via `saveShare` before button render.
    - + `deliverSurprise` likewise appends 👋 Send to buddy alongside 🚗 / 🔍.
    - + `callback_query` handler for `share:<token>` — replies in-chat with a Markdown message containing the deep link `https://t.me/<botUsername>?start=share_<token>` (in inline-code block so users can long-press → copy). 7-day expiry surfaced in the message.
    - + `/start` handler now matches `\S+` instead of `\w+` to capture share tokens with trailing `_`/`-` chars from base64url. If `param` starts with `share_`, the token is loaded → existing `deliverPicks` (for `kind: 'pick'`) or `deliverSurprise` (for `kind: 'surprise'`) renders the buddy's view.
- **[VERIFICATION (sandbox)]**
  ```
  node --check on index.js, share.js → OK
  node -e "require('./share')"      → exports saveShare, loadShare ✓
  ```
  Live Redis/Telegram round-trip not exercised in sandbox.
- **[STATUS]** PROD — auto-deploys with the next Railway build.
- **[TEST]**
  1. Run `/eat`. Each pick now shows two buttons: 🚗 Directions, 👋 Send to buddy.
  2. Tap **👋 Send to buddy** → bot replies with a Markdown message containing `https://t.me/<bot>?start=share_<TOKEN>` in code-block form. Long-press → copy.
  3. Forward that link to a friend via WhatsApp / iMessage / Telegram chat.
  4. Friend (who has *not* /start'd the bot) taps the link → Telegram opens the bot, calls `/start share_<token>` → bot replies "👋 A friend shared a sanctuary pick with you via Gia:" then renders the same Sanctuary read.
  5. Run `/surprise` → 👋 Send to buddy button appears alongside 🚗 / 🔍. Same flow.
  6. After 7 days, the token expires; tapping a stale link shows "Sorry, that share link has expired or never existed."
- **[KNOWN GAPS]**
  - Token reuse: any buddy who taps the link can claim it (potentially many times) within the TTL. Acceptable for Phase 1 (low abuse surface; payload only contains a venue, not user PII). Phase-2 hardening would add one-shot tokens or origin-restricted claims.
  - The originating user's name/handle is NOT included in the buddy's view. Adding that surface requires an explicit consent toggle and is deferred.
  - `/start share_<token>` reuses `deliverPicks` which itself recursively adds 👋 share buttons to the buddy's view. This is intentional — the buddy can re-share. Recursion is bounded by token TTL (each new share creates its own 7-day token).
  - Bot username detection: if `bot.getMe()` fails *and* `BOT_USERNAME` env var is unset, the link defaults to `t.me/gia_bot?start=…`. Production has it set; surfacing this as a clearer warn-level log in Phase 2.
