### [HDR-2] The embedded map: not a code bug, and not the key being invalid

- **[INTENT]** Operator, twice: *"the embedded map cannot be loaded. why"* /
  *"what happen, the map isn't loaded"*, with a screenshot reading *"Sorry!
  Something went wrong. This page didn't load Google Maps correctly."*

- **[FALSE STARTS, RECORDED]** Two hypotheses were stated before being measured,
  and both were wrong. (1) *Maps JavaScript API not enabled* — the bootstrap
  loader returns 200 and a valid script for this key, so the API resolves. (2)
  *HTTP-referrer restriction blocking `soleat.net`* — ruled out by the opposite
  evidence: a **referrer-restricted key is rejected outright for server-side web
  service calls**, and Geocoding succeeds from this sandbox with no `Referer`
  header at all. A browser reproduction via the pre-installed Chromium was
  attempted and abandoned — it cannot reach the sandbox egress proxy
  (`ERR_CONNECTION_RESET` on every host, `curl` unaffected).

- **[THE MEASUREMENT]** Three probes against the live key from `/maps-key`:

  | API | Result |
  |---|---|
  | Geocoding | ✅ valid Singapore results |
  | Places API (New) `searchText` | ✅ returns Lau Pa Sat |
  | Maps **Static** API | ❌ **403** — *"This API key is not authorized to use this service or API. Please check the API restrictions settings of your API key in the Google Cloud Console"* |

  That 403 is the **API-restrictions** message, not the *API-not-enabled*
  message — a distinction that names the cause exactly. The rotated
  `GOOGLE_MAPS_API_KEY` carries an allow-list containing the server-side APIs the
  bot calls (Geocoding, Places, Routes — the latter corroborated by the 30 billed
  requests in the operator's `/cost` reading) and **excluding** the browser-side
  Maps JavaScript API. The overlay the operator sees is `ApiTargetBlockedMapError`.

- **[DELTA]** **None.** No code changed for this. `web/_shared/lib/gmaps-loader.js`
  and `/maps-key` are both behaving correctly; the loader fetches a key that is
  valid but not permitted for the API it is being used with. The fix is entirely
  in GCP Console → Credentials → the key → API restrictions → add **Maps
  JavaScript API**. Recording a diagnosis with an empty delta on purpose: the
  next session should not go looking for a code cause.

- **[WHY IT LOOKED LIKE A REGRESSION]** It appeared immediately after the
  operator rotated `GOOGLE_MAPS_API_KEY`, alongside a genuine v0.62.721
  deployment. Restrictions on a replacement key are re-entered by hand, from
  memory, under time pressure — omitting one entry from a list of six is the
  normal outcome, not an unusual one.

- **[STATUS]** DIAGNOSED, awaiting an operator action in GCP Console. Nothing to

- **[KNOWN GAPS]** Which APIs are on the allow-list has not been read directly —

  unrestricted-by-referrer key that fails only in the browser. If adding Maps

- **[DEFECT FOUND IN THE LOG — `setMyDescription` has never once succeeded]**
  ```
  [setMyDescription] failed (non-fatal): ETELEGRAM: 400 Bad Request: BOT_DESC_INVALID
  ```
  Telegram caps `setMyDescription` at 512 characters. The v0.60.37 copy measures
  **520–524** — computed across every count value the two interpolations can
  produce (`'50+'/'100'` fallback, live figures, and a deliberately large pair),
  and over the cap in all of them. So the call has been rejected on **every boot
  since v0.60.37 (2026-05-08)**, and the bot's *"What can this bot do?"* panel
  has never displayed this text. The failure is caught non-fatally and logged,
  which is why it survived three months of deploys: it is one warning line in a
  healthy-looking boot sequence, and nothing downstream misbehaves.

    where the string is built. Hand-trimming to 511 was rejected as a fix: two

    buys a few characters and then breaks again, silently, identically.
    Sacrifice order is explicit — trailing hint paragraph, then whole command
