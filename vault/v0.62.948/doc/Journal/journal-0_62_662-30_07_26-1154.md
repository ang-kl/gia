## New

### [HDR] v0.62.662 — closing every en/fr-only gap across the three map TMAs

- **[INTENT]** Operator: *"let's catch up on the linguistic update - since we change quite a bit. Make sure
  all the language UI are updated."* Asked via `AskUserQuestion` whether this meant just the recent arc's new
  strings or a full repo-wide backfill; operator chose the full backfill.

- **[THE REAL SCOPE, DISCOVERED]** A first scan (regex over each i18n.js's base `STRINGS` object vs. its six
  non-en/fr overlay blocks — `ID_STRINGS`/`RU_STRINGS`/`DE_STRINGS`/`ZH_STRINGS`/`JA_STRINGS`/`ES_STRINGS`)
  found gaps far larger than "what we changed today": Transport was missing 43 keys per locale, Hawker 4, and
  Cuisine as many as 216 (Russian/German) — almost all pre-existing, some evidently months old, unrelated to
  this arc's work. This is what the operator's chosen answer committed to fixing.

- **[A SELF-CAUGHT BUG IN THE AUDIT ITSELF]** The first extraction script assumed single-quoted keys
  (`'key':`) everywhere. Cuisine's `i18n.js` mixes quoting styles — some blocks use `'key':`, others
  `"key":` — so the script silently missed every double-quoted entry, inflating Cuisine's Russian/German gap
  to 216 when the TRUE gap (confirmed independently by the Russian and German translation agents reading the
  live file themselves, and by a rewritten quote-agnostic extractor) was 10. Rewrote the extractor to walk
  brace-depth and skip over `'`/`"`/`` ` `` -quoted strings properly, producing an authoritative
  `true-missing.json` used as the single source of truth for what actually got inserted — agent output that
  didn't match a real gap was discarded rather than merged, so no duplicate or redundant keys landed.

- **[HOW THE TRANSLATION WAS DONE]** Six parallel agents, one per target language (id/ru/de/zh/ja/es), each
  reading 15-20+ already-shipped entries in that language first (to match established vocabulary/register)
  before translating its worklist. Placeholder tokens (`{n}`, `{when}`, `{v}`, …) were verified byte-for-byte
  present in every translation before merge — zero mismatches across 506 i18n.js insertions plus 36 in the
  shared component. One entry (`region.current.error`, Chinese) came back `null` because it inherited the
  pre-fix extraction bug's bad snapshot; patched by hand during merge, matching the pattern the other five
  language agents used when they hit the same stale-snapshot artifact (cross-referencing the live source
  file's real English text rather than translating a `null`).

- **[A SECOND MERGE BUG, CAUGHT BY THE BUILD]** The first merge pass inserted new lines assuming every
  existing block ends its last entry with a trailing comma. Cuisine's file doesn't consistently — the very
  first insertion attempt produced `"card.sent": "..."` immediately followed by a new entry with no comma
  between them, a straight syntax error caught instantly by `vite build`. Reverted via `git checkout` and
  fixed the merge script to detect a missing trailing comma at each insertion point and add one, rather than
  assuming the file's own style is consistent.

- **[A PRE-EXISTING BUG FOUND, NOT FIXED]** While verifying no NEW duplicate keys were introduced, found that
  `cat.sweetsFusion` already existed as a duplicate key inside Cuisine's `RU_STRINGS` block (two different
  Russian translations, "Десерты и фьюжн" vs "Сладости и фьюжн," of which JS object-literal semantics mean
  only the second silently wins) — pre-dating this session entirely (confirmed via `git diff`: neither line
  is in this entry's added content). Left untouched — fixing a *value* (not adding a missing key) is a
  different, more subjective edit than this entry's mandate, and picking which of two already-shipped
  translations is "more correct" isn't something to guess at. Logged as Register O-70.

- **[RESULT]** Re-running the fixed extractor against the final files confirms **zero remaining gaps**:
