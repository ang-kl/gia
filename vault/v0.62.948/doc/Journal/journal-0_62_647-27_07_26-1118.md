- **[INTENT]** Operator, as an acting brief: *"Act as a Senior Frontend Engineer specialising in Telegram
  Mini Apps (TMA). Your task is to first assess, and then implement, a native-feeling, swipe-to-close bottom
  sheet (drawer) with a theme-adaptive drag handle."* The brief named four assessment axes — **device widths**
  (*"Avoid stretching to 100% width on large screens; utilise a centered max-width"*), **orientation &
  viewport** (*"Consider dynamic viewport units like `dvh` or the Visual Viewport API"*), **input methods**
  (*"touch devices … versus pointer devices (Telegram Desktop)"*) and **theming & overlay** (*"guarantee
  contrast against complex backgrounds - such as interactive map handlers - in both Light and Dark modes using
  Telegram's native CSS variables"*) — and eight implementation rules covering markup, theming,
  responsiveness, physics and execution.

- **[WHY A NEW COMPONENT, NOT AN EDIT]** `web/_shared/components/BottomSheet.jsx` (v0.62.608) is a React
  **snap-point resizer**, not a dismissible sheet. Grepped before writing a line: it has **no**
  swipe-to-close, **no** scrim, **no** velocity term (nearest snap is chosen purely by distance), **no**
  `max-width`, **no** scroll lock, **no** `dvh` and **no** `visualViewport` — its only viewport source is
  `window.innerHeight` at line 24 — and its handle hit area is ≈**26 px** (`pt-3 pb-2` around an `h-1.5` bar)
  against the brief's **44 px** floor. It is also imported live by `hawker/src/App.jsx:8` and
  `transport/src/App.jsx:18`. Rewriting it in place would have swapped the drawer under two shipping TMAs in
  the same commit that introduced the new physics. The new component therefore lands **beside** it and
  **nothing is wired** — see `[STATUS]`.

- **[ASSESSMENT — the four axes, and what each one forced]**
  1. **Device widths.** `margin-inline: auto` + `max-width: 640px` (→ `560px` at ≥700 px and in landscape).
     On a phone the cap is never reached so the sheet is edge-to-edge; on iPad / Telegram Desktop it becomes a
     centred card with the map visible either side. Measured at 1024 px: width **560**, centred on **512**.
  2. **Orientation & viewport.** `dvh`, not `vh` — a `vh`-sized sheet leaves a dead strip when Telegram's
     chrome collapses. Landscape drops the cap from **88 dvh → 78 dvh** so the sheet cannot swallow a short
     viewport (the brief's *"prevent the UI from consuming the entire screen"*). Software keyboards are the
     Visual Viewport API's job: `window.innerHeight - vv.height - vv.offsetTop` **is** the keyboard inset, so
     it is written to `--gia-kb-inset` (the sheet's `bottom`) and `vv.height` to `--gia-vvh` (a second
     `max-height` clamp). `@supports not (height: 100dvh)` degrades to `vh` for legacy webviews.
  3. **Input methods.** The brief specifies `touchstart`/`touchmove`/`touchend`, so touch is the primary path
     — but Telegram Desktop has no touch, so a **separate** `mousedown`/`mousemove`/`mouseup` family drives
     the same `beginDrag`/`moveDrag`/`endDrag` core, with `drag.kind` locking the winner so a hybrid device
     that emits **both** cannot start two drags. Pointer Events would have unified them but would have
     violated the brief. Mouse listeners attach to `document` so a fast drag that leaves the handle still
     tracks. The pointer-free path is real too: the handle is a `<button>` (Enter/Space/↓ close), Escape
     closes, focus is trapped and restored.
  4. **Theming & overlay.** The surface is **opaque**. A translucent sheet over Google Maps has no
     guaranteeable contrast ratio — the tile underneath may be a dark-mode basemap, a satellite image or a
     white sea. Elevation is signalled per scheme instead: **light → drop shadow**, **dark → hairline top
     border** (a shadow is invisible on a dark map). Colours resolve through `--tg-theme-bg-color`,
     `--tg-theme-text-color`, `--tg-theme-hint-color` and `--tg-theme-section-separator-color`, each falling
     back first to this repo's own mapped `--tg-bg`/`--tg-text`/`--tg-hint` (set in each app's `tg.js`) and
     only then to a literal — correct in a real client, in a Gia TMA, and in a bare browser. The scheme comes
     from `Telegram.WebApp.colorScheme`, which is **authoritative**: a user can run a dark Telegram theme on a
     light OS, and `prefers-color-scheme` would then be wrong (it is kept only as the no-JS fallback).

- **[DELTA]** (5 new files, **0 changed** files outside `package.json`)
  1. `web/_shared/components/bottom-sheet/bottom-sheet.css` — tokens, scrim, sheet, 44 px handle zone,
     scheme-specific elevation, the responsive caps above. Resting positions live here, keyed off
     `data-open`; the drag offset is the **only** thing JS writes inline, so "let go" and "close" are the same
     one-line operation with no third source of truth.
  2. `web/_shared/components/bottom-sheet/bottom-sheet.html` — canonical markup: `.gia-sheet-root` →
     scrim + `role="dialog" aria-modal` sheet → `<button>` handle → title → scrolling content. Carries an
     in-file warning against nesting the root under any positioned ancestor with an explicit `z-index` —
     the stacking-context trap that has shipped **three** times in this repo (v0.62.630, v0.62.639,
     v0.62.646).
  3. `web/_shared/components/bottom-sheet/bottom-sheet.js` — pure, DOM-free physics
     (`resolveGesture` / `sampleVelocity` / `rubberBand`) plus the `createBottomSheet` controller. Physics
     detail worth recording: velocity is measured over a **trailing 120 ms window**, not the whole gesture,
     so a slow drag that ends in a flick reads as a flick; close fires on velocity **OR** distance, because
     velocity-only springs back on a deliberate slow drag and distance-only ignores a fast flick from the
     top; an upward flick vetoes a close however far down the sheet already is; upward over-drag is
     rubber-banded, asymptotic to 48 px. Execution detail: `data-dragging` removes the transition for the
     whole drag (1:1 finger mapping) and its removal on release restores
     `cubic-bezier(0.32, 0.72, 0, 1)` for the settle. Scroll lock uses `position: fixed` on `<body>`, not
     `overflow: hidden`, because iOS WKWebView — the platform a Mini App actually runs on — ignores the
     latter; `touchmove` on the scrim is swallowed (`passive: false`) so the map cannot pan behind the sheet.
  4. `web/_shared/components/bottom-sheet/demo.html` — the standing harness: a CSS stand-in "map" (built with
     **no** `z-index`, per the warning above) and the two controls the smoke drives.
  5. `__tests__/bottom-sheet.test.js` — **17** tests pinning the physics in the Node-only suite. Importing the
     module at all also proves it is side-effect-free under Node (nothing touches `document` at import time).
