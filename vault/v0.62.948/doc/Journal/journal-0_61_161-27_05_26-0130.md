## New

### [HDR] #362 | 01:30 SGT 27-05-26 | v0.61.161 — Progressive nearby widening (server-side ladder filter) | 5 files | 1 PR | 1 build |

- **[INTENT]** Tighten the cuisine-search "spread" so the result
  list prioritises venues near the user-set anchor, only widening
  when the inner tiers don't surface enough top-rated options.
  Implemented as a **post-fetch ladder filter** — single Places
  call (current 20 km default), then walk the
  `[2, 6, 8, 12, 15, 20] km` ladder in memory. The smallest tier
  with ≥ 3 venues with rating > 4 wins; final fallback at the
  widest available tier returns whatever exists (caller's downstream
  dedup + 12-cap slice handles surfacing).
  Saves the 6× Places API cost a naive multi-call ladder would
  incur.

- **[DELTA]**
  - **`cuisine-nearby-widen.js`** (NEW, ~85 lines). Pure module:
    - `LADDER_M = [2_000, 6_000, 8_000, 12_000, 15_000, 20_000]`.
    - `MIN_TOP_RATED = 3`.
    - `TOP_RATING_GT = 4.0` (strict — Places returns numeric
      ratings; equality doesn't count).
    - `countTopRated(venues, ratingGt)` — defensive
      finite-number rating filter.
    - `widenAndPick({ venues, ladder, cap, minTopRated, ratingGt })`
      → `{ venues, radiusM, satisfied, tier }`. Returns the
      smallest-radius subset that surfaces ≥ `minTopRated` venues
      with rating > `ratingGt`. Respects `cap` (Putrajaya 15 km,
      JB 30 km) — ladder tiers beyond cap are dropped. Final
      fallback at the widest in-cap tier returns ALL in-cap
      venues; `satisfied: false`.
  - **`__tests__/cuisine-nearby-widen.test.js`** (NEW, 22 tests
    across 5 `describe` groups). Coverage: constants; happy paths

    fallback; the anchor-cap drop (Putrajaya 15 km excludes the
    18 km venue); tight cap (1 km) drops the entire ladder;
    custom thresholds (`ratingGt: 4.5`, `minTopRated: 5`, custom
    `ladder`); defensive paths (non-array, missing `distanceM`).
  - **`index.js`** — single insertion in `/api/cuisine/search`

- **[KNOWN GAPS]**
  - **First-tier API cost unchanged.** The Places call still
    fetches the wide 20 km pool; the ladder runs on the in-memory
    result. So we don't pay the 6× ladder cost a naive multi-call
    impl would, but we DO still pay the wide fetch. Future:
    `pipeline.discover` could be told to fetch a tighter initial
    radius (e.g. 6 km) when the anchor is a precinct pick with a
    `radiusCapM` set, falling back to the wider fetch only when
    the tighter one returns too few.
  - **Top-rated threshold > 4 is strict.** A venue at 4.0
    exactly doesn't count. This matches the operator's spec
    ("rating > 4"). If a sparse anchor has a cluster of 4.0
    venues, the ladder would widen unnecessarily. Easy to relax
    to `>= 4` in `cuisine-nearby-widen.js`.
  - **Skipped for shuffle / Dessert paths.** Reason: those
    paths intentionally don't sort by distance (the lightShuffle
    tier rotation is the whole point). If the operator wants
    nearby-widening to apply there too, the lightShuffle order
    needs to be re-thought (probably: pick the shuffle inside
    the tightest satisfying tier instead of across the whole
    20 km pool).
  - **"Nearby" textQuery word** — the operator asked whether
    adding "nearby" to the Places search string would help. My
    in-chat answer: probably not — Places treats it as free
    text, not a structural keyword; the `locationRestriction.
    circle.radius` is what filters by distance. The ladder
    accomplishes the same goal cleanly. No code change for
    this in the PR.
