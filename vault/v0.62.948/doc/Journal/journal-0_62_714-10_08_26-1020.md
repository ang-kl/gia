# Journal — v0.62.714 (Cost-audit Phase B: fix the sanctuary redundant Places-Details fetch)

_(№ 1,053 — 10-08 '26 10:20 SGT)_

## New

### [HDR] v0.62.714 — sanctuary read reuses in-memory reviews instead of re-fetching from Places

- **[INTENT]** Second phase of the operator-approved 4-phase cost-audit remediation plan. This entry
  fixes the one CONFIRMED real "leak" identified during the original audit (verified by direct code
  inspection, not just an agent's claim — the cache-disable finding from the same audit turned out to
  be a deliberate v0.60.11 decision and was correctly excluded, but this one held up): `cuisine-enrich.js`'s
  SLOW phase deleted `v.reviews` from every venue in its finalise loop, then — several steps later in the
  same function — called `ctx.enrichSanctuaryRead(top, ctx.csLang)`, which (via `vibe-summary.js`'s
  `getOrCacheSummary` → `fetchReviewText`) issued a **fresh Google Places Details call requesting the
  exact same `reviews` field** that had just been discarded four lines earlier. Every cuisine search, for
  every venue needing a fresh (non-cached) sanctuary read, paid for a Places Details request purely to
  re-fetch data the base search response had already delivered.

- **[THE FIX — TWO PARTS, BOTH NEEDED]**
  1. **Reorder** (`cuisine-enrich.js`): `delete v.reviews` moved OUT of the finalise loop and deferred to
     a small standalone pass at the very end of `enrichSlow`, after travel-times, sanctuary, and footfall
     have all run. Reordering alone would have been enough to let sanctuary SEE the reviews, but not
     enough to stop it making its own second call — `getOrCacheSummary`'s signature had no way to accept
     already-fetched review data at all.
  2. **Reuse** (`vibe-summary.js` + `index.js`): `fetchReviewText` gained an optional `preFetchedReviews`
     parameter — when given a non-empty array, it formats and returns those reviews directly (same
     recency-filter + cap-8 + join logic as the live path, extracted into a shared
     `formatReviewsForSummary` helper so the two paths can never drift apart) and skips the network call
     entirely. `getOrCacheSummary` threads the parameter through; `index.js`'s `enrichSanctuaryRead` now
     passes `v.reviews` when calling it. Callers that don't carry `v.reviews` (Michelin, nation-iconic,
     cooking-method fan-outs — none of which fetch `places.reviews` on their base call) fall through to
     the unchanged live-fetch path, so this is additive, not a behaviour change for them.

- **[WHY BOTH PARTS WERE NECESSARY]** The reorder alone (part 1) would have fixed nothing by itself —
  `enrichSanctuaryRead`/`getOrCacheSummary`/`fetchReviewText` had no parameter to receive the
  already-in-scope reviews even if they existed at call time. The reuse alone (part 2) would have been
  dead code — by the time `enrichSanctuaryRead` ran (before this entry), `v.reviews` had already been
  deleted three phases earlier, so there would never be anything to pass. Both had to ship together.

- **[DELTA]** (3 source files + 2 test files)
  1. `cuisine-enrich.js` — `delete v.reviews` moved from inside the finalise loop to a new pass at the
     end of `enrichSlow`, after crowd/translate/dishes/finalise/travel/sanctuary/footfall have all run.
  2. `vibe-summary.js` — new `formatReviewsForSummary(reviews)` pure helper (extracted from the
     live-fetch path's own formatting logic, byte-identical behaviour); `fetchReviewText` gains an
     optional `preFetchedReviews` param with an early-return short-circuit; `getOrCacheSummary` gains
     the same param and forwards it; `formatReviewsForSummary` added to `module.exports` for testability.
  3. `index.js` — `enrichSanctuaryRead` now passes `v.reviews` as `getOrCacheSummary`'s 4th argument.
  4. `__tests__/cuisine-enrich.test.js` (extended) — 3 new tests pinning the reorder: sanctuary still
     sees `v.reviews` at call time and it's gone afterwards; a throwing `enrichSanctuaryRead` doesn't
     block the deferred delete; a reviews-less venue is untouched.
  5. `__tests__/vibe-summary-reviews.test.js` (NEW) — 8 tests: `formatReviewsForSummary`'s
     recency/cap/fallback/empty behaviour, and `fetchReviewText`'s `preFetchedReviews` short-circuit
     proven with **no `GOOGLE_MAPS_API_KEY` set** in every test — a non-empty result with the key absent
     is only possible if the in-memory path fired, since the live path returns `''` immediately without
     a key.
