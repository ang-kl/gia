# Journal — v0.62.690 (road & address search: the other half of the inspection overlay)

_(№ 1,030 — 01-08 '26 15:00 SGT)_

## New

### [HDR] v0.62.690 — road / address search via OneMap

- **[INTENT]** Operator: *"now do the road/address geocoding."* This closes **O-110**, opened one
  arc earlier when v0.62.689 shipped the station half of the operator's original request —
  *"when type in the road or train. you shuld place a temporary location…"* — and deliberately
  scoped the road half out (*"station-only for now"*).

- **[UPSTREAM — OneMap, and why not Google]** The project already had a working, authenticated,
  rate-limited, Redis-cached Google Places autocomplete pair (`/api/cuisine/place-autocomplete` +
  `/place-resolve`). Reusing it would have been the shortest path. It was not taken, for three
  reasons that all point the same way:
  1. **Cost.** Places Autocomplete is billable. Adding a new caller is a spend decision — gate G4,
     default no. OneMap's `common/elastic/search` is **free and needs no key**.
  2. **Fitness.** The ask is *roads*. Places Autocomplete has no road-only type filter; OneMap
     returns `ROAD_NAME`, `BLK_NO` and `POSTAL` as first-class fields.
  3. **Precedent.** This project already treats OneMap as SG-authoritative:
     `scripts/fetch-hawker-coords.js` calls this exact endpoint, `data/mrt-coords.json` was curated
     from OneMap building geocodes (v0.62.519), and `doc/Legal/legal-0_61_76-21_05_26-0944.md`
     already lists OneMap as an active source with the attribution string *"Source: OneMap / SLA"*.
     No new legal surface.
  The feature is Singapore-only by construction (hawker centres, MRT), so OneMap's SG-only coverage
  costs nothing here.

- **[CORRECTION TO A STANDING DOC NOTE]** `doc/Register/register-0_61_76-21_05_26-0944.md` records
  *"The sandbox cannot reach OneMap"* (D-61.63), and the v0.61.63 Journal repeats it as a G4 note.
  That is true of `public/nearbysvc/getNearestBusStops`, which requires `ONEMAP_API_KEY`. It is
  **not** true of `common/elastic/search`, which answers unauthenticated and was verified reachable
  from this sandbox while building this arc. Recorded as an amendment rather than a silent
  contradiction — the prior note was correct about the endpoint it was about.

- **[A TRAP IN THE PAYLOAD]** The keyless call returns a top-level
  `"error": "Authentication token missing. Please create an account and generate or renew your API
  Token."` **alongside a fully populated `results` array**. Any caller that branches on `error`
  throws away good data. Both the parser and the route key off `results` only, and the header of
  `onemap-search.js` says so in as many words so the next reader doesn't "fix" it.

- **[DELTA — `onemap-search.js` (NEW, root, CommonJS)]** Pure parsing, so it is unit-testable
  without a network. Sits at the repo root beside `michelin-sort.js` and `places-address-parser.js`,
  the existing home for server-side pure modules.
  - `normaliseOneMapResults(body, {limit})` → `[{name, sub, lat, lng, road, postal}]`.
  - `titleCase()` — OneMap SHOUTS everything. Keeps initialisms (`MRT`, `NUS`, `HDB`) upper and
    leaves digit-leading tokens (`20A`) alone.
  - `addressLabel()` — `"20 Bideford Road · S(229921)"`, built from parts rather than reusing
    OneMap's `ADDRESS`, which repeats the building name and appends `SINGAPORE <postal>` in caps.
  - `clean()` — OneMap writes the literal string `"NIL"` for an absent field.
  - SG bbox filter, reusing the bounds `scripts/fetch-hawker-coords.js` already uses.

- **[TWO LIST-QUALITY BUGS THE FIXTURES CAUGHT]** Both were found by running **live** payloads
  through the parser, not by reading the API docs. Neither would have failed a build or a test:
  - **Dedup by coordinate was not enough.** The first implementation keyed on `name|lat|lng`, which
    reads as obviously correct. A live `Jalan Kayu` query returned **six rows all titled "Jalan Kayu
    Estate"**, each a different house at different coordinates — nothing collapsed, and the user
    would have seen one name six times. Dedup is now **by name**. The cost is real and accepted: the
    live `Bishan` payload has "Bishan Loft" at blocks 31 and 33, ~60 m apart, and they now collapse
    to one row. For an *inspection* overlay whose job is "show me roughly here", that is the right
    trade; for a booking flow it would not be.
  - **ERP gantries are ordinary results.** On `Orchard Road`, **three of the first six rows** were
    toll gantries ("Orchard Road After Ymca - ERP(47)"). Filtered.
  Measured effect on the live fixtures — `Orchard Road` 6 rows → 5 useful ones (gantries gone, a
  post office, a church and a hotel surfaced instead); `Jalan Kayu` 6 near-identical rows → 2
  distinct ones; `Bishan` now surfaces **Bishan MRT Station** inside the top 6.

- **[DELTA — `index.js`, `GET /api/geo/road-search`]** New neutral `/api/geo/` prefix: the consumer
  is the *shared* field used by two TMAs, so mounting under `/api/cuisine/*` (which is where the
  auth chokepoint lives) would have been a lie about ownership. Redis `onemap:search:v1:{q}`, **24 h
  TTL** — road geometry does not move, and repeat typing of the same prefix never reaches the wire.
  Minimum 3 characters, 6-second upstream timeout. On any failure it returns
  `{results: [], error: 'upstream_unavailable'}` rather than a 5xx, because the station half of the
  field must keep working when OneMap does not.

- **[AUTH — a deliberate non-gate]** Unauthenticated, matching `/api/transport/stations` and
  `/api/hawker/centres-by-region`, which **this same field already calls unauthenticated**. It is a
  public catalogue lookup with no per-user data and no billable upstream. Since there is no chatId
  to key on, `makeRateLimiter` gained an optional **`keyFn`** (defaulting to the existing
  `req.tg?.user?.id`, so all five existing call sites are byte-identical in behaviour) and this
  route passes `keyFn: (req) => req.ip`, cap 300 / 15 min. The limiter here protects **OneMap's
  service**, not a budget — there is no spend to protect.

- **[DELTA — `StationLocationField.jsx`]** The road results are a **second section in the same
  field**, not a second field: one box answers "where do I want to look?" however the user phrases
  it. The two halves are deliberately asymmetric:
  - Stations — local `useMemo` substring filter over the already-loaded array. Instant, offline.
  - Addresses — debounced 250 ms against the new route, with the `addrQuery` **stale-response
    guard** ported from Cuisine's `LocationField` (added there after Codex review #216): without it
    a slow response for `"orc"` lands after a fast one for `"orchard"` and repaints stale rows under
    newer text.
  **Stations are listed first and never wait on the network.** If OneMap is slow or down, typing
  "Bishan" still resolves the station immediately and the address section simply does not appear.
  That ordering *is* the failure plan. Section headers only render when both kinds are present, so a
  station-only result set looks exactly as it did before. Copy widened from stations-only to
  "station or road" across **all 8 locales** (3 strings changed, 3 added = 48 translations).

- **[DELTA — hosts]** Both selections call the SAME `onSelectStation`, carrying `kind: 'station' |
  'address'`. **Hawker needed no change at all** — its `inspectStation` is coordinate-based.
  **Transport did**: an address has no codes and no lines, so letting it reach `setFocusedStation`
  would render a StationCard detail panel for something that is not a station. It now returns early
  on `kind === 'address'` with the map switch + the inspection overlay and nothing else.

- **[VERIFICATION (sandbox)]** `node --check` on all three changed `.js`; hawker + transport builds
  green; full `npm test -- --run` **156 files / 3901 tests** green (17 new). Compiled CSS confirmed
  to emit `text-[10px]`, `uppercase`, `tracking-wide`, `text-tg-hint/80`, `border-t` in both
  bundles; `road-search` present in both JS bundles.
  **Live upstream exercised** for `Orchard Road` / `Bishan` / `Jalan Kayu` / `Toa Payoh Lor 6` /
  a deliberate miss, and every fixture in the test file is trimmed from those real responses.

- **[TEST]** `__tests__/onemap-search.test.js` — 17 tests: the advisory-`error` trap, string→number
  coercion, relevance order preserved, bbox rejection, non-finite coords, per-unit dedup, the
  **Jalan Kayu** all-different-coordinates regression, ERP filtering, limit/default, `ROAD_NAME`
  fallback, junk input, label assembly with and without `NIL`, and `titleCase` initialism handling.

- **[STATUS]** DRAFT — branch `claude/handover-july-11-49uzvf`. Deploys to prod on merge via
  Railway's main-branch build.

- **[KNOWN GAPS]**
  - **The route itself was never executed end-to-end in-sandbox.** The agent proxy returns **405**
    to this repo's axios (1.15.2; `/root/.ccr/README.md` documents that axios < 1.16.1 sends
    non-CONNECT requests the proxy rejects). `curl` reaches OneMap fine, so the parser is validated
    against real payloads and the route body is validated by inspection — but the axios call, the
    Redis cache path and the rate limiter are **unexercised**. This is a sandbox artefact, not a
    production one; Railway has no such proxy. The dependency was **not** bumped — that is an
    unrelated change to a shared HTTP client used everywhere in this server.
  - Device confirmation outstanding (O-93, O-111): whether the two-section list is legible at
    `text-[10px]` on a phone, and whether 250 ms feels right on mobile data.
  - `titleCase` leaves brand initialisms it does not know about looking odd — the live fixture has
    "Spc Toa Payoh Lorong 6" (SPC, the fuel retailer). Enumerating every brand is unbounded; the
    `KEEP_UPPER` set covers structural initialisms only.
  - Dedup-by-name collapses genuinely distinct same-named places (see above). Reversible in one line
    if the operator wants unit-level precision.

- **[TIME ANCHOR]** Sovereign fetch, `api.data.gov.sg/v1/environment/air-temperature`:

### [AMD] D-61.63 "the sandbox cannot reach OneMap" — scoped to the keyed endpoint (AU-7)

**Prior content, verbatim** (`doc/Register/register-0_61_76-21_05_26-0944.md:82`):

> *"Nearest-bus-stop triangulation is an offline Haversine join from committed LTA open data
> (`stations.json` + `LTABusStop.geojson`); OneMap `getNearestBusStops` is a name-only pass,
> operator-run with their own key. **The sandbox cannot reach OneMap**; codes/coords come from open
> data, names from the keyed API — non-invention preserved."*

**Amendment.** The claim holds for `public/nearbysvc/getNearestBusStops`, which requires
`ONEMAP_API_KEY` and which the sandbox has no key for. It does **not** generalise to OneMap as a
host: `common/elastic/search` is keyless, and was verified reachable from this sandbox on
01-08 '26 while building v0.62.690 (fixtures captured for `Orchard Road`, `Bishan`, `Jalan Kayu`,
`Toa Payoh Lor 6`). The original wording was about the bus-stop name pass and is left standing for
that; this amendment narrows its scope rather than overturning it.

**Rationale.** Left unamended, a future session reading D-61.63 would conclude OneMap is
unreachable and reach for a paid geocoder instead — the exact decision this arc avoided.
