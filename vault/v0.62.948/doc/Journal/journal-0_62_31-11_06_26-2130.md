- **[A — HIGH: the v0.62.15 deadline burned the seen-set (my own #978 bug)]** When the 20 s D706
  deadline fired, the user got an **empty** degraded-200 — but the body kept running and
  `appendSeenSet` + `cuisineSession.recordPage` marked the **never-shown venues as seen** → the next 🔍
  tap silently skipped them (a self-inflicted "first-tap zero"). Fix:
  - `_deadlineFired` flag — set **after** the `res.headersSent` bail, so the **streaming** path (where
    headers go out WITH the venues — the user did receive them) keeps its writes; only the
    non-stream degraded case skips the seen-set + session-page writes.
  - `_gatheredRef` parks the fast-enriched page (the exact snapshot the Stage-2 stream flushes) — the
    D706 response now returns the **gathered venues** (`degraded:true`) instead of always-`[]`.
  - The 30 s payload cache write stays ON deliberately: seen-set unburned + cached payload = an
    immediate re-tap serves those venues fast (the correct recovery).

- **[B — MED: server-side label guard (D787)]** The v0.62.30 latch was **client-only**; any label-less
  `set-location` write could still clobber a labelled pick. `location-cache.setUserLocation` now
  refuses an **`opts.ambient`** write when the cached (chatId-level) entry carries a fresh label —
  returns `{ kept: true, label }`; the route replies `ok:true, kept:true` and skips notify/recents.
  `ambient: true` is wired end-to-end (`api.js` → `/api/cuisine/set-location` → **only** the 20 s
  follow-device sync sends it). Deliberate flows (chat share-pin, 📍 use-current, `/location`,
  autocomplete picks) pass no flag → full overwrite semantics, fully back-compat. *Known edge: the
  guard reads the chat-level key; per-device labelled picks write both keys, so covered in practice.*

  operator's "subtle", now actually ≥3:1 where it matters); the CSS comment states the real numbers.
