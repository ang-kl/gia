## 1. What the product is

**Soleat** ("Gia4lunch") is a Singapore-first dining concierge inside Telegram (`@soleat_bot`, served from **soleat.net**). It blends live public data (Google Places, LTA DataMall, NEA, data.gov.sg) with LLMs to find a good place to eat nearby, plus transport, carpark, weather and hawker utilities. It covers Singapore, Johor Bahru (Malaysia) and, increasingly, other cities and countries.

| Surface | Where in the code | What it does |
| :--- | :--- | :--- |
| Telegram bot (chat, slash commands, free text) | `index.js` (≈20,450 lines), `venue-templates.js`, `i18n.js` | Commands such as `/cuisine`, `/hawker`, `/recognised`, `/weather`, `/transport`, `/carpark`, `/location`, `/buddy`; free-text food questions; owner-only admin commands (`/log`, `/ftlog`, `/ver`, `/oversight`, `/external_update`) |
| **Cuisine** Mini App (the main surface) | `web/cuisine/` (React + Vite), served at `/app/cuisine/` from `public/cuisine/` | Map + result cards, cuisine & filter picker, place pin, 💬 free-text bar with the **Quick / AI lever** |
| Hawker, Menu, Transport, Oversight, About, Clipboard Mini Apps | `web/hawker`, `web/menu`, `web/transport`, `web/oversight`, `web/about`, `web/clipboard`; shared code in `web/_shared` | Hawker centres, settings/menu, transit, owner dashboard, about page, saved cards |
| Express server | `index.js` | `/api/cuisine/search` (normal search), `/api/cuisine/nl-query` (AI search), `/healthz`, `/readyz`, webhook, Mini App static hosting |

**Languages:** nine locales everywhere: `en, fr, id, ru, de, zh, ja, es, ko`. Every new user-visible string needs all nine, and there are count-pinned tests for this (section 5).

## 3. How a session must work (the process, condensed)

1. **Start of session.** Fetch the time (`date -u`, convert to SGT) and measure the serial (`node scripts/count-interactions.js --serial`).
   - **Remote containers hold a partial transcript.** The running serial = the last ledger row in `CLAUDE.md` + replies since. The latest rows say 3,686 → about 3,762 on 26-10. Never adopt a smaller script reading as "the" serial.
   - Prefix every substantive reply with `№ N · DD-MM'YY HH:MM SGT`.
2. **A fresh build request** gets the §14 gate: TL;DR, plus Intent, Interpretation (UNDERSTANDING, GAPS), Assumptions (with confidence) and Invariants (with checks). Ask (AskUserQuestion) if anything is below 95%.
3. **flow-kit.**
   - Write a spec to `doc/Feature/YYYY-MM-DD-<name>.spec.md` from `.claude/flow/spec.template.md`, with every assumption `confirmed` or `corrected`.
   - The operator types exactly `APPROVE <spec path>`. Only the exact line is recorded; a paraphrase or a prefix such as "§3,580·E - APPROVE …" is **not**.
   - Small, behaviour-neutral fixes can use `APPROVE QUICK <intent>`, valid until the next commit.
   - Tests come first; then implement inside the spec's `scope:` only. Touching a file outside scope, or editing an existing test, means raising a **FLOW ALERT** (F3/F7), adding an amendment to the spec and getting re-approval.
4. **Before committing:** `node --check` changed files, run the full `npm test`, do a `web/` build if `web/` changed, bump `package.json`, run mutations (section 8), write the journal entry, and rotate the anchor and counters.
5. **PRs.** Create them as **drafts**, subscribe to PR activity, and keep a check-in. Merge **only** on the operator's word ("merge when ready" / "merge"). Merge with `expectedHeadSha`, verify `git diff --quiet <head> origin/main`, and probe `/healthz` after the deploy.
6. **Merge records** (D-205 + D-210). Write the record **at merge time**, verified from the merged tree. It **never** gets its own PR: commit it locally, unpushed, and it rides the next substantive PR.
7. **Time anchor** (D-203). anchor = `max(sensor reading, latest known event time)`, computed with a tool. The source string's stated delta must equal the arithmetic exactly; the test checks it.

## 5. Architecture notes a newcomer needs

- **Search (`/api/cuisine/search` in `index.js`).** Steps in order:
  1. Free text goes through the dish-name guard, then place-anchor detection (`cuisine-tellme-anchor.js` + `place-detector.js`). That gives a 1.5 km place radius, or building/road scope.
  2. Queries are built from cuisines, modifiers and free text; a typed dish uses its home cuisine.
  3. `pipeline.discover` calls Places Text Search; the location circle is only a **bias**, so results are filtered afterwards.
  4. Venue filters, then the New filter (`newness-filter.js` review-age refute, with curated external venues merged **before** it).
  5. Rating floor, seen-set dedup, ring widening, building scope on the pool, slice, dish gate, enrichment (`cuisine-enrich.js`), and finally the response.
- **AI search (`/api/cuisine/nl-query`):**
  1. `tell-gia.js` (Anthropic model, 60 s cache, keyword fallback when the LLM is not ready) produces cuisines, filters and `location_override`.
  2. The place comes from `location_override`, else `detectPlaceFromText`.
  3. `nl-anchor.planNlSearch` (1.5 km, or building scope), then discover, `scopeToPlace`, newness, rating floor and response.
  4. The chat path runs the same logic in `nl-anchor.answerQuestionWithTellGia` with injected dependencies, so it is testable.
- **Redis** is the only store: sessions, caches, the 60/hour AI quota, `/ftlog` (`freetext:log`), the `ext:` curated store, user prefs. node-redis needs `error`/`ready` listeners; never test only `isOpen`.
- **Tests.** Vitest has 290 files and 5,861 tests. CI installs with `--ignore-scripts`, so **React is not available in the root test job**: Mini App components are tested by bundling with esbuild and a React stub (see `__tests__/tellme-ai-lever.test.js`), or by reading the source. Importing `web/.../i18n.js` directly into a root test is refused by `test-import-graph-guard.test.js`.
- **Pinned counts** fail on purpose when you add things:
  - i18n key counts: bot 297 keys; Cuisine Mini App 410; total Mini App surface 955.
  - `bot.onText` registrations: 34.
  - `isOwnerChat(` uses: 21.

  Moving them is legitimate, but they sit in test files outside most specs' scope, so add them to the spec's scope up front.

### 6.1 Challenges (structural)
- **`index.js` is about 20,450 lines.** Every search change touches it, and source-scan tests pin its text. Prefer extracting pure helpers into small modules (as `nl-anchor.js`, `building-scope.js`, `external-eateries.js`, `newness-filter.js` were) and test those by calling them.
- **Places Text Search treats the location as a bias, not a limit.** Always post-filter by distance or address.
- **Ephemeral containers.** Anything unpushed can vanish. D-210 knowingly accepts this for held merge records.
- **Cost.** Google Places SKUs depend on the field mask, so check Google's table before adding fields (G4). The AI route has a 60/hour per-user cap.
- **The operator tests on a real phone,** and screenshots often reveal what headless tests cannot (a lever hidden behind a map control, a card covered by a strip). Render the **built** app with the real surroundings (map controls, footer) before claiming UI work is done.

## 7. Mistakes made — do not repeat them

Each item is a real incident. The fix is a habit, not just a patch.

### 7.1 Leaking the owner's Telegram chat id (26-10 '26, and earlier under R-4)
- **What happened:** I copied a number from a Railway log line (`[LocDrift] … "chat":"…"`) into a test as a "sample chat id". It was the operator's real id. It was pushed to the PR branch at 17:29 SGT. `__tests__/no-owner-chat-id.test.js` caught it on the next run; the earlier full run had passed only because the new file was still **untracked**. It was fixed by amending and force-pushing with lease (`455acf1f` → `685c3024`).
- **Rule:**
  - Never copy identifiers from logs into files; use obviously synthetic values (`4242424242`).
  - Before every commit, run the full suite **after `git add`**, or grep the staged files.
  - The chat id and the owner's home coordinates must never appear in the repo, in PR bodies or in generated pages (`VibeCodingRecord/redact.mjs` exists because GitHub PR bodies still contain them).

### 7.2 Numbers stated before they were measured
Several numbers were reported without being measured first:
- a test count of "94" (really 72);
- "26 files / 47 places" (really 1,056 occurrences, because `git grep -c` counts lines);
- "123 of 123 non-empty" (really 111; `nil` strings);
- reply serials drifting 43 low;
- `next_serial` written where `serial_measured` belonged.

**Rule:** compute every number with a tool in the same turn and paste the output. If a number shapes the operator's decision, re-measure it.

### 7.3 Checks that measured nothing
These checks ran and reported a result, but measured nothing:
- a parser that read zero rows and printed four PASSes;
- a mutation harness that applied no mutation and counted "caught";
- `vitest` "No test files found" (exit 1) read as a catch;
- a regex sliced off its own anchor, so every value parsed as `NaN`.

**Rule:**
- Every check must **abstain loudly** when it parsed nothing.
- A mutation must prove it applied (count the match, refuse if it isn't exactly 1) before its outcome is read.
- Use the harness in `/tmp/claude-0/.../scratchpad/mut94x.py` as the pattern: replace exactly once, run, restore from a backup in `finally`.

### 7.4 Guards that watched the wrong side
This happened about 14 times:
- a test checked the generated JSON, not the builder;
- the table, not the call site;
- the source text, not the rendered output;
- a comment rather than the code;
- one call site of several.

**Rule:**
- Test by **calling** the function or rendering the component wherever possible.
- When fixing a datum, search for **every** call site ("one datum, several call sites" recurred 8+ times).
- After a fix, run a mutation that reverts it; if it survives, the test is guarding the wrong thing.

### 7.5 Merge records and branches
- **D-205/D-210:** never open a PR whose only content is a merge record.
- **After a squash merge,** restart the branch from `origin/main`. A fast-forward push onto the merged tip appends to a closed PR; it succeeds, and the work never reaches `main`.
- **The ledger of record** is `origin/<branch>` plus `CLAUDE.md`, not the container. A held record was lost once (07-09 '26) and had to be recovered from the transcript.

### 7.6 Infrastructure blind spots
- **Redis:** `/healthz` was green during a 7-hour outage because it touched nothing. It now PINGs. Keep `error`/`ready` listeners.
- **Shared routes:** `/healthz`'s status is consumed by `webhook-domain.js`. A 503 there could have dropped queued Telegram updates. Read the consumers before changing a shared route.
- **Repo going private** broke anonymous `git fetch` in workflows.
- **Billing holds** look like CI dying in under 5 seconds with `runner_id 0`. That is not the PR's fault; tell the operator to check GitHub Billing.

### 7.7 UI that "passed" but users could not see
- **The lever** shipped at 8×12 px and was invisible. At 12×18 it sat on top of a map control. Fixed by moving it inside the bar.
- **The Criteria card** was covered by the insight strip.

**Rule:** after any UI change, render the **built** Mini App (Playwright, Telegram stub, served from `public/cuisine` at `/app/cuisine/`), with stub data that makes the relevant controls appear. Check `elementFromPoint` for overlap, and look at a screenshot.

### 7.8 Process slips
- **Approval lines.** The operator's approval only counts when typed exactly. A paraphrase ("proceed with option (a)") does not record; ask for the exact line and don't build around the hook.
- **Out-of-scope pins.** Adding i18n keys, commands or owner checks moves pinned counts in out-of-scope test files. List those test files in the spec's `scope:` from the start, to avoid an amendment round-trip.
- **Version numbers.** When two specs run in parallel, the second may need the next version number; record it in the spec.
- **Spec edits after approval** void the approval. Append "Amendment 0.x" and ask for re-approval.

## 8. Pre-flight checklist (copy this into your head)

1. Read `CLAUDE.md`, `CLAUDE-protocol.md`, `.claude/rules/flow.md` and the last 3 Journal `[AMD-n]` entries.
2. Then, in order:
   1. `date -u` → SGT.
   2. `node scripts/count-interactions.js --serial` → compute the running serial from the `CLAUDE.md` ledger.
   3. `git fetch origin main && git status -sb`. Is the branch ahead/behind? Is the branch's PR merged? If so, restart the branch from `origin/main`.
