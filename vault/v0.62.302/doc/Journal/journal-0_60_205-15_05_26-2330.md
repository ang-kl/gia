# Journal — soleat v0.60.205

> Operator: *"look at .github/workflows/ and figure out why every job is failing."* Recon showed that the syntax-check `find` was walking 2,028 `.js` files (including 1,873 vault snapshots and `.vibe-journal/node_modules/` vendored 3rd-party + ESM bundle output) — any single failure red-flagged the whole pipeline, with zero diagnostic output. Tightening the scope + adding diagnostics + splitting the build's silent postinstall into an explicit step.

## New

### [HDR] #173 | 23:30:00 SGT 15-05-26 | v0.60.205 — CI: tighten syntax-check scope (2028 → 115 files) · add diagnostics · split build step | 3 files | 1 PR |

- **[INTENT]** Every PR this session (and prior) showed three CI jobs red on totally unrelated code changes — including a doc-only journal PR (#450). That's the textbook signature of a broken runner environment or over-broad scope, not real regressions. Audit traced two likely root causes:
  1. **Syntax-check scope was 2,028 files.** The `find` exclusion list covered `./node_modules/*`, `./web/*/node_modules/*`, `./web/*/dist/*`, `./__tests__/*` — but NOT `./vault/*` (1,873 historical snapshot copies of `index.js` / `weather.js` / etc.), `./.vibe-journal/node_modules/*` (vendored 3rd-party — `js-yaml`, `argparse`, etc.), `./dist/*` (top-level vibe-journal framework ESM bundle output), or `./public/*` (Vite bundle output when built locally). On node 20, ANY one of those failing `node --check` (e.g. an ESM bundle interpreted as CommonJS) red-flagged the whole job. And the `|| { echo FAIL }` pattern in the loop ate the actual error message, so failures were unattributable.
  2. **Build job relied on postinstall** chaining `npm run build` from a single full `npm install`. Failure surface is one giant log blob across 5 TMAs serially; impossible to tell from the Actions UI which TMA failed without scrolling.

- **[DELTA]**

  **`.github/workflows/ci.yml`** — three changes:

  *(1) Syntax-check scope tightened to source code only.* Switched from `-not -path` post-filter list to `-prune` based exclusion (faster + more explicit). Excluded paths:
  ```
  ./node_modules
  ./web/*/node_modules
  ./web/*/dist
  ./__tests__
  ./vault                    (1,873 immutable snapshots — already passed when shipped)
  ./public                   (Vite bundle output — ESM, not source)
  ./dist                     (.vibe-journal framework output)
  ./.vibe-journal/node_modules  (vendored 3rd-party)
  ./.git
  ```
  Scope shrinks from 2,028 files to **115 files** locally — top-level `.js` + `./scripts/*` + any in-tree `web/<tma>/` (almost all `.jsx`). Loop output enhanced: `FAIL: <path>` now also prints the captured stderr (indented two spaces) AND collects a final summary line listing every failing file. Success path prints `✅ All source .js files pass node --check`. Step `timeout-minutes: 5`.

  *(2) Diagnostics step added* to all three jobs before the install step: `echo "node $(node --version) | npm $(npm --version) | runner ${RUNNER_OS} | ref ${GITHUB_REF}"` + `ls -d vault .vibe-journal dist public 2>/dev/null` on the syntax job. Future failures now show the runner state at the top of every log.

  *(3) Build job split.* Was `npm install --no-audit --no-fund` (no `--ignore-scripts`) which fired postinstall → `npm run build` → 5 TMA installs + builds in one opaque blob. Now: explicit `npm install --no-audit --no-fund --ignore-scripts` followed by `npm run build`. TMA-specific failures now show in their own step in the Actions UI. Also bumped `timeout-minutes: 15` so a slow network can't hang the runner indefinitely. Job display name updated `cuisine + menu + hawker` → `cuisine + menu + hawker + transport + oversight` to reflect reality.

  **`package.json`** — `0.60.204 → 0.60.205` (PATCH; CI hygiene, no runtime change).

  **`doc/Journal/journal-0_60_205-15_05_26-2330.md`** — this entry (#173).

  **`doc/.serial-state.yml`** — `journal 172 → 173`, `commit 179 → 180`; re-anchored.

  ### Honest framing: what this PR is and isn't

  - **Is**: a scope + observability fix. The CI workflow was checking far more than its name implied and swallowing the error messages so we couldn't see what was failing.
  - **Isn't**: a definitive root-cause fix. Without authenticated access to the prior failing job logs (no `gh` CLI / no Actions-logs MCP tool in my sandbox), I could only reason from the workflow structure + local repro. The tightened scope is the most-likely cause given the symptoms — every PR red regardless of code touched + zero useful output — but if CI still fails post-merge, the new diagnostics + explicit build steps will show exactly why.
