## New

### [HDR] #12 | 08:30:00 SGT 30-04-26 | v0.8.1 | n/a kb | n/a lines
- **[INTENT]** Per Human Lead instruction: *"refactor the fetchLocations logic to include a maximum retry limit of 1. If no places are found after the first search, trigger the handleNoResults function instead of re-polling."* Implemented as interpretation **A** (fail-fast on the first Gemini candidate) per Human Lead's selection in the disambiguation question.
- **[DELTA]**
  - **`vibe-suggest.js` `pickValidated`** — refactored to fail-fast policy:
    - The first Gemini candidate is the gate.
    - If it doesn't validate within the 200 m proximity gate → return `{ venues: [] }` immediately. Caller surfaces `handleNoResults`.
    - If the first candidate validates → continue with candidates 2–N to fill up to `count` picks.
    - Seed-fallback re-poll path **removed**. The `fallbackList` parameter is now ignored (kept in signature for backward compat; renamed to `_fallbackList` to silence unused warnings).
  - **`index.js`** —
    - + `handleNoResults(chatId, mealLabel)` — extracts the no-results branch into a named helper (matches the user's vocabulary). Copy refreshed: *"Gia couldn't find a {mealLabel} sanctuary within 200m of you right now. Try sharing a different location or typing a place name."* Old copy "Gia has no sanctuary picks for you right now. Try again in a few minutes." is superseded.
    - `runFlow` no longer constructs a seed fallback list — passes `[]` explicitly to `pickValidated`.
    - `/api/sanctuary` route same change.
    - `pickLunch` import dropped (no longer referenced).
    - `⛔ Use Raffles Place default` handler tightened: pending-meal validation moved into a single ternary.
  - **`package.json`** — version → 0.8.1.
- **[RISK]** Med — this is a behavioural tightening, not a bug fix:
  - Users in dense areas (CBD core) likely see no change; the first Gemini candidate usually validates.
  - Users in fringe locations (e.g. typing a residential street) will hit `handleNoResults` more often than before — by design. The seed-fallback comfort path is gone.
  - **No regression for Gemini-disabled deploys**: when Gemini key is missing, `geminiCandidates` returns `[]` → `pickValidated` returns `{ venues: [] }` → `handleNoResults` fires with the helpful instruction copy. Same end-state as before, just via a different code path.
- **[STATUS]** PROD — auto-deploys with the next Railway build.
- **[TEST]** Manual:
  1. `/eat` from a CBD location → 3 picks return as before, walking-minute ranked (v0.8.0 behaviour).
  2. Type a real but obscure place (e.g. "Pulau Tekong") → first Gemini candidate likely won't validate within 200 m → `handleNoResults` fires with the new copy.
  3. Type a clearly off-grid string ("asdfgh") → `geocodeQuery` returns null first (no place found) → user gets the existing geocode-miss message; never reaches `pickValidated`. (Pre-existing behaviour; unchanged.)
- **[NEXT]** Vault import (Open #16, blocked on correct Takeout files), `/BusArrivalv2` UX (Open #13), MRT-stop expansion (Open #14).
- **[ADVICE]** Fail-fast pairs naturally with the 200 m radius — both prefer "honest miss" over "comfortable nearby alternative." If users complain about empty results too often, the fix is widening the radius (200 m → 400 m), not re-introducing the seed re-poll.
