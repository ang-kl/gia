- **[ROOT CAUSE]** The v0.61.186 visibility re-fetch (`refetchAndFlip`) runs on `viewportChanged` —
  which Telegram fires even on **keyboard open/close** — and overwrites the client anchor with the
  server cache, with **no explicit-pick latch** (the follow-GPS sync respects `explicitPickRef`;
  this path never did). When the pick's `set-location` was lost or out-raced, the stale server
  label (Hanoi, from the earlier capital auto-commit) was pulled straight over the fresh HCM pick:
  map + results at HCM, city pill back on HAN.

- **[FIX — operator pick 1 of 3]** New `reassertPickAfterSearch(snap)`:
  - Gated on `explicitPickRef` + a **named, finite-coords** anchor — plain GPS sessions untouched.
  - `fetchUserLocation()` → if the server label ≠ the pick's name → **silent re-push**
    (`saveUserLocation` with label + region (coords-inferred, else `snap.region`) + `countryPref`
    when OTHER + carried `radiusCapM`; **no `notify`** — no chat spam; no map move).
  - The Arrival Plate follows the re-push response (`setArrivalPlate`).
  - `D791` console line on every mismatch; whole helper fire-and-forget `try/catch`.
  - Called at the end of **both** result paths: `runSearch` success and `handleNLSubmit` success.

- **[NOT taken — deliberately]** Options 2 (latch the visibility re-fetch) and 3 (both) — the
  operator chose 1. The re-fetch still imports chat / Menu picks mid-session, unchanged.

- **[KNOWN EDGE]** A chat/Menu pick made *between* a TMA pick and the next search is overwritten by
  the re-assert — consistent with the "explicit pick wins this session" policy (v0.61.430). If that
  bites, option 2's latch is the follow-up.
